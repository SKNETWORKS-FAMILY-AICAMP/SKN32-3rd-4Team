# Codex MCP 도구 설계 원문 (2026-07-31)

- 채택 내역: [`MCP 도구설계`](../plans/2026-07-31_2000_MCP_도구설계.md)
- 원문 그대로이며 편집하지 않는다.

---

## 결론

- MCP는 **굵은 도구 3개**로 유지한다.
- 다단계 상태는 대화 세션이 아니라 서버의 **영속 `case_id` + revision**으로 관리한다.
- KCD 선택은 에이전트가 대신 결정하지 못한다. 에이전트는 사용자의 선택을 전달하며, 그 사실은 `agent_attestation / unverified`로 기록한다.
- MCP는 REST를 HTTP로 재호출하지 않는다. REST와 MCP가 **동일한 core 유스케이스와 응답 DTO**를 호출한다.
- “AI 에이전트입니다” 자기선언은 도입해도 된다. 단, 선택 사항이고 차단·권한·신뢰도 판단에 쓰지 않으며 **미검증 자기선언**으로만 집계해야 한다.

ERD는 문서 §0-1의 v2가 우선하므로 실제/데모 **DB 분리**, 증빙 검증은 **불변 사실 테이블** 기준으로 해석했다.

# 1. MCP 도구 설계

## (a) 도구 수와 경계

### 선택: 굵은 도구 3개

| 도구 | 책임 | 내부 단계 |
|---|---|---|
| `insurance_precheck` | 케이스 생성부터 KCD 확인·사전판정까지 | 후보조회 → 사용자 선택 대기 → 약관버전 확정 → 규칙판정 |
| `claim_cohort_query` | 확정된 케이스와 유사한 코호트 조회 | 매칭키 결정 → 최소표본/프라이버시 게이트 → 통계 반환 |
| `claim_evidence` | 증빙 업로드·제출·검수상태 조회 | 업로드 초기화 → 제출 확정 → 상태 조회 |

이유는 에이전트가 호출 순서를 추론해야 하는 표면적을 줄이면서도, 판정·통계·증빙이라는 **서로 다른 권한·부작용·감사 경계**를 보존하기 때문이다.

얇은 도구를 8~10개로 나누면 다음 문제가 생긴다.

- KCD 후보 조회 후 확인 없이 판정 도구를 호출할 수 있다.
- 약관버전 확정과 규칙판정 사이의 불변식이 MCP 호출자에게 노출된다.
- 재시도·멱등성·부분 실패 처리가 에이전트 프롬프트에 의존한다.

반대로 하나의 `insurance_agent` 만능 도구는 증빙 쓰기 권한과 통계 읽기 권한을 분리할 수 없다.

### 3종에서 빠진 흐름

별도 도구를 추가하지 않고 기존 3개에 흡수한다.

| 필요한 흐름 | 수용 위치 |
|---|---|
| 질병명→KCD 후보 | `insurance_precheck(operation="start")` |
| 사용자 선택 제출 | `insurance_precheck(operation="confirm_and_assess")` |
| 케이스 재개·현재 상태 확인 | `insurance_precheck(operation="get_status")` |
| 파일 업로드 URL 발급 | `claim_evidence(operation="init_upload")` |
| 검수 진행상태 조회 | `claim_evidence(operation="get_status")` |

따라서 **도구는 3개 그대로가 맞다.**

## (c) 다단계 상태

### 선택: 서버 발급 `case_id`

매 호출마다 전체 컨텍스트를 다시 받지 않는다.

```text
start
  → case_id, revision=1, selection_request_id
  → 사용자에게 후보 제시
confirm_and_assess(case_id, expected_revision=1)
  → revision=2, assessment
claim_cohort_query(case_id)
claim_evidence(case_id)
```

서버에는 대화 transcript가 아니라 다음 **도메인 상태만** 저장한다.

- 정규화된 상품·가입일·사고일·특약
- 제시한 KCD 후보와 `selection_request_id`
- 사용자 선택 및 확인 provenance
- 적용 약관버전과 matcher version
- 판정과 근거
- 증빙 제출·검증 사실

동시 호출 충돌은 `expected_revision`으로 `ConflictErr` 처리한다. 재시도 중복은 `(principal_id, idempotency_key)`로 막는다.

이 방식은 감사·재현·삭제가 가능하다. 프로세스 메모리 세션이나 장수명 MCP 연결에 상태를 두면 서버 재시작과 다른 전송 채널에서 흐름이 끊긴다.

## (d) 에이전트 상대의 “사용자 확인”

첫 응답을 정상적인 **사용자 행동 요청**으로 표현한다.

```json
{
  "status": "awaiting_user_selection",
  "abstained": true,
  "abstain_reason": {
    "code": "USER_SELECTION_REQUIRED",
    "message": "질병명은 여러 KCD에 대응합니다. 최종 사용자에게 후보를 제시하고 선택을 받아야 합니다."
  },
  "result": {
    "requires_user_action": true,
    "selection_request_id": "uuid",
    "candidates": []
  }
}
```

에이전트는 다음 순서를 따라야 한다.

1. 후보를 그대로 사용자에게 제시한다.
2. 의료 진단이 아니라 약관 검토용 코드 선택임을 알린다.
3. 사용자가 고른 값을 `confirm_and_assess`로 전달한다.
4. 에이전트 자신이 임의 선택한 경우 호출하지 않는다.

`agent_attestation`은 사람이 실제로 선택했다는 사실을 서버가 검증했다는 뜻이 아니다. DB에는 다음처럼 남긴다.

| 필드 | 값 |
|---|---|
| `selected_by` | `end_user` |
| `confirmation_method` | `agent_attestation` |
| `verification_status` | `unverified` |
| `selection_request_id` | 서버 발급 값 |
| `declared_by_principal_id` | 호출 에이전트 OAuth principal |

서버 nonce는 올바른 단계의 응답임을 증명할 뿐, 사람이 눌렀다는 사실은 증명하지 못한다.

## (e) 오류와 abstain

[MCP 도구 명세](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)는 잘못된 도구명·프로토콜 형식은 JSON-RPC 오류로, 도구 실행 중 발생한 검증·API·업무 오류는 `isError: true`로 구분한다.

| 상황 | MCP 표현 | 재시도 |
|---|---|---|
| 알 수 없는 도구·깨진 `tools/call` | JSON-RPC protocol error | 요청 수정 |
| `ValidationErr` | tool result `isError=true` | 입력 수정 후 |
| `NotFoundErr` | tool result `isError=true` | ID/범위 수정 후 |
| `ConfigError` | tool result `isError=true` | 운영 설정 복구 후 |
| `InfraError` | tool result `isError=true` | `retry_after` 이후 제한 재시도 |
| 근거 부족·소표본·사용자 선택 대기 | 성공 결과, `isError=false`, `abstained=true` | 필요한 조건 충족 후 |

도구 실행 오류 본문:

```json
{
  "isError": true,
  "structuredContent": {
    "error": {
      "code": "validation_error",
      "message": "KCD 차수와 코드가 모두 필요합니다.",
      "retryable": false,
      "invalid_fields": ["selected_kcd.version_label"],
      "request_id": "uuid"
    }
  }
}
```

`NotFoundErr`는 “지정한 case가 없다”처럼 리소스가 없는 경우다. “약관 근거가 부족하다”는 리소스 오류가 아니라 **판정 abstain**이다.

현재 [server.py](C:/Users/playdata2/Documents/llm_workspace/_unified_mall_3/app/mcp/server.py)의 nonce 문자열 마커는 자체 subprocess 클라이언트에서만 타입을 복원할 수 있다. 외부 MCP 클라이언트와의 계약으로 사용하지 말고 `structuredContent.error`로 교체해야 한다.

## (f) REST와 MCP parity

### 선택: REST 위 HTTP 래퍼가 아니다

```text
REST adapter ─┐
              ├─→ 동일 application DTO/usecase → core ports
MCP adapter ──┘
```

MCP가 REST를 다시 호출하면 다음이 이중화된다.

- OAuth 주체와 권한 전달
- 직렬화와 오류 매핑
- 타임아웃·재시도
- 관측 로그
- 내부 HTTP 장애

따라서 두 어댑터가 같은 입력 DTO, 유스케이스, 결과 DTO를 사용하고 계약 테스트로 parity를 강제한다.

현재 MCP에서 재사용할 부분:

| 자산 | 판정 |
|---|---|
| FastMCP decorator/Pydantic 기반 스키마 생성 | 재사용 |
| `structuredContent` 우선 처리 | 재사용 |
| AppError를 삼키지 않는 `_guard` 원칙 | 재사용 |
| `rag_qa`가 REST와 동일 유스케이스·view를 호출하는 방식 | 그대로 따라갈 기준 |
| 도구별 직접 DB 세션과 legacy service import | 폐기 |
| 호출마다 subprocess 기동·RAG 전체 warm-up | 운영에서 폐기 |
| nonce 문자열로 오류 타입 복원 | 구조화 오류로 교체 |

새 MCP 코드는 목표 구조에 맞춰 `app/outer/inbound/mcp/`에 두고 `app/core` 유스케이스만 호출해야 한다.

## (g) 인증·레이트리밋·남용 방지

HTTP MCP는 OAuth 기반 인증을 사용한다. 최신 MCP 인증 명세는 protected-resource metadata, 토큰 audience 검증, PKCE, token passthrough 금지를 요구한다. [공식 MCP Authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)

| 도구 | scope |
|---|---|
| `insurance_precheck` | `insurance:precheck` |
| 합성 코호트 | `cohort:demo:read` |
| 실제 코호트 | `cohort:real:read` |
| 증빙 제출 | `evidence:write` |
| 증빙 검수상태 | `evidence:status:read` |

시행 규칙:

- OAuth client, 대표 사용자, IP/네트워크, 도구별로 각각 제한한다.
- 인증 토큰의 `aud`가 MCP 서버와 일치해야 한다.
- MCP가 받은 토큰을 DB·스토리지 등 하위 서비스로 그대로 전달하지 않는다.
- 실제 코호트는 자유 필터가 아니라 `case_id` 기반의 사전 정의 매칭만 허용한다.
- 작은 셀은 정확한 `n`까지 숨긴다.
- 동일·인접 필터 반복 조회에 누적 privacy budget을 적용한다.
- rate limit뿐 아니라 “결과 차이를 이용한 추론” 패턴을 감사로그로 탐지한다.
- 증빙 URL은 단일 업로드·짧은 TTL·고정 크기·고정 SHA·허용 MIME으로 제한한다.
- 모든 로그에서 처방전 내용과 signed URL을 제거한다.

인증 실패는 도구 오류가 아니라 HTTP 경계의 401/403이다. 도구까지 진입한 뒤 권한을 확인하는 구조로 만들면 메타데이터와 일부 실행 비용이 이미 노출된다.

## (h) `llms.txt` / A2A 카드

`llms.txt`는 표준화된 인증 문서가 아니라 LLM용 문서 탐색 제안이다. 루트의 H1·요약·관련 문서 링크 구조가 기본이다. [llms.txt 제안](https://llmstxt.org/)

### `/llms.txt`에 넣을 것

- 서비스가 의료진단·보험금 지급 확정을 하지 않는다는 범위
- MCP endpoint, OpenAPI, 인증 문서 링크
- 3개 도구의 목적과 권장 호출 순서
- KCD 자동선택 금지 규칙
- `abstained`와 오류의 차이
- `synthetic`과 `verified_real`의 의미
- 최소표본 미달 시 값이 숨겨지는 규칙
- 증빙 `consistent != verified`
- 필수 scopes, rate-limit 정책, 지원범위 매니페스트
- 직접 업로드 방식과 민감자료 금지사항
- 자기선언 메타데이터를 보내는 방법
- 버전·변경이력·문의처

API 키, 내부 DB 구조, 실제 임계값 우회 방법, 남용 탐지 규칙은 넣지 않는다.

### A2A 카드

A2A는 저장소 계획대로 MVP 후순위가 맞다. 공개한다면 `/.well-known/agent-card.json`에 다음을 둔다.

- 이름·설명·서비스 버전·문서 URL
- endpoint와 지원 프로토콜
- `precheck`, `cohort-query`, `evidence-submission` skills
- JSON/PDF 등 input/output mode
- OAuth security scheme과 skill별 scope
- 스트리밍·push notification 지원 여부
- 비의료진단·비지급확정·합성데이터 경고
- 사람 확인이 필요한 KCD 선택 단계

A2A Agent Card는 기능·endpoint·skills·인증 요구를 기술하는 발견 문서다. 자격증명 자체는 카드에 넣지 않는다. [A2A Agent Discovery](https://a2a-protocol.org/latest/topics/agent-discovery/)

## (i) MCP 설계의 흔한 실수 3가지

1. **업무 단계를 얇은 도구로 노출해 불변식을 에이전트에게 맡긴다.**  
   KCD 확인 전 판정, 약관버전 미확정 판정 같은 불법 순서가 가능해진다.

2. **abstain을 오류로 만들거나 오류를 성공 JSON으로 감춘다.**  
   전자는 에이전트가 무한 재시도하고, 후자는 실패 결과를 정상 판정으로 전달하게 한다.

3. **모든 응답에 통계 필드를 억지로 채운다.**  
   미검증 증빙에 `verified_real`, 비통계 응답에 `n=0`, 검수 전 `verification_method`를 붙이면 필드는 존재하지만 의미가 거짓이 된다. 필드는 유지하되 적용 불가 값은 `null`/`[]`로 표현해야 한다.

- 누구를 대리하는가: `human_end_user/organization/self/unknown`
