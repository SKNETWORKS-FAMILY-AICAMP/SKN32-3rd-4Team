# ERD 핸드오프 교차검증 — 브리핑이 어느 설계도 반영하지 않고 있었다

2026-08-02 · 코덱스 3라운드 교차검증 · 전량 실측(1,367문서)

## 0. 요약

질문은 "핸드오프 ERD 브리핑이 지금 나오는 v4를 반영하고 있나"였다.
**아니었다. 그리고 문제는 수치가 낡은 것보다 컸다.**

| 확인한 것 | 결과 |
|---|---|
| 브리핑이 현행 ERD를 반영하나 | ❌ **테이블 이름이 하나도 겹치지 않는다.** 브리핑 15개 vs 현행 22개 |
| 브리핑 수치가 v4 기준인가 | ❌ 핵심 수치가 **v3·표본 400문서** 기준 |
| 현행 ERD가 v4 산출물을 담을 수 있나 | ❌ 식별키 충돌 · `suspect` 108건 담을 자리 없음 · 감사신호 7종 유실 |
| v4 산출물이 지금 적재 가능한가 | ❌ **확정 문서 0건.** `core` 전체가 0행 |
| ★근거 인용 검증기가 작동하나 | ❌ **1,367문서 중 1,191(87%)에서 무력화된다** |

마지막 항목이 이번에 발견한 것 중 가장 무겁다. 문서 문제가 아니라 **런타임 결함**이다.

|---|---:|---:|
| 현행 구현 `section + title + body` | 51,740 | 59.9% |
| `title + body` (section 제거) | 46,998 | 63.6% |

> 이 표는 코덱스가 독립적으로 계산한 값(`46,022 / 64.3%`)과 **정확히 일치했다.**
> 서로 다른 정규식·다른 코드로 같은 값이 나와 확정한다.

## 3. ★최상위 결함 — 인용 검증기가 87% 문서에서 무력하다

`app/core/domain/citation_guard.py` 는 이 서비스에서 **제0원칙을 강제하는 장치**다.
LLM이 근거에 없는 조항을 인용하면 그 답을 폐기한다.

그런데 `_clause_key()` 가 부 이름을 떼고 번호만 남긴다.

```python
def _clause_key(qualified_no: str) -> str:
    """`보통약관/제 9 조` → `제9조`. 부 이름은 떼고 번호만 본다."""
```

주석은 이 완화를 **의도적으로** 설명한다 —
*"LLM이 부 이름까지 정확히 쓰길 기대할 수 없다. 부까지 맞추길 요구하면 정답인데 폐기하는 일이 생긴다."*
의도는 타당하다. **결과가 뒤집혔다.**

```
_clause_key 충돌   71,707건 / 1,191문서 (전체의 87%)
한 키에 최대 조항   96개   (dbins/3dea54cde8ad)
```

특별약관마다 조 번호가 1부터 다시 시작하므로, 한 문서 안에서 서로 다른 조항 **96개**가
`"제1조"` 하나로 뭉친다. 그리고 `citation_guard.py:113` 이

```python
by_key = {_clause_key(e.qualified_no): e for e in evidence}
```

dict comprehension이라 **95개가 마지막 것에 덮인다.**

**결과 두 가지**
1. LLM이 **어느 특약의 제1조를 인용하든** `allowed` 를 통과한다 — 검증이 사실상 없다.
2. 인용문 원문 대조가 **엉뚱한 조항 본문**과 이뤄진다 — 틀린 근거가 "검증됨"으로 나온다.

같은 충돌이 두 곳에 더 있다.

| 위치 | 내용 |
|---|---|
| `app/core/ports/precheck.py:90` | `clause_id = f"{sha256[:12]}/{qualified_no}"` — 31,085건 충돌 후보 |
| `app/core/usecases/precheck.py:279` `_dedupe()` | 그 `clause_id` 로 dedup → **서로 다른 조항이 조용히 사라진다** |

> 계획서 §4는 이 문제를 알고 `(policy_version_id, section_id, clause_no)` 를 해법으로 제시했다.
> **그 해법으로는 안 된다.** v4의 `qualified_no` 는 이미 `"{section}/{clause_no}"` 형식이고
> section 라벨은 문서 내 유일하므로(표본 400문서 중복 0), 제안된 키는
> `(문서, qualified_no)` 와 동치다 — **31,085건이 그대로 남는다.**
> 원인은 조 번호 재시작이 아니라 **부(section) 탐지 입도가 특약보다 굵어서**
> 서로 다른 특약 여러 개가 한 라벨 아래 뭉치는 것이다.

실제 충돌 예 (`dbins/02aaee47b190`, 96쪽):

```
p.73  보험료 자동납입 특별약관/1.   "보험료 납입"               324자
p.73  보험료 자동납입 특별약관/1.   "특별약관의 체결 및 효력"    798자
p.73  보험료 자동납입 특별약관/2.   "보험료의 영수"              82자
p.73  보험료 자동납입 특별약관/2.   "특별면책조건의 내용"      2,605자
```

## 4. 적재가 지금 0행이다

| 사실 | 값 |
|---|---|
| `core.policy_version.confirmed_document_id` | **NOT NULL FK** → `confirmed_policy_document` |
| `confirmed_policy_document` 적재원 | `data/catalog/2026-07-31_document_manifest.jsonl` 의 `identification_status='confirmed'` |
| 그 매니페스트 행 수 | **573** (코퍼스 1,703 · 전처리 1,367 대비 **34%만 덮는다**) |
| 그중 `confirmed` | **0건** (ambiguous 555 · null 18) |
| 최다 격리 사유 | "세대 판정 규칙셋이 아직 없습니다" **555건** |
| 구조화 산출물의 `identification` | **1,367건 전량 `unidentified`** |

→ `confirmed_policy_document` 0행 → `policy_version` 0행 → `policy_clause` 0행.
**약관 코퍼스가 한 줄도 안 올라간다.**

이건 설계 결함이 아니다. FK가 **의도대로** 작동하는 것이다.
문제는 두 문서 어디에도 이 사실이 없고, 브리핑은 `1,240 판정 가능`이라고만 쓴 것이다.
팀은 데이터가 곧 적재된다고 읽는다.

### 4-1. 그런데 판정 코드는 확정 절차를 우회한다

`app/adapters/manifest_policy_resolver.py:34` 가 읽는 곳은
**`data/raw/manifests/*.jsonl` (2,121행)** 이다 — `data/catalog/` 의 확정 매니페스트가 아니다.
필터는 `excluded_reason` 과 `usable_for_judgment` 뿐이고,
`usable_for_judgment` 는 `date_confidence` 와 `sale_start` 유무만 본다(`ports/precheck.py:54`).

**`identification_status` 를 보지 않는다.** 확정 0건인데 `load_versions()` 는 **1,361건**을 돌려준다.

## 5. v4가 남긴 감사 신호가 ERD에 자리가 없다

v4는 "지우지 않고 세어 남긴다"를 지켰는데, 현행 ERD로 적재하면 전부 사라진다.

| v4 필드 | 실측 | ERD 자리 |
|---|---|---|
| `parse_status = suspect` | **108건** | ❌ enum이 `ok`/`no_clause_heads` 2값 |
| `parse_warnings` | 길이초과 108 · 조항부족 3 | ❌ |
| `numbering` | article 1,073 / numbered 275 / none 19 | ❌ |
| `unmapped_glyphs` | 187문서 · 5,749회 | ❌ (+ `to_clauses.py` 가 전달조차 안 함) |
| `control_removed` · `pua_removed` | 전 문서 | ❌ (동일) |
| `toc_pages` · `toc_pages_excluded` | 전 문서 | ❌ |
| `tables_on_pages` | 조항별 | ❌ (보장한도·자기부담금이 표에 있다) |
| `chunk_type='page_fallback'` | 439청크 / 10문서 | △ 계획서는 chunk 레벨, v4는 **clause 레벨** |

`numbering` 오판이 v3 산출물 **35% 손상**의 원인이었다. 그 판정 결과를 저장하지 않으면
같은 사고를 다시 진단할 수 없다.
`unmapped_glyphs` 는 항 번호 `①②③` 가 깨진 문서를 가리킨다 — **187문서에서 "제N항"을 특정할 수 없다.**

그리고 `app/adapters/file_clause_store.py:108,164` 는 `doc.get("parse_status", "ok")` 로
**없으면 `ok`** 다. fail-open이다. `suspect` 를 담을 자리가 없는 것과 같은 방향의 사고다.

## 6. 코덱스 교차검증 — 3라운드

CLAUDE.md §4에 따라 코덱스에 8개 쟁점을 넘겼다. 코덱스는 **12개를 더 제기했다.**
전부 코드로 확인했다.

### 확인된 것 (코덱스가 맞았다)

| # | 지적 | 확인 |
|---|---|---|
| 1 | `content_hash` 에 section이 섞였다 | `to_clauses.py:242` — 맞다. 내 59.7%가 과소집계였다 |
| 2 | `to_clauses.py` 가 정규화 감사신호를 전달 안 한다 | grep 0건 — 맞다 |
| 3 | resolver가 확정 절차를 우회한다 | §4-1 — 맞다 |
| 4 | `clause_id` 충돌 + `_dedupe` 로 조항 소실 | §3 — 맞다 |
| 5 | `citation_guard` by_key 덮어쓰기 | §3 — **맞고, 코덱스 지적보다 심각했다** |

| 11 | 코호트 뷰가 `policy_version_id` 를 그룹키에 안 넣어 "버전 roll-up 금지"를 스스로 위반 | 맞다 |
| 12 | `file_clause_store._latest_version_dir()` 전역 최신 폴더 자동선택 | 맞다. 부분 재실행 시 나머지 전 문서가 `InfraError` |

### ★정정 — 코덱스 지적 하나는 과장이었다

코덱스: *"보험사+가입일만으로 '가장 최근 상품'을 선택한다. DB손보 2026-07-01 후보는 236문서·189상품"*

후보 수는 **정확히 재현됐다**(236 / 189). 그러나 `resolve()` 를 실제로 호출하면
그 케이스는 **`ambiguous_product_line` 으로 기권한다.** 코드에 이미 두 겹의 기권 장치가 있다.

13개 보험사 × 5개 가입일 = 65케이스 실측:

```
ambiguous_product_line  33   (기권)
no_version_at_date      16   (기권)
ambiguous_product        6   (기권)
RESOLVED                10
```

확정한 10건 중 7건은 후보가 1건뿐이었다. **실제 결함은 3건**이다 —
상품 라인이 하나로 통일돼 있으면 시작일이 가장 늦은 것을 되묻지 않고 고른다.

```
NH농협생명  20180101  후보 10건·10종 → 'NH온라인실손의료비보험(갱신형,무배당)'
NH농협생명  20150101  후보  4건· 4종 → '실속만점NH실손의료비보험(갱신형,무배당)_1501'
흥국화재    20150101  후보  4건· 4종 → '무배당 흥국화재 실손의료보험(범용_1501)_1~2'
```

→ 결함은 실재하나 **범위가 좁다.** 리포트에는 이 형태로 싣는다.
반박을 실측으로 가린 사례이므로 기록해 둔다.

## 7. 합의문

3라운드 끝에 확정된 것. 코덱스 회신 "합의."

### 합의된 것

- `citation_guard` 번호 충돌은 **최상위 P0 결함** — 87% 문서에서 검증기를 우회하거나 엉뚱한 본문과 대조한다
- 인용 해소는 **ID 우선**, 번호 후보가 복수면 **기권** — 모호성을 정답으로 통과시키지 않는다
- `content_hash` 에서 section 제거 — 수록 문맥은 내용 정체성이 아니다
- canonical 해시는 **조 머리를 분리한 `title + content`** 로 재정의
- 식별자는 `policy_clause_id`, 유일성은 **`UNIQUE(document_extraction_id, ordinal)`** — `qualified_no` 는 식별자가 아니다
- 정규화 감사 신호를 extraction 산출물까지 전달
- 판정 resolver는 **confirmed catalog만** 사용 — 확정 0건이면 판정 가능 문서도 0건이어야 한다
- `parse_status` 는 `document_extraction` 의 3값(`ok`/`suspect`/`failed`) — `no_clause_heads` 는 상태가 아니라 `failure_reason`
- `policy_clause.kind='unclassified'` 허용 후 버전 있는 후처리 — 없는 분류를 지어내지 않는다
- `generation` 은 `policy_version` 에 둔다
- `clause_reference` 는 core P0에 포함 — 준용 순회를 약속했으면 엣지 저장소가 있어야 한다
- core 구현과 app/ops 구현을 분리 — 코퍼스 경로를 먼저
- **canonical 중복률 64.3%** (고유 46,022 / 129,086) — 조 머리·section 제거, `page_fallback` 제외 기준
- 핸드오프 재작성 범위는 `01·02·04·05·07·10` + `erd_briefing`, 프론트는 API 변경분만
- core P0 는 **`insurer` 포함 12테이블**
- app/ops 는 구현 P1, **그러나 알려진 결함은 지금 고쳐 쓰고** "P1 계약 초안"으로 표시
- **quote mismatch 는 경고가 아니라 폐기 사유**

### 내가 접은 것

| 내 입장 | 접은 이유 |
|---|---|
| `insurer` 는 `product.insurer_name` 흡수 유지 | 같은 회사가 이미 slug(`nhlife`)와 표시명(`NH농협생명`)으로 **동시에** 표현되고 크롤러·매니페스트·산출물이 갈라 쓴다. 문자열 하나가 아니다 |
| app/ops 결함은 P1로 넘긴다 | 행이 0개인 **지금이 고치기 가장 싼 시점**이라는 논리에 반박할 게 없었다 |
| quote mismatch 는 경고 유지 | 인용문이 원문에 없다는 것은 근거를 못 댄 것이다. 제0원칙에 걸린다 |
| 중복률 59.7% | 조 머리를 안 벗긴 값이었다. 64.3%가 맞다 |

## 9. 내가 틀렸던 것 (정직 기록)

1. **중복률 59.7%를 그대로 보고했다.** 해시 정의를 확인하지 않고 산출물 필드를 믿었다.
   코덱스가 `to_clauses.py:242` 를 열어 반박했고, 재측정하니 64.3%였다.
   **"산출물에 적혀 있다"는 근거가 아니다** — 어떻게 계산됐는지를 봐야 했다.
2. **`(section_id, clause_no)` 로 고치면 된다고 읽었다.** 계획서 §4를 그대로 믿고 검증을 늦췄다.
   실제로는 `qualified_no` 가 이미 section을 포함해 동치였고, 충돌은 그대로였다.
3. **코덱스 지적을 한 번에 다 수용할 뻔했다.** 12개 중 1개(§6)가 과장이었다.
   실측으로 가리지 않았으면 없는 결함을 P0에 올릴 뻔했다.
