## 2. 판정 가능 문서가 0건이 됐다 — 그게 정답이다

`manifest_policy_resolver` 가 `identification` 을 보지 않아
확정 0건인데 `load_versions()` 가 **1,361건을 내주고 있었다.**

ERD 는 `policy_version.confirmed_document_id` 를 **NOT NULL FK** 로 두어
"확인 안 된 약관으로 판정하지 않는다"를 **구조로** 만들었는데,
판정 코드가 매니페스트를 직접 읽으면서 그 절차를 우회했다.

```
실측(2026-08-02): identification 이 unidentified 2,117행 ·
                  확정 매니페스트 573행이 전부 ambiguous. confirmed 는 0건.
```

게이트를 켜니 **판정 가능 문서가 0**이다. 기능이 죽은 것처럼 보이지만
확인 안 된 약관으로 "보장됩니다"라고 말하는 것보다 낫다.

`GET /v1/support-manifest` 가 그 사실을 드러낸다.

```
⚠ 판정 가능한 약관이 0건입니다. 수집은 끝났으나
  '이 파일이 무엇인가'를 사람이 확정하는 절차가 아직 남았습니다.
```

시연이 급하면 `PRECHECK_ALLOW_UNCONFIRMED=1` 로 끌 수 있으나,
**끄면 응답 `notes` 에 꺼져 있다고 박힌다.** 조용히 미확정 약관으로 답하는 것이 가장 위험하다.

## 3. s5 는 회귀가 아니었다

`ok` 가 1,240 → 1,108 로 132건 줄어 회귀를 의심했다. 아니었다.

「한 쪽에 조항 과다」 규칙이 **별표 법령조문을 오탐**한 것이다
(135문서 중 **85문서, 63%**). 조세특례제한법 시행령·형법 조문을 별표에 실은 문서인데,
짧은 조항이 촘촘한 건 법령 조문의 **정상 모습**이다.

> ★s5 는 이미 조항마다 `statute` 를 붙여 표시하고 있었는데 **사후 검증이 그걸 안 봤다.**
> 표시해 놓고 안 쓴 것이다.

## 4. 용어 설명 — 사전을 만들지 않았다

용어의 뜻은 약관 안에 있다(「제2조 용어의 정의」·「붙임1_용어의 정의」).
바깥에서 가져와 두 벌이 되면 어긋났을 때 무엇이 맞는지 판단할 근거가 없다.

### 용어→뜻 쌍으로 파싱하지 않는다

정의표는 PDF 안에서 **테두리 없는 표**라 표 추출이 못 잡는다
(문서 하나에서 표 67개를 잡았는데 그중에 없었다). 본문에서는 칸이 무너져 이렇게 나온다.

```
용 어  정  의  계약 보험계약 진단계약 계약을 체결하기 위하여 …
```

여기서 "계약 = 보험계약"이라고 **끊어 읽는 것은 추측이다.**
끊는 규칙을 만들면 그럴듯하게 틀린 정의가 대량으로 만들어진다.
그래서 끊지 않고 **원문 구절을 그대로** 인용한다.

### 만들면서 두 번 틀렸다

| 무엇 | 얼마나 | 어떻게 알았나 |
|---|---|---|
| 머리말 규칙을 **표본 하나**로 정했다 | **763문서 누락** | 못 찾은 문서를 세어 보고 |
| **가리키는 말을 정의표로 잡았다** | 머리말 235회 중 **106회** | "상해"를 물었더니 「보장종목별 보상내용」이 나왔다 |

두 번째가 중요하다. 본문에도 머리말과 똑같은 글자가 나온다.

```
<붙임1_용어의 정의>와 같습니다.   ← 가리키는 말. 뒤에 보상내용이 이어진다
<붙임1_용어의 정의>
용 어  정  의  계약 보험계약 …    ← 진짜 표
```

머리말 **뒤를 보고** 갈랐다 — `용어정의` 로 시작하면 표, `와같습니다` 면 가리키는 말.

### 출력에 `verdict` 가 없다

챗봇이 *"그래서 저 보장되나요?"* 로 자연스럽게 넘어가는데,
거기서 답하면 약관버전 확정·인용검증·4단 판정을 **전부 건너뛴다.**
필드를 안 만들면 실수로도 답할 수 없다.

### `total_passages` 가 늘 200이었다

검색이 `limit` 에서 멈춰서다. 그건 **개수가 아니라 상한**인데
응답에는 "구절 200개"로 실렸고, `insurers` 도 훑다 만 순서대로 2개만 나왔다.
끝까지 세게 고쳤다(구절이 2,650개뿐이라 전부 훑어도 문자열 검사 2,650번이다).

## 5. 인덱스 A — 4~5시간짜리 작업이다

| | 값 |
|---|---|
| 적재 대상 | `parse_status == "ok"` 문서 1,108개의 **고유 조항 52,899** |
| 조각 | **132,535개** (조항 길이 중앙값 356자 · 90분위 1,742자) |
| 처리량 | 초당 **7~9개** (CPU 전용, CUDA 없음) |
| 예상 | **4~5시간** |

★부풀려 말하지 않는다. "곧 끝난다"고 하면 다음 사람이 중간 결과를 완성본으로 오해한다.
재개 가능하므로(이미 들어간 `content_hash` 는 건너뛴다) 끊겨도 처음부터 하지 않는다.

### 인덱스 B 와 테이블이 다르다

필터로 나누지 않는다. 두 가지가 무너지기 때문이다.

1. **인용이 섞인다.** "제9조에 따르면"과 "어떤 사용자 보고에 따르면"이 한 답에 들어간다.
2. **순위가 오염된다.** 사례 보고는 구어체라 질문과 문장이 비슷하고 약관 조항은 법률체 문어다.
   사후 필터로 사례를 빼도 **필요한 조항이 이미 top-k 밖으로 밀린 뒤**라 되살릴 수 없다.

### 필터에 기본값을 두지 않았다

```python
def search(conn, query_vec, *, sha256s: list[str] | None, limit: int = 8)
```

`sha256s` 는 키워드 필수다. 안 넘기면 호출이 실패한다 —
기본값이 있으면 판정 경로가 조용히 전역 검색을 하고,
2019년 가입자에게 2024년 조항이 근거로 붙는다.
**빈 목록은 "쓸 수 있는 약관이 없다"이지 "전부에서 찾자"가 아니다.**

### 부트스트랩이 새 기계에서 막혀 있었다

`scripts.pg start` 는 클러스터만 만들고 `setup` 은 없는 DB 에 바로 붙어
`FATAL: database "mall_vec" does not exist` 가 났다. 그런데 오류 메시지는
**"먼저 PG를 기동하세요"** 였다 — PG 는 이미 떠 있는데도. 사실을 잘못 전한다(CLAUDE.md §3).

DB·확장 생성을 넣고, **커머스 코퍼스를 적재하지 않는** `pg init` 을 갈라 뒀다.

```bash
python -m scripts.pg start
python -m scripts.pg init
python -m scripts.index.build_clause_index
```

## 6. 통합 저장소를 하나 더 만들지 않았다

조항 본문이 문서마다 중복 저장돼 있다(**중복 65.4%**).
파일 기반 통합본을 만들려다 그만뒀다 — 그러면 같은 본문이 **세 곳**에 생긴다.

```
data/structured/…   산출물.   추출기가 만든 그대로. 불변. 재생성의 근거
PG (인덱스 A)        질의 계층. 내용 한 벌 + 발생 여러 벌
```

`pg_clause_store` 가 `file_clause_store` 와 **같은 포트**를 만족하므로
조립 지점에서 `CLAUSE_STORE=pg` 로 바꿔 낀다.

★**기본은 `file` 이다.** 인덱스 A 적재가 긴 작업이라 기계마다 상태가 다르다.
없는 것을 있는 척하지 않는다.

ERD 는 이미 `clause_content`(정체성) / `policy_clause`(발생) 로 나뉘어 있었다 —
새로 나눌 것이 아니라 **코드가 그 설계를 따라간 것**이다.

## 7. 테스트 스위트가 빨간불이었다 — 51건

### (1) Windows 인코딩 — 49건

`test_requirements_matrix` 가 `pytest --collect-only` 를 서브프로세스로 도는데
`text=True` 만 두었다. Windows 는 **시스템 코드페이지(cp949)** 로 디코딩한다.
테스트 id 에 한글이 섞여 있어 리더 스레드가 `UnicodeDecodeError` 로 죽고
`proc.stdout` 이 `None` 이 되어 매트릭스 36개·보안 13개가 **통째로** 실패했다.

> ★CI(우분투)는 UTF-8 기본이라 **초록불**이었다. 로컬에서만 빨간불이었고,
> 나는 전체를 안 돌려서 몰랐다.

### (2) 레거시 격리가 남긴 끊어진 참조

커머스 테스트가 `legacy/v3_commerce.zip` 으로 들어갔는데
매트릭스와 보안 케이스가 계속 그 파일을 가리켰다.

`retired` 로 표시하되 **딱지가 되지 않게** 검사를 하나 더 뒀다.

- 폐기에는 **이유**가 있어야 한다
- 가리키는 파일이 **정말로 없어야** 한다. 살아 있으면 폐기가 아니라 **고쳐야 할 테스트**다

★폐기는 **노드 단위**로도 된다. `TEST-SEC-001` 은 두 노드 중 하나만 사라졌는데,
케이스째 폐기하면 **살아 있는 보안 검사까지 꺼진다.** (이 함정은 새 검사가 잡아냈다.)

### (3)~(5)

- `test_signup_secret` 이 `app.schemas.commerce` 를 붙들고 있었다(→ `app.schemas.auth`)
- CS 데이터셋이 레거시 zip 안이다 → `legacy_data` 마커. **왜 빠졌는지 테스트에 적었다**
- ARCH-004 가 내 설명문을 코드 참조로 잡았다. 줄 앞 `#` 만 보니 **여러 줄 문서화 문자열의
  가운데 줄**을 못 걸렀다. 설명을 지우면 자료가 어디로 갔는지 아무도 모르게 된다 —
  **규칙이 기록을 죽이면 안 된다.** AST 로 문서화 문자열만 정확히 뺐다
