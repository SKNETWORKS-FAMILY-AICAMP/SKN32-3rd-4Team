## 1. 작업 목표

ERD가 두 문서로 갈라져 있어 같은 테이블에 대해 서로 다른 답이 나오는 상태를 해소한다.
RULE.md §3.3 — *"같은 기능의 두 구현이 생기면 즉시 하나로 통합한다."*

계기: 팀에서 `insurance_user_info` · `session` 테이블을 전제로 한 설계 논의가 나왔는데,
**두 테이블 모두 ERD v2·v3 어디에도 없다.** 팀이 다른 스키마를 보고 있다는 신호였다.

## 3. 통합에서 실제로 발견한 것

### 3-1. "v2 vs v3 충돌"로 보였던 것 중 둘은 충돌이 아니었다

| 겉보기 충돌 | 실제 |
|---|---|
| v2는 스키마 분리 / v3는 DB 분리 | v2 §0-1 **개정1이 이미 DB 분리를 택했다.** v2 §1의 다이어그램이 폐기된 v1층 |
| 이름이 다르다 (`assessment_citation` ↔ `assessment_clause_citation`) | v3가 새로 지은 이름이 아니라 **v2 개정4가 정한 이름**. v2 §3 본문이 v1층 |

**근본 원인은 v2 문서 안에 v1층과 v2층이 공존하는 것이었다.** v2 §75에
*"§1~§6은 v1 기준 서술"* 이라는 경고가 있지만, 실제로 읽는 사람은 §1의 다이어그램부터 본다.

### 3-2. ★v2의 집계 뷰 SQL이 실제로 틀려 있었다

v2 §3의 `cohort_stats` 는 `WHERE o.status = 'verified'` 를 게이트로 쓰는데,
**그 컬럼은 v2 개정2가 없앤 것이다**(가변 상태 컬럼 → 불변 사실 테이블).

즉 v2 문서 안에서 §0-1과 §3이 서로 모순된다. 그대로 구현하면 존재하지 않는 컬럼을 참조한다.
현행판에서 `EXISTS (… JOIN evidence_verification …)` 형태로 정정했다.

### 3-3. ★v3의 흡수 하나가 강제력을 약화시켰다 — 미해결로 기록

v3 §1이 `confirmed_policy_document` 를 `policy_version` 의 `NOT NULL` 컬럼으로 흡수하면서
*"효과가 같다"* 고 했는데, **같지 않다.**

- v2 개정3의 논리: enum은 `UPDATE` 로 뚫린다 → FK면 `ambiguous` 상태에서 **버전 행 자체를 못 만든다**
- v3 흡수 후: `source_url NOT NULL` 은 "출처가 있다"만 보장하고
  `identification_status='confirmed'` 는 강제하지 못한다

현행판 §9-1에 **미해결로 기록**하고 보완책(constraint trigger + audit_log)을 제시했다.
**결정은 팀에 남긴다.**

### 3-4. 실측으로 보강한 것

`core.policy_clause` 의 식별키를 `(policy_version_id, section_id, clause_no)` 로 명시했다.
근거: 전처리 산출물에서 `qualified_no` 문서 내 중복 **62,477건**(s2 기준, 1,485/1,702 문서).
특별약관마다 조 번호가 1부터 다시 시작하기 때문이며, `qualified_no` 만으로는 유일하지 않다.

## 4. 검증

문서 작업이라 실행 검증 대상이 없다. 대신 **원문 대조로 확인한 것**:

| 확인 | 방법 | 결과 |
|---|---|---|
| 21개 목록이 v3 §4와 일치하는가 | 항목 대조 | 6 + 10 + 5 = 21 일치 |
| 흡수 7건이 v3 §1과 일치하는가 | 항목 대조 | 일치 (`actor_declaration_event` 는 v3 §4 각주에서 가져옴) |
| 컬럼 정의가 v2 §2~§4에 실재하는가 | 원문 대조 | 일치. **단 §3-2의 뷰 SQL은 정정** |
| DDL 파일 존재 여부 | `find . -name "*.sql"` | **0개** — 구현은 아직 없음 |
| 코드에 테이블 참조 존재 여부 | `grep -rn "agent_client\|evidence_verification\|cohort_stats"` | **0건** |

**즉 이 ERD는 아직 종이 위에만 있다.** 현재 코드의 모델은 커머스 시절 `app/db/models.py` 뿐이다.

## 6. 후속 결정 (2026-08-02, 같은 세션)

§3-3에서 미해결로 남긴 `confirmed_policy_document` 건이 **결정됐다 — 테이블을 되살린다.**

| 검토안 | 판정 |
|---|---|
| constraint trigger 로 보완 | ✗ 트리거는 `DISABLE` · 마이그레이션 누락 · 덤프 유실로 꺼진다 |
| **테이블 복원 + `policy_version.confirmed_document_id` NOT NULL FK** | ✓ **채택** |

**채택 근거 (현행판 §9-1에 기록):**

1. **v3 자신의 기준으로도 남았어야 했다.** v3 §1의 잣대는 "테이블을 나눠야만 얻는 것은 FK를
   걸 수 있다는 것뿐"인데, 이 테이블은 정확히 FK 대상이다. **기준의 예외가 아니라 오적용이었다.**
2. FK는 엔진이 항상 강제하지만 트리거는 꺼진다.
3. 상태 enum `UPDATE` → 확정 테이블 `INSERT` 로 바뀌어 감사 로그에서 성격이 달라진다.
4. ★**v3 §5가 "잃는 것"으로 적어둔 "1 PDF에서 여러 버전" 문제가 함께 해소된다.**
   가정이 아니라 매니페스트에 이미 존재한다 —
   `quarantine_reasons: ["변형 표기가 복수입니다: ['contract_conversion','conversion_resume','child_conversion']"]`

**변경 내용**
- 테이블 21 → **22개** (`core` 6 → 7), 물리 31 → 32개
- `core.confirmed_policy_document` 신설. `status` 컬럼 없음 — **행의 존재가 곧 확정**
- `identified_by` 를 `ops.admin_user` **NOT NULL FK** — 확정에 반드시 사람 이름이 붙는다
- `policy_version.identification_status` enum **제거**, `confirmed_document_id` NOT NULL FK 추가
- `source_url` · `sha256` · `fetched_at` 을 문서 테이블로 이동 (문서의 사실이지 버전의 사실이 아님)
- `policy_version.variant` 추가 (`standard`/`contract_conversion`/`conversion_resume`/`child_conversion`)
- §1 강제 원칙 표에 "확인 안 된 약관으로 판정하지 않는다" 행 복원
- §9-2 재검토 후보의 상한이 21→18 에서 **22→19** 로 변경

**남은 구멍 (정직 기록)**: FK는 "확정 테이블에 행이 있다"만 보장한다. 그 행이 **제대로 확정된
것인지**는 보장하지 못하며, 그 이상은 사람 검수 절차의 몫이다.
