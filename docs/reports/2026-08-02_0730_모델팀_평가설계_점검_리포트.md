## 4. 핵심 결함

### 4-1. ★자동 채점이 품질이 아니라 형식을 잰다

현재 채점 = **출처 표기 여부 + 거부 표현 여부**. 이 두 가지는 아래를 통과시킨다.

> **틀린 조항을 인용하면서 "보장됩니다"라고 답한 경우** — 출처가 붙어 있으므로 O

이 서비스에서 가장 위험한 실패 유형이 정확히 채점망을 빠져나간다.

**그리고 이 저장소에 이미 답이 있다.** `docs/reports/2026-08-01_판정_정직성_인용검증_설계.md`
§3-2·§4가 지표 5개(인용 정합률·근거 초과율·적절한 기권율·과잉 기권율·스키마 준수율)와
**"LLM이 인용한 조항을 넘겨준 근거의 `qualified_no` 집합과 대조"** 를 정의해 두었다.
팀 파이프라인에 이것이 반영되지 않았다. **문서가 모델팀에 전달되지 않은 것으로 보인다.**

### 4-2. 6문항 해석의 과대성

S5가 무효이므로 **유효 표본 5문항.** 여기서 "품질 대등", "faithfulness 실증",
"sLLM 티어링의 실증 근거"는 도출되지 않는다.

두 모델이 전 문항 동일 O/X였다는 관찰의 더 타당한 해석(코덱스):

> "두 모델이 대등하다"가 아니라 **현재 실험이 두 모델을 구분할 능력이 없다.**

대안 설명: 공통 retriever가 병목이라 생성 차이가 가려짐 / 문항이 차이를 드러낼 만큼 어렵지 않음 /
공통 프롬프트가 동일한 거부를 강제 / 채점 해상도가 낮음. **S2에서 둘 다 거부한 것이 첫 번째의 증거다.**

**S2 해석도 반쪽이다.** "LLM은 올바르게 행동했다"는 맞지만, 답할 수 있는 질문에 시스템이
답하지 못했으므로 **end-to-end 로는 실패**다. 생성기 안전성과 시스템 성능을 분리 기록해야 한다.

**정식 30문항도 부족하다.** 12개사 × 상품 × 판본 × 특약이면 보험사당 2.5문항.
위험 사례 30건에서 오류 0건이어도 rule-of-three 로 **실제 오류율 95% 상한 ≈ 10%** 다.

### 4-3. 임베딩 벤치 — 순위를 주장하기엔 부족

| 문제 | 내용 |
|---|---|
| 검정 없음 | hit@5 92% vs 90% 는 80문항에서 **1~2문항 차이**. paired 검정(McNemar/bootstrap) 없이 순위를 말할 수 없다. 팀이 §3에 *"소표본으로 결론 내리지 말 것"* 이라 써놓고 80문항에는 그 잣대를 대지 않았다 |
| 문항 자동 생성의 순환성 | `gen_questions.py` 가 청크에서 문항을 만들었다면 **그 청크를 잘 찾는 모델이 이긴다.** 생성 방법·seed 미기재 |
| ★필터가 정답을 미리 줬는가 | "검색 시 insurer/generation 메타필터 **필수**". 평가에서 그 값을 정답으로 줬다면 실사용 성능은 훨씬 낮다. **세대는 우리도 모른다** — `date_confidence` 3등급이고 `unknown` 은 판정 제외 |
| 지표 부적합 | 보장 판정에는 보장조항+면책+정의+특약+대기기간+한도가 **함께** 필요. 단일 정답 청크 hit@k 로는 못 잰다 |

★팀이 §11에 **부수 이슈**로 적은 *"긍정형 질문 ↔ 면책 조항 매칭 약함"* 은 주변 이슈가 아니라
**이 서비스의 핵심 위험**이다. `docs/plans/2026-07-31_1900_팀MVP6_구조설계.md` §2-1이
*"조항만 주면 안 된다. 면책조항을 함께 반환한다"* 고 못박은 지점이다.

### 4-4. 전처리 파이프라인 병존 — 재색인 전에 정리 필요

```
저장소:  PDF → to_page_json → to_clauses → data/structured/{보험사}/s{N}_{추출기}/{sha12}.clauses.json
팀:      chunks_main.jsonl / chunks_terms.jsonl → prep_new.py → Chroma (policy_e5 / terms_e5)
```

`chunks_main.jsonl` 은 이 저장소에 없다. 팀 로컬에 있을 수 있으나
**저장소만으로는 재색인이 재현되지 않는다.**

위험은 병존 자체가 아니라 **어느 버전으로 색인했는지 표시가 없다**는 것이다.
정황상 현재 색인은 s2 기반으로 보인다 — 팀이 S2 실패 원인으로 지목한
`'보상하지 않는 사항)'` 같은 **조각 청크가 정확히 s2의 부 경계·목차 오인 결함의 산물**이다.

| 지표 | s2 | s4 |
|---|---:|---:|
| `qualified_no` 문서내 중복 | 62,477 | 31,085 |
| 20,000자 초과 조항 | 897 | 391 |
| `sale_start` 없음 | 421 | 4 |

→ **재색인 전에 입력을 s4 로 통일해야 한다.** 지금 순서(전체 재색인 먼저)는
불확실한 계보를 두 배 규모로 복제한다.

→ **"재색인 전후 비교"는 그대로 성립하지 않는다.** 조항 경계가 바뀌어 정답 청크 ID가 깨지므로,
gold 를 **원문 페이지·의미 단위 기준으로 재정합**해야 한다. S2를 검증 지표로 지정한 발상은
좋으나 이 재정합 없이는 전후 숫자가 비교 불가다.

### 4-5. 숫자 정합 — 분모 정의가 안 맞는다

`PDF 1,858건` 은 저장소의 어느 값과도 일치하지 않는다.

```
물리 파일 1,690 · 고유 sha 1,367 · 매니페스트 1,765 · 격리 336 · s2 산출물 1,702 · s4 산출물 1,367
```

"기존 2배"는 **4개사 색인 기준**으로 보인다. 그렇다면 현재 벤치·스모크 결과는
**최대 4개사 범위의 탐색 결과**이고 12개사로 일반화할 수 없다.

### 4-6. 외부 전송 — 성능이 아니라 범위 문제

티어링에서 "무거운 판단은 GPT-4.1"은 **진료비 내역서·처방전을 외부 API로 보내는 구조**를 함의한다.
`docs/plans/2026-07-31_1600_MVP_기능선정.md` §3(최소 개인정보 통제)·§4(비범위)에 걸린다.

임베딩을 로컬 e5로 고른 이유가 *"민감정보 외부 전송 없음"* 이었는데 생성 단계에서 뒤집힌다.
**무엇을 외부로 보내는지가 4축(정확도·속도·비용·보안) 중 하나가 아니라 선행 제약이다.**

### 4-7. ★부수 발견 — 인수인계 계약서의 import 경로가 실제와 다르다

`docs/handoff/05_계약_AI2_판정.md` §3이 *"인용 검증은 이미 만들어져 있다"* 며
`from app.insurance.citation_guard import ...` 를 제시하는데, **그 모듈은 없다.**

```
$ python -c "import app.insurance"
ModuleNotFoundError: No module named 'app.insurance'
```

| 계약서 표기 | 실제 위치 |
|---|---|
| `app/insurance/citation_guard.py` | **`app/core/domain/citation_guard.py`** |
| `app/insurance/kcd.py` | `app/core/domain/kcd_ranges.py` |
| `app/insurance/precheck.py` | `app/core/usecases/precheck.py` |
| `app/insurance/assess.py` | 아직 없음 (담당 작업분) |

`tests/test_citation_guard.py` 는 올바른 경로(`app.core.domain.citation_guard`)를 쓴다.
**계약서를 그대로 따르면 import 에서 막힌다.** 계약서를 고치거나 모듈을 옮기거나 정해야 한다.

> ★이 발견의 함의가 더 크다 — **인용 검증기는 이미 구현돼 있다.**
> 모델팀이 "자동 채점에 인용 검증이 없다"는 상태인 것은 만들 것이 없어서가 아니라
> **있는 것이 연결되지 않아서**다. 붙이는 비용이 작다.

### 4-8. ★★더 심각한 것 — `verdict` enum 자체가 문서와 코드가 다르다

스토리보드를 실제 계약(`app/schemas/precheck.py`)에 맞추려다 발견했다.

| | 값 |
|---|---|
| **실제 코드** (`app/core/domain/insurance.py` 의 `Verdict`) | `likely_covered` · `unlikely` · `needs_documents` · `needs_expert` |
| `05_계약_AI2_판정.md` §4 · `08_계약_프론트.md` §1 | `covered` · `conditional` · `not_covered` · `unknown` |

**두 집합에 겹치는 값이 하나도 없다.** 프론트가 `08` 의 상태표대로 분기하면
**어떤 응답에도 매칭되지 않는다.** import 경로(§4-7)보다 이쪽이 더 위험하다 —
경로 오류는 즉시 `ModuleNotFoundError` 로 드러나지만, enum 불일치는 **조용히 빈 화면**이 된다.

`app/schemas/precheck.py` 주석이 경위를 남겨 두었다:

> *"처음에 `covered / not_covered / conditional / unknown` 4값을 여기 새로 만들었다가
> `app/core/domain/insurance.py` 에 이미 `Verdict` 가 있는 것을 뒤늦게 알았다.
> 같은 사실이 두 곳에 있으면 반드시 갈라진다(ARCH-003 이 이걸 막는다).
> 도메인 쪽 4단이 더 낫다 — '이진 판정은 만들지 않는다'는 원칙이 값 자체에 박혀 있다."*

**즉 코드는 이미 정리됐는데 handoff 문서 2건이 폐기된 이름을 들고 있다.**
그리고 기권 여부는 `verdict` 가 아니라 **별도 필드 `abstained: bool`** 로 나간다 —
`08` 의 "`unknown` 이면 확인 불가" 매핑은 `needs_expert` + `abstained` 로 바꿔야 한다.

→ `05` · `08` 을 코드 기준으로 정정해야 한다. **이 리포트는 정정하지 않았다**(점검 범위 밖).
   `docs/handoff/10_계약_모델_평가.md` §2-1 과 `storyboard.html` 에는 실제 값으로 반영했다.
