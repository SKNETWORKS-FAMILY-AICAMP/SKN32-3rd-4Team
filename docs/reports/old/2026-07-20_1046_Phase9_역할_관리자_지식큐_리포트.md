## 1. 구현
- **역할 모델**: `User.role`(기본 `USER`), 허용값 `USER`/`ADMIN`(`app/auth/roles.py`).
  **JWT에 role을 넣지 않는다** — 토큰에 박으면 강등이 만료 전까지 반영되지 않아 stale privilege가
  생긴다. `get_current_user`가 어차피 요청마다 DB에서 User를 읽으므로 **DB 값을 신뢰**하면
  추가 비용 없이 항상 최신 권한이 적용된다.
  **알 수 없는 role은 USER로 폴백하지 않고 `InfraError`**(데이터 오염 시 조용한 권한 부여/박탈 금지).
- **관리자 API**(`app/routers/admin.py`): `/orders`, `/events`, `/index`, `/knowledge-gaps`.
  **fail-closed는 라우터 전역** — `APIRouter(dependencies=[Depends(require_admin)])`.
  엔드포인트마다 붙이면 새 엔드포인트에서 누락되므로 라우터 단위로 강제하고 가드레일 테스트로 고정.
- **마이그레이션**(`scripts/manage.py`): `create_all`은 **기존 테이블에 컬럼을 추가하지 않는다**.
  `_add_missing_columns`로 `users.role`을 멱등 추가(기존 행은 전부 `USER`, 자동 승격 없음) +
  **`_verify_schema` 사후 검증**(실패 시 `InfraError`).
- **부트스트랩**: `python -m scripts.manage promote|demote <username>` **명시 CLI만**.
  환경변수·가입 시 자동 승격 같은 암묵 경로 없음. **마지막 ADMIN 강등 거부**(lockout 방지) +
  변경은 `run_events`에 감사 기록.
- **지식보강 큐**: `KnowledgeGap` 테이블 + `app/obs/knowledge_gaps.py`. RAG가 abstention한 질문을
  적재하되 **저장 전 PII 마스킹**(`app/obs/pii.py`). 적재는 유스케이스가 아니라 **라우터(인터페이스
  계층)**에서 — 유스케이스는 DB를 모른다(Clean Arch 경계). `purge-gaps --days N`로 보존기간 파기.

### Codex 지적 처리
**설계(FIX)** 4건 반영: 토큰에서 role 제외는 **맞는 선택**이나 알 수 없는 role 폴백 금지(반영),
ALTER TABLE 방식은 **사후 스키마 검증** 필요(반영), 질문 원문 PII 위험 → 마스킹·보존파기·관리자 전용(반영),
라우터별 수동 권한검사는 누락된다 → **라우터 전역 fail-closed**(반영) + promote 위험 → **마지막 ADMIN
보호·감사 기록**(반영).

**구현** 지적 반영:
1. **마스킹을 강제하는 구조가 없다**(가장 중요) → `KnowledgeGap` 직접 생성을 금지하는 **정적 스캔
   테스트** 추가 + `/knowledge-gaps` **출력 시에도 재마스킹**(심층 방어).
2. `/events`의 `detail`이 자유 문자열 → **출력 시 마스킹** 한 겹 추가.
3. `/index`가 `check_readiness()`를 그대로 노출(내부 경로 담긴 `hint` 포함) → **필드 화이트리스트**.
4. 카드 정규식 **부분 매칭**: 뒤 lookahead만으로는 부족 — 엔진이 시작 위치를 옮겨 중간부터 매칭해
   `"1234 [CARD]"`가 됐다(**내가 쓴 테스트가 실제로 잡아냄**). 앞쪽 lookbehind까지 추가해 해결.
5. `+82` 국제전화·소문자 주문번호·이메일 끝 문장부호 처리 보완.

**적용하지 않은 지적 1건**: "주문번호가 진짜 영숫자면 `[0-9A-Z]`여야 한다" → 이 시스템의 주문번호는
`uuid4().hex[:11].upper()`라 **16진수만 나온다**. 패턴은 그대로 두고 오해를 부르던 주석을 정정했다.

## 3. ★ 정직한 finding / 한계
- **PII 마스킹은 정규식이라 완전한 비식별이 아니다.** 이름·주소·계좌·여권번호·IP는 못 잡는다.
  Luhn 검증을 하지 않아 일반 긴 숫자열도 카드로 오탐할 수 있다(과잉 마스킹은 **안전한 방향의 오차**라
  의도적으로 허용). 그래서 마스킹 하나에 기대지 않고 **관리자 전용 + 저장 시 마스킹 + 출력 시
  재마스킹 + 보존기간 파기**의 다층으로 간다. "비식별 완료"라고 주장하지 않는다.
- **정적 스캔 가드레일의 한계**: 별칭 import·동적 접근·raw SQL 삽입은 못 잡는다(Codex 지적).
  그래서 출력 재마스킹을 함께 뒀고, 그 상황을 **직접 SQL 삽입 재현 테스트**로 고정했다.
- **Alembic 미도입**: 현재는 멱등 스크립트 + 사후 검증으로 충분하나, 제약조건 변경·롤백·이력·
  다중 인스턴스가 필요해지면 그때가 도입 시점(후속).
- 관리자에게 `user_id`·`trace_id`를 노출한다 — 운영상 필요한 식별자로 판단해 유지하되,
  최소노출 재검토는 열어둔다.
- 큐 **암호화 저장·관리자 세부권한 분리·조회 감사로그**는 후속(이번엔 마스킹·전용접근·파기까지).
