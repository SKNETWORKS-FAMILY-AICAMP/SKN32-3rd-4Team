# Phase 13 후속 — 얼굴 인식률 개선(품질 게이팅 + 조건부 전처리 + 다중 등록)

- 작성일시: 2026-07-20 22:30
- 계기: 사용자 지적 "insightface 인식률 낮던데 밝기 보정 같은 전처리 해야 하는 거 아니야?
  그리고 insightface가 최선이야?" — 웹서치 대신 **실측 데이터**로 원인을 규명하고 Codex와 논의.

## 1. 실측으로 원인 규명 (밝기 전처리가 답인지 먼저 검증)
- **검출은 저조도에 이미 robust**: RetinaFace가 평균밝기 14(거의 깜깜)에서도 얼굴 다 검출.
  CLAHE/감마가 검출 수를 안 바꿈 → "검출을 위한 밝기 보정"은 insightface엔 거의 무의미.
- **매칭(임베딩) 열화 원인은 정보 손실**: 동일인 코사인 —
  - 저조도 gain0.18(mean22): 원본 0.918 → CLAHE 0.955 (소폭↑)
  - 블러 k21: 0.680, 저해상 0.15배: 0.575 (전처리로 **복구 불가**)
  - 정상광: 0.985 / 타인 0.083 (분리 우수 — 모델 자체는 약점 아님)
- **정상광 CLAHE는 해로움**: 정렬 crop에 CLAHE를 정상광에서 적용하면 임베딩이 0.888로 이동.

## 2. Codex 논의 결론 (2라운드)
병목은 검출·모델이 아니라 **정보 손실 + 등록 오염**. 모델 스왑보다:
- (a) **품질 게이팅**(등록 strict / 검증 loose): 흐림(라플라시안 분산)·밝기·얼굴 크기·자세
  (yaw/pitch)·검출신뢰도로 저품질을 **명시적 재촬영 요구**로 거부(무폴백). 특히 나쁜 기준
  임베딩이 이후 매칭을 오염시키는 걸 막음.
- (b) **CLAHE는 정렬 crop luminance에, 저조도 조건부로만**(정상광 미적용). 검출 전 원본이 아님.
- (c) **다중 이미지 등록**(품질 통과분 임베딩 평균 후 재정규화).
- **insightface(ArcFace)는 CPU 오픈소스의 강한 기준선**. AdaFace(저품질 특화, CVPR2022)는
  현재 수치엔 **스왑이 과설계** — 고정 테스트셋에서 FAR 고정 시 FRR 유의미 개선 실증 시에만 채택.

## 3. 구현
- `app/ml/face.py` 파이프라인 재구성: 디코드 → 단일 얼굴 → **품질 게이팅** → 라이브니스 →
  `face_align.norm_crop`(112×112 정렬) → **저조도 조건부 CLAHE** → 임베딩(`rec.get_feat`).
  수동 정렬+인식 경로가 `app.get()` 임베딩과 코사인 1.0으로 동일함을 확인 후 CLAHE를 정확한
  지점(정렬 후·임베딩 직전)에 주입. `pose=[pitch,yaw,roll]`(insightface 소스 확인)에서 roll은
  정렬로 보정되므로 pitch·yaw만 게이팅.
- `app/services/face_service.py` `register_face(images: list)`: 각 샷 strict 게이팅 후 통과분
  임베딩 평균. 전샷 품질 실패 → 재촬영 사유 전파, 품질통과-라이브니스전멸 → 위조 일반 메시지.
- `app/routers/face.py`: `/register`가 `images`(다중) 수용. `app/core/config.py`에 품질 프로파일
  (REGISTER/VERIFY dict)·CLAHE 조건·등록 샷수 추가.
- 프론트 `mypage.js`: 등록 시 3프레임 자동 촬영(0.5s 간격)→`images` 다중 업로드, "품질 통과 N장
  평균" 표시.

## 5. 정직한 한계 (유지)
- 게이팅 임계는 112×112 정렬 기준 **시작값**이며 실 genuine/impostor 분포로 튜닝 필요(라플라시안
  분산은 카메라·리사이즈에 민감). CLAHE의 저조도 이득은 소폭(0.918→0.955)이고 정상광 미적용.
- 실 웹캠 3프레임 캡처·라이브 얼굴 수용은 헤드리스 환경에서 검증 불가(Phase 13과 동일).
- insightface 사전학습 모델 비상업 연구용, 라이브니스 단일 모델, 시도제한 인메모리(유지).
