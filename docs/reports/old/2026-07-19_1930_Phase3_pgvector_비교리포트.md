## 2. 구현 (같은 포트, 교체 가능)
- `app/adapters/pgvector_retriever.py`(`RetrieverPort`, backend="pgvector"): 쿼리 임베딩(ko-sroberta, FAISS와 동일)
  → `embedding <-> %(q)s`(L2) top-k → 중립 `Evidence`(score=1-d/2, 백엔드 distance 비노출). 연결실패→InfraError(무폴백).
- `app/adapters/pgvector_index.py`: `ensure_schema`(확장·`rag_chunks(vector(768))`·HNSW, 멱등), `ingest_corpus`
  (FAISS와 **동일 로딩·청킹·임베딩**으로 공정 비교, TRUNCATE 후 삽입).
- `scripts/pg.py`(start/stop/status/setup, 최소 clean 환경), config `PGVECTOR_DSN`, `pg` pytest 마커.

## 3. ★ FAISS vs pgvector 비교 (실측, 동일 rag_v1 30문항·동일 임베딩)
| 백엔드 | Hit@3 | 평균 검색시간/질의 |
|---|---|---|
| FAISS (in-proc) | **1.000 (22/22)** | ~288 ms |
| pgvector (PG 16.14, HNSW) | **1.000 (22/22)** | ~125 ms |

- **랭킹 동등**: 동일 임베딩이라 Hit@3·상위 출처가 일치(parity 테스트 통과). 벡터 저장·검색 엔진만 다름.
- 지연은 두 경로 모두 **쿼리 임베딩 계산이 지배적**(공통). 측정 차이는 주로 FAISS 첫 질의 워밍업·변동. 정직히
  "품질 동등, 지연은 임베딩 비용에 좌우"로 해석(소규모 corpus 8청크 기준). 대규모·필터·동시성 특성은 후속 측정.
- 학습 포인트: pgvector `<->`(L2)/`<=>`(cosine)/`<#>`(내적), HNSW 인덱스, register_vector, numpy 파라미터 어댑트.
