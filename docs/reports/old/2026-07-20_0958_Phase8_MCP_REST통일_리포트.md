## 1. 진단 — 실제 parity 위반은 하나였다
| 기능 | REST | MCP | 판정 |
|---|---|---|---|
| RAG 답변 | `build_answer_question()` 유스케이스 | **`app.rag.qa.answer()` 레거시** | **위반: 구현 2벌** |
| 벡터 검색 | `rag.service.search` | `rag.service.search` | 이미 단일 구현 → **손대지 않음** |
| 상품 카탈로그 | `db.query(Product)` | `db.query(Product)` | 질의 중복 |
| 커머스 도구 5종 | — | `commerce_tools`(에이전트와 공유) | 이미 단일 구현 |

`vector_search`는 응답에 `distance`가 포함된 기존 계약이라 포트 경유로 바꾸면 shape가
깨진다. **이미 REST와 같은 구현을 쓰므로 parity 위반이 아니다** → 계약을 흔들지 않고 그대로 뒀다
(YAGNI: 백엔드 교체성은 이번 DoD가 아님).

## 2. 구현
- **`app/adapters/rag_view.py`(신규)**: `AnswerResult → {answer, sources:[{source,page}]}` 변환을
  **1벌로 통합**. REST 라우터와 MCP `rag_qa`가 이 함수를 공유 → 변환이 두 벌이 아니라 어긋날 수 없다.
  응답 계약은 **`TypedDict`(`AnswerDict`/`SourceDict`)**로 고정(정적 검사 가능, Codex 지적 반영).
- **MCP `rag_qa` 수렴**: 레거시 `rag.qa.answer` → **REST와 동일한 `build_answer_question()`**.
- **`app/services/catalog_query.py`(신규)**: 상품 질의 1벌. **세션 수명은 호출자 소유**
  (REST=요청 스코프, MCP=`with_db`) — 공용 함수가 세션을 열지·닫지 않는다.
  **ORM 행이 아니라 세션 독립 불변 DTO(`ProductView`)를 반환**하고 `inventory`를 `joinedload`로
  세션 안에서 해석 → `DetachedInstanceError`·N+1 동시 제거(Codex 지적 반영).
- **레거시 삭제**: `app/rag/qa.py`, `order_service.create_order` (정적 호출자 0 확인 후).
  MCP의 미사용 import(`rag_qa_mod`, `Product`)도 제거.

### ★ 발견: 두 인터페이스의 의존성 바인딩 시점이 다르다
parity 테스트 작성 중 드러난 사실 — REST 라우터는 모듈 로드 시 `build_answer_question`을
import해 **조기 바인딩**하고, MCP 도구는 호출 시점에 import해 **지연 바인딩**한다.
운영 동작은 같지만 **테스트에서 한쪽만 패치하면 조용히 실제 LLM을 호출**한다(처음 테스트가
그렇게 실패했다). 두 참조를 모두 교체하도록 고치고, 이 차이를 테스트에 주석으로 남겼다.

### Codex 지적 처리
- 설계(FIX): 유스케이스 DTO는 내부 표준·**MCP 계약 shape는 어댑터가 명시 변환**(반영),
  공용 함수는 **세션을 소유하지 않게**(반영), parity는 **고정 Fake로 DTO 동등성**(반영),
  삭제 전 **정적 호출자 확인**(반영).
- 구현: ORM 반환의 `DetachedInstanceError` 위험 → DTO 반환으로 수정. `dict[str,Any]`가
  계약을 강제 못함 → `TypedDict`. 정렬 결정성·1:1 관계 전제 → **본 코드베이스에서 충족 확인**
  (`product_code: Mapped[str]` = NOT NULL + unique, `inventory`는 `uselist=False`).
- 카탈로그 projection이 REST(재고 포함)/MCP(재고 제외)로 다른 것은 **계약이 다른 것**이지
  중복 구현이 아님 — Codex도 동의.

## 4. ★ 정직한 finding — 테스트 수가 줄었다(커버리지 손실 아님)
CI **237 → 232**. 레거시 `test_qa.py` 8건을 지웠기 때문이다. **각 건의 행선지를 추적**했다:

| 삭제된 레거시 테스트 | 처리 |
|---|---|
| 빈 질문 → ValidationErr | 기존 `test_empty_question_raises_validation`이 커버 |
| 근거 없음 → NO_ANSWER | 기존 `test_req_rag_05_abstention_when_no_evidence` |
| 출처 dedup·1-based page | 기존 `test_citations_dedup_and_order` + parity 테스트 |
| 빈 LLM 응답 → LLMOutputError | 기존 `test_empty_reply_is_llm_output_error` |
| 프롬프트에 근거 본문 포함 | **이관**(아래 인젝션 방어 테스트가 함께 단언) |
| 프롬프트 인젝션 방어 | **이관** → `test_answer_question.py` |
| PDF 파싱 실패 → InfraError | **이관** → `tests/test_build_index.py`(신규). `test_rag.py`는 ml 마커라 거기 두면 CI에서 빠지므로 마커 없는 파일로 분리 |
| **LLM이 NO_ANSWER 반환 시 그대로 전달** | **대응 테스트가 없었음 → 신규 작성** |

마지막 항목이 실제 공백이었다. 추적하지 않았으면 조용히 잃었을 커버리지이고, 겸사겸사
"근거 없음 abstention(sources=[])"과 "모델이 스스로 abstain(근거는 있으므로 sources 유지)"이
**서로 다른 경로**라는 점을 테스트로 고정했다.

## 5. 남은 한계 / 후속
- `TypedDict`는 **런타임 검증이 아니다**(정적 힌트). 런타임 계약 강제는 parity 테스트가 담당.
- `config.py`의 provider 모델ID(LOCAL/OPENAI/GEMINI_MODEL)는 `llm_clients`가 실제 사용 중이라
  **이번 삭제 대상이 아니다**(레지스트리 단일화는 별도 과제). 신 코드 하드코딩 금지는 가드레일 유지.
- 카탈로그 전체 `.all()` — 규모가 커지면 pagination 필요(현 계약엔 없음, 후속).
- 조기/지연 바인딩 불일치는 두 진입점을 명시적 DI로 맞추면 더 견고(후속).
