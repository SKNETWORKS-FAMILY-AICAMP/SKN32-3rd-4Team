# SLM 파인튜닝 후보 조사 — 분류 체계 · 프로젝트 적용성 · 데이터 조달

- 일자: 2026-07-22
- 목적: 수업에서 배운 SLM 파인튜닝을 이 프로젝트(`_unified_mall_2`)에 적용할 후보를 조사·랭킹.
- 방법: 코드베이스 실측(데이터 자산·LLM 접점) + Codex 논의 + 웹 조사(한국어 공개 데이터셋).
- 결론(선정): **① CS 분류 QLoRA → ② 근거기반 QA 생성 QLoRA** 순차. 학습 환경 = 수업 제공 GPU 서버.

## 1. 파인튜닝 전체 분류 체계

### 1-A. 파라미터를 얼마나 갱신하는가 (PEFT 축)

| 방법 | 설명 | 컴퓨트 | 본 프로젝트 적합성 |
|---|---|---|---|
| Full fine-tuning | 전체 가중치 갱신 | 매우 큼 | ✗ 수업 규모 초과 |
| **LoRA** | 저랭크 어댑터만 학습(원본 동결) | 중 | ○ 대부분 태스크에 적합 |
| **QLoRA** | 4bit 양자화 베이스 + LoRA | 소(6~8GB~) | ◎ **채택** — 단일 GPU로 충분 |
| Adapter / (IA)³ / BitFit | 소형 모듈·일부 파라미터 | 소 | △ LoRA로 대체 가능 |
| Prefix / P-tuning / Prompt-tuning | soft prompt 벡터만 | 매우 소 | △ 성능이 LoRA보다 약함 |

### 1-B. 어떤 학습 신호를 쓰는가

| 방법 | 설명 | 본 프로젝트에서 |
|---|---|---|
| Continued pre-training | 도메인 원문(라벨 없음) 추가학습 | △ 커머스 말뭉치가 적어 효과 제한 |
| **SFT / Instruction tuning** | 입력→정답 쌍 지도학습 | ◎ **핵심 경로**(분류·근거지지·QA 전부) |
| 선호 최적화(DPO/ORPO/KTO) | 좋은답↔나쁜답 쌍 정렬 | △ 선호쌍 제작 부담, 수업 난이도 높음 |
| **Distillation(교사→학생)** | 큰 LLM 출력으로 SLM 학습 | ◎ **데이터 부족 돌파 수단**(②에서 사용) |
| Head fine-tuning(인코더) | BERT류 + 분류/NER 헤드 | ○ 분류·NER에 가장 저렴·확실 |

### 1-C. 모델 형태

- **판별형(Encoder + head)**: 분류·NER·회귀. 작고 빠르며 소량 데이터에 강함.
- **생성형(Causal SLM + LoRA/QLoRA)**: instruction·QA 생성. ← 수업 실습 목표에 부합.
- **Cross-encoder**: 리랭킹 전용(생성형 아님).

## 2. 프로젝트 태스크별 적용성 판정

전제: 본 프로젝트의 LLM/ML 접점은 **포트/어댑터 뒤**에 있어 모델 교체 후 기준선 대비 정량 비교가 쉽다.

| 태스크 | 권장 방법 | 연결 지점 | 판정 |
|---|---|---|---|
| **CS 티켓/의도 분류** | SLM QLoRA(SFT) 또는 인코더 head | `app/ml/intent.py`, `app/workflow/ticket_graph.py` | **최적** — 라벨 보유, 웹 보강 풍부, 규칙기반 기준선과 직접 비교 |
| **근거기반 QA 생성** | SLM QLoRA(SFT + distillation) | `ModelGateway` 포트 | **양호** — 데이터는 보강·증류로 해결 가능. LoRA 실습 취지에 가장 부합 |
| 근거 지지 판정(SupportCheck) | NLI SFT | `app/application/self_verify.py` | 양호 — 안전성 payoff 큼, KorNLI로 대량 보강 |
| RAG 리랭커 | Cross-encoder 파인튜닝 | `app/adapters/reranker.py`(RerankerPort) | 보통 — 유용하나 **생성형이 아니라** LoRA 실습 취지와 어긋남 |
| PII NER | 토큰분류(BIO) | 정규식 마스킹 앞단 | 보통 — 문서화된 정규식 한계를 실제 보완하나 라벨 제작 부담 |
| 감성분석 교체 | 인코더 head | `app/ml/sentiment.py` | **낮음** — 이미 KoELECTRA 사용 중, 원자료 빈약(칭찬 5·불만 8) |
| ReAct tool-calling | — | — | **제외** — 학습 궤적 데이터 없음, 로컬 Gemma tool_calls 미지원 |

## 3. 보유 데이터 실측

`data/cs_inquiries.csv` (본 조사에서 직접 집계):

- **총 60건 / 7클래스**: 상품문의 13, 환불 10, 교환 9, 결제 8, 불만 8, 배송 7, 칭찬 5
- 채널: 앱 16, 전화 14, 카카오톡 13, 웹 10, 이메일 7
- 본문 길이: 최소 19 / 평균 29.9 / 최대 36자

`data/eval/rag_v1.jsonl`: 30문항(answerable 20 / unanswerable 5 / adversarial 3 / paraphrase 2), 근거 출처·정답 포함.
`data/docs/`: 환불교환정책.pdf + 텍스트 문서 3종. `products.csv` / `orders.csv` / `inventory.csv`.

**라벨 체계 불일치(중요)**: `cs_inquiries.csv`의 7클래스(상품문의/환불/교환/결제/불만/배송/칭찬)와
`app/ml/intent.py`의 6클래스(주문/추천/조회/불만/칭찬/인사)는 **서로 다른 체계**다. 구현 계획서에서
학습 타깃 라벨 체계를 먼저 확정해야 한다(둘 중 택일 또는 매핑 정의).

## 4. 데이터 부족분 → 웹 보강 후보 (조사 결과)

| 태스크 | 보유 | 웹 보강 데이터셋 |
|---|---|---|
| CS/의도 분류 | 60건 + 라벨 | AI Hub 한국어 대화(소상공인·공공민원 대규모), AI Hub 민원상담 LLM instruction tuning 데이터, KLUE-TC(YNAT) |
| 근거지지/NLI | 30문항 | KorNLI(kakaobrain), KLUE-NLI(entailment/neutral/contradiction) |
| 근거기반 QA | 30문항 | KorQuAD, KLUE-MRC (+ 정책 PDF 기반 교사 합성) |
| 감성 | 칭찬 5·불만 8 | NSMC(네이버 영화리뷰), AI Hub 감성대화(7감정) |
| PII NER | 정규식만 | KLUE-NER(BIO 6종), nlp-kmu/kor_ner |
| 리랭커 | 30문항 | DPR-KO, KorQuAD positive passage, base=`cross-encoder/ms-marco-MiniLM-L6-v2` |
| instruction 포맷 참고 | — | KoAlpaca-RealQA / v1.1a(beomi), KULLM-v2, komt(davidkim205) |

**조달 리스크(정직 기록)**: AI Hub는 **회원가입 + 데이터 신청 승인**이 필요해 즉시 확보를 보장할 수 없다.
따라서 구현 시 **HuggingFace 즉시 가용분(KLUE·KorQuAD·KoAlpaca·NSMC)을 1차 경로**로 잡고, AI Hub는
승인 시 보강하는 구조로 설계한다 — 승인 지연이 과제를 막지 않도록 한다.

## 5. 선정 결과 및 근거

### ① CS 분류 QLoRA (1순위)
- instruction 포맷(`"다음 문의를 분류: {content}"` → 라벨)으로 소형 instruct 모델 QLoRA SFT.
- 데이터: 보유 60건(라벨 존재) + 웹 보강으로 클래스 균형화.
- 평가: **규칙기반 `intent.py` 기준선 대비** Accuracy·Macro-F1·혼동행렬.
- 선정 이유: 라벨이 이미 있고, 기준선이 코드로 존재해 개선폭을 정량 제시하기 가장 쉽다.

### ② 근거기반 QA 생성 QLoRA (2순위, ① 이후)
- 데이터 벽을 **보강 + 증류**로 돌파: KorQuAD로 근거기반 QA 대량 확보 + 정책 PDF에서 교사 모델로
  도메인 QA 합성(정답이 근거에 실제 포함되는지 규칙 검증으로 품질 필터) + KoAlpaca로 포맷 참고.
- 평가: abstention 정확도·citation 준수·근거 지지율(기존 `rag_v1.jsonl` 활용).
- **교사 모델 가용성 확인 결과**: `.env` 부재로 API 키 미설정이나, 로컬 Gemma(`gemma-4-e4b`)가 구동 중이며
  도메인 QA 합성은 정책 문서를 컨텍스트에 넣는 추출형이라 로컬 모델로도 수행 가능. API 키가 있으면
  교사 품질만 향상되며 **필수 조건은 아니다**.

### 순차 진행 이유
두 과제는 QLoRA 학습 하네스·instruction 포맷터·어댑터 연결·평가 리포트 틀을 공유한다. ①에서 공통
하네스를 완성·검증한 뒤 ②로 확장하면 총 작업량이 2배가 아니라 약 1.4배이며, 중간에 동작하는 산출물이
확보된다. 베이스 모델 1개에 **어댑터 2개를 스왑**하는 구성은 본 프로젝트의 포트/어댑터 구조와도 개념이 일치한다.

## 6. 다음 단계

구현 계획서(`plans/`) 작성 시 확정할 사항:
1. 학습 타깃 라벨 체계(cs_inquiries 7클래스 vs intent 6클래스 — §3 불일치 해소)
2. 베이스 모델 선정(수업 GPU 서버 사양에 맞춰 0.5B~3B급)
3. 파인튜닝 모델을 꽂을 **이음매 설계** — `intent.py`는 현재 포트가 아니므로, 기존 얼굴인식 백엔드
   선택 방식처럼 config 기반 백엔드 전환 도입 검토. 어댑터 부재 시 **무폴백(ConfigError)** 로 실패시킬 것.
4. 학습 산출물(가중치·어댑터) **커밋 제외**(.gitignore) 및 재현 스크립트 위치 규칙
