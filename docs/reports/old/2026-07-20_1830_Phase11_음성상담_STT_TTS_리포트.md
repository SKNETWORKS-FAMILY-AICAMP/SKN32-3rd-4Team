# Phase 11 — 음성 상담(STT/TTS)

- 작성일시: 2026-07-20 18:30
- 계기: `프로젝트설명.txt` [추가 서비스 제안] 6개 전부 반영 지시 (사용자 확인 완료) — 그중
  2번(음성 상담 챗봇, STT/TTS) 구현.

## 1. 기술 선택
- STT: `faster-whisper==1.2.1`(CTranslate2 기반, 로컬 실행, API 키 불필요)
- TTS: `pyttsx3==2.99`(Windows SAPI5, 완전 오프라인, 네트워크 호출 없음)
- Codex 검토(계획 단계)에서 GPU 미검출 확인됨 → `small` 모델 + CPU + int8로 확정(대형 모델
  시도 안 함).

## 2. 환경 실측 (구현 전 사전 검증)
- 이 머신에 한국어 SAPI5 보이스(Microsoft Heami)가 이미 설치되어 있음을 확인 — 별도 설치
  안내 없이 바로 사용 가능.
- TTS→STT 왕복 실측: "안녕하세요, 주문 상태를 확인하고 싶습니다." → TTS 0.17초 →
  faster-whisper(small, cpu, int8) 모델 로드 2.65초 + 추론 2.98초 → 인식 결과
  "안녕하세요. 주문 상태를 확인하고 싶습니다."(언어감지 ko, 확률 1.0) — 실제로 동작함을
  코드 작성 전에 먼저 확인.

## 3. 구현
- `app/ml/voice.py`: `transcribe_audio()`/`synthesize_speech()`. 감성분석(`app/ml/sentiment.py`)과
  동일한 패턴 — `lru_cache` 싱글턴 lazy 로드, 모델/보이스 로드 실패는 `ConfigError`, 빈 입력은
  `ValidationErr`. TTS 결과는 `wave` 모듈로 실제 오디오 프레임이 있는 유효한 WAV인지 검증 후
  반환(깨진 파일을 조용히 넘기지 않음).
- `app/routers/voice.py`: `POST /api/voice/stt`(multipart 파일 업로드) /
  `POST /api/voice/tts`(JSON → `audio/wav` 응답). 인증 불필요(에이전트 채팅과 동일하게 공개).
- `app/core/config.py`: `STT_MODEL`/`STT_DEVICE`/`STT_COMPUTE_TYPE`/`STT_LANGUAGE`/
  `TTS_VOICE_MATCH` 추가(하드코딩 금지 — 전부 설정으로).
- `app/static/common.js`: `transcribeBlob()`/`synthesizeAndPlay()`/`createVoiceRecorder()`
  공용 헬퍼 추가 — Phase 12(화상 상담)에서도 동일 함수를 재사용한다.
- `app/static/index.html`/`app.js`: 마이크 버튼(🎤, 토글식 녹음) + "응답 음성으로 듣기(TTS)"
  체크박스. 마이크 권한 거부는 조용히 텍스트 모드로 넘어가지 않고 `voiceStatus` 영역에 명시
  에러 메시지를 띄운다(무폴백).

## 4. 검증
- `pytest -m ml tests/test_voice.py` — 3 passed(TTS→STT 실 왕복, STT 빈입력, TTS 빈입력).
- `pytest -m "not llm and not ml and not pg and not mcp"` — 전체 통과(회귀 0).
- 실 dev 서버 + 브라우저로 라이브 확인:
  - `POST /api/voice/tts` 실제 호출 → 200 OK, 114KB WAV 반환, `synthesizeAndPlay()`로 실제
    재생 확인(`audio.paused === false`, `duration ≈ 2.17s`).
  - 마이크 버튼 클릭 → `getUserMedia` 권한 거부 시 정확히
    "마이크 권한이 거부되었거나 사용할 수 없습니다: Permission denied" 메시지 노출 확인
    (이 브라우저 자동화 환경은 실 마이크 입력 자체는 지원하지 않아 녹음→STT 왕복은
    `pytest`의 실 모델 테스트로 검증했고, 브라우저에서는 권한 거부 경로와 TTS 재생 경로를
    직접 확인했다).

## 5. 디버깅 메모 — 브라우저 자동화 도구의 캐시 문제(제품 버그 아님)
라이브 확인 중 `app.js`를 여러 번 수정했는데도 브라우저가 계속 예전 버전(마이크 코드 추가
이전)을 실행하는 문제를 겪었다. `curl`로 서버 응답은 최신임을 확인했고, `fetch(..., {cache:
'no-store'})`는 최신 내용을 받아왔지만 실제 `<script src>` 태그 로드는 계속 예전 캐시를
재사용했다 — `navigate(force:true)`도 이 서브리소스 캐시를 우회하지 못했다. 진단 마커
(`window.__DIAG_*`)를 코드에 임시로 심어 원인을 좁혔고, 쿼리스트링을 바꾼 완전히 새로운
문서 URL로 이동했을 때만 신선한 로드가 재현됨을 확인해 이 도구의 브라우저 캐시 문제임을
확정했다(서버·코드 문제 아님). 디버깅에 썼던 진단 마커는 전부 제거하고 커밋했다.
