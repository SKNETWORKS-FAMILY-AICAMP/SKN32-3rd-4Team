## 1. 배경 — Codex 전체분석 결과

시니어 리뷰어 관점 총평: **"통합 역량은 강하나 프로덕션 보안·생체 정확성을 입증한 시스템은
아니다. 포트폴리오에선 '완성형 플랫폼'이 아니라 '넓은 프로토타입 + 검증된 핵심 경계'로 정직히
제시하라."**

- 건전한 부분(실재): `application/ports.py` Protocol, `composition.py` 주입, `test_arch.py`
  프레임워크 import 금지, 주문 유스케이스의 트랜잭션·멱등 경계.
- 과장된 부분: 라우터가 서비스를 직접 조립하는 Composition Root 불일치, "무폴백"의 예외
  (stage 없는 JWT→full, DirectML 부재→CPU). 문서의 절대적 표현.

즉시 조치 가치가 명확한 3건을 선정해 개선(나머지 임계값 FAR/FRR·임베딩 암호화·fusion 점수
보정은 프로덕션 과제로 `docs/architecture.md §9 한계`에 정직 기록).

## 2. 개선 항목 (지적 → 조치 → 검증)

### (1) 고객 앱(공개 포트) 라우터 조이기
- 지적: `customer_app`에 admin뿐 아니라 rag/nlp/lab/mcp/workflow 운영·내부 API가 모두 실림.
- 조치: `app/main.py` — 공개 포트에는 상품·주문·결제·에이전트·음성·얼굴만 탑재. 운영/내부
  라우터는 미탑재 → 물리적 404. 어떤 고객 페이지도 이들을 호출하지 않음을 정적 확인.
- 검증: 라이브 `customer /api/rag/search → False`, `/api/products → True`;
  `test_customer_and_admin_apps_are_physically_separated` 확장.

### (2) 벤치마크 무인증 + 업로드 크기무제한 (모델연산 DoS)
- 지적: `/api/face/benchmark`(3모델 실측)가 무인증·크기무제한.
- 조치: `require_admin` 전용화(facebench.js에 `authHeaders()`+401/403 처리) + config 업로드
  상한(`FACE_MAX_UPLOAD_BYTES` 8MB / `VOICE_MAX_UPLOAD_BYTES` 16MB), `read_capped` 청크 검사로
  초과 시 무폴백 `ValidationErr`. **[재점검 후속]** 등록 다중샷 합산 DoS 차단용
  `FACE_MAX_ENROLL_IMAGES`(10) 장수 상한 추가.
- 검증: `test_benchmark_requires_admin`, `test_face_register_rejects_too_many_images`.

### (3) pre2fa 챌린지 토큰 재사용(리플레이)
- 지적: pre2fa 챌린지가 5분 창 안에서 재사용 가능.
- 조치: pre2fa 토큰에 `jti` 부여, 2차인증 성공 시 소비. **[재점검 후속]** 소비를 **원자적
  test-and-set(bool 반환)**으로 바꿔 동시요청 TOCTOU 차단(단일 프로세스 asyncio 내), 패배
  경로는 401. jti 없는 pre2fa 토큰은 **fail-closed 거부**(폴백 제거).
- 검증: `test_pre2fa_challenge_is_single_use`, `test_consume_challenge_is_atomic_single_use`,
  `test_pre2fa_without_jti_is_rejected`, `test_challenge_consume_loser_path_returns_401`.

## 3. Codex 재점검 2라운드 (adversarial)

- 1차 재점검이 3건 중 (3)의 **TOCTOU 비원자성·jti-less 폴백**, (2)의 **합산 상한 누락**을
  추가 지적 → 위 [재점검 후속]으로 반영.
- 2차 재점검이 **`auth.py`의 `AuthErr` import 누락**(패배 경로가 500 NameError) 회귀를 포착
  → import 수정 + `test_challenge_consume_loser_path_returns_401`로 회귀 방지.
- 최종: 세 지적 모두 "해소됨" 확인. 인메모리→공유저장소(멀티프로세스) 전환은 데모 한계로 문서화.

## 4. 원칙 준수

- 무폴백: 변경 파일에 `except→조용히 넘김` 패턴 없음. 크기·개수·jti-less·소비패배 전부 타입
  오류로 명시적 실패.
- 무하드코딩: 모든 상한값은 `Settings` config 기본값(env 오버라이드 가능).
- 정직 문서화: 챌린지 소비 원자성 범위(단일 프로세스), multipart 파싱 후 상한 동작(진짜 HTTP
  요청 상한은 배포 레이어 몫), 임계값 미튜닝을 `docs/architecture.md §7~9`에 기록.
