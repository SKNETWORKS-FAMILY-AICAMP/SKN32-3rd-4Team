## 2. OCR / VLM — 최우선

### 근거 수치

한국어 문서에서 **전통 OCR CER 0.89 vs VLM CER 0.35** — VLM 이 확연히 낫다.
2026-03 이후 `OmniDocBench` · `socOCRbench` 가 PaddleOCR-VL-1.5/1.6 · dots.ocr · GLM-OCR ·
FireRed-OCR · OlmOCR-2 등을 재평가했고, **PaddleOCR-VL-1.6 이 OmniDocBench v1.6 종합 96.33%** 를 표방한다.

### 합의 구성 — ★단일 모델이 아니라 이중 판독

| 역할 | 모델 | 크기·라이선스 |
|---|---|---|
| 주 판독 | `PaddlePaddle/PaddleOCR-VL-1.5` (또는 1.6) | 약 0.9~1.0B · BF16 ~1.93GB · Apache-2.0 |
| 교차 판독 | `PaddlePaddle/korean_PP-OCRv5_mobile_rec` + `PP-DocLayoutV3` | ~14MB + ~132MB · Apache-2.0 · CPU 가능 |
| 대안(난해 레이아웃) | `dots.ocr` · `DeepSeek-OCR` · Qwen2.5-VL 계열 | 손글씨·지저분한 레이아웃에 강함 |

★**교차 판독은 폴백이 아니다.** 주 모델이 실패했을 때 대신 답하는 구조면 폴백이고 금지다.
**두 판독기가 KCD 코드·상병명에 동의할 때만 채택하고, 불일치는 `needs_expert` 로 끝낸다.**

### ★절대 하지 않을 것 (양측 일치)

> **약 이름·처방 패턴으로 KCD 를 역추론하지 않는다.**
> 처방전에 코드가 안 적혀 있으면 OCR 도 알 수 없다. 명시된 코드·상병명만 추출하고,
> 코드 미기재·글자 혼동·판독기 불일치는 **기권이 정상 결과**다.

### 미확인 (정직 기록)

**PaddleOCR-VL 계열의 한국 처방전·진료비 내역서 KCD 필드 정확도는 공개 벤치마크로 확인되지 않았다.**
자체 문서로 반드시 측정한다. 도장·표·저품질 스캔이 실제 조건이다.

## 3. ★Claude 단독 발견 — 구조화 출력은 이미 "모델 선택 문제"가 아니다

**코덱스가 다루지 않은 축이고, 이번 조사에서 가장 실용적인 발견이다.**

### 제약 디코딩(constrained decoding)이 표준 인프라가 됐다

JSON Schema 를 **유한상태기계로 컴파일**해 매 토큰마다 허용되지 않는 토큰의 logit 을 `-∞` 로 만든다.
즉 **스키마 위반이 확률적으로 불가능해진다.**

- **XGrammar** 가 현재 표준이며 **vLLM·SGLang 양쪽의 기본 백엔드**다
- JSON Schema 기준 **토큰당 40µs 미만** — 사실상 공짜
- 효과: *"통계적 약속을 하드 보장으로 바꾼다. validate-retry 루프가 사라진다"*

### 우리 계약에 미치는 영향

`docs/handoff/10_계약_모델_평가.md` §1 은 **스키마 준수율**을 모델 선정 5지표 중 하나로 뒀다.
**제약 디코딩을 쓰면 그 지표는 100%로 고정되고, 모델 변별력이 사라진다.**

→ **남는 진짜 지표는 넷이다**: 인용 정합률 · 근거 초과율 · 적절한 기권율 · 과잉 기권율.
   그리고 이 넷은 **모델이 아니라 검사기가 판정한다**(`citation_guard.verify`).

### ★그러나 공짜가 아니다 — 반드시 측정할 것

| 위험 | 내용 |
|---|---|
| **Constraint Tax** | 구조화 출력 제약이 **도구 호출을 억제**한다는 실증 보고(2026) |
| **형식 제약의 품질 비용** | 형식을 강제하면 추론 품질이 떨어질 수 있다(*"Let Me Speak Freely?"*) |

**우리에겐 형식보다 내용이 중요하다.** 제약 디코딩 적용 전후로
**적절한 기권율·근거 초과율이 어떻게 변하는지** 반드시 재고 채택한다.
형식은 보장되는데 판정이 나빠지면 손해다.

### 관련 발견 — 모델 크기보다 프롬프트 전략

`LLMStructBench`(2026, 22개 모델)의 결론: **프롬프트 전략이 모델 크기보다 중요하다.**
6문항 스모크에서 GPT-4.1 과 Qwen3 8B 가 같은 O/X 를 낸 것과 일관된다 —
**모델을 바꾸기 전에 프롬프트·제약을 바꾸는 것이 비용 대비 크다.**

## 4. 생성 LLM — 결론: 모델 교체보다 **결정 방식**을 바꾼다

### 8GB 급 구조화 출력 실측 (공개 벤치마크)

| 모델 | JSON 파싱률 | 스키마 준수율 |
|---|---|---|
| Gemma 3 4B (Q4_K_M) | **100%** | 87% |
| Llama 3.2 3B | 47.8~56.5% | — |
| SmolLM2 1.7B (Q4_K_M) | 26.1% | 4.3% |

→ **3B 급은 구조화 출력에 부족하다.** 4B 급 유지가 맞다.
→ 단 위 수치는 **제약 디코딩 없이** 잰 것이다. 적용하면 파싱률은 무의미해진다(§3).

### 후보

| 후보 | 비고 |
|---|---|
| `google/gemma-4-E4B-it-qat-q4_0-gguf` (Apache-2.0) | Q4 로드 ~4.5GB → **8GB 가능**. BF16 ~17.9GB 는 불가 |
| `Qwen/Qwen3.5-4B` (Apache-2.0) | ★현재 공식 ID 는 `qwen3.5-4b-instruct` 가 **아니다**. BF16 ~9.3GB 라 **8GB 불가** → 4bit + 8~16K 문맥 제한 필요 |
| 외부 상한선 `gpt-5.6-sol` | 2026-07-09 공개. 1.05M 문맥 · $5/$30 per M. **원문 의료문서 금지**. 마스킹 경로에서 비교군으로만 |

★`model_registry.yaml` 상 두 로컬 모델은 **최대 1,024 토큰만 시험**됐고 체크섬·메모리 실측이 미확정이다.
**8K 정도에서 VRAM·기권율부터 재는 것이 모델 교체보다 먼저다.**

★외부 API 데이터 통제 주의: 기본 API 는 **최대 30일 abuse log** 가 가능하며
`store:false` 만으로 ZDR(Zero Data Retention)이 아니다.

## 5. 임베딩 — ★유지. 단 저장소 정합부터 고쳐야 한다

### 양측 합의: 바꾸지 않는다

- 80문항은 작지만 **우리 자료에 대한 실측**이다. 일반 MTEB 우위 ≠ 한국어 보험 약관 우위
- 교체하면 **21만 조항 전량 재색인 + 거리 임계값 재보정**
- MTEB v2(2026)는 v1 과 **직접 비교 불가**하고 보드(영어 v2 / 다국어 MMTEB)마다 순위가 다르다

### ★그보다 먼저 — 저장소가 선정 결과와 어긋나 있다 (코덱스 발견, 실측 확인)

```
app/core/config.py:62          ST_EMBEDDING_MODEL = "jhgan/ko-sroberta-multitask"   ← 4위 모델
app/adapters/pgvector_clause_index.py:44   _EMBED_DIM = 768                        ← e5-large 는 1024
```

**설정 문자열만 바꾸면 안 된다.** 차원이 안 맞아 색인이 깨진다.
`e5-large` 채택을 저장소에 반영하려면 **차원(1024) 변경 + 재색인**이 함께 가야 한다.

### 도전자 (지금 바꾸지 않되 기록)

| 후보 | 특징 |
|---|---|
| `Qwen/Qwen3-Embedding-0.6B` (Apache-2.0) | 100+ 언어 · **32K 문맥** · 1024차원 · instruction-aware. 장문 조항에 유리 |
| `BAAI/bge-m3` (MIT) | **8,192 토큰** · dense+sparse+multi-vector 하이브리드 |
| `kakaocorp/kanana-nano-2.1b-embedding` | 경량·저지연 지향 한국어 모델 |

★**e5-large 는 최대 512 토큰**이다. 조항이 수천 자인 우리 데이터에선
**조항 구조를 보존한 청킹이 전제**이며, 이게 장문 모델(bge-m3·Qwen3) 을 검토할 유일한 실익이다.

## 9. ★모델보다 중요한 것 — 최종 게이트 (양측 합의)

어떤 모델을 골라도 아래가 없으면 사람이 손해를 본다.

1. OCR 두 판독기가 KCD 코드에 **불일치하면 `needs_expert`**
2. 코드 **형식뿐 아니라 로컬 KCD 기준표에 실재하는지** 확인
3. `cited_clauses[]` 는 **검색 후보 ID 집합의 부분집합**이어야 한다
4. `quotes{}` 는 조항 원문에 **정확히 존재**해야 한다 (정규화는 공백·개행까지만)
5. JSON 파싱 실패 · 알 수 없는 조항 ID · 인용 불일치 · 근거 부족 → **전부 `needs_expert`**
6. 보장 판정은 **명시적 보장 조항 + 적용 조건이 모두 있고 면책이 배제된** 경우에만
7. NLI 는 보조 거부 신호로만
8. **"오류 나면 다른 모델로 재시도"하는 자동 폴백을 두지 않는다**

## 10. 추천하지 않는 것 (4주 MVP 기준)

- 4B/8B 임베딩·리랭커로 **전면 재색인**
- OCR·LLM·NLI **동시 파인튜닝**
- 일반 VLM 하나에 **OCR 과 보장 판단을 모두** 맡기기
- **약 이름·처방 패턴으로 KCD 역추론**
- 의료문서 이미지·OCR 원문을 **외부 API 전송**
- 약관 전량을 **외부 벡터스토어에 업로드**
- **NLI 점수 하나로 보장 판정**
- **6문항 스모크로 승자 선언**
- `buffalo_l` 가중치를 MIT 로 오인해 상용 배포

| **2** | **제약 디코딩(XGrammar) 도입 + 전후 기권율 비교** | 스키마 준수가 공짜가 된다. 단 **품질 비용을 재고** 채택 | 추론 엔진 설정 |
| **3** | **저장소 임베딩 정합** (`config.py` 모델명 + `_EMBED_DIM` 768→1024) | 지금 저장소는 4위 모델·틀린 차원을 들고 있다 | 재색인 |
| **4** | **리랭커 2종 비교** (`bge-reranker-v2-m3-ko` vs `Qwen3-Reranker-0.6B`) | 인덱스 재구축이 없어 가장 싸다 | 어댑터 추가 |
| **5** | 로컬 LLM **8K 문맥 VRAM·기권율 실측** | 레지스트리상 1,024 토큰만 시험됨 | 측정만 |
| — | 임베딩 모델 교체 | **하지 않는다** | — |

## 12. 모르는 것 · 확신 낮은 것 (양측 공통)

- **PaddleOCR-VL 의 한국 의료문서 KCD 필드 정확도** — 공개 벤치마크 없음. 자체 측정 필수
- 리랭커·임베딩의 **공개 다국어 점수가 한국어 보험 약관 성능을 보장하지 않는다**
- mDeBERTa NLI 는 **한국어 미세조정 언어에 포함되지 않는다**
- **3060 Ti 실측 VRAM·지연은 재보지 않았다.** 위 수치는 가중치 크기·공식 메모리 표 기준 판단
- 80문항 검색 / 6문항 생성은 **모델 선정 근거로 부족하다.**
  오탐 0건이어도 100건 시험으로 주장 가능한 오탐률 상한은 대략 **3%** 다
- 라이선스 표기는 **법률 의견이 아니다**
- **2026-08-02 이후 공개·변경된 모델은 모른다**

## 13. ★12GB 재검토 (2026-08-02 15:40 · 코덱스 재확인)

### 13-1. 가장 큰 변화 — **전부 상주가 가능해진다**

8GB 에서는 순차 로드/언로드가 강제됐다. 12GB 에서는 **파이프라인 전체를 한 번에 올릴 수 있다.**

**권고 조합 (전부 GPU 상주)**

```
PaddleOCR-VL-1.6  +  korean_PP-OCRv5_mobile_rec  +  e5-large BF16
                  +  Qwen3-Reranker-0.6B BF16   +  Gemma-4-E4B 공식 Q4(text only)
```

| 모델 | 가중치 | 실행 중 합계 |
|---|---:|---:|
| PaddleOCR-VL-1.6 BF16 | 1.79 GiB | 2.3~2.8 |
| korean PP-OCRv5 mobile rec | 0.014 | 0.05~0.1 |
| multilingual-e5-large BF16 | ~1.05 | 1.25~1.45 |
| Qwen3-Reranker-0.6B BF16 | 1.11 | 1.3~1.55 |
| Gemma-4-E4B Q4 (text only) | 4.80 | 5.4~5.8 |
| **상주 가중치 합** | **~8.8 GiB** | **피크 10.5~11.6 GiB** |

**조건**: 생성 4K · 리랭크 1K · 배치 1~4 · 동시 요청 1 · **Gemma 멀티모달 projector 미로드**.

★**코덱스 자기 정정**: 초판의 *"Gemma Q4 ~4.5GB"* 는 부족한 수치였다.
공식 Q4 GGUF 의 **텍스트 가중치만 5.15GB**, 멀티모달 projector 가 **추가 992MB** 다.
생성에는 projector 를 로드하지 않아야 한다.

### 13-2. 슬롯별 — 무엇이 바뀌나

| 슬롯 | 8GB 결론 | 12GB 결론 |
|---|---|---|
| OCR | PaddleOCR-VL-1.5 | **그대로.** 여유가 생겨 dots.ocr·DeepSeek-OCR 실험 여지 |
| 임베딩 | e5-large 유지 | **그대로 유지.** 재색인 비용은 VRAM 과 무관하다 |
| 리랭커 | 0.6B 급 | **그대로.** 4B 급은 근거 없이 올리지 않는다 |
| 생성 | Gemma Q4 만 | **`Qwen3.5-4B BF16` 이 순차 로드로 새로 가능**해졌다 |

★**`Qwen3.5-4B BF16`(9.34GB)은 12GB 에서도 전부 상주 불가**다 — 다른 슬롯까지 합치면 가중치만 **12.7 GiB**.
`OCR·검색·리랭크 → GPU 해제 → 생성` 순차 실행이면 가능하다. **새로 열린 선택지는 이것 하나다.**

`Gemma-4-E4B BF16`(체크포인트 16GB)은 12GB 에서 **순차 로드로도 불가능**하다.

### 13-3. ★RunPod — 연산 확장 자원이 아니다

**이게 이번 정정에서 가장 중요하다. Claude·코덱스 독립 동일 결론.**

| 올려도 되는 것 | 절대 안 되는 것 |
|---|---|
| 공개 모델 가중치·토크나이저 | 실제 진료비 내역서·처방전 이미지/PDF |
| 애플리케이션 코드·컨테이너·양자화 스크립트 | **OCR 결과 · 잘라낸 이미지 · 문서 청크 · 프롬프트 · 검색 결과 · 생성 로그** |
| **완전 합성** 진료비 내역서·처방전·약관 | 의료문서로 만든 **임베딩·벡터DB·캐시·LoRA 체크포인트** |
| 공개 벤치마크 | **약관 원문·스캔·OCR 텍스트·청크·임베딩** |
| 합성 데이터 기반 속도·VRAM 시험 | **일부 필드만 마스킹한 실제 문서** — 잔존 문맥·희귀 조합으로 재식별 가능 |

★**암호화 전송·암호화 저장을 해도 GPU 메모리에서는 평문으로 처리된다.**
"원문을 외부로 보내지 않는다"는 제약을 충족하지 못한다.

→ **RunPod 16/32GB 는 실제 서비스 파이프라인의 확장 자원이 아니다.**
   공개·합성 자료 기반 **개발·비교·부하시험 전용**이다.
   모델 가중치는 RunPod 이 인터넷에서 직접 받게 하고, **로컬 데이터 디렉터리를 마운트·동기화하지 않는다.**

### 13-4. 16GB / 32GB 의 MVP 실익 — 작다

| | 열리는 것 | 실익 |
|---|---|---|
| **16GB** | `Qwen3.5-4B BF16` 전부 상주가 **간신히** 가능(피크 14.5~15.8 GiB) | **작다.** BF16 로드 지연이 줄 뿐 — **OCR 정확도·근거성·기권 정책은 개선되지 않는다** |
| **32GB** | Gemma BF16 전체 · 4B 리랭커 동시 상주 · 12B Q4 · 일부 20B대 Q4 | **제한적.** 4B 리랭커가 일반 벤치에서 0.6B 보다 높지만 **한국 약관 검색 개선 폭은 미입증**. 반면 재색인·임계값 재보정·지연·테스트 범위는 **확실히 증가** |

**결론: 하드웨어를 늘려도 이 제품의 실패 모드(잘못된 보장 판정)는 줄지 않는다.**

### 13-5. 12GB 기준 권고 순서

1. **통합 데모·상시 상주 우선** — §13-1 조합 그대로. 12GB 의 값어치가 여기서 나온다
2. **생성 BF16 우선(로딩 지연 허용)** — 검색·리랭크 후 내리고 `Qwen3.5-4B BF16` 순차 로드
3. **`Qwen3.5-4B` Q4 전부 상주** — ★**로컬 골든셋에서 BF16 과 숫자·인용 정확도가 동등함을 확인한 경우에만**

★순서의 기준은 *"Qwen3.5 가 Gemma 보다 정확하다"* 가 아니다. 공개 근거로 도메인 우열을 확정하지 않았다.
**전부 상주 가능성**과 **BF16 실행 가능성**으로 나눈 것이다.

### 13-6. ★하드웨어가 늘어도 하지 말 것

- **4B/8B 리랭커·12B 이상 LLM 을 근거 없이 올리기** — 크기는 인용 정확성·기권 성능을 보장하지 않는다
- **32K·128K·262K 최대 컨텍스트를 그대로 열기** — KV 뿐 아니라 prefill 활성·지연이 급증한다. **MVP 는 생성 4K 부터**
- **OCR 불일치를 생성 LLM 이 "상식적으로 교정"하게 하기** — 불일치는 기권 대상이다
- **양자화 후 BF16 기준 임계값을 그대로 쓰기** — OCR·리랭킹·생성 모두 재보정 필요
- **단일 요청 VRAM 표를 동시 사용자에 그대로 적용하기** — KV·활성은 요청 수에 비례한다
- **12GB 전부를 모델에 할당하기** — 디스플레이 점유·CUDA context·파편화로 **0.8~1.5 GiB 여유 필수**
- ★**GPU 가 커졌다는 이유로 RunPod 에 실제 의료문서·약관을 보내기** —
  **하드웨어 증가는 데이터 반출 권한을 만들지 않는다**
