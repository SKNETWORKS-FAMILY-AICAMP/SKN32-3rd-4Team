# PostgreSQL 보험 도메인 S0·S1 착수 리포트

작성: 2026-08-04 21:14

범위: 계획서 작성, Claude 교차검토, fresh DB migration·핵심 무결성 검증

## 1. 목표

기존 ERD·핸드오프·PostgreSQL 자산을 재사용해 `core/app/ops`의 정본 계획을 고정하고, 실제 DB와 애플리케이션을 연결하기 전에 P0 스키마 결함을 빈 PostgreSQL에서 재현·보정한다.

## 2. 수행 내용

### 계획·교차검토

- 사용자에게 설명한 원안 3~5일, SSH 3대 병렬화 시 1.5~2.5일 내용을 계획서 기준선으로 기록했다.
- 저장소 재사용 자산을 반영한 뒤 Claude CLI로 `001~004`, 적용기, DB 핸드오프를 독립 대조했다.
- Claude가 지적한 판본 교차 인용, 코호트 판본 정본, verification 상태전이, 004 객체 owner/grant 문제를 모두 채택했다.
- 후속 논의에서 `claim`이 특정 `assessment`를 참조하지 않으면 코호트 뷰가 여러 판정으로 팬아웃함을 확인했다.
- 보정·검증 직렬 병목 0.5일을 반영해 실행 기준 일정을 2~3일로 조정했다.

### 스키마 보정

- `scripts/db/005_integrity_and_privileges.sql`을 추가했다.
- `app."case"`를 최신 핸드오프·제공 ERD의 정본인 `app.coverage_review`로 개명했다.
- assessment/citation의 판본 복합 FK와 policy clause content hash FK를 추가했다.
- `claim.assessment_id` 및 같은 coverage review 강제 복합 FK를 추가했다.
- `cohort_stats`를 `assessment.policy_version_id`와 해당 policy version의 product/generation으로 집계하도록 교체했다.
- consistent는 evidence 컬럼, verified/rejected는 append-only verification 행으로 강제했다.
- runtime 역할의 verification 직접 DML을 회수하고 전용 SECURITY DEFINER 함수만 허용했다.
- 004 이후 객체의 owner와 runtime grant를 재적용했다.

### 재현 검증기

- `scripts/db/verify_insurance_schema.py`를 추가했다.
- 기존 DB를 건드리지 않고 `insurance_schema_verify_<uuid>` 임시 DB를 생성한다.
- 001~005 적용, fixture 삽입, FK·상태전이·코호트·멱등성·owner·privilege를 검증하고 임시 DB를 즉시 삭제한다.

```text

owner 불일치 객체: 0
```

## 5. 미완료·다음 단계

- migration checksum 변조·동시 실행·부분 적용 실패 경로는 아직 미검증이다.
- PostgreSQL 16에서는 001의 `gen_random_uuid()`가 동작했지만, 구버전 호환을 위한 extension 선행 정책은 미확정이다.
- 비-superuser migration 로그인 역할의 `insurance_owner` membership/preflight를 적용기에서 아직 강제하지 않는다.
- full CI 기준선은 아직 실행하지 않았다.
- 다음 최소 단계는 위 세 migration 실패 경로를 닫은 뒤 보험 전용 ORM/Repository 경계를 구현하는 것이다.

## 6. 안전 기록

- `mall_vec`와 `insurance_demo`에는 SELECT만 수행했다.

- 임시 DB 3개는 각 검증 종료 후 이름 prefix를 확인하고 모두 삭제했다.
