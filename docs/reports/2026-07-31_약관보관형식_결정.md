# 약관 보관 형식 결정 — PDF 원문을 계속 들고 있어야 하는가

- 작성: 2026-07-31 · 상태: **검토 2/3 반영 (3/3 대기)**
- 질문: "어차피 RAG에 쓸 건 텍스트인데 PDF를 보관할 필요가 있나?"
- 방법: 주장 → 실측 검증 → 코덱스 교차검토 3회 → 확정

---

## 0. 결론 (검토 1 반영으로 **수정됨**)

**PDF는 불변 원본 아카이브로 보존한다. 구조화 JSON은 조회·RAG용 파생 저장소다.**

> ★초안의 결론 (C) "PDF를 캐시로 취급, 디스크 부족 시 오래된 것부터 비운다"는 **철회한다.**
> 코덱스 지적이 맞다 — **"재취득이 불확실하다"고 주장하면서 삭제 가능하다고 한 것은 자기모순**이다.
> 저장비 절감은 되돌릴 수 있지만 **원본 삭제는 되돌릴 수 없다.**

| 계층 | 역할 | 보존 정책 |
|---|---|---|
| **PDF 원문** | 증거 · 재추출 입력 | **불변 보관.** 로컬에서 내리더라도 별도 사본 필수. 자동 삭제 없음 |
| **구조화 JSON** | 검색·청킹의 기준 파생물 | 추출기/스키마 버전별 보존. 새 버전이 이전 것을 덮지 않는다 |
| RAG 청크·인덱스 | 서빙 산출물 | 재생성 가능한 캐시 |
| 표 CSV·검수 화면 | 사람 검수용 파생물 | 재생성 가능. 단 **검수 결과는 별도 영속 저장** |

| 초안 후보 | 판정 |
|---|---|
| (A) PDF 전량 보관 + 텍스트 별도 | 초안은 "1차 조회가 PDF가 되어 매번 재파싱한다"고 썼는데 **이 근거는 성립하지 않는다.** 보존 정책과 조회 경로는 독립된 결정이다(코덱스) |
| (B) 텍스트만 보관, PDF 삭제 | ✗ 반대 (§2) |
| (C) JSON 1차 + PDF **캐시** | ✗ **철회** — 캐시로 분류한 것이 자기모순 |
| **(D) PDF 불변 아카이브 + JSON 파생** | ✅ **채택** |

## 1. 실측 — 용량은 얼마나 주는가

무작위 20건(seed=42), 페이지별 JSON(텍스트+표 셀 배열)으로 변환.

| 지표 | 값 |
|---|---|
| 합계 기준 | PDF 47.7MB → JSON 5.6MB (**11.7%**) |
| 파일별 비율 **중앙값** | **14.9%** |
| 최소 / 최대 | 4.0% / 29.2% |
| 현재 보유분 추정 | 1.58GB (556건) → **약 185MB** |

### ★검토 1 지적: 이 수치는 아직 재현 불가능하다

코덱스가 지적한 결함:
- **표본 SHA 목록·추출 코드·모집단 스냅숏 시각이 문서에 없다.** 그래서 남이 재현할 수 없다.
- 보험사·연도·스캔여부·페이지수로 **층화하지 않았다.**
- **JSON만** 쟀고 CSV·인덱스·검수 메타데이터를 포함한 **총 저장량**은 재지 않았다.
  (실제 예: JSON 626,032B + 표 CSV 57,487B → 채택안 전체 비율은 더 높다)
- "큰 PDF는 스캔 이미지 비중이 높아서"는 **근거 약함** — 이미지 면적을 측정하지 않았다.
  큰 파일의 비율이 낮다는 **상관만** 보였다.
- 압축(gzip/zstd) 후 크기를 재지 않았다.

→ 이 수치는 **탐색적 추정**이며, 보존 정책을 결정하는 근거로는 부족하다.
   (다만 결론 (D)는 용량이 아니라 **비가역성**에 근거하므로 이 결함이 결론을 바꾸지는 않는다.)

### ★정직 기록 — 앞선 "3%"는 틀렸다

처음에 "PDF 대비 3%"라고 보고했는데, **가장 큰 파일 5건만 뽑은 편향된 표본**이었다.
무작위로 다시 재니 **합계 11.7% / 중앙값 14.9%** 이고 파일별로 4~29%까지 갈린다.

합계와 중앙값이 다른 이유는 **큰 파일이 합계를 지배**하기 때문이다.
(초안은 여기에 "큰 PDF는 스캔 이미지 비중이 높아서"라는 설명을 붙였는데, **이미지 면적을
측정한 적이 없으므로 삭제한다.** 관찰된 것은 "큰 파일일수록 비율이 낮다"는 상관뿐이다.)
**둘 다 적어야 정직하다** — 하나만 쓰면 유리한 쪽을 고른 것이 된다.

## 2. 실측 — 텍스트만 남기면 무엇을 잃는가

### 2-1. 표: 행·열 연결이 끊긴다 (직접 비교)

같은 PDF 8쪽의 **자기부담금 표**를 두 방식으로 뽑았다.

**A. `find_tables()` — 셀 구조 유지**
```
| 담보명                        | 자기부담금 차감금액
| - 급여(상해) - 급여(질병)      | 입원치료 : 보장대상의료비의 20% …
| - 비급여(상해) - 비급여(질병)  | 입원치료 : 보장대상의료비의 30% …
| - 비급여(3대)                 | 공제금액(3만원)과 보장대상의료비의 30%중 큰 금액
```

**B. `get_text()` — 같은 영역**
```
담보명
자기부담금 차감금액
- 급여(상해)
- 급여(질병)
입원치료 : 보장대상의료비의 20%
통원치료 : 병원급별 공제금액(1~2만원)과 보장대상 의료비의
20%중 큰 금액
- 비급여(상해)
…
```

**무엇이 사라졌나**: B에도 값은 다 있고 순서도 남는다. 사라진 것은 **셀 경계**다.
`20%`가 급여에 속하고 `30%`가 비급여에 속한다는 **연결이 구조로 보장되지 않는다.**

> ★과장하지 않기 위해 덧붙인다. 이 표는 **2열**이라 사람이 순서로 읽어낼 수 있다.
> 열이 늘수록 손실이 커진다는 것이 정확한 표현이다.

#### ★검토 1 지적 — 내 논증에 구멍이 있었다

| 초안 주장 | 판정 |
|---|---|
| 평문은 셀 경계를 잃는다 | **입증됨** |
| `find_tables()`가 **셀 구조를 유지한다** | ★**과장.** 셀 배열을 출력한 것과 원 구조를 정확히 복원한 것은 다르다 |
| 6열 표는 텍스트만으로 **복원 불가** | ★**미검증·과도한 단정.** 좌표 포함 word/block 추출, 레이아웃 텍스트, 규칙 복원 등 반론이 가능하다 |
| 구조화 표를 쓰면 판정 오류를 막는다 | ★**미검증.** 실제 오류율이 줄었는지 시험하지 않았다 |

**가장 아픈 반증은 우리 산출물 자체다.** 코덱스가 실제 JSON을 열어보니
"보험금 청구서류" 표가 7열×28행으로 검출됐지만 — 병합 헤더가 여러 행으로 분해되고,
`사망`·`장해`가 불필요하게 갈라지고, 공통 서류인 `청구서`·`신분증`이 다른 행으로 밀리고,
빈 행이 다수 삽입됐다. 앞의 §2-1 예시에서도 확인된다.

→ **"평문보다 낫다"는 말할 수 있어도 "셀 구조를 유지한다"고는 말할 수 없다.**
   표현을 수정한다. 그리고 표 정확도는 **표 30~50개를 사람이 정답 전사해 측정**해야 한다.

자기부담금이 급여 20% / 비급여 30% / 3대비급여 공제 3만원으로 갈리는데, 이 연결이 틀리면
**판정 금액이 틀린다.** 우리가 막으려는 실패가 정확히 이것이다.

### 2-2. 규모: 표는 예외가 아니라 본문이다

무작위 20건에서 표가 **0~151개**, 130쪽 약관 한 건에 **73~95개**가 나왔다.
표는 부록이 아니라 약관의 뼈대다.

### 2-3. 재현성: 추출 로직은 반드시 바뀐다

지금 추출기는 `pymupdf/1.28.0`이다. 표 인식은 완벽하지 않고(이번 실행에서도
`Advanced encoding /UniKS-UTF16-H not implemented` 경고와 `low_text` 6건이 나왔다)
로직을 고쳐 **다시 뽑아야 할 때가 온다.**

그때 원본이 없으면 다시 받아야 하는데, **판매중지 상품 URL은 언제 내려갈지 모른다.**
우리가 가진 것의 상당수가 판매중지분이다(삼성화재 실손 508행 중 483행, DB손보 462건 중 406건).

### 2-4. 원본성: 해시의 의미가 달라진다

`sha256(PDF 바이트)`는 **보험사가 배포한 그 파일**을 가리킨다.
텍스트 해시로 대체하면 **추출기 버전이 바뀔 때 해시가 바뀐다** — 같은 약관인데 다른 해시가 된다.
판정 근거의 출처를 증명해야 하는 구조에서 이건 치명적이다.

## 3. 채택안의 구체 형태

```
data/raw/insurance_terms/<보험사>/<sha12>_<원본명>.pdf        ← ★불변 원본(git 미커밋, 별도 사본 필요)
data/extracted/<보험사>/<버전태그>/<sha12>.json               ← 파생물(버전별, 덮어쓰지 않음)

  버전태그 = s{스키마버전}_{추출기}   예: s1_pymupdf-1.28.0
```

JSON 스키마:
```json
{
  "schema_version": "1",
  "extractor": "pymupdf/1.28.0",
  "extracted_at": "…",
  "source": {"insurer","product_name","product_code","sale_start","sale_end","url","sha256","bytes"},
  "identification": "unidentified",
  "stats": {"pages": 134, "text_length": 233208, "tables": 73},
  "pages": [{"page": 5, "text": "…", "tables": [[["셀"]]]}]
}
```

- `extractor`를 기록한다 — 로직이 바뀌면 결과가 달라지므로 **어느 버전이 뽑았는지**가 근거의 일부다.
- ★검토 1: 현재 스키마는 **페이지 번호 + 평문 + 셀 배열뿐**이라 안정적 청킹·정밀 인용·검수에
  부족하다. 최소한 **셀/블록 좌표(bbox), 표 신뢰도, 병합 셀 표시, 조항 경계 후보**가 필요하다.
  (다음 회차에서 스키마 v2 를 정한다)
- `identification`은 `unidentified`로 시작한다. 추출은 식별이 아니다.
- 표 인식 실패는 `table_extraction_failed: true`로 남긴다. **빈 배열과 구분**해야 한다.

### ★CSV를 아예 만들지 않는다 (검토 2 이후 변경)

초안은 "표별 CSV를 사람 검수용으로 함께 만든다"였다. **철회한다.**

- 표는 이미 JSON 안에 셀 배열로 있다. CSV는 **같은 데이터의 두 번째 사본**이고,
  둘이 어긋나면 무엇이 맞는지 판단할 근거가 없다.
- 831건 × 표 수십 개 = **수만 개 파일**이 된다.
- 애초에 CSV를 넣은 이유가 "사람이 엑셀로 열어보게"였는데, 그건 **검수 화면이 없으니
  파일로 때운 것**이다. 검수는 ⑤ 담당이 만들 화면에서 표를 렌더링해 한다.
- 파생물은 재생성 가능해야 한다는 원칙과도 어긋난다 — 영구 저장하면 원본처럼 굳는다.

→ 엑셀이 필요하면 그때 JSON에서 뽑는다.

## 4. 한계 (정직 기록)

- 표본 20건은 **삼성화재·DB손보·NH농협생명**에 치우쳐 있다. 13개사로 늘면 비율이 달라질 수 있다.
- 표 인식 정확도를 **측정하지 않았다.** "표가 뽑힌다"는 확인했지만 "정확히 뽑힌다"는 검증하지 않았다.
  실제 판정에 쓰기 전에 **표 정확도 표본 검수**가 필요하다.
- 재취득 가능성은 **가정**이다. 판매중지 상품 URL의 수명을 측정한 바 없다.
  → ★그래서 결론을 (C)에서 (D)로 바꿨다. **가정 위에 비가역적 삭제 정책을 세울 수 없다.**
- (검토 1 추가) OCR·레이아웃 손실, 버전 간 중복, 페이지 번호 신뢰성, 출처 인증,
  쓰기 원자성, 운영 비용(재추출 CPU·인덱스 재구축)이 한계 목록에서 빠져 있었다.
- 표 **정확도**를 측정하지 않았다(검출 여부만 확인). 판정에 쓰기 전 필수.
