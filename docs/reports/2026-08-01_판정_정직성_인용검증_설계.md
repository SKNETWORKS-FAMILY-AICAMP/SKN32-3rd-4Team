# 판정 정직성 — 프롬프트를 방어선으로 삼지 않는다

작성 2026-08-01 · 대상 `app/application/answer_question.py` · 모델팀 공유용

---

## 0. 왜 이 문서가 필요한가

이 서비스는 **"보장됩니다"라고 잘못 말하면 사람이 손해를 본다.**
사용자는 그 말을 믿고 청구하거나, 반대로 청구를 포기한다.

그래서 "환각을 줄인다"가 아니라 **"근거 없는 답을 내보내지 못하게 막는다"** 가 목표다.

---

## 1. 팀 안에서 제기된 문제 인식 — 맞다

> 그래프 레벨에서는 근거가 아예 없으면 `knowledge_gap` 으로 보내 LLM 에게 질문이
> 안 가게 막아 놨다. 그런데 근거가 **조금이라도** 있어서 판정 단계까지 온 경우엔,
> LLM 이 그 조금 있는 근거를 넘어서 나머지를 자기 지식으로 추측해 채울 위험이 있다.
>
> 예: 조항에 "우울증"이라는 단어가 없는데 LLM 이 "이건 정신과 질환이니까 아마
> 비슷하게 보장될 겁니다" 처럼 지어내는 것.

**이 진단은 정확하다.** 실제로 지금 코드가 딱 그 구조다.

```python
# app/application/answer_question.py
evidence = self._retriever.search(q, k=self._top_k)
if not evidence:
    return AnswerResult(answer=NO_ANSWER, sources=[])   # 근거 0건 → 차단
reply = self._model.complete(_build_prompt(q, evidence), max_tokens=256)
```

근거가 **1건이라도** 있으면 LLM 이 호출되고, 그 다음은 프롬프트에 맡겨진다.

---

## 2. 다만 "프롬프트가 유일한 방어선"이라는 결론에는 동의하지 않는다

**프롬프트는 지켜지길 바라는 것이지 강제되는 것이 아니다.**
그리고 이건 코드로 강제 가능한 형태로 바꿀 수 있다.

### 핵심 아이디어

```
LLM 출력에서 인용한 조항 번호를 뽑는다
  → 넘겨준 근거에 그 조항이 실제로 있는지 대조한다
  → 없으면 그 답을 버린다
```

**프롬프트를 무시하는 모델이라도 이 검사는 통과하지 못한다.**
"제9조에 따르면…" 이라고 지어내면, 제9조가 근거에 없으므로 답이 폐기된다.

### 지금 왜 못 막나

`_citations()` 는 **검색된 근거 목록을 그대로 붙일 뿐**,
LLM 이 실제로 무엇을 인용했는지 대조하지 않는다.

```python
def _citations(evidence: list[Evidence]) -> list[Citation]:
    """(source, locator) 중복 제거 출처 목록(검색 순서 유지)."""
```

그래서 LLM 이 지어낸 답에도 **검색 결과가 출처로 그대로 달려 나간다.**
근거가 붙어 있으니 **오히려 더 그럴듯해 보인다.** 이게 더 위험하다.

---

## 3. 방어를 층으로 겹친다

| 층 | 방법 | 강제력 | 현재 |
|---|---|---|---|
| 입력 | 근거 0건이면 LLM 호출 안 함 | **강제** | ✅ 있음 |
| 입력 | 프롬프트 인젝션 무력화 (`_neutralize_labels`) | **강제** | ✅ 있음 |
| 지시 | "문서에 답이 없으면 확인 불가라고만 답하라" | 약함 | ✅ 있음 |
| 출력 | 빈 응답을 정상 답변으로 반환 금지 | **강제** | ✅ 있음 |
| **출력** | **인용 조항이 근거에 실재하는지 대조** | **강제** | ❌ **없음** |
| **출력** | **구조화 출력** (`verdict` + `cited_clauses[]`) | **강제** | ❌ 없음 |
| 감사 | 답변별 근거·인용 로그 | — | ❌ 없음 |

아래 둘이 이 문서가 제안하는 것이다.

### 3-1. 구조화 출력

자유 텍스트를 받으면 검증할 수가 없다. 형태를 강제한다.

```json
{
  "verdict": "covered | not_covered | unknown",
  "cited_clauses": ["보통약관/제9조", "특별약관/제3조"],
  "reason": "…",
  "applied_terms": { "insurer": "…", "sale_start": "20190501", "generation": 3 }
}
```

- `verdict="unknown"` 이 **정상적인 답**이다. 부끄러운 답이 아니다.
- `cited_clauses` 가 **비어 있으면** `covered`/`not_covered` 를 낼 수 없다.

### 3-2. 인용 검증

```
1) cited_clauses 의 각 항목이 넘겨준 근거의 qualified_no 집합에 있는가
2) 없으면 → 답 폐기, verdict="unknown" 으로 대체, 감사 로그 기록
3) 본문에 `제N조` 가 나오는데 cited_clauses 에 없으면 → 경고 기록
```

`qualified_no` 는 이미 조항 JSON 에 있다(`"부/제9조"` 꼴).
**추가 데이터 없이 지금 구현할 수 있다.**

### 3-3. 판정에 쓸 수 없는 데이터는 애초에 넣지 않는다

인용 검증만으로는 부족하다. **근거 자체가 못 믿을 것일 수 있다.**

| 표시 | 뜻 | 처리 |
|---|---|---|
| `parse_status != "ok"` | 조항 구조화 실패(목차 오인 등) | 판정 근거에서 제외 |
| `date_confidence == "unknown"` | 판매시점 모름 | **"어느 시점 약관인지 확인 불가"** 로 답한다 |
| `chunk_type == "page_fallback"` | 조항이 아니라 페이지 덩어리 | 검색엔 쓰되 판정 근거로는 안 씀 |

## 4. 모델팀에 전할 것 — 관점을 바꿔야 한다

원래 제기된 결론은 이랬다.

> 모델을 바꾸거나 파인튜닝할 때, 이 "확인 불가라고 답해라" 지시를
> 잘 따르는 모델인지 확인해야 한다.

**맞는 말이지만 우선순위가 다르다.**

| 무엇을 볼 것인가 | 왜 |
|---|---|
| ~~지시를 잘 따르는가~~ | 측정이 애매하다. 프롬프트·질문마다 달라진다 |
| **구조화 출력을 안정적으로 내는가** | **코드로 검증 가능하다.** JSON 스키마를 못 지키면 그 자리에서 걸린다 |
| **근거에 없는 것을 인용하는 비율** | 숫자로 잰다. 모델 비교의 기준이 된다 |
| **`unknown` 을 낼 줄 아는가** | 모르면 모른다고 하는 능력. 정확도보다 중요할 수 있다 |

즉 **"착한 모델"을 고르는 게 아니라 "검사에 걸리는 모델"을 만드는 것**이 목표다.
검사를 세워 두면, 모델이 규칙을 어겨도 사용자에게 도달하지 않는다.

### 모델 평가 지표 제안

```
인용 정합률   = 인용한 조항 중 근거에 실재하는 비율          (높을수록 좋음)
근거 초과율   = 근거에 없는 내용을 답에 포함한 비율           (낮을수록 좋음)
적절한 기권율 = 근거가 부족할 때 unknown 을 낸 비율          (높을수록 좋음)
과잉 기권율   = 근거가 충분한데 unknown 을 낸 비율            (낮을수록 좋음)
스키마 준수율 = 구조화 출력을 형식대로 낸 비율                (높을수록 좋음)
```

## 5. 지금 구현 상태 요약

`nodes/judge_coverage.py` 는 **이 저장소에 없다.**
같은 역할을 하는 것은 `app/application/answer_question.py` 이고,
거기에는 근거 0건 차단·프롬프트 규칙·인젝션 방어·빈 응답 금지가 **이미 있다.**

**빠진 것은 인용 검증과 구조화 출력이다.** 그 둘이 없으면
"프롬프트가 유일한 방어선"이라는 진단이 실제로 맞는 상태가 된다.

---

## 6. 할 일

1. `AnswerResult` 에 `verdict` · `cited_clauses` · `applied_terms` 추가
2. LLM 출력을 구조화 JSON 으로 받고 스키마 검증
3. `cited_clauses` ↔ 근거 `qualified_no` 대조. 불일치 시 폐기 + 감사 로그
4. `parse_status` / `date_confidence` 로 판정 가능 여부 사전 판별
5. 위 5개 지표로 모델 비교 하네스 작성 (모델팀 인계용)
