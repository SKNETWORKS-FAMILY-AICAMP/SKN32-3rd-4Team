# 그래프DB로 갈 것인가 · 일자별 규칙을 어떻게 지킬 것인가

작성 2026-08-01 · 실측 기반 결정 기록

---

## 0. 결론 세 줄

1. **그래프는 필요하다.** "자료가 많아서"가 아니라 **참조의 2/3이 문서 밖을 가리키기 때문**이다.
2. **Postgres 위에 올린다.** 30만 엣지는 별도 그래프DB가 필요한 규모가 아니고,
   `pgvector` 와 같은 DB에 있어야 "유사 조항 + 그 조항이 준용하는 조항"을 **한 번에** 조인한다.
3. **그래프보다 일자 정리가 먼저다.** 지금 데이터로는 "가입일에 맞는 약관"을 고를 수 없다.

---

## 1. 그래프가 필요한 이유 — 참조가 문서를 넘는다

표본 300문서 실측:

```
준용 참조 —  같은 문서 안 7,853   /   문서 밖(보통약관 등) 15,792
```

**3분의 2가 밖을 가리킨다.** 실제 문장:

> `제1조(자기부담금) 회사는 보통약관에서 정한 손해가 발생하는 경우 손해액에서
>  1사고당 ( )을 빼고 보통약관 제9조(지급보험금의 계산)에 따라 손해를 보상하여 드립니다.`

이 특별약관만 읽으면 **자기부담금을 알 수 없다.** 괄호는 비어 있고 계산식은 다른 문서에 있다.
보장 판정을 하려면 **반드시 타고 넘어가야** 한다. 이건 조인이 아니라 순회다.

### 중복이 그래프를 더 강하게 요구한다

| 지표 | 값 |
|---|---:|
| 조항 총수(표본 400문서) | 12,534 |
| 서로 다른 조항 내용 | 4,860 |
| **중복 비율** | **75%** |
| 한 조항의 최대 재사용 | **73개 문서** |

문서마다 조항을 복사해 넣으면 같은 내용을 네 벌 저장하고,
**"이 조항이 개정되면 어느 상품이 영향받나"** 를 물을 수 없다.

---

## 2. 그런데 왜 별도 그래프DB는 아닌가

전량 환산 규모:

```
문서 1,703 · 조항 약 53,000 · 상호참조 약 307,000 · 고유 조항 약 20,000
```

30만 엣지는 **어떤 DB에게도 작다.** Postgres 재귀 CTE로 밀리초다.
그리고 `app/adapters/pg_graph.py` 에 `graph_nodes`/`graph_edges` + `WITH RECURSIVE walk` 가 이미 있다.

**그래프DB가 값어치를 하는 지점은 규모가 아니다:**

| 조건 | 여기 해당? |
|---|---|
| 깊이를 모르는 순회 | ✅ 준용 사슬이 몇 단인지 모른다 |
| 경로 자체가 답 | ✅ "왜 면책인가"를 조항 경로로 설명해야 한다 |
| 스키마가 자주 바뀜 | ❌ 약관 구조는 안정적이다 |
| 수억 엣지 | ❌ 30만이다 |

앞의 둘은 재귀 CTE로 된다. **분리하면 잃는 것이 더 크다** —
`pgvector` 유사도와 그래프 관계를 두 DB에 나누면 질의를 두 번 나눠 해야 한다.

## 3. 일자별 규칙 — 지금 어떻게 처리되고 있나

### 지금

조항 JSON 이 문서 단위 시점을 들고 있다.

```json
"source": { "insurer": "…", "product_name": "…",
            "sale_start": "20220401", "sale_end": "" }
```

**딱 여기까지다.** 문제가 셋.

| 문제 | 실측 | 영향 |
|---|---|---|
| 판매개시일 없는 문서 | **427건** | 가입일 → 약관 매칭 불가 |
| `sale_end` 가 거의 빔 | 대부분 | "2020년 3월 가입자에게 어느 약관?"을 못 정한다 |
| 버전 사슬 없음 | 전부 | 흩어진 문서 1,703개일 뿐 |

### `content_hash` 로 합치면 일자가 사라지나 — 아니다

**날짜를 노드가 아니라 엣지에 붙인다.** 파일에 이미 쓰는 Artifact/Occurrence 와 같은 원칙이다.

```
[조항 노드] content_hash=abc…  "제9조 지급보험금의 계산"      ← 내용이 정체성
     ↑ 수록 (2015-01-01 ~ 2017-03-31)
     ↑ 수록 (2017-04-01 ~ 2021-06-30)                      ← 날짜는 여기
     ↑ 수록 (2021-07-01 ~ )
[약관 문서 노드]
```

- 조문이 **개정되면 내용이 달라져 해시가 달라진다** → 자동으로 다른 노드.
  옛 버전은 옛 문서에 붙은 채 남는다. **개정 이력이 보존된다.**
- 안 바뀌었으면 한 노드에 여러 기간이 붙는다 →
  **"이 조항은 2015년부터 그대로다"** 가 데이터로 드러난다.

목표 답변 형태:

> "2019년 5월 가입이시니 3세대 약관이 적용됩니다. 해당 시점 약관 **제9조**에 따르면
>  자기부담금은 급여 10%·비급여 20%입니다. 이 조항은 2017년 4월부터 2021년 6월까지 유효했습니다."

## 4. 날짜를 어떻게 채울 것인가 — 실측으로 가린 결과

### 4-1. 사이트 재조회 — **막혔다**

| 보험사 | 없는 문서 | 재조회 가능? |
|---|---:|---|
| 메리츠화재 | 157 | ❌ **WAF 차단 화면**(`Detect time`) 반환 |
| NH농협생명 | 52 | ❌ 어댑터 주석대로 **목록에 판매기간 컬럼 자체가 없다** |
| NH농협손보 | 12 | ❌ 표 구조가 달라 판매기간 없음 |

우회하지 않는 원칙이므로 여기서 멈췄다.

### 4-2. PDF 메타데이터 `CreationDate` — **못 쓴다**

100% 존재하지만 판매개시일이 아니다. 둘 다 아는 250건으로 비교:

```
중앙값 -1일    ±7일 128/250(51%)   ±30일 203/250(81%)
최대 오차 1,725일 (재생성된 PDF)
```

절반은 맞지만 19%가 한 달 넘게 틀린다. **이걸 판매개시일이라 부르면 지어내는 것**이다.
`pdf_created` 로 따로 저장해 감사에만 쓴다.

### 4-3. PDF 1페이지 표기 — **여기에 있다**

처음에 "표지에 날짜 0건"이라고 보고했는데 **틀렸다.**
조항 JSON 앞부분만 봤고 정규식이 실제 표기를 몰랐다. 원문을 뜯어보니:

```
NH농협생명   '약 관 | 판매월 2026.05'
NH농협손보   '판매일 2026년 7월'
메리츠화재   '메리츠일반-특종/기타/기타A-16-2607A'      ← 끝 2607 = 2026.07
흥국화재     '준법감시인확인필 [장기상품]-[L2461]-LP-220324-01'   ← 2022-03-24
흥국화재     '무배당 흥국화재 실손의료보험(범용_1601)_1~2종'      ← 1601 = 2016.01
```

### 4-4. 그래서 신호를 등급으로 나눈다

날짜를 **아는** 문서 300건으로 추정기를 검증했다.

```
추정 성공 173 / 못 찾음 127
정확(같은 달) 125  ±1달 1  틀림 47   →  정확도 72%
근거별: 상품명YYMM 168건(오답 44) · 표지YYMM 5건(오답 3)
```

**72%는 판정에 쓰기엔 부족하다.** 그래서 등급을 나눈다.

| 등급 | 근거 | 처리 |
|---|---|---|
| `exact` | 사이트 판매기간 · `판매월 2026.05` · `시행일` 명시 | 그대로 쓴다 |
| `month` | 상품코드 `_2605`, 관리번호 끝 `2607` | 월 단위로만 쓴다. `inferred=true` |
| `unknown` | 아무 근거 없음 | **자동 판정에서 제외.** "시점 확인 불가"로 답한다 |

`month` 등급은 **세대 판정에는 충분하다**(세대 경계가 월 단위다).
다만 "정확히 어느 개정판인가"에는 못 쓴다.

---

## 5. 날짜가 없으면 전처리를 다시 해야 하나 — **날짜 때문은 아니다**

전처리는 `PDF → 페이지 → 조항` 이고, 날짜는 매니페스트에서 오는 **메타**다.
매니페스트를 채운 뒤 조항 JSON 의 `source` 만 갱신하면 된다. 전량 재추출이 아니다.

**다만 다른 이유로 어차피 다시 해야 한다** — 목차 오인 결함(§별도 리포트).

---

## 6. 그래서 순서를 바꾼다

```
(원래)  전처리 → 그래프 → 세대 판정
(수정)  전처리 재실행(목차 결함) → 일자·버전 정리 → 그래프 → 판정
```

일자·버전이 **그래프의 엣지가 될 재료**다. 그걸 먼저 만들어야 그래프가 의미를 갖는다.

### 일자·버전 정리에서 할 일

1. **날짜 추정기 적용** — 등급을 붙여 채운다(§4-4). 지어내지 않는다.
2. **`sale_end` 추론** — 같은 상품의 다음 버전 시작일 하루 전. `inferred=true`.
3. **버전 사슬** — 상품별 시간순 `이전/다음` 관계.
4. **세대 부여** — 판매개시일로 1~4세대(5세대는 실재 여부 확인 후).
5. **`unknown` 문서 격리** — 자동 판정 대상에서 뺀다.
