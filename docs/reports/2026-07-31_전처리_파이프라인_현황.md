## 1. 단계별 상세

### 1) 원본 PDF ✅

| 보험사 | 약관 PDF | 수집 방식 |
|---|---|---|
| DB손해보험 | **454** | JSON API (`insuPcPbanFindProductStep5_AX.do`) |
| 삼성화재 | **325** | JSON API (`VH.HDIF0103.do`) |
| NH농협생명 | **52** | HTML POST + 세션 |
| 동양생명 | **10** | HTML GET (별도 도메인) |
| **합계** | **841** | **2.6GB** |

남은 9개사 중 **삼성생명·NH농협손보는 API 직접 호출이 막혔다**(삼성생명은 요청 본문 암호화).
Playwright 렌더링 방식이 필요하다.

### 2) 문서 식별·중복 제거 ⚠ 절반

**된 것 — 중복 제거**
`Artifact(sha256)` 와 `SourceOccurrence(수집 사건)` 을 분리했다.
URL 기준 중복 제거는 **중복을 놓치면서 동시에 변경 이력도 덮으므로** 쓰지 않는다.

**안 된 것 — 식별**
`IdentifyDocument` 는 후보와 격리 사유만 만든다. **자동 확정은 코드로 금지**되어 있다
(`IdentificationResult` 가 `CONFIRMED` 로 생성되면 `ValidationErr`).
실행 결과 **302건 전부 `AMBIGUOUS`** 였다. 격리 사유 분포:

| 사유 | 건수 |
|---|---|
| 세대 규칙셋 미검토 | 28 |
| 표지 상품명이 카탈로그와 불일치 | 8 |
| 문서종류 후보 복수(`policy_terms`+`business_method`) | 5 |
| 변형 표기 복수(계약전환용+재개용+자녀전환용 동시) | 4 |
| 문서종류 후보 복수(`policy_terms`+`product_summary`) | 3 |

→ **사람 검수 단계가 11단계 목록에 빠져 있다.** 이게 없으면 전 파이프라인이
`unidentified` 상태로 굴러간다.

### 3) PDF 유형 판별 ❌ 건너뜀

**무엇인가**: PDF는 두 종류다.

| | 텍스트 PDF | 스캔 PDF |
|---|---|---|
| 내용물 | 글자가 데이터로 | 종이 사진(이미지)뿐 |
| 텍스트 추출 | 정상 | **빈 문자열** |
| 필요한 처리 | 그대로 추출 | **OCR** |

유형을 안 가리면 **스캔본이 "내용 없는 문서"로 조용히 통과**한다.

**★정직 기록**: 앞서 "`low_text` 6건은 스캔본"이라고 말했는데 **근거 없이 단정한 것이었다.**
확인해 보니 841건 중 **페이지당 200자 미만인 문서는 0건**이다. `low_text` 6건은 전체 2,000자
미만인 짧은 문서였을 가능성이 크다. **현재 우리 파일에는 스캔본 증거가 없다.**

그래도 이 단계는 필요하다 — 13개사로 늘면 섞일 수 있고, 그때 **감지 없이 통과하면 안 된다.**
다만 **지금 당장의 병목은 아니다.**

### 4) 레이아웃 기반 파싱 ⚠ 시범 2건

`scripts/extract/to_page_json.py` — PyMuPDF로 페이지별 `{page, text, tables[][]}` 생성.
**841건 중 2건만 변환**했다(파일럿).

측정된 것:
- 용량: PDF 대비 **합계 11.7% / 중앙값 14.9%** (무작위 20건, 파일별 4~29%)
- 표: 130쪽 약관 한 건에서 **표 73~95개** 검출

★한계: 표가 **검출**된다는 것과 **정확히** 뽑힌다는 것은 다르다. 실제로 병합 헤더가
여러 행으로 분해되고 빈 행이 삽입되는 것을 확인했다. **표 정확도는 측정하지 않았다.**

### 5) 문서 구조 복원 ❌
목차·장/절 계층을 복원하는 코드가 없다.

### 6) 조항·별표·표 단위 구조화 ❌ ★최대 병목

**지금은 페이지 단위까지만 왔다.** 그래서 판정 근거를 **"몇 쪽"** 까지만 인용할 수 있는데,
실제로 필요한 것은 **"제○조 몇 항"** 이다.

이 단계가 없으면 아래가 전부 막힌다:

```
6 조항 구조화 ─┬─→ 8 중복·공통조항 처리 (조항 단위 해시가 필요)
               ├─→ 9 계층형 청킹     (조항이 청크 경계)
               ├─→ 10 색인          (청크가 있어야 임베딩)
               └─→ 11 검색 평가      (인용 정확도를 조항 단위로 채점)
```

우리 ERD의 `assessment_clause_citation` 이 `policy_clause` 를 FK로 참조하는데,
**그 `policy_clause` 를 만드는 단계가 바로 6번**이다. 지금은 테이블만 설계돼 있고 채울 수 없다.

### 7) 메타데이터 부착 ⚠ 절반

| 메타 | 상태 | 위치 |
|---|---|---|
| 출처(보험사·URL·sha256·판매기간) | ✅ | `data/raw/manifests/<보험사>.jsonl` |
| 상품라인(일반/노후/유병력자) | ⚠ 후보만 | `data/catalog/*_document_manifest.jsonl` |
| 문서변형(계약전환용/재개용/자녀전환용) | ⚠ 후보만 | 〃 |
| 세대(1~5) | ⚠ **확정 0건** | 〃 · 규칙셋 `review_status=unreviewed` |

★수집 기록과 식별 결과를 **다른 파일로 나눈 것은 의도적**이다. 수집은 "받았다"는 불변 사실이고,
세대·유형은 **바뀔 수 있는 판정**이다. 한 파일에 섞으면 판정이 바뀔 때 수집 기록까지 덮게 된다.

### 8) 중복·공통조항 처리 ❌

같은 상품의 개정판이 수십 개다(삼성화재: 고유 상품 174개에 버전 409개).
개정판끼리는 대부분 내용이 같고 일부 조항만 바뀐다.

설계 논의만 있고 구현이 없다. **6번이 되어야 시작할 수 있다.**
핵심 쟁점: 같은 조항 번호라도 내용이 다르면 다른 조항이고, 번호가 바뀌어도 내용이 같을 수 있다
→ **정체성을 번호가 아니라 내용 해시로** 잡아야 한다.

### 9~11) 청킹·색인·검색 평가 ❌
전부 미착수. 6번에 막혀 있다.

## 2. 11단계 목록에서 빠진 것

| 빠진 단계 | 왜 필요한가 |
|---|---|
| ★**사람 검수** | 2번에서 격리한 `AMBIGUOUS` 를 확정하는 단계. 없으면 전 파이프라인이 `unidentified` 로 굴러간다 |
| **표 정확도 측정** | 표가 "뽑힌다"와 "맞게 뽑힌다"는 다르다. 판정에 쓰기 전 필수 |
| **버전 매칭** | 사용자의 계약에 **어느 약관 버전이 적용되는지** 정하는 단계. RAG 앞이 아니라 판정 직전에 온다 |
| **재추출 경로** | 추출기가 바뀌면 다시 뽑아야 한다. 산출물을 버전별로 보관하고 있으나 재처리 절차가 없다 |

## 4. 한계 (정직 기록)

- 이 문서는 **2026-07-31 시점 스냅숏**이다. 수집이 계속 돌고 있어 건수가 달라진다.
- "표 정확도 미측정"은 4번의 신뢰도를 알 수 없다는 뜻이다 — **6번을 시작하기 전에 재야 한다.**
- 동양생명은 **페이징이 아직 안 뚫렸다**(총 671건 중 28건만 확보). 프레임워크 페이징
  파라미터를 넣으면 HTTP 500이 난다. 미해결로 남긴다.
- 11단계 각각의 **완료 기준(DoD)을 정하지 않았다.** "됐다"의 판단이 사람마다 다를 수 있다.
