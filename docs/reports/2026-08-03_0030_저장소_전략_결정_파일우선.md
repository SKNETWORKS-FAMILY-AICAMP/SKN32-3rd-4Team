# 저장소 전략 — 왜 DB가 아직 없고, 언제 세우나

2026-08-03 00:30 · 실측 기반 · ★**§3 은 팀 결정이 필요하다 (내 권고만 적었다)**

> 발단: *"ERD 22테이블 중 없는 게 엄청 많은데 구현 계획이 뭐냐"*
> 답을 찾아보니 **계획에 DB 트랙 자체가 없었다.** 없는 게 아니라
> **파일 어댑터로 우회 중**인데 그 결정이 어디에도 안 적혀 있었다. 그것부터 적는다.

## 1. 실측 — ERD 22테이블 중 **구현 0개**

확인 방법(재현 가능):

```bash
grep -rl "CREATE TABLE IF NOT EXISTS <이름>\|__tablename__ = \"<이름>\"" app/ scripts/ --include=*.py
```

22개 전부 미구현이다.

| 스키마 | 테이블 | 상태 |
|---|---|---|
| `core` (7) | `confirmed_policy_document` · `product` · `policy_version` · `policy_clause` · `clause_chunk` · `kcd_version` · `kcd_code` | ❌ 0/7 |
| `app` (10+뷰1) | `subject` · `policy_holding` · `case` · `case_diagnosis` · `assessment` · **`assessment_clause_citation`** · `claim` · `outcome` · `evidence` · **`evidence_verification`** · `cohort_stats`(VIEW) | ❌ 0/11 |
| `ops` (5) | `agent_client` · `interaction_log` · `consent` · `admin_user` · `audit_log` | ❌ 0/5 |

### 실제로 존재하는 테이블은 16개 (전부 ERD 밖)

```
보험 (생 SQL · pgvector_clause_index.py)
  policy_clause_content · policy_clause_occurrence · policy_clause_chunk

커머스 RAG (생 SQL)
  rag_chunks · graph_nodes · graph_edges

커머스 (SQLAlchemy · app/db/models.py)
  users · face_credentials · products · inventory · orders
  order_items · order_idempotency · payments · knowledge_gaps · run_events
```

★**`products` 는 커머스의 판매 상품이다.** ERD의 `core.product`(보험 상품)와 **이름만 같고 다른 것**이다.
나중에 같은 DB에 올리면 충돌한다.

## 2. 결정 ① — **파일 어댑터 우선으로 간다** (명시적 기록)

지금까지 암묵이었다. 여기서 명시한다.

### 지금 무엇이 무엇을 대신하고 있나

| ERD가 정한 것 | 지금 | 어댑터 |
|---|---|---|
| `core.policy_version` · `confirmed_policy_document` | `data/raw/manifests/*.jsonl` | `manifest_policy_resolver.py` |
| `core.policy_clause` · `clause_chunk` | `data/structured/**` (기본) · PG(선택) | `file_clause_store.py` · `pg_clause_store.py` |
| `app.cohort_stats`(뷰) | 파일 | `file_cohort_stats.py` |
| `app.claim` · `outcome` · `evidence` | `data/external/**` | `external_submission_store.py` |
| `core.kcd_code` | 미적재 (`version_label` 을 비워 들고 다닌다) | — |

### 왜 이게 맞나

1. **채울 데이터가 0건이다.** 확정 문서 0건 · 실제 청구결과 0건. 빈 테이블 22개를 먼저 만들 이유가 없다
2. **포트가 이미 뚫려 있다.** 유스케이스는 `CohortStatsPort` · `ClauseStore` 같은 포트만 알고 파일/DB를 모른다. 어댑터 교체 비용이 낮다
3. **선례** — `pg_clause_store.py` 가 이미 같은 포트로 완성돼 있다. `CLAUSE_STORE=pg` 로 갈아끼우면 된다(회귀 미완)

### ★언제 DB로 가나 — 조건을 못박는다

"나중에"는 안 온다. **아래 중 하나라도 참이 되면 그 자리에서 착수한다.**

| 방아쇠 | 착수할 것 |
|---|---|
| **확정 문서가 1건이라도 생긴다** | `core` P0 — `confirmed_policy_document` · `policy_version` · `product` |
| **실제 청구결과가 1건이라도 들어온다** | `app` P1 — `claim` · `outcome` · `evidence` · `evidence_verification` |
| **판정 결과를 이력으로 남겨야 한다** | `assessment` · `assessment_clause_citation` |
| **에이전트 클라이언트를 실제로 등록한다** | `ops.agent_client` · `audit_log` |

★**방아쇠가 당겨지기 전에 미리 만들지 않는다**(RULE.md §3.3 YAGNI).
★**당겨졌는데 미루지도 않는다.** 파일로 흉내내기 시작하면 그때부터 폴백이다.

### 파일로 가는 동안 **주장하면 안 되는 것**

- ❌ "합성/실제를 **물리적으로** 분리했다" — 파일로는 못 한다(§3)
- ❌ "증빙 검증이 **FK로 강제**된다" — 테이블이 없다
- ❌ "판정 근거를 약관 조항으로 **제약했다**" — `assessment_clause_citation` 의 FK가 그 장치인데 없다.
  현재는 코드(`EvidenceTier`)로만 막는다 — **코드는 고칠 수 있고 FK는 못 뚫는다**

## 3. ★결정 필요 ② — MVP 필수 ②③을 어떻게 하나

**이건 내가 정할 수 없다. 팀 결정이 필요하다.**

[MVP 기능선정 §2](../plans/2026-07-31_1600_MVP_기능선정.md) 의 제품 MVP 8개 중 둘은 **DB 없이는 구현이 안 된다.**

| # | 기능 | 왜 DB 필수인가 |
|---|---|---|
| ② | 합성/실제 **물리 분리** + 혼합 차단 테스트 | 설계가 **DB 2개 분리**다. `is_synthetic` 컬럼으로 대체하지 말라고 §2가 못박았고, 파일 분리는 그보다도 약하다 |
| ③ | 증빙 상태 전이 `submitted→consistent→verified` | `evidence_verification` **행의 존재**가 곧 상태. append-only + `verification_method NOT NULL` 이 장치다 |

그런데 [MVP §8](../plans/2026-07-31_1600_MVP_기능선정.md) 이 이렇게 정해뒀다:

> 줄인다면 순서는 ⑧화면 축소 → ⑥검색 범위 축소 → ①매니페스트 축소이며,
> **②③은 줄이지 않는다**(정직성 장치).

**줄이면 안 된다고 정한 둘이 지금 계획에 없다.** 세 갈래 중 하나를 골라야 한다.

| 안 | 내용 | 대가 |
|---|---|---|
| **A** | **DB 2개 + `app` 6표를 지금 세운다** | 실제 데이터 0건이라 **빈 껍데기를 데모한다.** 다만 ②③을 "구현했다"고 말할 수 있다 |
| **B** | ★**데모 DB 하나만 세운다** (`insurance_demo`) | `evidence_verification` 행 전이를 **실제로 보여줄 수 있다**(③ 충족). ②는 "실제 DB는 아직 없음"으로 정직하게 표시 |
| **C** | 둘 다 미루고 **비범위로 선언** | MVP §8 을 뒤집는 것. **명시적 결정과 기록**이 반드시 필요하다 |

### 내 권고 — **B**

이유는 [MVP §5](../plans/2026-07-31_1600_MVP_기능선정.md) 가 정한 데모의 핵심이 이 두 줄이라서다:

```
consistent 제출 → n 그대로  /  verified 처리 → n+1
```

*"정합성만으론 통계가 안 움직이고, 검증돼야 움직인다"* — 이게 **우리가 파는 것**이라고 문서가 못박았다.
이걸 보여주려면 `evidence` · `evidence_verification` · `cohort_stats` 뷰가 **실제로 돌아야** 한다.
합성 데이터로는 돌릴 수 있다.

반대로 ②(실제 DB)는 **실제 데이터가 0건인 한 물리 분리를 증명할 대상이 없다.**
`insurance_real` 을 빈 채로 세우는 것은 껍데기다.

**B 를 택하면 필요한 최소 표**: `evidence` · `evidence_verification` · `outcome` · `claim` ·
`case` + `cohort_stats`(뷰) = **6개**. `insurance_demo` 한 DB에만.

★단, B 를 택해도 **"물리 분리를 구현했다"고 말하면 안 된다.** 화면·리포트에
*"실제 경로는 DB 미구축 · n=0"* 을 그대로 표시한다.

## 4. 결정 ③ — ERD를 구현 이름으로 확정 (반영 완료)

[ERD v4 §4 `core.policy_clause`](../plans/2026-08-02_0700_ERD_현행_v4_통합.md) 에 반영했다.

**무엇이 문제였나** — ERD는 `policy_version` 하나에 조항을 매달아 `body` 를 버전마다 복제한다.
s6 실측에서 조항 등장 **204,121** / 고유 **69,422**(**중복 66.0%**), 한 조항 최대 **170문서**다.
DB 2벌 복제까지 곱하면 본문이 약 **40만 벌**이 된다.

★**ERD가 CLAUDE.md §1(정체성/발생 분리)을 조항에만 적용하지 않은 자리**다. 자기 원칙을 어겼다.

**구현이 맞다** — 3계층으로 쪼개져 있다:

```
policy_clause_content     content_hash PK              ← 본문 한 벌
policy_clause_occurrence  content_hash+sha256+…        ← 어느 문서 어디에
policy_clause_chunk       content_hash+chunk_ix        ← 임베딩
```

**남은 숙제**: 이 3표에 `kind`(`coverage`/`exclusion`) · `parse_status` · `locator.char_offset` 이
**없다.** 판정 게이트가 그 값들에 의존한다 — `occurrence` 에 붙일지 별도 표로 뺄지 정해야 한다.

## 5. 한계 · 정직 기록

- **§3 은 결정이 아니라 제안이다.** 팀 승인 없이 진행하면 안 된다
- 이 문서는 **00:27 기준 관측**이다. 다른 세션이 `pgvector_clause_index.py` 를 **00:26에** 고쳤다.
  컬럼 단위 현행은 항상 `ensure_schema()` 가 정본이다
- **DDL `.sql` 파일이 여전히 0개**다. 스키마가 어댑터 코드에 흩어져 있어 전체 모양을 한눈에 못 본다.
  ERD §9-3 이 *"`.sql` 은 P0에서 작성한다"* 고 한 것이 그대로 남아 있다
- 마이그레이션 도구(alembic 등)가 없다. `CREATE TABLE IF NOT EXISTS` + `ADD COLUMN IF NOT EXISTS`
  로 멱등을 흉내내는 중인데, **컬럼 타입이 바뀌는 변경은 이 방식으로 못 한다**
