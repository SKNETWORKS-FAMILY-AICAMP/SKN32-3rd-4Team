## D2. ★`target_modules: [q_proj, k_proj, v_proj, o_proj]` 가 이 모델에서 **그대로는 안 먹는다**

### 위치

[05D §4-1](../../submission/05D_파인튜닝_모델_설계.md) 의 LoRA 설정 블록.

### 실측

```
ValueError: Target module Gemma4ClippableLinear(
  (linear): Linear4bit(in_features=768, out_features=768, bias=False)
) is not supported. Currently, only the following modules are supported:
`torch.nn.Linear`, `torch.nn.Embedding`, `torch.nn.Conv1d`, ...
```

### ★원인 — 감싸개는 **비전 타워 쪽**이다 (2026-08-05 정정)

처음엔 "gemma-4-E4B 가 q/k/v/o 를 `Gemma4ClippableLinear` 로 감싼다"고 적었다.
**틀렸다.** 비전 타워를 제외하고 다시 훑으니 대상 이름이 이렇게 나왔다.

```
[LoRA] 대상 모듈 132개, 예: ['model.language_model.layers.0.self_attn.q_proj',
                             'model.language_model.layers.0.self_attn.k_proj', ...]
```

`.linear` 접미사가 **없다** — 언어모델의 q/k/v/o 는 평범한 `Linear4bit` 다.
감싸개가 있는 쪽은 **비전 인코더**였고, 오류 메시지의 `in_features=768` 도
언어모델 차원이 아니라 비전 인코더 차원이었다. (132 = 33층 × 4)

**따라서 정확한 결함은 이것이다** — `target_modules: [q_proj, k_proj, v_proj, o_proj]` 는
이름만으로 매칭하므로 **멀티모달 모델에서 비전 타워까지 함께 잡는다.**
그 비전 타워 쪽이 `Gemma4ClippableLinear` 라서 **실행 전체가 죽는다.**
비전·오디오 타워를 빼면 설계서의 그 목록이 **그대로 동작한다.**

### 위험도

- 설계서를 그대로 옮기면 **학습이 시작조차 안 된다** — 원인은 언어모델이 아니라 비전 타워다.
- 원인을 잘못 짚고 "안쪽 `.linear` 를 쓰라"고만 고치면, 비전 타워를 **학습 대상에 남긴 채**
  돌아가 버린다. 우리 과제(05D §1-1 형식·기권 태도)는 텍스트 생성이라
  이미지 인코더를 학습할 이유가 없고, VRAM 만 먹는다.
- 실측: 비전 타워 제외로 GPU 점유 **11,938 → 9,112 MiB**(경합 있던 시각이라 절대값은 참고용).

### 조치

`scripts/finetune/train_qlora_pilot.py` 의 `_find_targets()` — `vision_tower`·`audio_tower`
계열을 제외하고 q/k/v/o 를 찾는다. 감싸개가 있으면 안쪽 Linear 를 쓰고, 없으면 그대로 쓴다.
모델 판이 바뀌면 또 달라지므로 이름을 손으로 적지 않는다.

## D3. 학습 스택 두 가지가 이 환경에서 막힌다 (환경 결함)

### D3-a. `datasets` / `trl` — Windows Application Control

```
ImportError: DLL load failed while importing groupby:
An Application Control policy has blocked this file.
  → pandas/core/groupby/groupby.py → pandas._libs.groupby
```

`trl.SFTTrainer` 는 `datasets` 를, `datasets` 는 `pandas` 를 탄다. x600 의 정책이
`pandas._libs.groupby` DLL 을 막는다. **보안 정책이므로 끄지 않았다.**

→ `trl` 없이 05D §4-2 값을 그대로 지키는 수동 학습 루프로 대체했다
(batch 1 · accum 16 · gradient checkpointing · lr 2e-4 cosine · warmup 3% ·
epoch 2 · max_grad_norm 0.3 · `PagedAdamW8bit` · seed 42).

### D3-b. `expandable_segments` 미지원

```
UserWarning: expandable_segments not supported on this platform
```

OOM 메시지가 권하는 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` 가
이 플랫폼(Windows)에서 **무시된다.** 단편화 완화 수단이 하나 없다.

05D §4-3·§5 의 빈칸(peak VRAM · step/s · 안전한 seq_len)은 **여전히 미측정**이다.

★**절차 위반도 함께 적는다.** RULE.md §3.5 는 이 상자를 공용이라 못박고
`scripts/ops/remote_who.ps1` 로 **프로세스를 먼저 보라**고 한다.
나는 `nvidia-smi` 로 GPU 0 MiB 만 확인하고 들어갔다. 그건 "지금 비었다"이지
"앞으로 안 들어온다"가 아니다. 뒤에 들어온 작업과 경합했고, 그 결과를 하마터면
**모델·설계 탓으로 보고할 뻔했다.**

→ 남의 작업은 죽이지 않는다. GPU 가 빌 때까지 대기하고, **깨끗한 상태에서 다시 잰다.**
