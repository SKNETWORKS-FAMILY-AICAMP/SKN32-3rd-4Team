## ① `01_부록_전처리_시각화.html` §G 가 s5 시절 숫자였다 — 고침

### 위치

`scripts/viz/build_preprocess_viz.py:151-162` (고치기 전) — HTML 표가 **문자열로 박혀 있었다.**

```html
<tr><td>조항(수록)</td><td>211,131</td><td>156,946</td><td>-54,185</td></tr>
<tr><td>고유 내용</td><td>63,963</td><td>2,221</td><td>-61,742</td></tr>
<tr><td>청크</td><td>(미산출)</td><td>6,208</td></tr>
…
"적재가 중간 상태다. 수록은 74% 들어갔는데 고유 내용은 3.5%뿐이다."
```

### 왜 위험했나

이 파일은 **제출물** `docs/submission/01_부록_전처리_시각화.html` 다.
그 사이 S7.1 이 적재돼 실제로는 `s6` 발생 **210,733** · 청크 **122,772** 인데,
문서를 여는 사람은 **「DB 가 3.5%만 적재됨」으로 읽는다.**
같은 제출물의 `05` §9 는 `readiness ready=true` 라고 적고 있어 **서로 모순된다.**

파일 안에 *"오른쪽(DB 적재)은 s5 시절 적재 결과다"* 라는 주석은 있었지만,
**표의 숫자가 먼저 읽히고 주석은 나중에 읽힌다.**

★재생성(`VIZ_TAG=s6`)만으로는 안 고쳐진다 — 그림 8장은 이미 s6 였고,
**이 표만 손으로 적혀 있었다.**

### 고침

`_db_section()` 을 만들어 **문서를 만들 때마다 DB 를 조회**한다.

```python
def _db_section() -> str:
    try:
        import psycopg
        from app.core.config import get_settings
        with psycopg.connect(get_settings().PGVECTOR_DSN, connect_timeout=10) as conn:
            ...   # occurrence/content/chunk 를 세대·source_kind·embed_model 별로 센다
    except Exception as exc:
        return head_ + '<div class="box w"><b>DB 에 붙지 못해 적재 수치를 싣지 못했다</b>…'
```

★**못 붙으면 옛 숫자를 대신 채우지 않고 못 붙었다고 적는다.** 조용히 남기는 것이 가장 나쁘다.

첫 실행에서 실제로 `ModuleNotFoundError: No module named 'app'` 이 났고
(스크립트를 `-m` 없이 돌리면 저장소 루트가 `sys.path` 에 없다),
**그 실패가 HTML 에 그대로 찍혔다** — 설계대로 동작했다. `sys.path` 를 붙여 고쳤다.

## ② 옛 `ko-sroberta@128` 조각 46,385개가 **DB 에 없다** — 정정만

`CLAUDE.md` 상태표는 이렇게 적고 있다.

> 옛 `ko-sroberta@128` 46,385조각은 `embed_model` 로 갈려 섞이지 않으므로 **지우지 않았다**

실측(2026-08-04):

```sql
SELECT embed_model, count(*) FROM policy_clause_chunk GROUP BY 1;
-- dragonkue/snowflake-arctic-embed-l-v2.0-ko|-|d1024|L8192|c448|o80   122,772
-- (끝. 다른 embed_model 은 없다)
```

`policy_clause_chunk` 의 `embed_model` 은 **Arctic-ko 하나뿐**이다.

### 위험도

**판정·인용에 영향 없음.** 옛 벡터는 어차피 검색에서 안 쓰였다.
다만 **문서가 사실과 다른 상태**였고, 이 세션의 `05A_DB_스키마.md` 초판도
그 문장을 **세어 보지 않고 옮겨 적었다.** 옮겨 적기 전에 세는 것이 규칙이다(`CLAUDE.md` §5 ★).

### 남는 것

**언제 어떻게 사라졌는지 확인하지 못했다.** 삭제 기록을 찾지 못했다.
`CLAUDE.md` 상태표도 같은 정정이 필요하다.

## ③ `s6` 발생 8,116건이 `content` 테이블에 대응 행이 없다 — 정정만

### 실측

```
s6 발생의 고유 content_hash : 72,723
policy_clause_content 행    : 64,607
차이                        :  8,116
```

`source_kind` 별로 나누면:

| `source_kind` | 고유 해시 | `content` 있음 | 없음 |
|---|---:|---:|---:|
| `clause` | 67,187 | 63,143 | **4,044** |
| `annex` | 5,461 | 1,299 | **4,162** |
| `approved_ocr_table_fact` | 75 | 75 | 0 |

### 위험도

**본문이 없으면 부모 조항 복원이 안 되므로 인용에 쓸 수 없다.**
`annex` 는 5,461개 중 **1,299개만** 본문이 있다 — 부록 쪽이 특히 비어 있다.

다만 이 행들이 **검색 결과에 나타나는지**는 확인하지 않았다.
`citation_eligible` 게이트에서 걸러지는지, 아니면 검색에는 나오고 인용에서만 빠지는지가 다르다.

### 다음

1. 벡터는 있는데 `content` 가 없는 조합이 몇 건인지 센다
2. 그 행들이 `citation_eligible=true` 인지 본다 — `true` 인데 본문이 없으면 **게이트 결함**이다
3. `annex` 의 4,162건은 별표 적재 경로를 따로 봐야 한다
