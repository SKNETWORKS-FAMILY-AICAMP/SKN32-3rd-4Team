## 1. 위치

`langgraph_agent/nodes/mcp_caller.py`

```python
from concurrent.futures import TimeoutError as FutureTimeoutError

def _call_with_timeout(func, *args, **kwargs):
    executor = ThreadPoolExecutor(max_workers=1)
    future = executor.submit(func, *args, **kwargs)
    try:
        result = future.result(timeout=MCP_TIMEOUT_SECONDS)
        executor.shutdown(wait=False)
        return result
    except FutureTimeoutError:                      # ← ★여기
        executor.shutdown(wait=False, cancel_futures=True)
        raise TimeoutError(
            f"MCP 호출 타임아웃 ({MCP_TIMEOUT_SECONDS}초 초과): {func.__name__}"
        )
```

`except FutureTimeoutError` 는 **`future.result()` 가 낸 대기 초과**만 잡을 의도로 쓰였다.

## 2. 원인 — 파이썬 3.11 에서 두 예외가 같은 것이 됐다

`concurrent.futures.TimeoutError` 는 **3.11 부터 내장 `TimeoutError` 의 별칭**이다.
(같은 판에서 `asyncio.TimeoutError` 도 그렇게 바뀌었다.)

그래서 이 `except` 절은 두 가지를 **구분 없이** 잡는다.

| 실제로 일어난 일 | 잡히나 | 밖에서 보이는 메시지 |
|---|---|---|
| `future.result()` 대기 초과 | O | `MCP 호출 타임아웃 (10초 초과): …` ← 맞다 |
| **도구 함수가 스스로 `TimeoutError` 를 던짐** | **O** | `MCP 호출 타임아웃 (10초 초과): …` ← **틀렸다** |

두 번째는 원격 서버가 "타임아웃"이라고 응답했거나, `requests`/소켓 계층이
자기 사정으로 던진 것이다. **우리 쪽 10초 상한과는 아무 상관이 없다.**
그런데 메시지는 "10초 초과"라고 단정한다.

## 3. 재현

```python
# repro_mcp_timeout.py — 팀 코드 그대로 옮긴 것
import sys, threading
from concurrent.futures import ThreadPoolExecutor
from concurrent.futures import TimeoutError as FutureTimeoutError

MCP_TIMEOUT_SECONDS = 1

def _call_with_timeout(func, *a, **k):
    executor = ThreadPoolExecutor(max_workers=1)
    future = executor.submit(func, *a, **k)
    try:
        result = future.result(timeout=MCP_TIMEOUT_SECONDS)
        executor.shutdown(wait=False)
        return result
    except FutureTimeoutError:
        executor.shutdown(wait=False, cancel_futures=True)
        raise TimeoutError(f"MCP 호출 타임아웃 ({MCP_TIMEOUT_SECONDS}초 초과)")

print("concurrent.futures.TimeoutError is TimeoutError →",
      FutureTimeoutError is TimeoutError)

def tool_raises_its_own():
    raise TimeoutError("실은 서버가 준 오류다")      # 0초 만에 즉시 던진다

try:
    _call_with_timeout(tool_raises_its_own)
except TimeoutError as e:
    print("밖에서 보이는 메시지:", repr(e))
```

실행 결과 (이 개발기, **Python 3.12**):

```
concurrent.futures.TimeoutError is TimeoutError → True
밖에서 보이는 메시지: TimeoutError('MCP 호출 타임아웃 (1초 초과)')
```

★**1초를 기다린 적이 없다.** 함수는 즉시 던졌는데 "1초 초과"라고 보고한다.
원문 예외 메시지(`실은 서버가 준 오류다`)는 **통째로 사라진다** —
`raise ... from e` 도 아니고 새 예외로 갈아치우기 때문이다.

## 6. 수정

원인별로 예외를 갈라 잡고, 원문을 버리지 않는다.

```python
import concurrent.futures as _cf

def _call_with_timeout(func, *args, **kwargs):
    executor = ThreadPoolExecutor(max_workers=1)
    future = executor.submit(func, *args, **kwargs)
    try:
        return future.result(timeout=MCP_TIMEOUT_SECONDS)
    except _cf.TimeoutError as e:
        #: ★3.11+ 에서 내장 TimeoutError 와 같은 객체다. 그래서 이것만으로는
        #:   '우리가 기다리다 지친 것'과 '도구가 스스로 던진 것'을 못 가른다.
        #:   future 가 아직 안 끝났는지로 판별한다 — 그게 진짜 대기 초과다.
        if not future.done():
            raise TimeoutError(
                f"MCP 호출 타임아웃 ({MCP_TIMEOUT_SECONDS}초 초과): {func.__name__}"
            ) from e
        raise                       # 도구가 던진 것이다. 그대로 올린다
    finally:
        executor.shutdown(wait=False, cancel_futures=True)
```

- `future.done()` 이 판별자다. **대기 초과면 future 는 아직 안 끝나 있다.**
- 도구가 던진 것이면 **원문을 그대로** 올린다. 갈아치우지 않는다.
- 우리가 만든 타임아웃도 `from e` 로 원인을 남긴다.
- `finally` 로 옮긴 것은 §7 때문이다.

**이 수정안을 그대로 돌려 확인했다** (네 경우 전부):

```
① 도구가 스스로 TimeoutError → TimeoutError('실은 서버가 준 오류다')     ← 원문 그대로 올라온다
② 진짜 대기 초과            → TimeoutError('MCP 호출 타임아웃 (1초 초과): tool_hangs')
                              (1.0초 기다림 — 실제로 기다린 뒤에만 이 메시지가 나온다)
③ 정상 호출                 → '정상'
④ ValueError 50회 뒤 스레드 증가 → 0        (수정 전 15)
```

## 7. 같은 함수에서 함께 나온 것 — executor 누수

`shutdown` 이 **성공 경로와 타임아웃 경로에만** 있고 `finally` 가 없다.
도구가 `ValueError` 처럼 일시 오류가 아닌 예외를 던지면 그냥 빠져나간다.

```
ValueError 50회 → 활성 스레드 1 → 16 (15개 누수)
```

`bugfix_summary.txt` 가 방금 고쳤다는 **스레드풀 고갈과 같은 종류**다.
호출마다 격리해서 "다른 호출을 막지 않게" 만들었지만, 실패 경로에서
executor 를 안 닫아 워커 스레드가 살아남는다. §6 의 `finally` 가 이것도 같이 막는다.

## 8. 우리 저장소는 어떤가 — 확인함

같은 코드가 없다. 실측:

```bash

grep -rln "ThreadPoolExecutor" --include=*.py .          # 0건 (저장소 전체)
```

이 경로를 안 탄다. **이 결함은 팀 저장소 `feature-agent` 브랜치에만 있다.**

다만 교훈은 우리에게도 적용된다 — **예외를 새로 만들어 던질 때 원문을 버리지 않는다.**
`raise X from e` 를 쓰거나, 아예 올려 보낸다.
