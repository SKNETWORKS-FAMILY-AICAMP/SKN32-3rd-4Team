# 수집·전처리 제출 문서의 계보와 재현 명령 오류

- 발견: 2026-08-04 14:23 KST
- 위치: `docs/submission/01_수집데이터_및_전처리.md`
- 상태: 본문 보강 작업에서 정정 완료
- 위험도: 중간 — 제출자가 수집량의 단위를 혼동하거나, 현행 코드로 12개사 전체를 한 명령에 재수집할 수 있다고 오인할 수 있음

## 1. 확인된 결함

### 1-1. 수집 스냅샷과 최종 고유 문서가 한 축처럼 보인다

기존 문서는 `수집 원문 1,703문서`라고만 쓴다. 그러나 실제 계보는 다음과 같다.

| 단계 | 단위 | 실측 |
|---|---|---:|
| 수집 발생 | `SourceOccurrence` | 2,121행 |
| 고유 원문 | SHA-256 `Artifact` | 1,703개 |
| 격리 | 고유 SHA | 336개 |
| 판정·전처리 대상 | 고유 SHA | 1,367개 |

`docs/reports/2026-08-01_실손약관_수집_결과보고.md`의 `1,817건·5.16GB`는
삼성생명 등이 아직 진행 중이던 중간 체크포인트다. 최종 정본 수치로 쓰면 안 된다.

### 1-2. 보험사별 대상 문서 합계가 총계와 다르다

기존 표의 보험사별 수를 합치면 1,363개다. 표 상단의 1,367개와 4개 차이가 난다.
현행 raw manifest와 `s6` 산출물을 직접 세면 삼성생명은 196이 아니라 200개이고,
이를 반영하면 합계가 1,367개가 된다.

### 1-3. `update_all.py`가 12개사 전체 수집 진입점처럼 적혀 있다

현행 `scripts/crawl/update_all.py:36`의 `ADAPTERS`에는 삼성화재와 DB손해보험만 등록돼 있다.
나머지 사이트는 개별 어댑터 또는 `scripts/crawl/browser_collector.py`의 사이트 설정을 사용한다.

또한 `scripts/crawl/update_all.py:86`의 `--recheck`는 인자로 선언돼 있지만 이후 실행 로직에서
사용되지 않는다. 기존 문서의 “`--recheck`로 기존 URL 내용 변경을 감지한다”는 현행 재현 명령으로
성립하지 않는다.

### 1-4. 역사적 감사와 현행 온라인 게이트가 섞여 있다

- 1,817건의 `%PDF`·`%%EOF` 전수 감사와 65,536바이트 잘림 165건 복구는 실제 수행 이력이다.
- 현행 `scripts/crawl/browser_collector.py:306`의 온라인 저장 게이트는 `%PDF` 시작과 60MB 상한을 검사한다.
- 따라서 EOF 검사를 현행 `_save()`가 항상 수행한다고 쓰면 안 되고, 당시 사후 전수 감사로 구분해야 한다.

### 1-5. 65,536바이트 잘림 감사 결과를 크기 하한처럼 잘못 표현했다

보강 초안은 수집 완료 시점 감사를 `65,536B 이상 0`이라고 적었다. 이 표현은
65,536바이트보다 큰 정상 PDF도 없었다는 뜻이 되어 사실과 다르다. 근거 보고서가 확인한 것은
HTTP 206 잘림의 특징이었던 **정확히 65,536바이트인 파일이 0개**라는 사실이다.

같은 행의 `2,121`은 매니페스트 발생행이고 `2,030`은 당시 물리 PDF 수이므로 단위도 분리해야 한다.

### 1-6. s6 보류 통계를 2열 후보 총수로 잘못 해석했다

보강 초안은 `tables_withheld_unverified=109,301`을 고유 `2열짝짓기` 후보 수라고 썼다.
현행 s5 전량을 직접 세면 2열 후보는 109,421개이고 모두 자동 부착 차단 상태다. s6 통계
109,301은 일반 문서의 2열 후보 109,192개에 reject된 선 후보 109개를 더한 값이며,
`no_clause_heads` 9문서의 fallback 2열 후보 229개는 포함하지 않는다. 두 수는 같은 분모가 아니다.

### 1-7. S7의 선 표 우선순위를 현행 부착 게이트 검증으로 과장했다

`scripts/extract/build_s7_hybrid.py:156`은 선 후보를 고를 때 역사적 `is_table is not False`를
사용하고 현행 `attachment_verdict(T9)`를 호출하지 않는다. 선 후보 813개 중 S7 builder가
verified로 보는 것은 777개지만 현행 부착 게이트 통과는 704개다. 즉 현행 s6이 거절하는 73개를
S7 page mode는 verified로 분류한다. accepted clause 복제본의 mismatch 0과 page mode 선 표
안전성은 별개다.

### 1-8. KCD 표 단일 사례와 정답셋 평가 분모를 합쳤다

흥국화재 대표 22행 표가 native 추출에서 2행×3열로 붕괴한 것은 단일 사례다. 짝 정확도
`0.455→1.000`은 그 한 표의 결과가 아니라 동일 조판 3표·66레코드 정답셋 전체 결과다.
한 문장에 묶으면 22행이 평가 분모인 것처럼 읽힌다.

### 1-9. 삼성생명 화면 대비 차이 2건 중 1건만 원인이 확인됐다

삼성생명은 화면 223건 대비 수집 221건으로 차이가 2건이다. 근거 보고서로 확인되는 것은 DRM
컨테이너 1건뿐이고 나머지 1건의 원인은 확정되지 않았다. 차이 전체를 DRM으로 설명하면 안 된다.

### 1-10. KCD 정확도 0.455의 기준선을 native table로 잘못 붙였다

`0.455`는 PyMuPDF `page.find_tables()`가 만든 native table의 정확도가 아니다. 표 파이프라인 통합 전
평평한 페이지 텍스트에서 질병명과 KCD 코드를 짝지은 기준선의 3표·66레코드 정확도다. native의
2행×3열 붕괴는 별도 대표 사례이므로, 기준선 이름도 분리해야 한다.

## 2. 재현

```powershell
# 최종 s6 문서 수와 보험사 slug별 산출물 수
Get-ChildItem data\structured -Directory | ForEach-Object {
  $n = (Get-ChildItem $_.FullName -Directory -Filter 's6_pymupdf-*' |
    ForEach-Object { (Get-ChildItem $_.FullName -Filter '*.clauses.json').Count } |
    Measure-Object -Sum).Sum
  if ($n) { "{0} {1}" -f $_.Name, $n }
}

# 전체 updater에 실제 등록된 어댑터와 --recheck 사용 여부
Select-String -Path scripts\crawl\update_all.py -Pattern 'ADAPTERS|recheck'

# 동결된 s6 입력·산출물·환경 해시 검증
python -m scripts.extract.build_manifest --schema s6 --verify
```

실측한 `s6` 폴더 합계는 1,367이며 삼성생명 slug는 200개다.

## 3. 영향

- `1,817`, `2,121`, `1,703`, `1,367`을 모두 “문서 수”로 부르면 중복 제거와 격리 성과가 사라진다.
- 보험사별 표의 산술 불일치는 제출 수치 전체의 신뢰를 떨어뜨린다.
- 동작하지 않는 `--recheck`와 2개사 updater를 전체 재현 경로로 안내하면 팀원이 같은 결과를 재현할 수 없다.
- 역사적으로 수행한 PDF 감사와 현재 코드의 자동 게이트를 구분하지 않으면 품질 보증 범위를 과장하게 된다.

## 4. 정정 방향

1. 수집 발생 2,121행 → 고유 SHA 1,703 → 격리 336 → 전처리 대상 1,367 계보표를 둔다.
2. `1,817건·5.16GB`는 2026-08-01 중간 체크포인트로만 설명한다.
3. 삼성생명을 200개로 고쳐 보험사별 합계를 1,367로 맞춘다.
4. 사이트별 어댑터·브라우저 공통 엔진을 실제 진입점으로 설명하고, `update_all.py`는 두 API 어댑터용이라고 한정한다.
5. 수집 당시 전수 감사 결과와 현행 crawler의 온라인 방어를 별도 표로 나눈다.
6. 사이트 재조회는 부하를 유발하므로 자동 재현 명령으로 권하지 않고, 필요 시 단일 보험사로 제한한다.
7. 수집 완료 시점 파일 감사는 `발생행 2,121·물리 PDF 2,030개(5.75GB)`로 단위를 쓰고,
   `정확히 65,536바이트인 파일 0`으로 표현한다.
8. s5 원시 2열 후보 109,421개와 s6 보류 통계 109,301의 조성을 따로 설명한다.
9. S7 선 표 순서는 역사적 `is_table` 기준이라고 낮추고, T9 게이트 미통합을 남은 한계로 적는다.
10. KCD 22행 단일 붕괴 사례와 3표·66레코드 정확도 분모를 두 문장으로 분리한다.
11. 삼성생명 차이 2건은 DRM 확인 1건·원인 미확정 1건으로 쓴다.
12. KCD 3표·66레코드의 `0.455`는 `평평한 페이지 텍스트 기준선`으로 표시한다.
