## 1. 조사 과정 (요약)
가설을 하나씩 재현·배제하며 좁혀갔다:
1. **stdout 오염**(tqdm 진행바가 JSON-RPC 스트림을 오염) — stdout/stderr를 분리 리다이렉트해
   확인. tqdm/HF 경고는 stderr로만 감(오염 아님). **배제**.
2. **일반 서브프로세스 콜드 임포트 지연** — 플레인 `subprocess.run`으로 같은 import를
   실행: 1.2~9초(정상). **배제**.
3. **`anyio.open_process` 자체의 오버헤드** — MCP 클라이언트가 쓰는 것과 동일한 spawn을
   직접 호출: 1.2초(정상). **배제**.
4. **Windows Job Object 할당**(`create_windows_process`) — MCP의 실제 헬퍼로 직접 spawn:
   1.5초(정상). **배제**.
5. **HuggingFace Hub 네트워크 재검증**(캐시돼 있어도 매번 HEAD 요청 15~20개) — 실재하는
   지연 요인(인프로세스 호출에서 19.67초 관측, "unauthenticated requests" 경고 확인)이지만
   `HF_HUB_OFFLINE=1`로도 실제 stdio 행은 안 풀림. **부분 요인, 주원인 아님**.
6. **`mcp.run(transport="stdio")` 루프가 이미 도는 동안의 지연 로딩** — 계측 로그로 정확히
   포착: `from langchain_community.vectorstores import FAISS` **import 문 하나가 74~79초**
   걸림(다른 모든 맥락에서는 0.7~1.5초). **재현 확정**: mcp.run() 시작 **전**에 같은 로딩을
   하면 22~27초로 매번 정상 완료. mcp.run() 시작 **후** 도구 안에서 지연 로딩하면 180초
   넘게 무응답.

**정직한 한계**: SDK 내부의 정확한 메커니즘(어느 부분이 지연 로딩과 stdio 루프를 충돌시키는지
— 유력 후보는 stdin 비동기 읽기용 백그라운드 스레드와의 GIL/자원 경합이나 Windows
ProactorEventLoop 관련 이슈이나 확정하지 못했다)은 **특정하지 못했다**. 아래 수정은
**우회책(workaround)**이지 근본 수정이라 주장하지 않는다.

## 2. 수정 — mcp.run() 시작 전 워밍업 (범위를 재현된 것으로 한정)
`app/mcp/server.py`에 `_warm_up_rag_store()` 추가, `__main__` 진입점에서 `mcp.run()` **전**에
호출. `rag_service.get_store()`만 워밍업한다(vector_search/rag_qa/recommend_products가
`get_embeddings()`를 공유하므로 셋 다 커버). **감성분석 모델(`ml_sentiment._get_pipeline()`)은
뺐다** — 최초 수정 때 "일관성"을 이유로 같이 넣었으나, **재현 검증한 적이 없는 것을 추측만으로
워밍업에 포함시키는 것은 근거 없는 확장**이라는 Codex 지적을 받아들여 제거했다(범위를
실제로 재현된 것만으로 좁힘).

### 정직한 트레이드오프 (Codex 지적, 전부 수용해 문서화)
- MCP는 호출마다 새 subprocess를 띄우므로, 이 워밍업은 **RAG와 무관한 도구(`get_price` 등)도
  똑같이 ~25초 고정비를 부담**한다.
- RAG 인덱스 로드가 실패하면(파일 없음 등) **다른 9개 도구까지 서버가 아예 못 뜬다** — 단,
  `check_readiness()`가 이미 `vector_index_ready`를 앱 전체 준비 조건으로 요구하므로, 이
  블라스트 반경은 기존 운영 가정과 새로 어긋나는 것은 아니다(기존 전제의 연장으로 판단).
- **stdio 통합 테스트 스위트가 17초 → 226초로 느려졌다**(신규 회귀 테스트 1건 포함, 전부 통과).
  `-m mcp`는 원래도 CI 빠른 경로에서 제외돼 있어 개발 루프에는 영향 없다.
- "고쳤다"고 과장하지 않는다 — 무한 행을 **유계 시간(수십 초)**으로 바꾼 것이지, 왜 그런지는
  모른다. 코드 주석·이 리포트에 명시했다.

## 3. 검증
- 실제 stdio 경로(환경변수 없이, 진짜 `python -m app.mcp.server` subprocess)로 27~32초
  안에 매번 정상 완료(3회 반복 확인, 결과 3건 반환).
- **신규 회귀 테스트** `tests/test_mcp_stdio.py::test_stdio_vector_search_with_real_embedding_completes`
  — 실제 stdio로 vector_search를 호출해 성공·결과 존재를 확인. 이 조합(실제 stdio + 실제
  임베딩)을 검증하는 **최초의 테스트**다(기존 케이스들은 검증 오류 경로만 짚어 실제 임베딩
  코드에 도달한 적이 없었음 — 이게 이 버그가 발견되지 않았던 이유).
  한계: `pytest-timeout` 미설치라 이 테스트 자체엔 강제 타임아웃이 없다(회귀 재발 시 이
  테스트도 같이 멈춤 — 자연 완료 시간에 의존).
- CI **320**(회귀 0), **MCP 12**(+1, 전부 통과, 226초), pg **10**. Codex short-consult
  1라운드(**FIX** → 스코프 축소·문구 정정·트레이드오프 명시 전부 반영).

## 4. 남은 한계 (정직)
- SDK 내부 근본 원인 미특정 — 다음에 시간이 있다면 `mcp.server.stdio` 소스를 읽어 정확한
  메커니즘(백그라운드 스레드 유무 등)을 확인할 가치가 있다.
- 감성분석(`analyze_sentiment`)이 같은 문제를 가지는지는 **검증하지 않았다** — 재현되면
  같은 패턴(entry point 전 워밍업)으로 대응 가능하나, 지금은 추측성 수정을 넣지 않는다.
- 더 근본적인 해법(예: MCP 서버를 세션 동안 재사용하는 장수명 프로세스 풀)은 이 프로젝트의
  "학습용 시연이며 운영 구조 아님" 범위 밖 — 별도 과제로 열어둔다.
