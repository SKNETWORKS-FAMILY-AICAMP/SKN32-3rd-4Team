## 0. 한 줄 요약

**52건을 잘 받던 코드는 멀쩡했다.** 그 뒤 내가 얹은 수정 네 개가 차례로

## 1. 어떻게 확인했나 — 옛 버전을 그대로 돌렸다

"이전 버전 확인하면 뭐가 문제인지 알 것 아니냐"는 지적이 정확했다.
52건을 받던 커밋 `8cdafaa` 의 파일을 꺼내 **그대로 실행**했다.

```
  p1: 행 10개
    [OK] 희망사랑보험5.0(무배당) 1,028,052B
    [OK] 희망사랑보험5.0(무배당) 2,753,529B
    [OK] 희망사랑보험5.0(무)       853,312B
    [OK] 희망사랑보험4.0(무배당) 1,868,888B
수집 4건        ← 크래시 0건, 크기 정상
```

**옛 코드는 지금도 정상이다.** 따라서 원인은 그 뒤의 내 수정이다.

기능 차이를 세어 보니 이렇게 나왔다.

## 2. 근본 원인 — 65,536B 파일을 "잘렸다"고 오진했다

### 2-1. 관찰

수집물 중 **정확히 65,536바이트인 파일이 165개** 나왔다.
`%%EOF` 가 없었다. 나는 이걸 **"스트리밍이 끝나기 전에 body를 읽어 잘렸다"** 로 판단했다.

### 2-2. 그 판단은 틀렸다 (코덱스가 반박)

코덱스가 "65,536 = 정확히 64KiB 다. 잘린 파일이 이렇게 딱 떨어질 리 없다.
**Range 요청을 의심해라**" 고 지적했다. 실측해 보니 그대로였다.

```
status=206  range요청=bytes=0-65535  content-range=bytes 0-65535/1028052  len=65,536
status=200  range요청=None                                                len=1,028,052
```

**Chromium PDF 뷰어가 파일을 열 때 앞 64KiB 를 Range 로 먼저 받는다.**
내 응답 훅이 그 206 응답을 **본문인 줄 알고 저장**한 것이다.
같은 파일의 200 응답이 뒤이어 오는데, 나는 먼저 온 206 을 저장하고 끝냈다.

**진짜 고칠 것은 한 줄이었다.**

```python
if resp.status == 206:
    return
```

## 3. 오진이 만든 연쇄 — 수정 하나가 다음 크래시를 낳았다

```
오진: "스트리밍 중에 읽어서 잘렸다"
  │
  ├─(1) resp.finished() 를 넣어 '끝날 때까지 기다리자'
  │        → Playwright 가 응답 훅 안에서 페이지를 붙잡는다
  │        → ★ Target closed / Target page has been closed
  │
  ├─(2) "팝업이 먼저 닫혀서 그렇다" 며 팝업을 안 닫음
  │        → PDF 뷰어 탭이 계속 쌓인다
  │        → ★ Page crashed (메모리)
  │
  ├─(3) "크래시 나니 배치로 쪼개자" — batch_pages / skip_budget
  │        → 상태가 늘어 이어받기 지점이 어긋난다
  │        → ★ 같은 페이지 반복 / 수집 0건
  │
  └─(4) "%%EOF 없으면 버리자" 는 검사 추가
           → 206 을 **버리기는 하나 원인은 그대로**
           → 정상 파일까지 InfraError 로 떨어지는 경우 발생
```

각 단계마다 나는 **직전 증상**을 고쳤고, **원인**은 한 번도 건드리지 않았다.
그래서 고칠수록 나빠졌다.

## 4. 두 번째 버그 — 페이지네이션이 10페이지씩 건너뛰었다

206 을 고친 뒤에도 삼성생명은 **3페이지만 돌고 수집 0건**이었다.
검색 결과는 223건(23페이지)인데 3페이지에서 끝났다.

### 4-1. 실측

목록 첫 셀의 일련번호를 찍어 봤다.

```
step1: 첫행='223  개인>보장성>실손 |실손의료비보장보험2.0(갱신형,무배당)|'  next=enabled
step2: 첫행='123  개인>보장성>실손 |삼성생명노후실손의료비보장보험6.0…|'   next=enabled
step3: 첫행=' 23  개인>보장성>실손 |삼성간편실손의료비보장보험4.0…|'       next=disabled
```

**223 → 123 → 23.** 10이 아니라 **100씩** 뛰었다.

### 4-2. 원인

DOM 을 열어 보니 페이징이 두 층이었다.

```html
<div class="pagination-number">
  <button class="btn-paging-first" disabled>…</button>
  <button class="btn-paging-prev"  disabled>…</button>
  <ul>
    <li class="current"><button>1</button></li>
    <li><button>2</button></li> … <li><button>10</button></li>
  </ul>
  <button class="btn-paging-next">…</button>   ← ★이건 '다음 10페이지 묶음'
  <button class="btn-paging-last">…</button>
</div>
```

`btn-paging-next` 는 **다음 페이지가 아니라 다음 묶음(11~20)** 이었다.
그것만 눌러서 **1·11·21 페이지 = 30행**만 긁었고, 그 30행은 이미 받은 것이라
"수집 0건"이 됐다.

### 4-3. 수정

번호 버튼을 하나씩 누르고, 번호가 안 보일 때만 묶음을 넘긴다.

```python
def _goto_next_page(cfg, page, want: int) -> bool:
    moved = _click_number()                 # 1) 번호 버튼 먼저
    if not moved and cfg.next_page_selector:
        nxt.click()                         # 2) 없으면 묶음 이동
        if _current_page(cfg, page) == str(want):
            return True
        moved = _click_number()             # 3) 새 묶음에서 다시 번호
```

### 4-4. 결과

파일 **56 → 69개**로 즉시 늘기 시작했다.

## 5. 세 번째 지적 — 페이지 전환 확인을 첫 행으로 하면 안 된다

코덱스가 별도로 지적한 것:

> 첫 행 텍스트 비교는 **전환 중 옛 DOM 을 읽어** "안 넘어갔다"고 오탐한다.
> 활성 페이지 번호 변경을 기다리는 편이 안전하다.

받아들여 `current_page_selector` 를 두고 **번호로 확인**하도록 바꿨다.
번호를 읽을 수 없는 사이트에서만 첫 행 비교를 쓴다.

```python
if page_no > 1 and not cfg.current_page_selector and first == seen_first_cell:
```

## 6. 매니페스트 정합 — 부수적으로 드러난 어긋남

같이 감사했더니 두 종류가 나왔다.

| 증상 | 건수 | 원인 | 처리 |
|---|---:|---|---|
| 기록은 있는데 파일 없음 | 17 | `_file2`/`_file3`(사업방법서·상품요약서)를 지우면서 **행을 안 지움** | 행 삭제 |
| 파일은 있는데 기록 없음 | 66 | 기록 유실(디스크 풀 / 배치 중간 사망) 잔재 | 파일에서 복원 |

복원 행은 URL 을 **모른다.** 지어내지 않고 `url=""` + `recovered=true` 로 남겼다.
(`scripts/crawl/reconcile_manifest.py`)

감사 후: **기록 1,889행 / 파일 1,860개, 어긋난 것 0.**

## 7. 내가 반복한 실수 패턴

1. **증상을 원인으로 착각했다.** 65,536 이라는 딱 떨어지는 숫자가
   "이건 프로토콜 레벨의 일"이라고 말하고 있었는데 읽지 못했다.
2. **오진 위에 수정을 쌓았다.** 검증 없이 다음 수정을 얹으니 상태가 늘고
   재현이 어려워졌다.
3. **셀렉터의 의미를 이름으로 추측했다.** `btn-paging-next` 는
   "다음 페이지"처럼 읽히지만 실제로는 묶음 이동이었다.
   **일련번호를 찍어 봤으면 첫날 알았다.**
4. **옛 버전을 먼저 돌려 보지 않았다.** git 에 있었는데 쓰지 않았다.
   돌려 보니 5분 만에 "내 수정이 원인"이 확정됐다.

## 8. 앞으로의 규칙

- **딱 떨어지는 크기·개수는 프로토콜을 의심한다** (64KiB, 정확히 100, 정확히 10).
- **수정 하나를 넣으면 그것만 검증하고 다음으로 간다.** 여러 개를 겹치지 않는다.
- **회귀가 의심되면 옛 커밋을 먼저 실행한다.** 추측보다 빠르다.
- **페이지네이션은 일련번호나 총건수로 검증한다.** 버튼 이름을 믿지 않는다.
- **오진했던 내용은 코드 주석에 남긴다.** 다음 사람이(또는 내가) 되풀이하지 않도록.
