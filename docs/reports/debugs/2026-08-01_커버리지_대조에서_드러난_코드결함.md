# 커버리지 대조에서 드러난 코드 결함 4가지

작성 2026-08-01 · 관련 리포트 `docs/reports/2026-08-01_커버리지_대조_결과.md`

---

## 0. 왜 따로 쓰나

커버리지 대조의 **결과**는 "12곳 전부 누락 0" 이다. 그건 본 리포트에 있다.
여기 적는 것은 그 과정에서 드러난 **코드의 결함**이다.
셋은 고쳤고 하나는 남겨 뒀다. 전부 **조용히 틀린 답을 내는 종류**였다.

---

## 1. 오류 메시지가 사실을 잘못 전했다 — 통신 실패를 robots 거부로 보고

### 증상

```
InfraError: robots가 허용하지 않습니다: https://www.hi.co.kr/ajax.xhi
```

이 메시지를 읽고 나는 **"현대해상이 우리를 막았다"** 고 판단했다.
robots 를 우회하지 않는다는 원칙이 있으니 여기서 멈추는 게 맞다고 생각했다.

### 실제

직접 확인해 보니 허용이었다.

```
robots.txt HTTP 200 / 335B
User-agent: *
Allow: /
Disallow: /jsp/bin/CL ...   (ajax.xhi 는 금지 목록에 없다)
→ 판정: True / 200 → allow
```

### 원인

```python
except (urllib.error.URLError, socket.timeout, TimeoutError) as e:
    return False, f"robots 확인 불가({type(e).__name__})"
```

**"확인 못 했다"와 "거부당했다"를 같은 값(False)으로 돌려줬다.**
호출부는 False 를 보고 `robots가 허용하지 않습니다` 를 찍는다.

fail-closed 자체는 옳다 — 확인 못 한 채 남의 서버를 긁으러 가면 안 된다.
**틀린 것은 그 이유를 사실과 다르게 말한 것이다.**

### 고친 것

일시적 통신 실패는 몇 번 더 물어보고 판정한다. 그래도 안 되면 여전히 거부로 둔다.

```python
_ROBOTS_TRIES = 3
_ROBOTS_BACKOFF_SEC = 2.0
...
except urllib.error.HTTPError as e:
    if e.code == 404:
        return True, "robots 없음(규칙 부재)"
    #: HTTP 상태가 온 것은 서버의 **답**이다. 재시도하지 않는다.
    return False, f"robots HTTP {e.code}"
except (urllib.error.URLError, socket.timeout, TimeoutError) as e:
    last = type(e).__name__
    if attempt < _ROBOTS_TRIES - 1:
        time.sleep(_ROBOTS_BACKOFF_SEC * (attempt + 1))
    continue
...
return False, f"robots 확인 불가({last}, {_ROBOTS_TRIES}회 시도)"
```

### 아직 남은 것

호출부가 여전히 두 경우를 **같은 문장**으로 찍는다.

```python
raise InfraError(f"robots가 허용하지 않습니다: {API_URL} ({verdict})")
```

`verdict` 에 이유가 들어 있긴 하지만, 앞 문장이 "허용하지 않습니다"라 오해를 부른다.
**"확인 실패"와 "거부"는 다른 문장이어야 한다.**

## 2. 조용한 스킵 — 실패를 세지 않아 커버리지가 부풀었다

### 증상

현대해상 대상 조회가 `대상 246건` 을 냈다. 그런데 카탈로그에는 303건이 있다.

### 원인

```python
for it in m.fetch_catalog():
    if it.is_travel:
        continue
    try:
        out.add(m.pdf_url(m.file_meta(it.terms_file_id)))
    except InfraError:
        continue          # ★실패를 세지 않고 넘어간다
```

메타 조회에 실패한 **57건이 조용히 빠졌다.**

### 왜 위험한가

이 값은 **커버리지의 분모**다.

```
누락 = 대상 - 수집
```

분모가 303 이 아니라 246 으로 줄면 **커버리지가 실제보다 좋아 보인다.**
"전부 받았다"는 결론이 **조회에 실패한 만큼만 사실**이 된다.

빈 `except ... continue` 는 편해 보이지만, 그 자리에서 잃는 것이
**나중에 내리는 판단의 근거**일 때는 조용해선 안 된다.

### 아직 안 고쳤다

`verify_coverage._t_hyundaimarine` 은 그대로다.
고치려면 실패 건수를 세어 결과에 함께 실어야 한다.

```python
resolved, failed = 0, 0
...
except InfraError:
    failed += 1
...
# 결과에 {"target": len(out), "unresolved": failed} 로 싣는다
```

이번에는 서버가 응답을 끊어 재조회를 못 했고, 대신 오프라인 대조로 확인했다.
**서버가 회복되면 이걸 고치고 다시 돌려야 한다.**

## 3. 상품명에 날짜가 붙어 있었다 — 같은 상품이 다른 상품으로 보였다

### 증상

흥국생명이 "3건 누락"으로 나왔다. 그런데 파일은 멀쩡히 있었다.

### 원인

```
20240909_(무)흥국생명 실손의료비보험(갱신형)
20220101_(무)흥국생명 실손의료비보험(갱신형)
20230401_(무)흥국생명 실손의료비보험(갱신형)
```

기록이 유실됐을 때 **파일명으로 복구**했는데
(`rebuild_manifest.py`), 파일명이 `날짜_상품명.pdf` 꼴인 보험사가 있었다.
그 전체를 상품명에 그대로 넣었다.

대조는 `(상품명, 판매개시일)` 로 맞춘다.
상품명에 날짜가 붙어 있으면 **키가 달라져 같은 상품이 다른 상품으로 보인다.**

### 왜 위험한가

이건 대조만의 문제가 아니다. **버전 매칭이 실손 판정의 전제**다.
"이 계약 시점에는 이 약관이 적용된다"를 정하는 열쇠가 상품명과 판매개시일이다.
그게 어긋나 있으면 **판정이 조용히 틀린다.**

### 고친 것

전 보험사에서 35행을 찾았고, 상황이 셋으로 갈려 나눠 처리했다
(`scripts/crawl/fix_name_date_prefix.py`).

| 경우 | 건수 | 처리 | 이유 |
|---|---:|---|---|
| 접두어 = `sale_start` | 3 | 접두어만 뗀다 | 정보 손실 없음 |
| `sale_start` 가 **비어 있음** | 27 | 접두어를 `sale_start` 로 **옮긴다** | 접두어가 그 날짜의 유일한 출처 — 정보 이득 |
| 접두어 ≠ `sale_start` | 5 | 이름만 정리, 날짜는 `file_date` 로 **보존** | 뜻이 다를 수 있다(파일 개정일 vs 판매개시일) |

세 번째를 그냥 덮어썼으면 판매개시일이 조용히 바뀌었을 것이다.
**판단할 근거가 없을 때는 덮어쓰지 않고 따로 남긴다.**

KB손보는 파일명이 `{날짜}_{상품코드}_{슬롯}_{상품명}` 이라 코드·슬롯도 떼고
`product_code` 가 비어 있으면 거기에 채웠다.

## 4. 병합 규칙을 잘못 잡아 행이 부풀었다 (즉시 발견·수정)

`merge_legacy_manifest.py` 를 처음 `(sha, 상품명, 개시일)` 키로 짰다.

```
dbins  현재 454 + 통합 462 → 658행     ← 부풀었다
```

복구본은 상품명·개시일이 비어 있어서 통합본과 **다른 키**로 잡혔다.
같은 파일인데 두 벌이 남는다.

sha 기준으로 다시 재 보니 관계가 분명했다.

```
samsungfire  통합 409행/307sha · 현재 386행/307sha · 통합에 없는 sha 0
dbins        통합 462행/258sha · 현재 454행/258sha · 통합에 없는 sha 0
myangel      통합  10행/ 10sha · 현재  14행/ 13sha · 통합에 없는 sha 3
```

통합본이 상위집합이므로 그쪽으로 대체하고, 통합본에 없는 sha 만 지켰다.

**dry-run 을 먼저 돌려서 발견했다.** 바로 적용했으면 658행이 그대로 남았을 것이다.

## 5. 공통점 — 넷 다 "조용히 틀린 답"이었다

| # | 결함 | 어떻게 조용했나 |
|---|---|---|
| 1 | 통신 실패를 robots 거부로 보고 | 오류가 나긴 났는데 **이유가 틀렸다** |
| 2 | 실패 건수를 안 셈 | 오류 자체가 **안 났다** |
| 3 | 상품명에 날짜 접두어 | 대조가 **누락으로 오인** |
| 4 | 병합 키를 잘못 잡음 | 행이 늘었는데 **성공으로 보였다** |

크래시는 눈에 띈다. 이 넷은 **그럴듯한 숫자**를 냈다.
`대상 246건` 도 `658행` 도 그 자체로는 이상해 보이지 않는다.

### 그래서 앞으로

- **분모를 만드는 코드는 실패를 세야 한다.** `except: continue` 로 넘긴 것이
  나중 판단의 근거가 된다면 조용해선 안 된다.
- **오류 메시지는 원인을 사실대로 말해야 한다.** "확인 실패"와 "거부"는 다르다.
- **데이터를 합치거나 고치는 스크립트는 `--dry-run` 을 먼저 돌린다.**
  이번에 4번을 그렇게 잡았다.
- **의심스러운 숫자는 다른 기준으로 다시 세어 본다.** sha 로 다시 세지 않았으면
  658행을 못 봤을 것이다.
