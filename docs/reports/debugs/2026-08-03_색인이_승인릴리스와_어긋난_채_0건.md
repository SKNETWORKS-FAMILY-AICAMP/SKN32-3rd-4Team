# 색인이 승인 릴리스와 어긋난 채 **조용히 0건**을 돌려줬다 — 2026-08-03

**분류: 결함 · 발견 경위: 프로젝트 점검 중 DB 를 직접 셈 · 조치 완료, 재적재 미완**

---

## 무슨 일이 있었나

승인 릴리스가 가리키는 값과 DB 에 실제로 든 값이 **하나도 안 맞았다.**

```
승인 index_generation = 's5'
DB 실제               = 's6' 195,617 · 's5-mixed' 158,186      ← 's5' 는 0건

승인 embed_model      = ''      (embed_profile 이 비어 있음)
DB 실제               = 'jhgan/ko-sroberta-multitask@128' 46,385
```

두 필터가 **동시에** 아무것도 안 맞는다. 그런데 이렇게 나갔다.

| 호출 | 그때 결과 |
|---|---|
| `pg_clause_store.stats()` | InfraError "조항 기록이 없습니다" |
| `pg_clause_store.load_clauses()` | InfraError "색인에 없습니다" |
| `pg_clause_store.search()` | **`[]` — 조용히** |
| `pgvector_clause_index.search()` | **`[]` — 조용히** |

★**근거가 없는 것**과 **필터가 아무것도 안 맞는 것**이 같은 모양으로 나갔다.
호출자는 "그 약관엔 그런 조항이 없다"로 읽는다. 판정은 근거 없이 기권하고,
원인은 감춰진다. [CLAUDE.md](../../../CLAUDE.md) §0 「폴백으로 조용히 메우지 않는다」에 어긋난다.

---

## 왜 몰랐나

기본 저장소가 `file` 이라 **판정이 당장 깨지지 않았다.**
`CLAUSE_STORE=pg` 는 **환경변수 하나 차이**인데, 그 경로에 아무 검사도 없었다.

그리고 `current_embed_model()` 주석에 이렇게 적혀 있었다.

> ★**승인된 프로필이 없으면 빈 문자열**이다. 그러면 검색이 0건이 된다 —
> **그게 정직한 상태다.**

앞부분은 맞다 — 모델이 미확정인데 아무거나 고르면 잘린 벡터가 근거로 올라온다.
**뒷부분이 틀렸다.** 0건을 그냥 돌려주는 것은 정직한 게 아니라 **말하지 않는 것**이다.

---

## `s5-mixed` 를 `s5` 로 갈아 끼우지 않은 이유

`s5-mixed` 는 세대 컬럼을 나중에 붙이며 들어간 **컬럼 기본값**이다.

```sql
ADD COLUMN IF NOT EXISTS index_generation text NOT NULL DEFAULT 's5-mixed'
```

즉 "s5 로 적재했다"가 아니라 **세대 불명**이라는 뜻이다.
`s5` 로 바꾸면 세대를 모르는 158,186행이 **승인 세대로 둔갑한다.**
모르는 것을 안다고 하면 안 된다 — 그래서 남겨 두고 진단에 그 사실을 적었다.

## 조치

### 1. 색인 현황을 **DB 를 세어** 보고한다

`pgvector_clause_index.index_state(conn)` — 설정이 아니라 실제 행을 센다.
`release.ensure_ready()` 는 **디스크**만 봤다. 산출물이 온전해도 색인에 안
들어가 있으면 검색은 0건인데, 그 구멍을 아무도 안 보고 있었다.

### 2. 검색 경로가 **먼저 막는다**

`ensure_index_matches_release(conn)` 이 실제 숫자를 담은 InfraError 를 던진다.

```
색인이 승인 릴리스와 맞지 않습니다.
  · 승인된 임베딩 프로필이 **없습니다**(`embed_profile` 이 비었습니다). …
  · 발생: 승인 세대 's5' 로 적재된 것이 **0건**입니다.
         DB 에 있는 것 — {'s6': 195617, 's5-mixed': 158186}
    ★`s5-mixed` 는 … **기본값**입니다. 세대 불명이라는 뜻이지 s5 라는 뜻이 아닙니다.
  → `python -m scripts.index.build_clause_index` 로 다시 적재하세요.
```

★**"색인 오류"만 말하면 못 고친다.** 무엇이 몇 건인지 적어야 고칠 수 있다.

`pg_clause_store.search()` 의 `except Exception` 이 이 오류를 다시 감싸
`조항 검색에 실패했습니다: …` 로 만들고 있었다 — 질의가 실패한 것처럼 읽힌다.
InfraError 는 통과시킨다.

### 3. 준비 상태가 **묻기 전에** 말한다

`GET /api/health/ready` 에 `clause_index` 를 넣었다.
검색 경로의 차단은 **요청이 와야** 드러난다.

★상위 `ready` 는 **지금 쓰는 저장소가 요구하는 것만** 반영한다.
`file` 이면 인덱스 A 가 비어도 판정은 돌므로 `ready:true` 다.
`pg` 인데 어긋나면 검색이 전부 실패하므로 `ready:false` 다.
(고치기 전에는 하위가 `false` 인데 상위가 `true` 였다.)

★PG 에 못 붙어도 여기서 죽지 않는다. 다만 **「확인 못 함」과 「준비됨」을 구분**해
`checked:false` 와 이유를 적는다 — 섞으면 그게 폴백이다.

### 4. 시험 7건

[`tests/test_index_release_match.py`](../../../tests/test_index_release_match.py) —
2026-08-03 실측값을 그대로 재현해 **예외가 나는지** 본다.
`s5-mixed` 를 `s5` 로 읽지 않는지도 고정했다.

★마지막 하나는 **검사를 실제로 부르는지** 본다.
정적 UI 차단 목록이 그랬다 — 목록만 있고 막을 파일이 없었다.
검사를 만들어 두고 안 부르면 아무것도 안 막힌다.

## 남은 일 — 재적재

진단은 붙었지만 **색인은 여전히 비어 있다.**

| | 지금 | 필요한 것 |
|---|---|---|
| `embed_profile` | 비어 있음 | 모델 선정 후 기입 → [브리핑](../../handoff/13_임베딩모델_선정_브리핑.md) |
| `index_generation` | `s6`·`s5-mixed` | 승인 릴리스 세대로 재적재 |
| `policy_clause_chunk` | `ko-sroberta@128` 46,385 | ★**버려야 할 모델**로 채워져 있다 |

★46,385조각은 임베딩 브리핑에서 **제목 −0.122 · 뒷부분 −0.184 로 최하위**라고
결론 낸 그 모델·그 설정(128토큰)이다. 조항의 **83.7%가 잘린 채** 임베딩됐다.
모델을 정하면 **전량 재임베딩**이 필요하다.

> ★**모델을 고르는 일과 색인을 채우는 일이 따로 돌고 있었다.**
> 브리핑이 아무리 정확해져도 색인이 그대로면 서비스는 안 바뀐다.

## 이 결함이 알려준 것

- **빈 결과에는 이유가 있다.** 이유를 구분하지 않으면 "없다"가 두 가지 뜻이 된다.
- 설정을 한 곳으로 모으는 것(단일 진실원)만으로는 부족하다 —
  **그 값이 데이터와 맞는지**는 별개로 확인해야 한다.
- 준비 상태를 **디스크만** 보고 판단하면 색인 쪽 구멍을 못 본다.
- 하위가 `false` 인데 상위가 `true` 면, 상위를 아무도 안 믿게 된다.
