## 0. 요약

계획서 L2 가 *"3열 이상 표가 2열 경로로 간다"* 를 고치려고 `find_multi_col()` 을 만들었고,
상태를 **"◐ 구현했으나 미검증 · 파이프라인 미연결"** 로 적어 놓았다.

**"미검증"이 아니라 "거의 발화하지 않는다"** 가 맞다.

```
무작위 14문서 · 984쪽 스캔
find_multi_col 결과   k=0(실패) 832 · k=2 151 · k=3 1 · k≥4 0
                                                    ↑ 984쪽에 단 1건
```

## 3. 실측 — 통로는 찾는데 점수가 안 나온다

**통로(corridor) 탐지는 정상이다.**

```
corridors 개수 분포 (507쪽)
  0개 242 · 1개 103 · 2개 49 · 3개 37 · 4개 37 · 5개 22 · 6개 8 · 7개 5
  → 통로가 3개 이상인 쪽이 109개(21%)
```

**막히는 곳은 품질 점수다.**

| `cols` | 시도 수 | 품질 중앙값 | 최대 | **≥0.6 통과** |
|---:|---:|---:|---:|---:|
| 2 | 265 | 0.000 | 1.000 | **58** |
| 3 | 162 | 0.285 | 1.000 | **4** |
| 4 | 113 | 0.224 | 0.941 | **2** |
| 5 | 76 | 0.161 | **0.457** | **0** |
| 6 | 39 | 0.127 | 0.357 | **0** |

★**`cols=5` 는 최대값이 0.457 이다. 문턱 0.6 을 넘는 것이 구조적으로 불가능하다.**

## 4. ★원인 — 점수 식에 열 수가 분모로 들어간다

```python
def _grid_quality(g):
    rows   = [비어있지 않은 행]
    filled = [행마다 채워진 셀 개수]
    mode   = filled 의 최빈값
    consistency = filled.count(mode) / len(rows)
    if mode <= 1: return 0.0
    return consistency * (mode / ncol)      # ★여기
```

`mode / ncol` 항이 **열이 늘수록 상한을 끌어내린다.**

| 열 수 | 모든 열이 찰 때 | 한 열이 자주 비면 | 두 열이 자주 비면 |
|---:|---:|---:|---:|
| 2 | 2/2 = **1.00** | — | — |
| 3 | 3/3 = 1.00 | 2/3 = **0.67** | — |
| 4 | 4/4 = 1.00 | 3/4 = 0.75 | 2/4 = **0.50** |
| 5 | 5/5 = 1.00 | 4/5 = 0.80 | 3/5 = **0.60** |

여기에 `consistency`(1 이하)가 곱해진다. 즉 **3열에서 한 열이라도 자주 비면 상한이 0.67**,
consistency 가 0.9만 돼도 0.60 으로 문턱에 걸린다.

### 왜 이게 실제 약관에서 치명적인가

약관 표는 **병합 셀(rowspan)이 흔하다.** 「구분 | 보상금액」에서 `구분` 이 여러 행에 걸치면
그 행들의 첫 열이 빈다 → `mode` 가 내려가고 `consistency` 도 흩어진다.

**2열은 이 벌점을 거의 안 받는다**(`mode=2, ncol=2 → 1.0`). 그래서 문턱 0.6 은 실질적으로
**"2열만 통과시키는 필터"** 로 동작한다. L2 가 고치려던 바로 그 편향을 점수 함수가 다시 만든다.

### 함수 주석과 실제가 어긋난다

```python
"""★열을 많이 쪼갤수록 word_coverage 는 그대로라 그걸로는 k 를 못 고른다."""
```

`word_coverage` 의 k 무관성을 피하려고 만든 식인데, **반대 방향으로 과보정**됐다.
`word_coverage` 는 k 를 못 가리고, `_grid_quality` 는 **k 가 작은 쪽을 편든다.**

## 5. 두 번째 결함 — 통로 조합을 탐색하지 않는다

```python
for combo in (sorted(cands[:k]),):     # ★후보 중 앞에서 k개만
```

주석은 이렇게 약속한다:

> ★k 를 1..kmax 로 다 세워 보고 **행별 채움이 가장 고른 것**을 택한다
> …각 후보 조합을 `build_grid` 로 세워 점수로 고른다

**조합을 세우지 않는다.** `cands` 상위 k개를 그대로 쓴다.
진짜 3열 경계가 상위 3개 안에 없으면 **시도조차 안 된다.**

`corridors()` 정렬 기준이 폭이라면 "넓은 통로가 진짜 경계"라는 가정 위에 서 있는데,
그 가정 자체가 미검증이다. §3 — *"주석의 약속과 구현이 다르다"* 는 이미 한 번 겪은 종류다.

## 6. 위험도

**중.** 판정을 직접 틀리게 하지는 않는다 — `find_multi_col` 이 **파이프라인에 연결돼 있지 않기 때문**이다
(`extract()` 는 `find_two_col` 만 부른다).

다만 두 가지가 남는다:

1. **계획서 상태가 사실과 다르다.** "미검증"으로 적혀 있으면 다음 사람이 *"검증만 하면 쓸 수 있다"* 로 읽는다.
   실제로는 **연결해도 3열이 안 나온다**
2. 3열 이상 표(질병분류표·장해분류표가 여기 많다)가 **여전히 2열로 쪼개진다.**
   L2 는 열려 있는 채다

## 7. ★내가 잘못 보고했던 것

이 조사에 앞서 사용자에게 *"문턱(`min_quality`)을 낮추면 후보가 80건 안팎 나온다"* 고 말했다.
**숫자는 맞지만 진단이 얕았다.**

문턱을 낮추는 것은 **응급처치**다. 근본 원인은 문턱이 아니라 **점수 식이 k 에 불공정한 것**이고,
문턱만 낮추면 **2열 오탐이 같이 늘어난다**(2열은 이미 통과선 위에 몰려 있다).

## 8. 제안 (미수정 — 결정 필요)

### 즉시 (검수 재료 확보용)

- `min_quality` 를 낮춰(0.3) **후보를 만들어 낸다.** 지금은 문턱이 후보를 다 죽여
  **사람이 볼 것이 1건**이다
- ★이건 고치는 게 아니라 **재료를 만드는 것**이다. 이 상태로 파이프라인에 연결하면 안 된다

### 근본

- **`mode / ncol` 항을 다시 본다.** 열 수에 대한 벌점이 필요하다면
  (과분할 방지) **명시적인 tie-break** 로 두고, 통과 여부는 `consistency` 로 판단하는 편이 맞다
  — 지금은 둘이 한 곱셈에 섞여 있어 무엇 때문에 떨어졌는지 알 수 없다
- **병합 셀을 빈 셀로 세지 않는다.** rowspan 은 표의 정상 형태다
- **통로 조합을 실제로 탐색**하거나, 안 할 거면 **주석을 구현에 맞춘다**
- ★임계값과 점수 식은 **사람이 라벨한 결과로 맞춘다**. 지금처럼 먼저 박아두면
  검수할 후보 자체가 안 생긴다
