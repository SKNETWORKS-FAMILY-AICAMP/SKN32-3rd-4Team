- 작성일: 2026-08-03
- 대상: `_unified_mall_3`
- 세대: 조항 `s6_pymupdf-1.28.0` / 원문 쪽 `s5_pymupdf-1.28.0`
- ★파일명 예외: RULE.md §4.1 은 `YYYY-MM-DD_HHmm_` 를 요구하지만, 이 리포트는

## 0. 결론 먼저

**세 지표 중 둘은 쟀고, 하나는 "표적이 거의 없어서 사실상 못 쟀다."**

| 지표 | 상태 | baseline(낱말 포함 검색, s6) |
|---|---|---|
| ① 목차형 contamination@k | ★**의미 있는 측정 실패** | 0.0000 (검색결과 2,073항목 중 0건 @k=10) — 다만 코퍼스 목차형이 19,356 중 **8개(0.041%)**뿐이라 검정력이 없다 |
| ② 면책 recall@k | 쟀다 | 타사표현 질의 **recall@5 0.3947 · hit@5 0.8962**, **recall@1 0.1661 · hit@1 0.4245** |
| ③ 페이지 해소 | 쟀다 | `page_from` 적중 **0.9851**, 불일치 **0.0011**(2/1,880), 검증불가 0.0138 / `page_to` 적중 **0.9218** |

가장 중요한 발견은 지표 자체가 아니라 **지표를 재다가 드러난 것**이다.

1. ★**표기가 다르면 면책 조항을 못 찾는다.** 같은 뜻인데 다른 보험사 표기
   (「보상하지 않는 사항」 ↔ 「보험금을 지급하지 아니하는 사유」)로 물으면
   hit@1 이 **0.9245 → 0.4245** 로 떨어진다. 낱말 검색의 한계이고,
   임베딩 검색이 반드시 넘어야 할 선이다.
2. ★**면책 조항의 14.87% 는 인용 게이트에 걸려 애초에 검색될 수 없다**
   (gold 491개 중 인용가능 418개). recall 의 천장이 검색기가 아니라 게이트에 있다.
3. ★**서빙 세대(s5)에서는 면책 질의 106개 중 28개(26.4%)가 결과 0건**이다.
   전부 `parse_status == "suspect"` 문서이고, `usable` 조항이 **0개**다.
   즉 "면책 조항을 못 찾는다"의 최대 원인은 검색기가 아니라 **문서 전체 배제**다.
   같은 표본에서 s6 는 2건(1.9%)으로 줄어든다.

## 1. 작업 목표

팀이 검색·인용 착수 **선결조건**으로 요구한 지표 3종의 **계산 코드와 검증셋**을 만든다.

- 임베딩 벡터는 아직 없다(`config/accepted_extraction.json` 의 `embed_profile` 이 비어 있다,

- 대신 지금 가능한 **낱말 포함 검색**(`app/adapters/file_clause_store.search`)으로

계획서 단계 대응: 이 작업은 `docs/plans/` 의 기존 단계에 정의돼 있지 않다.
검색·인용 착수 전 선결 측정으로 별도 수행했다(RULE.md §2 의 범위 규칙에 대한 예외이며,
계획서 갱신은 이 리포트를 근거로 다음 세션이 해야 한다 — §6).

## 2. 수행 내용

### 2.1 변경/추가 파일

| 파일 | 성격 |
|---|---|
| `scripts/eval/retrieval_quality.py` | **신규.** 검증셋 생성(`build`) + 채점(`score`) |
| `data/eval/retrieval_probes.json` | **신규.** 검증셋(1.03MB) |
| `docs/reports/2026-08-03_검색품질_지표_설계.md` | **신규.** 이 리포트 |

기존 파일은 하나도 고치지 않았다. 특히 `app/` 과 `config/` 는 읽기만 했다.

### 2.2 질의를 지어내지 않았다

`scripts/eval/build_retrieval_set.py` 머리말의 원칙을 그대로 따른다 —
LLM 으로 질문을 만들면 **평가가 모델이 아니라 질문 생성기를 재게 된다.**
그래서 질의는 **문서에 이미 적힌 조항 제목 원문**만 썼다.

★그런데 제 문서에 적힌 제목을 그대로 물으면 **낱말 검색이 글자만 겹쳐 봐도 맞는다.**
그건 검색 품질이 아니라 문자열 일치를 재는 것이다. 그래서 질의를 두 갈래로 나눴다.

| 질의 종류 | 만드는 법 | 무엇을 재나 |
|---|---|---|
| `동일표현` (106개) | 그 문서에 적힌 면책 조항 제목 그대로 | **하한 점검.** 이걸 못 맞히면 고장이다 |
| `타사표현` (106개) | 다른 문서에 적힌 다른 표기 중, 그 문서 본문에 **글자로 없는 것** | **진짜 시험.** 표기가 달라도 찾는가 |

관측된 면책 제목 표기(표본에서 실제로 나온 것만, 지어내지 않음):

```
보상하지 않는 사항 / 보상하지않는사항 / 보상하지 아니하는 손해 / 보상하지 않는 손해
보험금을 지급하지 않는 사유 / 보험금을 지급하지 아니하는 사유
보험금을 지급하지 아니하는 보험사고 / 특별면책조건의 내용 / 특약면책조건의 내용
```

★일부러 **뺀 것**: 「약관상 보장하지 않는 원인으로 사망시 지급금」.
이름에 '보장하지 않는'이 있지만 **면책 조항이 아니라 지급금 조항**이다.
이걸 gold 에 넣으면 gold 가 오염되고 recall 이 실제보다 낮게 나온다.

### 2.3 "무엇이 목차인가"를 정의했다 — 그리고 한 번 틀렸다

★**처음 정의가 틀렸다. 고친 과정을 남긴다**(CLAUDE.md §3 "오진했던 내용을 주석에 남긴다").

처음엔 신호 A 를 「`page_from`~`page_to` 가 문서 `toc_pages` 를 **지나면** 목차형」으로 썼다.
표본 119문서에서 **89건**이 걸렸다. 전수 확인하니 **81건이 정상 조항**이었다 —
목차 쪽을 **가로질러 뻗은** 긴 조항이다(예: 롯데손보 `제35조` page 2→34).
목차 쪽은 이미 조립에서 빠지므로 본문에 목차가 들어오지 않는다.
즉 이건 목차 오염이 아니라 **조 경계 실패**이고 다른 지표에서 세야 한다.

좁혀서 `page_from ∈ toc_pages` 로 바꾼 뒤 실측 **0건**.

최종 규칙(`scripts/eval/retrieval_quality.py`):

| 신호 | 정의 | 표본 적중 |
|---|---|---|
| A `시작쪽이_목차쪽` | `locator.page_from ∈ toc_pages` | **0건** |
| B `점선줄` | 점선 리더 줄 비율 ≥ 0.30 (줄 4개 이상) | 8건 |
| C `쪽번호줄` | 끝이 맨 숫자인 줄 비율 ≥ 0.50 | 1건(B와 중복) |

★A 가 0건인 이유는 전처리가 목차 쪽을 **이미 통째로 배제**하기 때문이다.
그래서 남은 오염은 **목차로 판정되지 못한 쪽**에 있고, B·C 만 그걸 잡는다.
A 는 아무것도 안 잡지만 **회귀 감시용으로 남겼다** — 전처리가 목차 배제를 느슨하게
바꾸면 여기서 먼저 터져야 한다.

★임계값 0.30 의 근거(실측): 표본 120문서·조항 14,036개에서 목차 밖 조항의
점선줄 비율 p99 가 **0.0** 이고, 0.30 을 넘는 것이 **7개**뿐이었다.

### 2.4 세대를 자동으로 고르지 않는다

`app/core/release.py` 의 `release.pinned(rel)` 을 써서 평가용 세대를 **명시적으로** 고정했다.
`file_clause_store` 를 고쳐서 세대를 바꾸지 않았다 — 평가가 서빙 코드를 건드리면
**평가한 것과 서빙되는 것이 달라진다.**

검증셋 파일에 `built_from_tag` 를 박고, 다른 세대로 채점하려 하면 **멈춘다**(fail-closed).
실제로 동작을 확인했다:

```
$ python -m scripts.eval.retrieval_quality score        # 승인 릴리스 = s5
검증셋은 s6_pymupdf-1.28.0 로 만들었는데 채점은 s5_pymupdf-1.28.0 입니다.
★gold 가 세대별 content_hash 라 섞으면 recall 이 0 으로 나옵니다.
```

### 3.2 검증셋 크기 — ★작다

| 항목 | 수 | 비고 |
|---|---|---|
| 문서 | **119** | 전체 1,367 중 **8.7%**. 보험사 12곳에서 각 10건씩(1곳은 9건) |
| 면책 질의 | **212** | 동일표현 106 + 타사표현 106 |
| 페이지 탐침 | **1,880** | 문서당 최대 20조항, 조항을 고르게 훑어 추출 |
| 목차형 표시 조항 | **8** | 조항 총 19,356개 중 **0.041%** |
| gold(면책 조항) | **491** | 질의당 1~12개, 중앙 4~5개 |

문서 `parse_status`: ok 111 · suspect 5 · no_clause_heads 3.
면책 조항이 **하나도 없는 문서 13건**은 질의를 만들지 않았다(대부분 조항 3~14개짜리 짧은 문서).

### 3.3 지표 ② 면책 recall@k — **쟀다**

낱말 포함 검색 baseline (s6, 질의 212개). 검색 실패(예외) **0건**.

| 질의 종류 | k | 면책 recall@k | 면책 hit@k | recall@k(인용가능 gold만) |
|---|---|---|---|---|
| 동일표현 | 1 | 0.2992 | **0.9245** | 0.3446 |
| 동일표현 | 3 | 0.4757 | 0.9623 | 0.5529 |
| 동일표현 | 5 | 0.5512 | 0.9623 | 0.6372 |
| 동일표현 | 10 | 0.6629 | 0.9623 | 0.7553 |
| **타사표현** | **1** | **0.1661** | **0.4245** | 0.1895 |
| **타사표현** | **3** | **0.3106** | 0.8396 | 0.3694 |
| **타사표현** | **5** | **0.3947** | 0.8962 | 0.4594 |
| **타사표현** | **10** | **0.5180** | 0.9340 | 0.6063 |
| 전체 | 5 | 0.4729 | 0.9292 | 0.5483 |

★**지표 이름을 정확히 부른다.**

- `면책 recall@k` = `|상위 k ∩ gold| / |gold|` 를 질의별로 내고 평균(macro).
  **"정확도"가 아니다.**
- `면책 hit@k` = 상위 k 안에 gold 가 **하나라도** 있는 질의 비율. **recall 과 다른 지표다.**
- `recall@k(인용가능 gold만)` = 인용 게이트를 통과한 gold 만 분모로. 검색기가 도달 가능한 천장.

★**recall@k 는 정의상 1.0 에 못 닿을 수 있다.** gold 가 k 보다 많은 질의가 있다
(gold 6개인 질의 40개, 10개 이상인 질의 14개). 그래서 hit@k 를 함께 본다.

★**동일표현 수치는 품질 추정치가 아니다.** gold 본문에 질의 문자열이 그대로 들어 있어
낱말 검색에 유리하다. **하한 점검**으로만 읽는다. 판단 근거는 **타사표현** 쪽이다.

#### 3.3.1 ★인용 게이트가 recall 의 천장을 정한다

gold 491개 중 `citation_eligible is not False` 인 것 **418개 = 85.13%**.
나머지 **14.87%(73개)의 면책 조항은 검색기가 아무리 좋아도 못 내놓는다.**
이건 검색 과제가 아니라 전처리·게이트 과제다.

#### 3.3.2 ★서빙 세대(s5)에서는 26.4%가 결과 0건

같은 검증셋 설계로 서빙 세대 `s5` 를 따로 재 봤다(참고 측정, 검증셋은 s5 로 재생성).

| | s5 (승인·서빙) | s6 (미승인) |
|---|---|---|
| 동일표현 hit@1 | 0.6698 | **0.9245** |
| 동일표현 hit@10 | 0.7358 | **0.9623** |
| 결과 **0건**인 동일표현 질의 | **28 / 106 (26.4%)** | 2 / 106 (1.9%) |

28건 **전부** `parse_status == "suspect"` 문서이고, `usable` 조항이 **0개**다.
즉 사용자가 「보상하지 않는 사항」을 물으면 **아무것도 안 나온다.**
CLAUDE.md §0 대로 "확인 불가"라고 답하는 것은 맞지만,
**이 비율이 26%라는 사실은 어디에도 기록돼 있지 않았다.**

### 3.4 지표 ③ 페이지 해소 — **쟀다**

조항 본문 앞 30자가 `locator.page_from` 쪽 **원문에 실제로 있는지** 본다.

| 값 | 결과 |
|---|---|
| 탐침 수 | 1,880 |
| `page_from` **적중** | **0.9851** (1,852) |
| `page_from` **불일치** | **0.0011** (2) |
| `page_from` **검증불가** | 0.0138 (26) |
| `page_to` 적중 | **0.9218** |

★**세 갈래로 나눴다.** "검증불가"를 불일치에 섞으면 **없는 결함을 있다고 말하게 된다.**
검증불가 26건은 전수 확인 결과 **앵커가 쪽 경계를 넘어간 것**이다 —
조항 본문이 쪽을 이어 붙이면서 머리말·쪽번호 조각이 끼어 어느 한 쪽에도 연속으로 없다.
검색 결함이 아니라 **측정 도구의 한계**다.

★**앵커를 `citation` 으로 잡았다가 한 번 틀렸다.** `citation`("제26조(회사의 손해배상책임)")은
조립된 문자열이라 원문의 「제26조 **【**회사의 손해배상책임**】**」과 안 맞는다.
citation 기준 적중이 **0.8397** 로 나왔는데, 그 14%는 검색 결함이 아니라 **내 측정 도구의 결함**이었다.
본문 앞 30자로 바꾸니 0.9851 이다. 앵커 길이별 실측:

| 앵커 길이 | 적중 | 검증불가 |
|---|---|---|
| 30자 | 0.9858 | 0.0142 |
| 40자 | 0.9732 | 0.0268 |
| 60자 | 0.9534 | 0.0466 |

원문 쪽 세대는 `s4` 로 재도 결과가 **완전히 동일**했다(적중 0.9851 · 불일치 0.0011).

#### 3.4.1 ★불일치 2건 — 결함이다

| 보험사 | sha12 | 조항 | 인용 쪽 | 실제 쪽 |
|---|---|---|---|---|
| 동양생명 | `e37e4f070156` | `머리말/제13조(해약환급금)` | 96–97 | **176** |
| 동양생명 | `30d4e2e96b98` | `머리말/제14조(해약환급금)` | 108–109 | **95, 152** |

둘 다 `section == "머리말"` 이다. 인용에 쪽수를 붙여 사용자에게 보여 주면
**사람이 그 쪽을 펴도 그 조항이 없다.** 위험도: 인용 신뢰성 직결.
★RULE.md §4.0 은 결함을 `docs/reports/debugs/` 에 따로 쓰라고 한다.
이 세션은 **파일 3개만 만들라는 제약**이 있어 쓰지 못했다 — §6 의 미해결 항목이다.

#### 3.4.2 목차 쪽을 가로지르는 조항 81건 (문서 45개)

지표 ① 에서 반려된 신호 A(구버전)가 잡던 것을 여기로 옮겨 세었다.

- 건수 **81** / 문서 **45** (표본 119문서 중 **37.8%**)
- 쪽폭 분포: 2쪽 15건 … 32쪽 **6건**, 30쪽 1건, 22쪽 1건

조 경계 실패로 보인다. 인용에 `page_from~page_to` 를 그대로 쓰면
**사용자를 목차 쪽으로 보낸다.** 이건 지표 ③ 이 잡아야 할 문제다.

### 3.5 지표 ① 목차형 contamination@k — ★**사실상 못 쟀다**

| 질의 종류 | k | contamination@k(항목 기준) | 검색결과 항목수 | 목차형 항목수 |
|---|---|---|---|---|
| 전체 | 1 | 0.0000 | 208 | 0 |
| 전체 | 5 | 0.0000 | 1,038 | 0 |
| 전체 | 10 | 0.0000 | 2,073 | 0 |

★**0.0 을 "검색기가 잘한다"로 읽으면 안 된다.**

- 코퍼스에 목차형 조항이 **19,356개 중 8개(0.041%)**뿐이다. **표적이 거의 없다.**
- ★**rule of three** — 2,073항목에서 오염 0건이면 오염률 **95% 상한은 3/2073 = 0.145%**.
  즉 "0.145% 보다 낮다"까지만 말할 수 있고 "없다"고는 말할 수 없다.
- 목차형 판정 규칙의 **precision** 은 표본 8건 전수 확인으로 **8/8** 이었으나,
  rule of three 상 오탐률 95% 상한은 **3/8 = 37.5%** 다. 작은 표본이다.
- ★목차형 판정 규칙의 **recall 은 못 쟀다.** 목차 정답셋이 없다. **놓친 오염은 못 센다.**

#### 3.5.1 그래도 8건은 실물이고, 전부 인용 가능 상태다

전수 확인 결과 8건 모두 진짜 목차·색인 잔재이고, **8건 모두 `citation_eligible == True`** 다.

```
흥국생명 abc2ba1bf387 제31조(규정의 준용)  → 본문이 '제 31 조 【규정의 준용】·········' 점선뿐
삼성화재 01dda5aefa18 제8조(준용규정)      → '특별약관 색인 / <ㄱ> 해당없음 / <ㄴ> 해당없음 …'
삼성화재 7f7f6233b254 제7조(준용규정)      → '<참고> 약관에서 인용된 법·규정 [법규1] 의료법 ……'
```

말미 조항이 **뒤따르는 색인·법규목록을 통째로 흡수**한 형태다.
지금은 검색 상위에 안 나왔을 뿐, **근거로 인용될 자격이 열려 있다.**

## 4. 이 baseline 을 어떻게 읽어야 하나

★**이 점수는 임베딩 검색의 점수가 아니다.** 승인 릴리스에 임베딩 프로필이 없다
(`embed_profile.model == ""`). 낱말 포함 검색은 의미가 아니라 글자를 본다.

임베딩 검색이 붙으면 **같은 검증셋으로 다시 잰다.** 그때 비교할 기준선은 이것이다.

| 지표 | 낱말 검색이 세운 선 | 넘어야 할 이유 |
|---|---|---|
| 타사표현 hit@1 | **0.4245** | 표기가 다르면 절반 이상 놓친다. 의미 검색이 여기서 이겨야 존재 이유가 있다 |
| 타사표현 recall@5 | **0.3947** | 면책 조항 5개 중 2개만 상위 5에 든다 |
| 동일표현 hit@1 | **0.9245** | 여기서 지면 **회귀**다. 글자가 그대로 있는데 못 찾는 것이다 |

## 5. 정직하게 못 한 것

1. ★**임베딩 검색 점수는 못 쟀다.** 모델 미확정이라 잴 대상이 없다.
2. ★**목차형 contamination@k 는 값은 나왔지만 검정력이 없다.** 표적 8개(0.041%)로는
   0.0 이 나오는 게 정상이다. 목차 오염이 많은 문서를 골라 뽑는 **표적 표본**이 따로 필요하다.
3. ★**목차형 판정 규칙의 recall 을 못 쟀다.** 목차 정답셋이 없다.
4. ★**표본이 작다.** 문서 119 / 1,367 = 8.7%. 보험사별 10건 고정이라
   문서가 많은 보험사가 과소대표된다. 조판이 회사마다 다르므로
   **회사 단위 편향은 줄었지만 문서 단위 대표성은 보장 못 한다.**
5. ★**gold 라벨은 조항 제목 정규식**이다. 제목이 깨진 조항의 면책은 gold 에 안 들어간다.
   즉 **실제 recall 은 이 값보다 낮을 수 있다.**
6. ★**`page_to` 적중 0.9218 의 실패 7.8% 를 분해하지 않았다.** 표 레코드 흡수가
   섞여 있는 것으로 보이나 **확인하지 않았다.**
7. ★**RULE.md §2 의 이력·§4.0 의 결함 리포트를 남기지 못했다** — 파일 3개 제약 때문이다.
