올바른 보험비서 — 사람이 아니라
AI 에이전트를 직접 사용자로 삼는 커머스

이 문서는 “이 프로젝트가 무엇이고, 어디를 고치면 되는가”를 파악하는 용도입니다. 화면별 사용 흐름은 화면 워크스루를, 지식 검증 설계는 바운티 브리핑을 보세요.

01 왜 만들었나 — 문제부터

지금 웹은 전부 “사람이 화면을 보고 클릭한다”를 전제로 만들어져 있다

AI 에이전트가 그 웹에서 정보를 얻으려면 브라우저를 조작하고, HTML을 걷어내고, 값을 다시 검증해야 합니다. 매번 토큰·시간·실행 비용이 들고, 그렇게 얻은 값이 최신인지 인용해도 되는지는 여전히 알 수 없습니다. 검색해도 바로 쓸 수 있는 데이터가 아니라 설명 페이지가 돌아옵니다.

그래서 최근 llms.txt·JSON-LD 같은 기계가 읽는 웹 표준과, AI를 데이터·도구에 연결하는 MCP, 에이전트끼리 협업하는 A2A가 등장했습니다. 이 프로젝트는 그 흐름을 서비스의 전제로 삼습니다.

직접 사용자는 사람이 아니라 AI 에이전트다

화면을 보는 건 사람이지만, 이 서비스가 상대하는 사용자는 AI 에이전트입니다.
사람이 웹페이지를 돌아다니는 대신, 에이전트가 출처·최신성·라이선스·변경이력이 붙은 데이터와 실행 기능을 직접 검색·검증·구매·호출합니다.

그런데 “AI들이 모이는 커뮤니티”를 만드는 건 약하다 — 이 판단이 설계를 갈랐다

AI는 목표·예산·책임을 스스로 소유하지 않습니다. 그래서 “AI가 좋아할 사이트”가 아니라, 사람·기업의 목표를 대신 수행하는 AI가 반복해서 돌아올 이유가 있어야 합니다. 그 이유의 핵심은 여기서 얻은 데이터로 실제 과업이 성공하는 것입니다(비용·속도·신뢰도도 함께 작용합니다).

그래서 쇼핑몰과 결합했다 — 콜드스타트를 피하려고

“모든 분야의 AI용 인터넷”을 만들면 데이터도 사용자도 없는 상태로 시작합니다. 그래서 거래가 실제로 완결되는 좁은 분야(커머스)에 붙였습니다. 쇼핑몰이 목적이 아니라, 에이전트가 검색 → 근거 확인 → 구매 승인 → 결과 확인까지 한 번에 도는 실사용 맥락을 주기 위한 결합입니다.

비전과 현재 구현을 구분해서 봐야 한다 중요

구분내용
가설(비전)사람이 웹을 돌아다니는 대신, 에이전트가 신뢰할 수 있는 데이터·기능을 직접 검색·검증·구매·호출하는 기계용 마켓플레이스가 필요하다
지금 검증 중인 것커머스 한 분야에서 그 흐름이 실제로 끝까지 도는가: 근거 있는 답변 → 미리보기 → 명시 승인 → 주문 확정, 그리고 MCP·A2A로 외부 에이전트도 같은 기능을 쓸 수 있는가
검증 방법외부 고객 AI를 기다리지 않고, 내부 참조 에이전트가 외부와 동일한 MCP 도구를 사용하게 만들어 확인. 외부에는 도구를 allowlist로만 공개
아직 아닌 것범용 데이터 거래소, 실제 정산·현금화, 외부 판매자 제휴 미구현

평판을 “좋아요”로 매기지 않는 이유

사람 커뮤니티의 추천수는 AI용 신뢰도로 쓸 수 없습니다. 대신 과업이 실제로 성공했는지를 봅니다 — 요청한 데이터를 찾았는가, 그걸로 작업이 끝났는가, 출처가 주장을 뒷받침하는가, 지금도 유효한가, 다른 에이전트가 재현했는가. 이 관점이 지식 바운티 검증 모델의 출발점입니다.

실제로 이렇게 동작합니다 (프로젝트에 들어 있는 실제 데이터 기준)

상황 1 — 정책 질문 (근거가 있는 경우)

고객 “단순 변심으로 반품하려면 며칠 이내에 신청해야 하나요?”

↓ 시스템이 환불교환정책.pdf에서 관련 조항을 검색

답변 “7일 이내에 신청하셔야 합니다.” 출처: 환불교환정책.pdf

상황 2 — 문서에 없는 질문 (이 프로젝트의 핵심 차별점)

고객 “이 청소기 부품을 3년 뒤에도 구할 수 있나요?”

↓ 검색해도 근거 문서가 없음

답변 “제공된 문서에서 찾을 수 없습니다.” 그럴듯하게 지어내지 않음

→ 이 질문은 운영자 확인 목록에 쌓여, 나중에 문서를 보강하는 재료가 됩니다.

상황 3 — 주문

장바구니에 담기 → 미리보기(“이어버드 2개, 158,000원, 재고 충분”) → 고객이 승인 → 주문 확정

미리보기 단계에서는 재고가 줄지 않고 주문도 생기지 않습니다. AI가 대신 주문을 넣는 일은 없습니다 — 사람의 승인이 있어야만 성립합니다.

왜 이렇게 만들었나 — 다른 실습 프로젝트와 다른 점

한 가지만 기억하면 됩니다: 모르는 것을 그럴듯하게 메우지 않는다

보통 AI 데모는 모르면 그럴듯한 말을 만들어냅니다(환각). 설정이 빠지면 조용히 기본값으로 돌아가고, 오류가 나면 빈 결과를 돌려줍니다. 이 프로젝트는 전부 반대로 합니다 — 근거가 없으면 답하지 않고, 설정이 없으면 ConfigError로 멈추고, 검증에 실패하면 초안을 버립니다.

덕분에 “동작하는 것처럼 보이지만 사실은 틀린 상태”가 생기지 않습니다. 대신 오류 메시지를 자주 보게 되는데, 그게 의도된 설계입니다. 이 원칙을 무폴백(no-fallback)이라 부르고, 코드 리뷰·테스트·문서의 공통 기준으로 씁니다.

※ “모든 경로가 검증됐다”는 뜻은 아닙니다. 검증 범위와 한계는 §08에 따로 정리했습니다.

맥락: 수업에서 만든 실습 자산(RAG·에이전트·MCP·쇼핑몰 등)을 하나의 제품으로 다시 통합하면서, 학습용 데모에서 실무 관행(권한 분리·멱등성·감사 로그·한계 문서화)으로 끌어올린 팀 프로젝트입니다.

재고는 원자적으로UPDATE ... WHERE stock >= qty 조건부 차감 + rowcount 확인. 설계·단위 테스트 범위에서 초과판매를 차단합니다 — 병렬 부하 실측은 미수행입니다.
2차인증 챌린지 일회성pre2fa 토큰에 jti 부여 → 성공 시 원자적 소비. 재사용·동시요청 차단
업로드 상한얼굴·음성 업로드 크기·장수 상한(config) → 모델연산 DoS 표면 축소

경로무엇이 있나

pip install -r requirements.txt

준비 상태는 GET /api/health/ready로 확인합니다(미준비면 명시적으로 알림 — 조용히 빈 결과를 주지 않습니다). 관리자 권한: python -m scripts.manage promote <username>

고객 앱과 개발용 전체 앱이 같은 8080을 씁니다. 동시에 띄우지 마세요. 서버 기동 직후 첫 요청은 수 초 걸립니다.

08 품질과 한계

검증돼 있는 것

  • 외부 인프라 없이 도는 결정론 테스트가 CI(GitHub Actions)에서 매 푸시 실행 — 2026-07-22 확인 시점 통과(최신 상태는 저장소 Actions 탭에서 확인)
  • 외부 의존 테스트는 마커로 분리: llm(실 LLM) · ml(무거운 모델) · mcp(stdio) · pg(PostgreSQL)
  • 요구사항↔테스트 매트릭스로 각 요구사항이 실제 수집되는 테스트에 연결됨을 검사
  • 실측 근거가 있는 선택: pgvector vs FAISS 동일 조건 비교, 얼굴 인식 3백엔드 열화 이미지 비교, DirectML 가속

한계 반드시 인지

  • 사실성은 판정하지 않는다. 근거성만 확인 — 근거가 거짓이면 통과합니다.
  • 자기검증은 같은 모델의 자기 점검이라 공유 오류를 잡지 못합니다.
  • PII 마스킹은 정규식 기반 → 완전 비식별 아님(이름·주소·IP 미탐지).
  • 얼굴 매칭·라이브니스 임계값은 실 분포로 튜닝되지 않은 시작값. 실 웹캠 라이브 정확도 미검증.
  • 시도 제한·2FA 챌린지 소비는 인메모리 → 멀티프로세스·재시작 무결성 없음(공유 저장소 필요).
  • 동시성은 구현·정적 리뷰만 — 부하 테스트 미수행.
  • DirectML 가속은 Windows 전용. MCP stdio 지연은 근본원인 미특정 우회책.

테스트 수를 정확성 증명으로 읽지 마세요

테스트는 정의된 계약대로 동작한다는 뜻입니다. 설계가 옳음이나 실사용 품질을 증명하지 않습니다.

# ① 외부 의존 없는 결정론 테스트 — CI와 동일 조건. 커밋 전 필수

pytest tests/test_arch.py tests/test_requirements_matrix.py

pytest -m ml

pytest -m pg   |  pytest -m mcp

①이 통과하지 않으면 커밋하지 마세요. ①은 CI가 도는 조건과 같습니다. ②~⑤ 실패는 환경(모델·DB) 부재일 수 있으니 오류 타입(ConfigError/InfraError)을 먼저 확인하세요.
