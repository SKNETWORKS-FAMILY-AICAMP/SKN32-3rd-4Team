01

최종 판단: 한 번의 통합 버전으로 구현 가능

기반 기능이 이미 있으므로 “기능을 새로 전부 만든다”가 아니라 “경계를 재정의하고 흐름을 연결한다”가 핵심이다.

진행 권고: GO. 단, 검색·추천 데모가 아니라 근거 기반 상담 → 정보 부족 감지 → 지식 바운티 → 검증 → 구매 승인 → 주문 → 관리자 보고서까지 닫힌 루프를 완성한다.
REUSE

기존 기능 유지

쇼핑몰, 로그인, 장바구니, Tool, LangChain, MCP, Agent 코드를 baseline test로 고정하고 감싼다.

MODERNIZE

구식 결합 제거

모델 SDK와 LangChain 객체가 라우터·DB·주문 로직에 직접 섞이지 않게 Ports/Adapters로 이동한다.

PROVE

사업 가설 검증

지식 바운티가 상품 추천 정확도와 설명 가능성을 실제로 개선하는지 정량 평가한다.

02

필수 기술을 한 제품 흐름으로 묶는다

부트캠프 요구사항을 별도 미니 프로젝트로 나누지 않고, 하나의 사용자 시나리오 안에서 모두 사용한다.

그림 1. 상담, RAG, 커머스, 멀티에이전트를 하나의 사용자 가치 흐름으로 통합한다.

04

목표 아키텍처: 모듈러 모놀리스 + Ports/Adapters

배포는 단순하게 유지하면서 팀이 독립적으로 개발할 수 있는 경계를 만든다.

그림 2. LangChain·MCP·모델 SDK는 바깥쪽 Adapter에 위치한다. 주문·권한·포인트 정책은 안쪽에 남는다.

Domain

프레임워크 없는 비즈니스 규칙

Application

유스케이스와 인터페이스 계약

Adapters

모델·DB·Vector·외부 API 구현

Interfaces

REST·MCP·Realtime·Worker

05

Clean Architecture 적용 여부가 팀 작업을 어떻게 바꾸는가

초기 속도만 보면 미적용이 빠르지만, 모델 4개·채널 3개·주문·바운티가 합쳐지는 순간 결과가 역전된다.

적용 버전
  • Backend는 Order Use Case를 개발
  • AI팀은 Model/Retriever Adapter를 개발
  • Agent팀은 같은 Use Case를 LangGraph/MCP에서 호출
  • Frontend는 OpenAPI DTO로 독립 작업
  • Fake Port로 외부 API 없이 테스트
  • 모델 교체가 주문 코드에 전파되지 않음
미적용 버전
  • 모두 agent.py와 shop.py를 수정
  • Router가 LangChain·DB·주문을 직접 호출
  • MCP와 REST 로직이 복제
  • 프론트 JSON이 모델 출력에 따라 변경
  • 테스트마다 실제 LLM·DB가 필요
  • merge conflict 때문에 순차 작업

09

텍스트·음성·화상은 하나의 대화 코어를 공유

채널별로 비즈니스 로직을 복제하지 않고 입력·출력 Adapter만 바꾼다.

텍스트

SSE/WebSocket 스트리밍, 출처 카드, Tool 상태, 구매 승인 UI.

음성

Realtime/Live, barge-in, transcript, STT-LLM-TTS fallback.

화상

카메라 미리보기, 동의 기반 프레임 샘플링, 제품·문서 이해.

얼굴을 보고 대화하는 기능과 얼굴 인증은 분리한다. 상담용 카메라 프레임은 모델 입력이고, 로그인은 WebAuthn/Passkey의 기기 생체인증을 사용한다.
