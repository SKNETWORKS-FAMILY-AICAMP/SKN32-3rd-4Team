실제로 무엇이 보이고,
어떤 상태 전이가 일어나는가

목업이 아니라 실행 중인 앱을 캡처한 18장입니다. 각 화면에 “무엇을 확인해야 하는지”를 달았습니다. 구조·설계 이유는 프로젝트 전체 설명을 보세요.

캡처 기준 — 2026-07-22 전량 재생성

18장 모두 현재 코드·당시 브랜드로 다시 촬영했습니다. 실 LLM(로컬 Gemma)·PostgreSQL(pgvector·그래프)을 띄운 상태에서 실제 클릭·실제 API 응답을 찍은 것이며, 손으로 그린 목업이 아닙니다.

재생성 방법: scripts/pg.py start → scripts/pg.py setup → local_model_server.py → run_dev_server.py → capture_screenshots.py(01–08) · capture_screenshots_admin.py(09–12) · capture_screenshots_mcp.py(13–14) · capture_screenshots_customer.py(15–18)

이 문서를 읽는 방법

화면별로 나열하지 않고 사용자 흐름 순서로 배열했습니다. 특히 거부 화면(422·409)은 버그가 아니라 설계된 방어 동작입니다 — 이 프로젝트에서 가장 중요한 부분이라 흐름 2에 모아 뒀습니다.

01AI 에이전트 상담/static/index.html · :8080
사용자 목표
자연어로 묻고, 상품·주문 정보까지 포함된 답을 받는다
입력·행동
“P0001 상품 가격 알려줘” 입력 → 전송
기대 결과
설계상: 에이전트가 get_price 도구를 호출하고, 밟은 단계와 종료 사유가 함께 표시된다
이 캡처에 실제로 보이는 것
도구가 실행되지 않았습니다. 답변 영역에 <|tool_call|>call:get_price{…} 같은 원시 문자열이 그대로 찍혀 있고 단계 목록은 비어 있습니다. 로컬 Gemma가 도구 호출(tool calling)을 지원하지 않아 도구를 부르는 대신 그 형식을 흉내낸 텍스트를 최종 답변으로 낸 것입니다. 화면 상단에도 “로컬 Gemma는 도구호출을 못하므로 실제 도구 사용은 OpenAI/Gemini 키 필요”라고 적혀 있습니다. 버그가 아니라 로컬 모델의 제약이며, 실키를 넣으면 도구가 실제로 실행되고 단계가 채워집니다.
확인할 안전장치
종료 사유(stopped_by: final_answer)가 항상 노출됩니다 — 왜 멈췄는지 숨기지 않습니다(다른 값: duplicate_tool_call·max_steps). 에이전트는 읽기 전용 도구만 쓸 수 있어 스스로 주문을 만들지 못합니다. max_steps를 화면에서 조절할 수 있어 루프가 무한정 돌지 않습니다.

05정상 승인 + 멱등 재생POST /api/orders · Idempotency-Key 필수
사용자 목표
미리보기 내용대로 주문을 확정한다
입력·행동
① 정상 승인 → ② 같은 키로 재요청
기대 결과
①에서 주문번호 발급, ②는 새 주문을 만들지 않고 기존 주문을 그대로 반환(재고 추가 차감 0)

네트워크 재시도·중복 클릭으로 이중 주문이 생기지 않습니다. 재고 차감은 UPDATE … WHERE stock >= qty 조건부 원자 연산이라 동시 요청에도 초과판매가 나지 않습니다.

관련: 07(같은 키·다른 내용은 409로 거부)

06키 없이 승인 시도 → 422거부 경로 ①
무슨 일이 일어났나
Idempotency-Key 헤더 없이 주문을 시도 → 422로 거부
왜 이게 옳은가
서버가 임의로 키를 만들어 주면 멱등성이 무력화됩니다(재시도마다 새 키 = 중복 주문). 그래서 키를 필수로 두고, 없으면 실패시킵니다 — 무폴백 원칙의 대표 사례입니다.
오해 방지
이 422는 버그가 아닙니다. 기존 호출부를 고쳐야 했던 의도적 호환성 파괴였습니다.
07같은 키 · 다른 내용 → 409거부 경로 ②
무슨 일이 일어났나
이미 쓴 키로 내용을 바꿔 요청 → 409 Conflict
왜 이게 옳은가
같은 키는 “같은 요청”이어야 합니다. 내용이 다르면 재생이 아니라 키 오용이므로 거부합니다. 요청 내용을 JSON 정규 지문으로 비교해 판별합니다.
08재고 초과 주문 → 422 · 주문 목록거부 경로 ③
무슨 일이 일어났나
재고보다 많은 수량 주문 → 422. 아래에 확정된 주문 목록 표시
왜 이게 옳은가
미리보기에서 feasible: false로 미리 알려주고, 승인 단계에서도 DB 레벨에서 다시 막습니다(이중 방어). 미리보기와 승인 사이에 재고가 줄어드는 경쟁 상황을 가정한 설계입니다.

흐름 3 권한과 운영 운영 전용 :8081

같은 화면이 권한에 따라 다르게 응답합니다. 401 → 403 → 200 순서로 보세요.

09미인증 접근 → 401/static/admin.html
무슨 일이 일어났나
로그인 없이 관리자 데이터 요청 → 401. 화면은 “관리자 로그인이 필요합니다” 안내만 표시
확인할 안전장치
관리자 라우터는 라우터 전역 의존성으로 잠겨 있습니다. 엔드포인트마다 붙이는 방식은 새 엔드포인트에서 누락되므로, 전역으로 걸고 테스트로 고정했습니다(fail-closed).
10일반 사용자 → 403로그인했지만 권한 없음
무슨 일이 일어났나
정상 로그인한 일반 사용자가 관리자 API 요청 → 403
확인할 안전장치
401(누구인지 모름)과 403(누구인지 알지만 권한 없음)을 구분합니다. 권한은 JWT에 넣지 않고 매 요청 DB에서 조회하므로, 관리자를 강등하면 토큰 재발급 없이 즉시 403이 됩니다.

입력·행동
python -m scripts.manage promote <username> 후 재조회
확인할 안전장치
관리자 승격 UI 버튼이 없습니다. CLI 전용이며, 마지막 관리자의 강등은 거부됩니다(잠김 방지). 승격·강등은 감사 기록으로 남습니다.
