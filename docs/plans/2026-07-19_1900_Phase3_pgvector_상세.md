# Phase 3 — PostgreSQL + pgvector 학습 트랙 (FAISS와 비교)

## 목표
동일한 `RetrieverPort` 뒤에 **pgvector 기반 `PgVectorRetriever`**를 붙이고, **동일 rag_v1 평가셋**으로
FAISS vs pgvector를 **Hit@3·지연·인덱싱 비용**으로 비교한다. 비교 자체가 학습 산출물(v3.2 ADR-005').

## 환경 결정 (중요)
- **Docker·시스템 PostgreSQL 미가용**(확인함). → **conda userspace PostgreSQL 16.14 + pgvector 0.8.3**
  (전용 conda env `pgv`, base 격리). 관리자 권한·Docker 불필요.
- 클러스터는 프로젝트 하위(`data/pgdata`, **gitignore**)에 initdb, 비표준 포트(예: 5433)로 기동.
- 앱은 base env의 `psycopg[binary]`(설치됨) + `pgvector` 바인딩으로 접속.
- `pg` pytest 마커 신설(실 PG 필요 → 결정론 CI 제외; ml/llm/mcp와 동일 패턴).

## 설계
- `app/adapters/pgvector_retriever.py`: `RetrieverPort` 구현(backend="pgvector"). 쿼리 임베딩(ko-sroberta,
  기존 `rag.embeddings` 재사용) → pgvector 유사도 검색(L2/`<->`) → `Evidence`(정규화 score). DB 연결 실패 → InfraError(무폴백).
- `app/adapters/pgvector_index.py`: 스키마(`rag_chunks(id, source, page, content, embedding vector(768))`) 생성 +
  `CREATE EXTENSION vector` + corpus 청크·임베딩 적재(기존 청킹 로직 재사용, 임베딩은 FAISS와 동일 모델).
- `scripts/pg.py`: userspace PG 라이프사이클(init/start/stop/status) + `scripts.manage`에 pgvector ingest 연동.
- 설정: `PGVECTOR_DSN`(config, .env; 기본 로컬 5433). 모델ID 아님(접속정보) — RULE 3.1 config 허용.
- 비교기: `app/eval/compare_retrievers.py` 또는 테스트가 `evaluate(rag_v1, FaissRetriever)` vs
  `evaluate(rag_v1, PgVectorRetriever)`를 돌려 Hit@3·평균 검색지연을 리포트.

## 원칙
- 무폴백: pg 접속 실패는 FAISS로 자동 대체하지 않고 명시 오류(백엔드는 명시 선택).
- 임베딩은 FAISS와 **동일 모델**(공정 비교). pgvector는 저장·검색만 담당.
- 비교는 정직: Hit@3가 같으면 "랭킹 동등"을, 지연/인덱싱 차이를 있는 그대로 리포트.

## 완료 후
- 비교 리포트 + Codex 초점 consult(무폴백·정규화·연결수명) + history/plan 갱신 → Phase 4(Hybrid+Rerank).
