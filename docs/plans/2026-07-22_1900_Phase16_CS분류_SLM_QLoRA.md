## 1. 목표

CS 문의를 7개 카테고리로 분류하는 **소형 생성형 모델(SLM)을 QLoRA로 파인튜닝**하고,
기존 LLM 프롬프트 기반 분류기(baseline) 대비 성능을 정량 비교한다.

**이 과제의 정직한 위상(Codex 검토 반영)**: 원본 60건 규모에서는 "성능이 개선됐다"는
**일반화 주장을 할 수 없다.** 본 Phase의 목표는 **QLoRA 파이프라인이 실제로 동작하고,
기존 기준선과 어떤 트레이드오프를 갖는지 불확실성과 함께 보고**하는 것이다.

**성공 기준**(단일 holdout 판정 금지):
1. 반복 교차검증에서 baseline 대비 Macro-F1 차이를 **분산·신뢰구간과 함께** 보고할 것
2. 어느 쪽이 이기든 **수치를 그대로 보고**할 것(유리한 분할을 고르지 않는다)
3. 동일 하드웨어·워밍업 조건에서 추론 지연을 측정해 함께 제시할 것

## 2. 이 과제를 고른 근거 (코드 실측)

| 조건 | 현황 | 의미 |
|---|---|---|
| 라벨 데이터 | `data/cs_inquiries.csv` 60건, `category_hint` 보유 | 즉시 학습 가능 |
| 라벨 체계 일치 | `app/prompts/templates.py::CATEGORIES` == csv의 7클래스 | **매핑 작업 불필요** |
| 기준선 존재 | `app/prompts/classifier.py::classify_one` (로컬 Gemma 프롬프트) | 개선폭 측정 가능 |
| 측정 함수 존재 | `app/prompts/classifier.py::measure_accuracy` | 평가 코드 재사용 |
| 이음매 존재 | `classify_one(text, chat_complete)` — `chat_complete` 주입형 | 모델 교체가 구조적으로 쉬움 |

7클래스: `결제 / 환불 / 상품문의 / 교환 / 배송 / 칭찬 / 불만`
(`app/ml/intent.py`의 6클래스는 **대화 의도**라는 별개 태스크 — 본 범위 아님)

## 3. 데이터 계획

### 3.1 현황 (실측)
- 60건 / 7클래스: 상품문의 13, 환불 10, 교환 9, 결제 8, 불만 8, 배송 7, 칭찬 5
- 본문 길이: 19~36자 (평균 29.9)
- **문제**: 절대량 부족 + 클래스 불균형(13 vs 5)

### 3.2 보강 전략 (3단)
1. **원본 60건** — 테스트셋 확보에 우선 배정(진짜 분포).
2. **증강** — 교사 LLM으로 패러프레이즈 생성, 클래스당 최소 30건까지 균형화.
   품질 필터: 생성문이 원 라벨과 모순되지 않는지 규칙·재분류로 교차 확인.
3. **외부 데이터** — AI Hub 민원상담/한국어 대화(승인 필요), KLUE-TC(즉시 가용).
   **AI Hub 승인 지연 대비**: HuggingFace 즉시 가용분을 1차 경로로 삼고, AI Hub는
   확보되면 보강한다. 승인 대기가 과제를 막지 않게 한다.

### 3.3 분할·검증 (개정 — 단일 holdout 폐기)

단일 holdout은 **쓰지 않는다**. 20% test = 12건이고 칭찬 클래스는 **1건**이라, 한 건만
틀려도 Macro-F1이 요동쳐 baseline과의 우열을 판단할 수 없다(Codex 지적).

- **원본 60건만으로 5-fold stratified CV**를 수행하고, **여러 seed로 반복**한다.
- fold별 **paired 차이**(같은 fold에서 baseline vs 파인튜닝)를 구해 **평균 ± 분산/신뢰구간**을 보고한다.
- **group 분할**: 증강문은 원본의 계보(lineage) ID를 갖고, **같은 원본에서 나온 문장은
  같은 fold**에만 들어간다.
- **증강은 train fold에만** 넣는다. valid/test fold에는 **원본만** 둔다.
- 외부 데이터(AI Hub/KLUE 등)를 쓸 경우 7클래스 매핑을 **수동 감사**한다 — 자동 매핑은
  라벨 오염 위험이 크다.
- 최종적인 "운영에서도 통한다"는 주장은 **별도로 확보한 미사용 데이터**로만 할 수 있다.
  본 Phase 범위에서는 그 주장을 하지 않는다.

## 4. 모델·학습

- **베이스 후보**: Qwen2.5-0.5B/1.5B-Instruct, LLaMA-3.2-1B-Instruct 중 택1
  (수업 GPU 사양 확인 후 확정. 한국어 성능·라이선스 함께 고려)
- **방법**: QLoRA (4bit 양자화 베이스 + LoRA 어댑터)
- **형식**: instruction SFT
  ```
  지시: 다음 고객 문의를 [결제/환불/상품문의/교환/배송/칭찬/불만] 중 하나로 분류하라.
  문의: {content}
  분류: {label}
  ```
- **산출물**: LoRA 어댑터만 저장(수백 MB 이하). **가중치는 커밋하지 않는다**(.gitignore).

## 5. 평가 (개정 — 저렴한 기준선 필수 추가)

| 항목 | 방법 |
|---|---|
| 지표 | Accuracy, **Macro-F1**(불균형이라 필수), 클래스별 혼동행렬 |
| 검증 | **반복 5-fold stratified CV**, fold별 paired 차이 + 분산/신뢰구간 (§3.3) |
| 부가 | 추론 지연(ms) — **동일 하드웨어·워밍업 후 측정**, 미분류(`UNCLASSIFIED`) 발생률 |

**비교 대상(4종)** — QLoRA만 단독 비교하지 않는다(Codex 지적):

1. **TF-IDF + 선형 분류기** — 가장 싼 기준선. 이걸 못 이기면 SLM을 쓸 이유가 없다.
2. **한국어 인코더 분류기**(KoELECTRA-small 등 head 파인튜닝) — 소량 데이터에 강한 정공법.
3. **LLM 프롬프트**(`classify_one`, 로컬 Gemma) — 현재 운영 기준선.
4. **QLoRA SLM** — 본 과제.

`measure_accuracy`를 재사용하되 Macro-F1·CV 집계·신뢰구간은 추가 구현한다.

> 이 4종 비교가 이 과제의 진짜 가치다. "SLM이 최고"가 아니라 **어느 지점에서 어떤 방법이
> 합리적인지**를 데이터로 보여주는 것이 리포트의 결론이 된다.

## 6. 통합 설계 (어디에 어떻게 꽂나)

- **이음매**: `ticket_graph.py`의 classify 단계는 `classify_one(content, chat_complete)`를
  호출한다. 파인튜닝 모델을 **`ChatComplete` 구현체**로 주입하면 그래프 코드는 무수정이다.
- **선택 방식**: 얼굴인식 백엔드 선택(`FACE_RECOGNITION`)과 같은 패턴으로
  `TICKET_CLASSIFIER=(prompt|finetuned)` config 도입 — 하드코딩 금지, 런타임 비교 가능.
- **분기 위치(Codex 지적)**: config 해석과 모델 로드는 **composition root**에서 하고,
  `classify_one` 내부에 백엔드 분기를 넣지 **않는다**. `classify_one`은 어떤 백엔드인지
  몰라야 한다(주입만 받는다) — 그래야 기존 Clean Architecture 경계가 유지된다.
- **무폴백**: 어댑터 파일이 없거나 로드 실패하면 **`ConfigError`로 명시 실패**한다.
  조용히 프롬프트 방식으로 되돌아가지 않는다(그것이 폴백).
- **학습 코드 위치**: 앱 런타임과 분리(`scripts/finetune/`). 앱은 추론만 한다.

## 8. 리스크 · 정직 기록

- **데이터 60건은 파인튜닝에 절대 부족**하다. 증강·외부 보강으로 메우지만, 그렇게 만든
  성능은 "실제 운영 분포에서의 성능"이 아니다. 리포트에 이 한계를 명시한다.
- **증강은 새 정보가 아니다**(Codex): 원본과 교사 모델의 표현·편향을 복제할 뿐이다.
  교사로 만든 데이터를 교사로 재검증하는 것도 **독립 검증이 아니다** — 품질 필터를
  "검증"이라 부르지 않는다.
- 외부 데이터의 **7클래스 매핑 오류·도메인 차이**가 증강보다 더 큰 위험이다 → 수동 감사 필수.
- 반복 CV를 쓰더라도 원본이 60건이라 **신뢰구간이 넓게 나올 것**이다. 넓으면 넓은 대로
  보고하고 "유의미한 개선"이라고 쓰지 않는다.
- 소형 모델이 baseline(더 큰 Gemma)을 못 이길 수 있다. **못 이기면 그대로 보고한다**
  — "졌지만 더 빠르고 작다"도 유효한 결과이며, 억지로 좋은 수치를 만들지 않는다.
- AI Hub 승인 지연 가능성 → HF 데이터 1차 경로로 회피(§3.2).
