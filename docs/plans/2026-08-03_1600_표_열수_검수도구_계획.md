2026-08-03 16:00 · 상위 [표추출 한계 5종](2026-08-03_1200_표추출_한계5종_해결계획.md) **L2**
· 근거 [find_multi_col 이 3열을 거의 못 만든다](../reports/debugs/2026-08-03_1500_find_multi_col이_3열을_거의_못만든다.md)

> ★**먼저 밝힌다 — 이 도구는 표 인식 정확도를 올리지 않는다.**
> 지금은 **잴 수가 없어서 못 고치는** 상태이고, 이 도구는 **자를 만드는 것**이다.
> 정확도는 이 자로 잰 뒤에 고쳐야 오른다.

---

## 0. 왜 필요한가

계획서 L2 가 *"3열 이상 표가 2열 경로로 간다"* 를 고치려 `find_multi_col()` 을 만들었고,
상태를 **"◐ 구현했으나 미검증 · 파이프라인 미연결"** · 사유 *"열 수 선택을 확인할 정답이 없음"*
으로 적어 두었다.

실측해 보니 **"미검증"이 아니라 "거의 발화하지 않는다"** 였다.

```
무작위 14문서 · 984쪽    k=0(실패) 832 · k=2 151 · k=3 1 · k≥4 0
```

원인은 셋이고, **셋 다 사람이 찍은 정답 없이는 못 고친다.**

| | 결함 | 왜 정답이 필요한가 |
|---|---|---|
| ① | `_grid_quality` 가 `mode/ncol` 때문에 **열이 늘수록 불리** | 벌점을 얼마나 깎을지 정할 근거가 없다 |
| ② | 통로 조합을 탐색하지 않음(`cands[:k]` 앞자르기) | 놓친 경계가 몇 %인지 모른다 |
| ③ | `kmax=5` → **6열 상한**. 그런데 7열 표가 실재 | 몇 열까지 필요한지 모른다 |

## 1. 무엇을 만들었나

```
scripts/eval/build_table_review.py     후보 추출 + 페이지 렌더 + HTML 생성
  → docs/review/table_review_YYYYMMDD.html   자기완결 (이미지 base64 내장)
```

```bash
python -m scripts.eval.build_table_review --docs 10 --limit 30 --min-quality 0.3
```

**첫 실행 결과**: 문서 3 · 쪽 125 → 카드 **30개** · 7.8 MB

### 화면 구성

```
┌ 원본 페이지 이미지 ─┬ 후보 격자 (점수 상위 3개, 열 수 라벨) ─┐
│                    │  [2열] 품질 0.83  · 12행                │
│   (110 DPI 렌더)   │  [3열] 품질 0.61  · 12행                │
│                    │  [4열] 품질 0.44  · 11행                │
└────────────────────┴────────────────────────────────────────┘
  어느 후보가 맞나   [2열][3열][4열]
  ★정답 열 수        [ 숫자 직접 입력 ]   ← 상한 없음
  □ 병합 셀이 있다   □ 표가 아니다(본문)
  메모               [                 ]
  [✓ 후보가 맞다] [✗ 후보에 정답이 없다] [? 애매하다]
```

### 설계에서 특히 신경 쓴 것 넷

**① 열 수를 고정해 보여주지 않는다.**
"2열/3열/4열 중 고르시오"로 물으면 **정답이 후보에 없는 경우를 못 잡는다.**
7열 표를 보여줘도 후보가 2~6열뿐이면 사람이 말할 방법이 없다.
→ **점수 상위 3개**를 열 수 라벨과 함께 보여주고, **정답 열 수는 숫자로 직접 적게** 한다.

**② "후보에 정답이 없다" 버튼.**
이 비율이 곧 **`kmax` 를 올릴 근거**이자 **통로 탐지가 놓친 비율**이다.

**③ "병합 셀이 있다" 체크.**
`_grid_quality` 의 `mode/ncol` 벌점이 **병합 셀 때문**이라는 가설을 가른다.
가설이 맞으면 벌점 식을 고치는 것이 답이고, 아니면 다른 곳을 봐야 한다.

**④ "표가 아니다(본문)" 체크.**
L4(2열짝짓기 과탐)의 **알려진 거짓** 집합이 여기서 공짜로 나온다.
[15번 의뢰서](../handoff/15_표_정답셋_라벨링_의뢰.md) A 항목과 같은 재료다.

### 운영 편의

- **localStorage 자동 저장** — 한 번에 다 안 해도 된다. 다시 열면 이어서
- **"다음 미완료로"** 버튼 · 진행률 표시
- 셀에 마우스를 올리면 **잘린 내용이 펼쳐진다**(표가 넓어도 읽을 수 있게)
- **"결과 내려받기"** → `table_review_labels_YYYYMMDD.json`

## 2. ★문턱을 낮추는 것의 성격

```
파이프라인 기본값   min_quality = 0.6
검수 도구 기본값    min_quality = 0.3
```

**이건 고치는 것이 아니라 재료를 만드는 것이다.**

문턱 0.6 에서는 984쪽에 후보가 1건이라 **검수할 것이 없다.**
0.3 으로 낮추면 볼 것이 생긴다. 그뿐이다.

★**이 상태로 파이프라인에 연결하면 안 된다.** 2열은 이미 통과선 위에 몰려 있어서
문턱만 낮추면 **2열 오탐이 같이 는다.** 스크립트 독스트링과 산출물 `_주의` 에 박아 두었다.

## 3. 라벨이 무엇을 결정하나

| 라벨 항목 | 결정하는 것 |
|---|---|
| 정답 열 수 분포 | **`kmax` 상한** — 7 이상이 나오면 올려야 한다 |
| "후보에 정답이 없다" 비율 | **통로 탐지·조합 탐색**(결함 ②)을 고칠지 |
| 병합 셀 ↔ 품질 점수 상관 | **`mode/ncol` 벌점**을 어떻게 고칠지(결함 ①) |
| 맞은 후보의 품질 점수 분포 | **문턱을 어디에 둘지** — 지금 0.6 은 근거 없이 정해진 값이다 |
| "표가 아니다" | L4 과탐 판별기의 **알려진 거짓** |

★**지금은 `consistency` 와 `mode/ncol` 이 한 곱셈에 섞여 있어 무엇 때문에 떨어졌는지 알 수 없다.**
라벨이 모이면 둘 중 어느 것이 진짜 판별력이 있는지 나뉜다.

## 6. ★이 작업의 위치 — 지금 판정에는 영향이 없다

확인한 사실:

```python
# app/core/usecases/precheck.py
for m in kcd.scan_clause(c.text):      # ← 조항 **본문 텍스트**
```

**판정 경로는 표를 전혀 쓰지 않는다.** KCD 코드를 조항 텍스트에서 뽑는다.
표가 필요한 것은 **자기부담금·장해지급률 같은 수치**인데, 그건 L3(스키마 설계)가 미착수라
아직 판정에 연결도 안 돼 있다.

→ **표 인식을 고쳐도 오늘의 판정 정확도는 안 바뀐다.** L3 가 붙었을 때를 위한 선행 작업이다.
그 사실을 알고 우선순위를 정해야 한다.
