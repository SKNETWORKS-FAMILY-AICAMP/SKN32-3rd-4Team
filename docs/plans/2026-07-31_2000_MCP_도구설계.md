## 1. 도구는 **굵게 3개**

| 도구 | 책임 | 내부 단계 |
|---|---|---|
| `insurance_precheck` | 케이스 생성 → KCD 확인 → 사전판정 | 후보조회 → **사용자 선택 대기** → 약관버전 확정 → 규칙판정 |
| `claim_cohort_query` | 유사 코호트 통계 | 매칭키 결정 → 최소표본·프라이버시 게이트 → 반환 |
| `claim_evidence` | 증빙 업로드·제출·검수상태 | 업로드 초기화 → 제출 확정 → 상태 조회 |

**왜 얇게 8~10개로 쪼개지 않나** — 얇으면 **불변식을 에이전트에게 맡기게 된다.**
KCD 확인 없이 판정을 부르거나, 약관버전 미확정 상태로 판정하는 **불법 순서가 가능해진다.**
반대로 만능 도구 하나면 증빙 쓰기 권한과 통계 읽기 권한을 분리할 수 없다.

빠진 흐름은 도구를 늘리지 않고 `operation` 파라미터로 흡수한다
(`start` / `confirm_and_assess` / `get_status` / `init_upload`).

## 2. 다단계 상태 — 서버 발급 `case_id`

```
start                          → case_id, revision=1, selection_request_id
confirm_and_assess(case_id, expected_revision=1)  → revision=2, assessment
claim_cohort_query(case_id)
claim_evidence(case_id)
```

서버에 저장하는 것은 **대화 기록이 아니라 도메인 상태**다(상품·가입일·사고일·특약, 제시한 후보,
사용자 선택 provenance, 적용 약관버전, 판정과 근거, 증빙 사실).
동시 호출은 `expected_revision`으로 `ConflictErr`, 재시도 중복은 `(principal_id, idempotency_key)`로 막는다.

> 프로세스 메모리 세션에 상태를 두면 서버 재시작·다른 전송 채널에서 흐름이 끊기고,
> 감사·재현·삭제가 불가능해진다.

## 3. ★에이전트에게 "사용자 확인"을 요구하는 법

질병명→코드는 1:N이라 **에이전트가 대신 고르면 안 된다.** 그런데 호출자는 사람이 아니다.
→ 첫 응답을 **정상 결과이면서 행동 요청**으로 표현한다(오류가 아니다).

```json
{
  "status": "awaiting_user_selection",
  "abstained": true,
  "abstain_reason": { "code": "USER_SELECTION_REQUIRED" },
  "result": { "requires_user_action": true, "selection_request_id": "…", "candidates": [] }
}
```

그리고 **에이전트가 사람에게 물었다는 것을 우리가 검증할 수는 없다.** 그래서 그대로 기록한다:

| 필드 | 값 |
|---|---|
| `selected_by` | `end_user` |
| `confirmation_method` | `agent_attestation` |
| `verification_status` | **`unverified`** |

> 서버 nonce는 "올바른 단계의 응답"임을 증명할 뿐 **"사람이 눌렀다"를 증명하지 못한다.**

## 4. 오류 vs abstain — 에이전트가 구분할 수 있어야 한다

| 상황 | MCP 표현 | 재시도 |
|---|---|---|
| 알 수 없는 도구·깨진 호출 | JSON-RPC protocol error | 요청 수정 |
| `ValidationErr` · `NotFoundErr` · `ConfigError` | `isError=true` | 입력·설정 수정 후 |
| `InfraError` | `isError=true` + `retry_after` | 제한적 재시도 |
| **근거 부족 · 소표본 · 선택 대기** | **성공**(`isError=false`) + `abstained=true` | 조건 충족 후 |

★**abstain을 오류로 만들면 에이전트가 무한 재시도**하고, **오류를 성공 JSON으로 감추면
실패를 정상 판정으로 전달**한다. 둘 다 흔한 실수다.

## 5. REST ↔ MCP parity — 래퍼가 아니다

```
REST adapter ─┐
              ├─→ 동일 유스케이스 · 동일 결과 DTO → app/core
MCP adapter  ─┘
```

MCP가 REST를 HTTP로 재호출하면 인증 주체 전달·직렬화·오류 매핑·타임아웃·관측이 **이중화**되고
내부 HTTP 장애가 새로 생긴다. 두 어댑터가 같은 유스케이스를 부르고 **계약 테스트로 parity를 강제**한다.

기존 커머스 MCP 자산 판정: FastMCP 스키마 생성·`structuredContent` 우선·`AppError` 미삼킴은 **재사용**,
도구별 직접 DB 세션·legacy service import·호출마다 subprocess 기동·nonce 문자열로 오류 복원은 **폐기**.
새 코드는 `app/outer/inbound/mcp/`에 두고 `app/core` 유스케이스만 호출한다.

## 6. 인증·남용 방지

scope를 도구가 아니라 **부작용 단위**로 나눈다:
`insurance:precheck` / `cohort:demo:read` / **`cohort:real:read`** / `evidence:write` / `evidence:status:read`

- 토큰 `aud` 검증, **받은 토큰을 하위 서비스로 그대로 전달하지 않는다**
- ★**실제 코호트는 자유 필터 금지** — `case_id` 기반 사전 정의 매칭만 허용
- 작은 셀은 **정확한 `n`까지 숨긴다**
- 동일·인접 필터 반복 조회에 **누적 privacy budget** 적용
- rate limit만으로 부족하다 — **"결과 차이를 이용한 추론" 패턴을 감사로그로 탐지**
- 인증 실패는 도구 오류가 아니라 **HTTP 경계의 401/403** (도구까지 들어오면 이미 메타데이터가 샌다)

## 7. "당신은 로봇입니까?" — 도입해도 된다

**자발적·비차단 설문이면 문제없다.** 처음 반대 사유("주 고객인 에이전트를 차단한다")는
차단이 아니라는 전제에서 사라진다. 문제는 **이 값을 검증된 판별값으로 쓰는 것**이다.

### 조건

- 선택 사항이며 `prefer_not_to_say` 제공 · **미응답·AI 선택에 어떤 차등도 없음**
- CAPTCHA·행동탐지와 연결하지 않음 · **인증·레이트리밋·부정사용 판정에 사용 금지**
- 보존기간·삭제 경로 · 대시보드에 **항상 "미검증 자기선언" 표시**

### 문구

> "당신은 로봇입니까?" 대신
> **"이 요청을 수행하는 클라이언트 유형을 선택해 주세요 —
> 사람용 웹 브라우저 / AI 에이전트 / 기타 자동화 클라이언트 / 응답하지 않음"**

### ★저장 — `is_ai` boolean을 만들지 않는다

검증된 고정 신원처럼 보이기 때문이다. **append-only 선언 사건**으로 쌓고 네 축을 분리한다
(`app/core/domain/actor.py`에 구현):

| 축 | 값 |
|---|---|
| 무엇이라 주장했나 | `human_browser` / `ai_agent` / `automated_system` / `other` / `prefer_not_to_say` / `unknown` |
| 누구를 대리하나 | `human_end_user` / `organization` / `self_operating_agent` / `unknown` |
| 근거 | `self_declaration` / `authenticated_client_metadata` / `inferred` / `none` |
| 검증됐나 | `unverified` / `verified` |

행동 추정은 **별도 테이블**(`ops.actor_inference`)에 둔다. 자기선언과 추정을 같은 컬럼이나
우선순위 로직으로 **합치지 않는다.**

> ★초안 포트 `classify() -> "declared"|"inferred"|"unknown"` 은 **'무엇이라 주장했나'와
> '근거가 무엇인가'를 한 값에 섞고 있었다.** Codex 지적으로 `ActorDeclarationPort`로 교체했다.

### 채널 — 웹 체크박스는 주 채널이 아니다

| 채널 | 선언 방식 |
|---|---|
| MCP | 초기화/요청 `_meta`의 namespaced 필드 |
| REST | 전용 구조화 헤더 또는 인증 client metadata |
| A2A | Agent Card의 agent identity |
| 웹 | 체크박스 |
| `User-Agent` | **선언이 아니라 추정 보조자료** |

> MCP `clientInfo`는 소프트웨어 이름·버전을 알려줄 뿐,
> **그 요청을 AI가 자율 수행했는지 사람이 수동 조작했는지는 증명하지 않는다.**

### 대시보드 — "AI 사용자 30%" 카드를 만들지 않는다

| 지표 | 예 |
|---|---|
| 전체 요청 | 10,000 |
| 선언 응답률 | 40.0% |
| 전체 요청 중 AI 자기선언 | 12.0% |
| 선언 응답 중 AI 자기선언 | 30.0% |
| 근거 | 자기선언, **미검증** |

문구: **"전체 요청의 12.0%가 AI 클라이언트라고 자기선언했습니다.
선언 응답률은 40.0%이며, 이 정보는 검증되지 않았습니다."**

★에이전트는 호출량이 많으므로 **요청 수 비율을 사용자 수 비율로 바꾸면 안 된다.**
`요청` / `고유 OAuth client` / `고유 세션`을 각각 분리한다.

## 8. 한계

- 이 문서는 설계이며 구현이 없다. MVP 대상은 도구 3종 + 응답 봉투 + 오류 규약이다.
- OAuth·privacy budget·추론 패턴 탐지는 **MVP 범위를 넘는다.** 무엇을 뒤로 미뤘는지 명시해 둔다.
