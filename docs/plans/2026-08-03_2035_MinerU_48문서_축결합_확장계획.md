# MinerU 48문서·3쪽 창 축 결합 확장 계획

- 작성: 2026-08-03 20:35 KST
- 선행 계획: `2026-08-03_1850_오프라인_OCR_SOTA5_벤치마크_계획.md`
- 선행 실측: `../reports/2026-08-03_2010_오프라인_OCR_SOTA5_x600_실측.md`
- 범위: 자기부담금 업무 후보의 구조 회수, 축 결합, 검증 및 확대 게이트 수립
- 안전: 모든 신규 산출물은 `candidate/shadow`이며 serving·citation·승인 포인터에 연결하지 않는다.

## 1. 결론과 이번 차수의 질문

7쪽 예비실험에서는 MinerU2.5-Pro가 가장 안정적이었다. 이번 차수는 모델 5종을 다시 순위화하지 않고,
MinerU를 실제 주 추출기 후보로 올렸을 때 기존 방식보다 나은 업무 fact를 만들 수 있는지 검증한다.

> 48개 서로 다른 원문에서 앞·현재·뒤 3쪽을 함께 보존했을 때,
> `plan × service × institution × coverage × amount/formula × source_bbox`를
> 재현 가능하게 만들고 위험한 결과를 자동 차단할 수 있는가?

“완벽”은 오류가 없다고 선언하는 뜻이 아니다. 실패가 누락되지 않고, 같은 입력에서 같은 결과를 만들며,
검증되지 않은 fact가 운영으로 새지 않는 상태를 완료 기준으로 삼는다.

## 2. 기존 방식과 달라지는 점

1. `2열짝짓기` 후보의 k×n 조합을 저장하지 않는다.
2. 페이지를 MinerU가 다시 구조화하고 HTML의 rowspan/colspan을 논리 격자로 확장한다.
3. 금액·비율이 있는 행만 찾고 그 행으로 이어지는 header path만 계산한다.
4. 페이지 경계의 누락 축은 앞·뒤 페이지 문맥으로 **후보 보완**하되 `inferred=true`로 차단한다.
5. 모든 fact에 원문 이미지 SHA256, 페이지, 표 bbox, HTML 행을 남긴다.
6. 문자·금액·축·출처 validator를 통과하지 못하면 자동 승인하지 않는다.

## 3. 평가 패킷

### 3.1 표본 단위

- 서로 다른 PDF SHA 48개
- 문서당 자기부담금 후보 중심 페이지 1개
- 중심 페이지의 이전·현재·다음 페이지를 렌더링한 3쪽 창
- 최대 144페이지. 문서 첫/끝 페이지는 실제 존재 페이지만 포함
- 원격에는 SHA 이름의 PNG, 비식별 manifest, 실행 코드만 전송

### 3.2 층화 축

- 보험사: 가능한 한 12개 보험사 모두 포함
- 실손 세대: `config/generation_profiles.json`의 검토된 날짜 경계를 보조 제약으로 사용
- 상품군: 일반·노후·유병력자/간편·전환용 후보
- 조판: 기존 `선`/`2열짝짓기`, 열 수, 행 수, 상단/하단 표, 연속 페이지
- 기존 결과: `is_table=true/false/null`, 현재 후보 성공/보류

기존 결과에 조건화된 표본 편향을 막기 위해 48문서는 다음 세 층을 각각 16문서로 고정한다.

- `missed`: 업무 키워드는 있으나 현재 페이지의 `tables`와 `tables_coords`가 모두 0개인 미탐 후보
- `withheld`: 표 후보는 있으나 전부 `is_table=false/null`인 보류·거절 후보
- `accepted`: 기존 `pages[].tables`가 비어 있지 않거나 하나 이상의 `is_table=true` 표 후보가 있는 기존 수락 후보

기존 7쪽은 모델 선정에 이미 사용했으므로 회귀셋으로만 쓰며 48문서 holdout에서 제외한다.

상품명 marker는 일부 미검수이므로 표본 설명용으로만 쓰고 정답 라벨로 쓰지 않는다.

## 4. 출력 계약

각 fact 후보는 최소 다음 필드를 가진다.

```json
{
  "candidate_id": "sha256:...",
  "document_sha12": "...",
  "page_1based": 26,
  "table_bbox": [0.162, 0.157, 0.865, 0.870],
  "html_row_index": 4,
  "plan": "표준형",
  "service": "처방조제비",
  "institution": "약국 ...",
  "coverage": ["급여", "비급여"],
  "amount_formula": "8천원과 ... 20% 중 큰 금액",
  "amount_tokens": ["8천원"],
  "rate_tokens": ["20%"],
  "inferred": false,
  "validation": {"status": "review", "reasons": []},
  "serving_eligible": false
}
```

candidate ID는 의미 필드와 근거 위치의 정규화 JSON SHA256으로 만든다.

## 5. 지표와 판정

### 자동 산출

- 문서/페이지 처리 성공률, cold/warm latency, peak VRAM
- HTML 표 생성률과 bbox 보존율
- 금액/비율 token 추출률
- 완전 축(`plan/service/amount/source`) 후보율
- 페이지 경계 `inferred` 비율
- 문자 위험(`I↔1`, `O↔0`, 비한글 CJK), 중복 출력, 빈 축 비율
- 검수 큐 유입률과 자동 차단 사유 분포

### 성능 주장 제한

- 현재 48문서에는 행·열 결합 정답셋이 없으므로 자동 지표만으로 precision/recall 향상을 주장하지 않는다.
- `precision 99.5%에서 fact recall`은 사람이 승인한 gold가 생긴 뒤 계산한다.
- 이번 차수의 채택 판정은 **실행 가능성·근거 보존·검수 가능성**과 기존 7쪽 gold/silver 회귀로 제한한다.

### 확대 게이트

- 144페이지 프로세스 성공률 98% 이상
- 성공 표의 bbox 보존율 100%
- candidate fact의 `serving_eligible=false` 100%
- 기존 KCD 22쌍에서 문자 치명 오류 증가 0
- 기존 자기부담금 6쪽의 알려진 금액 token 회귀 0
- 48문서 검수 gold를 2인이 독립 라벨하고 불일치를 합의하며 IAA를 보고할 것
- 사람 검수 기준 금액·비율 오결합 0건, cross-page 오결합 0건, 핵심 축 결합 오류 0건
- 고정 이미지 2회 실행의 정규화 출력과 candidate ID가 일치할 것
- 운영 인덱스·릴리스 경로가 `data/eval/ocr_shadow48/`을 읽지 않는 격리 테스트가 통과할 것

위 조건을 모두 통과하면 별도 200페이지 검수 게이트 계획을 만든다. 200→800~1,000페이지는
새 표본의 결합 오류율과 실패 disposition을 다시 승인하기 전까지 잠근다. 대규모 확대 전에는
109,192·109,421·162,170으로 혼재한 후보 분모도 같은 추출기·시점·단위로 재산출한다.

## 7. 중단 조건

- 공용 GPU에 다른 사용자의 계산이 있으면 새 추론을 시작하지 않는다.
- 동일 입력 2회 OOM 또는 30분 초과 시 임의 설정 탐색을 중단하고 실패로 기록한다.
- 원문 SHA 또는 이미지 SHA가 맞지 않으면 해당 결과를 폐기한다.
- bbox가 없거나 cross-page로 추정한 값은 자동 승인하지 않는다.
- 정답셋 없이 precision/recall 또는 “기존 대비 향상” 수치를 확정하지 않는다.
