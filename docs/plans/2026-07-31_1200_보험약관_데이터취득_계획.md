`scripts/crawl/check_robots.py`로 19개 호스트 점검. **조회만 했고 약관 PDF는 내려받지 않았다.**

| **확인불가(금지 취급)** | **3** | 한화생명·교보생명·DB생명 |

### 집계처 3곳 — ★Codex 권고가 막힌다
| 대상 | 판정 |
|---|---|
| 생명보험협회 공시실 `pub.insure.or.kr` | **금지**(robots에 Disallow 명시) |
| 손해보험협회 공시실 `kpub.knia.or.kr` | 확인불가 |

Codex는 "협회 공시를 1차 카탈로그로"라고 권했으나, **생보협회 공시실은 robots에서 금지**하고
손보협회·파인은 확인이 안 된다. → **현 시점에서 집계처 자동수집 전략은 성립하지 않는다.**

### 판정 근거는 어디에 있나 (재현·반박 가능해야 한다)

| 자료 | 위치 | 내용 |
|---|---|---|
| **robots.txt 원문** | `docs/reports/2026-07-31_robots_raw/<호스트>.txt` | ★판정의 **직접 근거**. 출처 URL·수집시각(UTC)·HTTP 상태·sha256 헤더 + 원문 무수정 |
| 판정 표 | `docs/reports/2026-07-31_robots_점검.md` | 사람이 읽는 요약 |
| 판정 요약(기계) | `docs/reports/2026-07-31_robots_점검.json` | 프로그램 판독용 |
| 점검 도구 | `scripts/crawl/check_robots.py` | 재실행하면 위 3종이 다시 생성된다 |

예시 — 두 판정의 실제 근거:

```
# www.samsungfire.com  (허용)
User-agent: *
Allow: /

# pub.insure.or.kr  (금지) — 네이버(Yeti)·다음(daumoa)만 예외
User-agent:*
Disallow:/
```

> 판정 결과만 남기면 "왜 허용인가"를 나중에 증명할 수 없다. 이 원칙(원본·해시·수집시각 불변 저장)은
> 처음에 PDF 수집기에만 적용하고 점검 도구에는 빠뜨렸다가, **사용자 지적으로 보완**했다.

### 정직 기록 — 이 결과의 한계
- `확인불가` 5건은 DNS는 해석되나 TLS 연결이 실패했다. **사이트 차단인지 우리 망(방화벽) 제약인지
  구분할 수 없다.** 다른 네트워크에서 반드시 재점검해야 한다.
- ★**점검 도구의 결함을 실측으로 발견해 고쳤다**: 1회 시도만 했을 때 현대해상이 `확인불가`로
  나왔으나 재시도하니 HTTP 200이었다. **일시적 오류를 영구 판정으로 굳히면 잘못된 결론이
  문서에 남는다** → 3회 백오프 재시도를 추가했고, 허용이 12→13으로 정정됐다.
- **robots 통과는 수집 허가가 아니다.** 이용약관·저작권·재배포 조건은 별도 확인 사항이다.

## 3. 수집 원칙 (Codex 설계 채택)

| 원칙 | 내용 |
|---|---|
| **확인불가 = 금지** | RFC 9309. "응답이 없으니 일단 긁자"는 폴백이다 |
| **식별 가능한 UA** | 위장 금지. 연락처 포함 |
| **저속·백오프·킬스위치** | 호스트별 지연, 업무시간 회피, `ETag`/`Last-Modified` 활용 |
| **원본 불변 저장** | 원본·해시·URL·수집시각·응답상태를 그대로 보존 |
| **불확실 문서 격리** | 자동 확정하지 않고 `Unidentified`/`Ambiguous`로 분리 후 사람 검증 |

### 절대 하지 않을 것
CAPTCHA·인증·차단 우회 · UA 위장 · 무제한 병렬 수집 · **불확실 문서의 자동 확정** ·
**현행 약관을 가입 시점 약관으로 대체** · 권리 확인 없는 원문 재배포

## 4. '수집'보다 '식별'이 어렵다

PDF를 받아오는 건 쉬운 부분이다. 어려운 것은:

> 이 PDF가 **어느 보험사·어느 상품·몇 세대·시행일 언제·판매기간 언제**의 약관인가?

같은 파일을 받아도 **사용자의 계약에 적용되는 약관인지 모르면 쓸모가 없다.**

```
수집(Fetch) → 식별(Identify) → 버전 매니페스트 → 색인
                   ↑ 여기가 진짜 작업
```

식별 설계(Codex): 표지·상품코드·목차·본문 문구를 **교차 추출**해
`보험사/상품/세대/문서종류/valid_from/valid_to/revision` 후보를 만들고,
**모순되거나 후보가 복수면 `Ambiguous`로 격리**해 사람이 확정한다. 그 뒤 계약일 구간과 조인한다.

이 메타는 기존 **신선도 게이트 매니페스트**에 `insurer·product·generation·sales_period·
license·redistributable`을 추가하면 그대로 쓸 수 있다.

## 5. 포트 설계 (Application 계층은 프레임워크 무의존 유지)

| 포트 | 책임 |
|---|---|
| `CatalogSource` | 어떤 문서가 존재하는지 목록화(협회·보험사) |
| `ArtifactFetcher` | 실제 파일 취득(robots·지연·재시도·해시) |
| `DocumentIdentifier` | 이 문서가 무엇인지 판정 → 확정 or `Ambiguous` |

오류는 삼키지 않고 타입으로 전파한다(`ConfigError`/`InfraError`/`ValidationErr`).
**흔한 실패**(Codex): 최신판으로 조용히 대체 · 예외 삼키기 · URL 기준 중복제거 ·
OCR 실패 무시 · **셀렉터를 도메인 규칙으로 오인**.

## 5-1. ★돌파 방법 (2026-07-31) — 다른 사이트에도 같은 순서로

정적 크롤링 0건 → JS 렌더링 → **데이터 엔드포인트 직접 호출**로 뚫렸다.

```
1. 홈페이지를 렌더링해 '약관찾기/공시실' 링크를 찾는다   → /vh/page/VH.HPIF0103.do
2. 그 페이지를 열고 네트워크 요청을 관찰한다              → POST /vh/data/VH.HDIF0103.do
3. 화면을 긁지 않고 그 엔드포인트를 직접 호출한다          → 빈 POST 한 번에 9,404건
```

**화면 자동조작이 아니라, 사이트가 자기 화면을 그릴 때 쓰는 데이터를 그대로 받는다.**
HTML 셀렉터에 의존하지 않아 화면 개편에 잘 견딘다. 응답에 `saleStDt`/`saleEnDt`가 있어
**약관 버전의 적용 구간이 그대로 나온다** — ERD의 `policy_version`에 바로 대응된다.

### 6-1. S6 시범 수집 결과 (2026-07-31)

| 항목 | 값 |
|---|---|
| 대상 | 삼성화재 실손의료비보험 약관 (robots 허용 확인 호스트) |
| 출처 | `https://www.samsungfire.com/publication/pdf/ZPB293050_0_20250101_file1.pdf` |
| 결과 | HTTP 200 · **2,326,191 바이트** · sha256 `968e67f4d3b6…` |
| 내용 검증 | **134쪽 / 추출 텍스트 244,314자** — 표지 "실손의료비보험 무배당 삼성화재 보험약관 (2501.5)", 본문에 실손 336회·통원 150회·입원 153회·비급여 116회 → **실제 실손 약관이 맞다** |
| 식별 상태 | `unidentified` — **받았다는 이유로 무엇인지 안다고 하지 않는다.** 세대·시행일·판매기간 확정은 별도 식별 단계 |
| 원문 취급 | `data/raw/insurance_terms/`에 저장하고 **gitignore로 커밋 제외**(저작물·재배포 금지). 커밋되는 것은 `fetch_manifest.jsonl` 메타데이터뿐 |

수집기(`scripts/crawl/fetch_pilot.py`)는 **매번 robots를 재확인**하고, 확인 실패·금지면 받지 않고
`InfraError`로 명시적 실패한다. 사이트를 크롤링하지 않고 **사람이 확인한 URL만** 받는다.

**참고 — 이 1건이 보여주는 규모감**: 약관 1건이 24만자다. 현재 커머스 코퍼스 전체가 2,086자였으니
**약관 1건만으로 기존 코퍼스의 117배**다. 즉 코퍼스 규모 문제는 약관 몇 건으로 해소되지만,
**그것이 코어(실제 지급 결과)를 대신하지는 않는다**(§0).

## 7. 부트캠프 현실 배분

| 데이터 | 방법 |
|---|---|
| 약관 4·5세대 | 허용 확인된 보험사에서 수집 — **여기부터** |
| 약관 1~3세대 | 구하기 어려움 → **합성 약관으로 대체하고 그 사실을 명시** |
| 사용자 계약 | 폼 입력(가장 안전). 증권 업로드는 익명 샘플 시연만 |
| 진료·청구 사실 | 사용자 입력 + 합성 케이스 |
| 분쟁사례 | **쟁점 5~7개 × 3~5건 수동 구조화**(무작위 300건보다 쟁점 커버리지) |
| **실제 결과** | **합성 + 물리 분리**(v4.0 §5-1). 실제 통계라고 절대 말하지 않는다 |

## 8. 한계 (정직 기록)

- ★**정정(2026-07-31, Codex 지적)**: 이 항목은 원래 "약관 PDF를 한 건도 내려받지 않았다"였다.
  §6-1에서 S6 시범 수집 1건을 기록하면서 이 문장을 고치지 않아 **같은 문서 안에서 모순**이 났다.
  현재 상태는 **시범 수집 1건 완료**이며, 확대 수집(S7)은 S5 이용약관 확인 전까지 하지 않는다.
  — 계획서가 실제 상태와 어긋나면 그 자체가 우리가 막으려는 실패다.
- robots 판정은 **2026-07-31 시점·이 네트워크 기준**이다. 변경될 수 있고, 확인불가 5건은
  우리 망 제약일 가능성이 있다.
- **robots 허용 ≠ 수집·재배포 허가.** 저작권·이용약관 검토는 별도이며 본 문서가 대신하지 않는다.
- 협회 공시 전략이 막혔으므로 **보험사 개별 수집**에 의존해야 하는데, 이는 사이트별 구조가
  달라 유지보수 부담이 크다. 셀렉터가 깨지는 것을 **도메인 규칙 변경으로 오인하지 않도록**
  수집 실패를 명시적 오류로 남긴다.
