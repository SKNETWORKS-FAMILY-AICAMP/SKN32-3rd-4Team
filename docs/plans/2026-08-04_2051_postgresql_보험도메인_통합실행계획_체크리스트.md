## 1. 합의한 기준선 — 사용자에게 설명한 내용 그대로

현재 기준으로 “DB 구현 + PostgreSQL 연결 + 실제 보험 흐름 연결”까지는 원래 약 **3~5일** 규모다.

- PostgreSQL 스키마 완성: **0.5~1일**
  - `core`, `app`, `ops` 전체 테이블
  - FK, 인덱스, 검증 제약조건
  - 마이그레이션 실행 검증
- SQLAlchemy 모델/Repository 연결: **1~1.5일**
  - `subject → policy_holding → case`
  - `assessment → claim → outcome → evidence`
  - `consent`, `interaction_log`, `audit_log`
- 기존 API를 PostgreSQL 저장 흐름으로 전환: **1~2일**
  - `/v1/prechecks`
  - 관찰 결과/청구 결과 저장
  - evidence verification
  - cohort 통계 조회
  - agent interaction 기록
- 테스트/데이터 마이그레이션/운영 설정: **0.5~1일**
  - Docker/PostgreSQL 실행
  - 기존 SQLite 커머스 기능 회귀 테스트
  - PostgreSQL 통합 테스트
  - seed 및 readiness 체크

기존 스키마·코드·문서·pgvector 어댑터를 최대한 재사용하고 SSH 3대를 병렬로 사용하면 전체를 약 **1.5~2.5일**로 단축하는 것이 현실적인 목표다. PostgreSQL 연결과 API 통합은 순차 의존성이 있어 컴퓨팅 자원만으로 정확히 3배 단축되지는 않는다.

Claude 교차검토에서 판본 교차 인용 방지와 검증 상태전이 보강에 S1 약 0.5일이 추가로 필요하다고 확인했다. 따라서 실행 기준 일정은 여유를 포함해 **2~3일**로 보정한다. P0 보정이 한 migration에서 끝나고 기존 PG 자산을 그대로 재사용할 수 있으면 2일 목표를 유지한다.

권장 병렬 구성은 다음과 같다.

- 로컬 제어면: PostgreSQL/마이그레이션, ORM, 핵심 API 연결
- SSH 작업자 A: 기존 보험 문서·clause 데이터 적재 리허설
- SSH 작업자 B: 임베딩/pgvector 인덱스 및 검색 대조
- SSH 작업자 C: 데이터 검증·seed·통합 테스트

단계별 예상은 다음과 같다.

1. PostgreSQL 기동 및 스키마 적용: **2~4시간**
2. 기존 코드와 ORM/Repository 연결: **4~8시간**
3. 핵심 보험 흐름 `subject → policy_holding → case → assessment` 연결: **4~6시간**
4. `claim/evidence/verification/cohort` 연결: **4~8시간**
5. 원격 적재·임베딩·통합검증: 병렬 **4~8시간**

첫날 목표는 PostgreSQL 연결, `core/app/ops` 마이그레이션, 기존 SQLite 회귀 보존, 보험 케이스 1건 저장·조회다. 이후 원격 3대에서 데이터 적재·검증을 병렬 수행하는 동안 API와 검증 흐름을 연결한다.

- [ ] 전체 CI + PostgreSQL 통합 테스트 + API smoke
- [ ] 결과 리포트와 history 갱신

완료 게이트: 재기동·장애·롤백을 포함한 운영 리허설이 통과한다.

## 6. SSH 3대 병렬 운영 계획

원격 작업은 로컬 제어면의 스키마 결정을 앞질러 같은 DB를 동시에 변경하지 않는다. 모든 작업자는 시작 전 현재 프로세스·CPU·GPU·디스크·코드 revision을 확인한다.

| 작업자 | 주 작업 | 산출물 | 금지 |
|---|---|---|---|
| 로컬 | migration/ORM/API 통합, 최종 merge·검증 | 코드·migration·집중 테스트 | 검증 전 운영 컷오버 |
| SSH A | 빈 PostgreSQL 적용·권한·무결성 테스트 | schema/owner/privilege 결과 | 공유 DB에 임의 DDL |
| SSH B | 파일→PG 적재 dry-run, count/hash/drift 대조 | manifest·대조표 | 실제 트랙에 합성 seed |
| SSH C | pgvector/profile/search 회귀와 전체 테스트 | 검색 대조·pytest 결과 | model/profile 불일치 적재 |

병렬화 규칙:

- [ ] `remote_who` 또는 동등한 점검으로 자원 선점 여부 확인
- [ ] 세 작업자 모두 동일 commit/revision과 schema migration checksum 사용
- [ ] 입력과 출력에 SHA/manifest 기록
- [ ] 같은 PostgreSQL DB에 migration을 동시 적용하지 않음
- [ ] 원격 결과는 count/hash/test log를 확인한 뒤 로컬에서 채택
- [ ] 임베딩은 기존 profile이 유효하면 재계산하지 않고 검증만 수행

## 7. 테스트 매트릭스

- [ ] 단위: repository, 상태 전이, masking, 멱등성
- [ ] SQLite 회귀: 기존 빠른 테스트와 커머스 잔재 영향 확인
- [ ] PostgreSQL 통합: fresh apply, FK/CHECK/trigger/function/privilege
- [ ] API: precheck, observation, verification, cohort, consent, interaction
- [ ] 데이터: count, SHA, manifest, real/demo 격리, core drift
- [ ] 검색: file/PG 결과, citation eligibility, embedding profile
- [ ] 장애: DB down, schema stale, extension missing, role 부족, partial transaction
- [ ] 운영: 재기동, migration 재실행, rollback rehearsal

## 8. 완료 정의

- [ ] `core/app/ops`가 빈 PostgreSQL에서 전량 생성되고 재실행이 멱등이다.
- [ ] 보험 케이스 1건이 사전검토부터 인용까지 DB에서 추적된다.
- [ ] 지급 결과는 verified 전에는 코호트에 반영되지 않는다.
- [ ] 합성·실제 데이터와 DB가 물리적으로 섞이지 않는다.
- [ ] DB 장애를 SQLite/file 결과로 위장하지 않는다.
- [ ] 권한·보존·동의·감사 제약이 DB와 코드 양쪽에서 검증된다.
- [ ] 기존 SQLite 기반 회귀 테스트와 PostgreSQL 통합 테스트가 함께 통과한다.
- [ ] 계획서 체크박스, 작업 리포트, history, 운영 복구 절차가 최신이다.

## 9. 중단·재논의 조건

- 기존 적용 migration의 checksum을 바꿔야만 진행할 수 있는 경우
- 이미지 명칭과 정본 명칭 중 어느 것을 외부 계약으로 노출할지 결정이 달라지는 경우
- 실제 개인정보/청구 데이터를 넣기 위한 법적 동의·보존 정책이 없는 경우
- 두 DB의 core 동기화 방법 없이 citation FK를 약화해야 하는 경우
- 기존 PG 데이터의 embed profile·schema generation을 재현할 수 없는 경우
- 다른 작업자의 변경과 동일 파일·동일 migration 번호가 충돌하는 경우

## 10. Claude CLI 교차검토 기록

검토일: 2026-08-04  
방법: 계획서와 `001~004`, `apply.py`, DB 핸드오프를 읽기 전용으로 직접 대조  
절차 기록: 첫 호출은 2분 제한에 걸려 출력 없이 종료됐다. 읽기 범위와 출력 길이를 제한한 두 번째 호출은 97.3초에 완료됐다.

### 지적과 판단

- [x] **채택 — 판본 교차 인용 P0.** 004에는 citation의 `policy_version_id`와 assessment의 판정 당시 판본을 함께 묶는 복합 FK가 없다. `app.assessment UNIQUE(id, policy_version_id)`와 citation의 판본 컬럼·복합 FK 3개를 신규 보정 migration에 추가한다.
- [x] **채택 — 코호트 판본 오염 P0.** 현재 뷰는 `policy_holding.policy_version_id`로 묶는다. 판정 이후 계약 메타데이터가 바뀌어도 재현되도록 `assessment.policy_version_id`를 집계 정본으로 바꾼다.
- [x] **채택 — 검증 상태전이 P0.** 004의 result CHECK는 값만 검사한다. append-only event 또는 전용 함수/트리거/권한 중 계약과 맞는 방식을 S1에서 확정하고 잘못된 전이 테스트를 먼저 만든다.
- [x] **채택 — owner/grant P0.** 002의 테이블 owner 루프는 004보다 먼저 실행된다. `apply.py`도 `SET ROLE insurance_owner`를 하지 않으므로 004 객체가 연결 계정 소유로 남고 default privilege가 적용되지 않을 수 있다. 신규 migration에서 owner와 명시 권한을 재적용한다.
- [x] **채택 — 직렬 병목.** S0~S5는 사실상 직렬이며 SSH 3대의 큰 이득은 S6 적재·검색 검증에서 발생한다. S1이 닫히기 전 원격 작업은 읽기·대조·fresh DB 리허설만 수행한다.
- [x] **채택 — 일정 보정.** 기존 1.5~2.5일 추정에 P0 보정·검증 0.5일을 더해 실행 기준을 2~3일로 조정한다.
- [x] **채택 — claim→assessment 연결 누락 P0.** 첫 리뷰 후 별도 대조에서 cohort가 판정 당시 판본을 사용하려면 claim이 특정 assessment를 직접 참조해야 함을 발견했다. Claude 후속 검토도 `claim.assessment_id`와 `(assessment_id, case_id) → assessment(id, case_id)` 복합 FK를 최소안으로 확인했다. 단순 case join 또는 최신 assessment 자동 선택은 팬아웃·오배분 때문에 금지한다.

### Claude가 제안한 첫 최소 실행 순서

1. 신규 보정 migration: assessment/citation 판본 복합 FK, cohort view 판본 정본, owner/grant 보정
2. claim→assessment 직접 FK와 같은 case 복합 FK를 추가하고 cohort view를 해당 assessment로 join
3. 빈 DB에서 001부터 전량 dry-run·적용·재실행하고 FK 스냅샷 저장
4. verification 상태전이 제약과 실패 테스트를 닫은 후 ORM 단계 착수

기존 claim 행이 있을 때 assessment를 “최신값”으로 임의 백필하지 않는다. migration은 기존 행 존재 시 명시적으로 중단해 매핑 입력을 요구하고, 현재처럼 실제 트랙 행이 0건인 fresh DB에서만 NOT NULL을 확정한다.

### 추가 검토가 필요한 판단

- [ ] verification을 한 행의 상태 UPDATE로 볼지 append-only event로 볼지 핸드오프 계약과 기존 004를 재대조
- [x] `case` 대신 `coverage_review`로 개명 — 최신 핸드오프와 제공 ERD가 일치하고 아직 실제 DB 적용 전이라 호환 대상 없음
