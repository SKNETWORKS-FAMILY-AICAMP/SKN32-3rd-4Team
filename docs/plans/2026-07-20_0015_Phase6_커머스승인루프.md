- REQ: REQ-COM-01(미리보기), REQ-COM-02(명시 승인), REQ-COM-03(멱등), NFR-REL-01(원자성)

## 1. 목표 / DoD
상담(LLM)이 제안한 주문을 사용자가 **미리보기**로 확인하고 **명시적으로 승인**해야만 주문이
성사되며, 승인(주문 생성)은 **멱등**하다. LLM은 제안자일 뿐 — 미리보기는 DB를 바꾸지 않는다.

DoD(계획서 원문): **미리보기 전 DB변경 0, 승인 없는 주문 0, 멱등, 재고부족·타인주문 4xx.**

## 2. 설계 (Clean Architecture strangler 계속 — Phase 1과 동일 구조)
### app/application/commerce.py (프레임워크 무의존, TEST-ARCH-001 준수)
- **DTO**: `OrderLine(product_code, quantity)`, `PreviewLine(product_code, name, unit_price,
  quantity, subtotal, available, sufficient)`, `OrderPreview(lines, total, feasible, issues)`,
  `PlacedOrder(order_no, status, total, lines)`.
- **Ports**:
  - `CatalogPort`: `get_product(code) -> ProductInfo | None`, `get_stock(product_id) -> int`.
  - `OrderRepositoryPort`: `find_by_idempotency_key(user_id, key) -> IdempotentHit | None`
    (기존 키 조회 — 반환에 저장된 요청지문 포함), `place(user_id, lines, key, fingerprint) ->
    PlacedOrder` (원자적: 주문+항목 스냅샷+재고차감+**멱등레코드(키,지문,order_id) 기록** 1 commit;
    키 unique 경합 시 재조회로 수렴).
- **Use cases**:
  - `PreviewOrder(catalog)`: 빈 목록→`ValidationErr`. 각 라인 상품/재고 조회 → subtotal·total 계산,
    `available`/`sufficient` 표기. 미상품·재고부족은 `issues`에 수집하고 `feasible=False`.
    **DB 변경 0**(읽기 전용 포트만 사용) — "미리보기 전 DB변경 0" 보장의 핵심.
  - `PlaceOrder(catalog, orders)`: **멱등키 필수(누락→ValidationErr 422, 서버 UUID 폴백 금지 —
    Codex 지적)**. 요청 라인의 **정규 지문(fingerprint)** 계산 → 키로 기존 조회:
    (a) 있고 지문 일치 → 기존 주문 반환(신규 쓰기·재고차감 0, 멱등 재생),
    (b) 있고 지문 불일치 → `ConflictErr`(409, 같은 키·다른 payload),
    (c) 없음 → 재검증(빈→422, 미상품→404, 재고부족·수량≤0→422) 후 원자적 place.
    → "승인 없는 주문 0"은 미리보기(읽기)와 승인(쓰기)을 **분리된 유스케이스**로 강제해 달성.

### 어댑터 (SQLAlchemy로 포트 구현)
- `app/adapters/sql_catalog.py`(`SqlCatalog`): products/inventory 읽기.
- `app/adapters/sql_order_repo.py`(`SqlOrderRepository`): 멱등 조회 + 원자적 place
  (기존 `order_service.create_order`의 검증·스냅샷·재고차감·단일 commit 로직을 이관/재사용).

### 스키마 / 라우터 / 조립
- `app/db/models.py`: **별도 `OrderIdempotency` 테이블**(Codex 권고) — `user_id`, `idempotency_key`,
  `request_hash`, `order_id`(FK) + `UniqueConstraint(user_id, idempotency_key)`. Order 컬럼 대신
  별도 테이블로 요청지문 저장 → 같은 키·다른 payload 거부 가능. 마이그레이션은 `create_all`(멱등).
- `app/core/errors.py`: `ConflictErr`(http_status=409) 추가 — 멱등키 재사용·payload 불일치용.
- `app/routers/orders.py`:
  - `POST /api/orders/preview` → `PreviewOrder` (무변경). 응답=OrderPreview.
  - `POST /api/orders` → `PlaceOrder`. **`Idempotency-Key` 헤더 필수**(누락→422). 응답 shape·
    404/422/403 코드 **보존**. 기존 주문 테스트는 헤더 제공하도록 갱신(계약 변경 명시).
- `app/composition.py`: `build_preview_order(db)`, `build_place_order(db)` (요청 스코프 세션 주입).

## 3. DoD ↔ 테스트 매핑
- **TEST-COM-PREVIEW-001**(무변경): 미리보기 호출 후 orders 행수·inventory 재고 **불변**;
  total·per-line·feasible 정확(재고부족 라인은 sufficient=False, feasible=False).
- **TEST-COM-APPROVE-001**(승인 경계): 미리보기만으로는 주문 0건 — create 호출이 있어야 주문 생성.
- **TEST-COM-IDEM-001**(멱등): 동일 Idempotency-Key로 create 2회 → 같은 order_no 1건,
  재고 **1회만** 차감(두 번째는 기존 반환).
- **TEST-COM-4XX**: 재고부족 422 / 미상품 404 / 타인주문 403 — 기존 테스트 유지(회귀 0).
- **NFR-REL-01**(원자성): place 중 예외 시 롤백 → 부분 주문/부분 재고차감 없음(결정론 테스트).
- 결정론: Fake catalog/repo로 preview·place·idempotency 로직 단위 검증 + API 통합.

## 4. Codex 설계 리뷰 결과 (반영 완료)
Codex short-consult(low effort) 판정 **FIX** → 3건 반영:
1. **멱등키 저장 = 별도 테이블**(요청지문 저장으로 같은 키·다른 payload 거부) — 반영(§2 OrderIdempotency).
2. **Idempotency-Key 누락 시 서버 UUID 생성 = 무폴백 위반** → 헤더 필수, 누락 시 422 거부 — 반영.
3. **동시성/원자성**: 키 unique 충돌은 기존 주문 반환으로 수렴, 재검증+재고차감+키기록을 단일
   트랜잭션 1 commit — 반영. (재고 조건부 차감: SQLite는 쓰기 직렬화로 안전; PG 동시성은 §5 참조.)

## 5. 범위 밖(YAGNI, 후속) / 정직한 한계
- 장바구니 영속화, 부분 취소/환불, 재고 예약(hold) — 후속.
- **PG 동시성**: 진짜 병렬 재고 초과차감 방지는 `SELECT FOR UPDATE`/조건부 `UPDATE ... WHERE
  stock>=qty` rowcount 확인이 필요. 현재 기본 DB는 SQLite(쓰기 직렬화로 테스트 경로 안전) —
  PG 병렬 락은 동시성 테스트 인프라가 필요해 후속으로 두고, 리포트에 한계로 명시(과장 금지).
- 에이전트가 미리보기→승인을 오케스트레이션하는 것은 **Phase 7**(쓰기 API 직접호출 0 강제).
