# 0. 이 문서의 위상

이 v3.1은 v3.0을 **대체**한다. v3.0은 방대하고 정교하나 (1) 기존 자산을 과대평가하고 (2) YAGNI를
깨는 아키텍처·데이터 전환을 한 번에 요구하며 (3) RULE(무폴백)·하드웨어(약 5GB/CPU)·검증기준과 충돌한다.
→ **v3.0 그대로는 착수 금지(No-Go). 범위를 축소한 v3.1로 진행(Go).** (근거: Codex 고도화 리뷰 A·D)

- 규범 강도: **MUST**(완료 판정 필수) / **SHOULD**(사유 없으면 이행) / **MAY**(자원 여유 시) / **후속**(별도 릴리스).
- 모든 구현은 `REQ-*`, `TEST-*` 식별자를 커밋·PR·테스트명에 연결한다.
- **전면 재작성 금지.** 기존 기능을 테스트로 고정 → 포트/유스케이스 뒤로 이동 → 한 호출부씩 전환 → 회귀 확인.
- 작업 규칙은 승계한 [`RULE.md`](../RULE.md)가 최상위다(무하드코딩·무폴백·YAGNI·검증우선·리포트의무·phased).

# 1. 제품 정의와 닫힌 루프

## 1.1 한 문장

> 인증 사용자의 텍스트 질문을 이해하고, 출처 있는 문서 RAG와 결정론적 상품·재고·주문 도구로 근거 있는
> 답변·추천·비교를 제공하며, **주문은 사용자의 명시적 승인 뒤에만** 생성하고, 모든 처리를 trace로 추적해
> 관리자가 확인하며, 동일 조회 기능을 REST와 MCP 양쪽에 노출하는 AI 상담·커머스 플랫폼.

## 1.2 핵심 닫힌 루프 (이걸 빼면 제품가치가 죽는다)

```
인증 → 질문 → (RAG 근거 / 상품·재고 도구) → 추천·비교 → 주문 미리보기
     → 명시적 승인 → 주문 생성(멱등) → trace 기반 관리자 확인 → 동일 조회를 MCP로 재사용
```

## 1.3 MUST / 후속 경계 (v3.0 대비 축소)

**이번 v3.1 MUST**
- 기존 로그인·상품·주문·결제 회귀 유지 (JWT·SQLite·트랜잭션·E2E)
- 텍스트 RAG 상담: TXT/PDF ingest, FAISS 검색, 답변 단위 출처(source/page), 근거 부족 시 abstention
- 상품 검색·추천·비교 (기존 DB 도구 + 임베딩 추천 재사용)
- 주문 미리보기 → 명시적 승인 → 멱등 주문 생성 (승인 없는 주문 0)
- 최소 에이전트 1경로(기존 수동 ReAct)로 RAG+커머스 닫힌 루프
- MCP stdio **읽기** 도구를 REST와 **동일 유스케이스**로 통일
- USER/ADMIN 역할 + 최소 관리자 화면(인덱스 상태·상품/주문 수·실패 trace·최근 질의)
- 요구사항↔테스트 매트릭스 + 보안 최소 케이스 + 닫힌 루프 시연 1회

**후속(별도 릴리스, 이번 범위 아님)** — 근거: Codex B·F
- 음성/화상 상담, WebAuthn/Passkey, 풀 바운티 경제(Provider/Validator/포인트 원장),
  4모델 실시간 라우터, PostgreSQL+pgvector, Streamable HTTP·OAuth MCP·쓰기 도구,
  Hybrid/Reranker/claim-checker(평가로 개선 입증될 때만), MD/HTML/외부URL ingest,
  SELLER/PROVIDER/VALIDATOR/AUDITOR 역할, LLM 서술 보고서·PDF 저장.
- "지식 바운티"의 방향성은 **관리자 지식보강 큐**(SHOULD)로 최소 보존: "모름" 응답 → 관리자 보강 작업 연결.

## 1.4 MUST NOT 주장 (v3.0 승계)

국내 전 쇼핑몰 실시간 연동, 카드 완전 무인 결제, 포인트 현금 출금, 수천 외부 에이전트 경제망,
얼굴 원본/생체 템플릿 서버 저장, RAG의 환각 완전 제거.

# 2. 아키텍처 결정 (ADR 요약)

- **ADR-001 모듈러 모놀리스**: 단일 FastAPI 배포. (v3.0 승계)
- **ADR-002 개념적 Clean Architecture + 수직 Strangler**: 풀 DDD·엔티티 복제 금지. **실제 변동 경계와
  승인 정책에만** Domain/Port를 도입한다. 폴더 일괄 대이동이 아니라 슬라이스별 전환.
- **ADR-003 REST 유스케이스가 기준 계약**: MCP는 같은 Application Use Case를 부르는 Interface Adapter.
- **ADR-004 LLM은 제안자, 결정권자 아님**: 가격·재고·주문승인·권한·포인트·인증판정·삭제는 코드가 수행.
- **ADR-005 SQLite + FAISS 유지** *(v3.0의 PG/pgvector 철회)*: 현재 트랜잭션·검색이 검증돼 있고 corpus·
  배포 규모가 작다. `RetrieverPort`·`Repository` 추상화만 도입하고 pgvector adapter는 선제 생성하지 않는다.
  **PG 전환 트리거(후속 ADR 조건)**: 다중 writer/프로세스, 온라인 증분 인덱싱, DB-ACL 결합검색, 또는 목표
  corpus에서 p95 검색 SLA 실패 중 하나가 **실측**될 때.
- **ADR-006 자동 fallback 금지** *(RULE 무폴백 정합)*: 교차모델/STT-TTS 자동 전환을 삭제. 선택 프로필 실패 시
  명시 오류. 다른 프로필은 사용자/관리자가 새 요청으로 명시 선택.

## 2.1 계층 경계 (도입되는 것만)

```
Domain        순수 규칙·정책(프레임워크 import 0): 주문승인 정책, 워크플로 rules
Application   유스케이스·포트: AnswerQuestion, SearchProducts, PrepareOrder, ApproveOrder, ...
Adapters      구체 구현: SQLAlchemy Repo, FAISS Retriever, LLM Gateway, MCP
Interfaces    FastAPI 라우터, MCP 서버, (static) UI
```
의존성 규칙: Domain은 LangChain/FastAPI/SQLAlchemy/LLM SDK를 import하지 않는다. Application은 구체
구현을 import하지 않는다. Adapter가 Port를 구현한다. Interface는 Use Case만 호출한다.
→ 검증: `TEST-ARCH-001`(Application 계층에서 금지 import 0 정적 검사).

# 4. 모델 정책 (현실화)

- **결정론 CI**: `FakeModelGateway`만. 실제 모델 자동 fallback 없음. 런타임 provider 미설정 = 명시 오류.
- **기본 로컬 후보**: 기존 검증된 **Qwen3.5-4B Q4** 1개(도구호출 검증 이력). GGUF repo/revision/SHA256을
  레지스트리에 기록 후 승인. Gemma 4 E4B는 RAG 평문 실험 MAY(약 5GB RAM에서 OOM 실측 필수).
- **제외(현 로컬 환경)**: Qwen3.6-27B/35B, Gemma 4 12B — 공식 존재는 확인되나 메모리(약 6.7GB Q4 등)로 로컬 배치 불가. cloud/별도 GPU는 후속.
- **Cloud acceptance**: 키가 제공된 OpenAI 또는 Gemini **1개 stable snapshot ID**만.
- **Router/자동 fallback 삭제**: 명시 선택된 profile만 호출.
- **`model_registry.yaml`**(비밀 아님) 필수 필드: `profile_id, provider, provider_model_id, revision,
  artifact_sha256, runtime, quantization, verified_at, supported_tasks, max_tested_context,
  memory_peak_mb, tool_call_verified`. **비밀은 `.env`.** `latest` alias·family-only pin·미확인 checksum 금지.
  → RULE 3.1 정합: 소스에 있던 모델 ID(`gemma-4-e4b`/`gpt-4o-mini`/`gemini-2.5-flash` 등)를 레지스트리로 이동.

> **Phase 0 성격 명시(YAGNI 해석)**: Phase 0의 "전체 복제"는 **이미 검증된 제품**(결정론 182 통과)을 그대로
> 옮기는 것이다. 이는 RULE의 "레거시 raw 프로젝트에서 핵심만 이관" 대상이 아니라 **제품 자체의 기준선**이며,
> 최적화(포트화·승인루프·역할)는 Phase 1~7에서 슬라이스별로 수행한다. 무변경 복제 후 즉시 182를 재현해
> "기준선 = 원본과 동일 동작"임을 증명하는 것이 Phase 0의 목적이다. (원본은 그대로 보존됨.)

## 5.1 DoD ↔ 자동검증 연결 (RULE 검증·리포트 의무)

- `tests/requirements_matrix.yaml`: `REQ ID → pytest node ID → 실행 명령 → 기대 결과 → 산출물`.
- 테스트명에 REQ ID 포함(`test_req_rag_04_*`).
- `scripts/verify_requirements.py`가 MUST REQ의 테스트 누락·존재하지 않는 node ID를 실패시킨다.
- CI는 JUnit XML·평가 JSON을 artifact로 저장. live model test는 결정론 CI와 분리(모델 ID·revision·prompt
  version·실행시각을 리포트에 기록).
- `Fake`는 `tests/fakes/`에만. 런타임 설정에서 Fake 선택 불가.

# 7. 최종 시연 시나리오 (v3.1 단일 경로)

```
1. 관리자가 환불정책/제품매뉴얼(TXT/PDF)을 명시적 ingest 명령으로 색인
2. 사용자가 로그인(USER)
3. 텍스트로 환불정책 질문 → 답변 + 출처(source/page) 확인, 근거 없는 질문엔 abstain
4. 상품 조건을 자연어로 → 의도 DTO → 상품 검색·비교(결정론 가격·재고)
5. 주문 미리보기 → 사용자가 명시 승인 → 멱등 주문 생성
6. 관리자(ADMIN) 화면에서 인덱스 상태·주문·해당 요청 trace 확인
7. 동일 상품/RAG 조회를 MCP(stdio)에서 호출해 REST와 동일 결과 확인
```
