## 2. 기능별 검토

### 1. 약관 RAG (1~5세대) ✅
그대로 간다. 두 가지만 못박는다.

- **1~3세대는 판매중지라 구하기 어렵다**(취득계획 §0). 4·5세대부터 시작하고,
  1~3세대는 **합성 약관으로 대체하되 화면에 "합성"이라고 표시**한다.
- 조항만 주면 안 된다. **면책조항을 함께** 반환한다(`policy_clause.kind='exclusion'`).

### 2. 청구승인율 (33건/40건) ⚠ 제품의 코어이자 최대 리스크

방향은 맞다. **이게 우리를 약관 챗봇과 구분해 주는 유일한 기능**이다. 다만 세 가지가 걸린다.

| 문제 | 내용 | 대응 |
|---|---|---|
| **데이터가 없다** | "이전 지급받은 고객의 데이터를 받아서"의 **"받아서"가 미해결**이다. 케이스 단위 지급 결과는 공개 데이터가 없다 | MVP는 **합성으로 데모**하고, 실제 수집 경로(동의·증빙·검수)를 **구조로 준비**한다 |
| **40건으로 비율을 내면 안 된다** | 33/40 = 82.5%로 보이지만, 표본 40건의 **95% 신뢰구간은 대략 ±12%p**다. "82.5%"라고 단정하면 거짓이다 | **최소표본 게이트** + `n`과 구간을 **항상 함께** 표시. 미달이면 비율 자체를 숨긴다 |
| ★**생존 편향** | **지급받은 사람이 더 많이 제보한다.** 부지급 당한 사람은 말하지 않는다 → 승인율이 실제보다 **높게** 나온다 | 사후 보정이 **불가능한 구조적 편향**이다. `warnings[]`에 항상 명시하고, **"우리 표본 기준"**이라고만 말한다 |

> 화면 문구는 "승인율 82.5%"가 아니라
> **"우리가 검증한 40건 중 33건 승인 (표본이 적어 실제 비율과 다를 수 있음 · 제보 편향 있음)"** 이어야 한다.

### 3. 유사 케이스 + 연령대 통합 ⚠ 이건 전처리가 아니다

"10대·20대로 카테고리를 통합"하는 건 맞는 방향인데, **이유가 정확도가 아니라 프라이버시다.**

- 생년월일 그대로 두면 `(생년월일 + 질병코드 + 보험사)` 조합으로 **개인이 특정된다.**
- 그래서 ERD의 `subject`에 **생년월일이 없고 `age_band`만** 있다.
- ★**이걸 "전처리"로만 이해하면 나중에 "정확도 높이자"며 다시 세분화하게 되고, 그 순간 개인이 특정된다.**

**규칙: 최소 셀 크기(k)** — 어떤 코호트든 `n < k`면 통계를 공개하지 않는다.
세분화 요청이 와도 k를 깨면서까지 쪼개지 않는다.

### 4. 질병명 → 질병코드 ⚠ 1:N이라 자동 확정하면 안 된다

"우울증"은 코드 하나가 아니다 — `F32`(우울에피소드) · `F33`(재발성) · `F34.1`(기분저하증) 등이고,
**약관 판정이 코드마다 다르다.** 자동으로 하나 골라 판정하면 **틀린 답을 확신 있게** 준다.

```
질병명 입력 → 후보 코드 N개 + 각 설명 제시 → ★사용자가 선택·확인 → 그 코드로 판정
                                             (처방전 OCR과 동일한 원칙)
```

- `case_diagnosis.user_corrected`가 이걸 기록한다.
- **의료 진단이 아니다**(명시적 비범위). "이 증상은 F32입니다"가 아니라 "F32는 약관에서 이렇게 다룹니다".

### 5. 약관 용어 챗봇 ✅ 가장 안전하고 효과 큰 기능

그대로 간다. 두 가지만.
- 근거 없으면 **답하지 않는다**(abstain). 용어라고 지어내면 안 된다.
- ★**용어 설명과 보장 판정을 분리한다.** "이 용어는 이런 뜻입니다"와 "그래서 당신은 보장됩니다"는
  다른 유스케이스다. 챗봇이 판정으로 넘어가면 규칙엔진을 우회하게 된다.

### 6. 개발자 대시보드 ✅ / "당신은 로봇입니까?" ❌

**대시보드는 좋다.** 어떤 정보가 오가는지 보이는 관리자 페이지는 L6에 있다.

**"당신은 로봇입니까?"는 반대한다.**

> 우리 서비스의 **주 고객이 AI 에이전트**다. 로봇을 걸러내는 장치를 만드는 건 **주 고객을 막는 것**이다.
> 게다가 CAPTCHA류는 우리 비범위에 이미 들어가 있다.

필요한 건 **차단이 아니라 식별과 분기**다.

| 하지 말 것 | 대신 할 것 |
|---|---|
| "당신은 로봇입니까?" 체크 | **에이전트 신원 선언** — API 키(`agent_client`) · User-Agent · `llms.txt` |
| 로봇이면 막기 | **로봇이면 기계용 응답** — 필드 많은 JSON, 사람이면 화면 |
| 판별했다고 믿기 | ★**확실히 알 수 없다는 것을 인정** |

★**정직 기록**: 사람인 척하는 에이전트를 100% 판별하는 방법은 없다.
그래서 **판별에 의존하지 않는 설계**를 한다 — 판별에 실패해도 안전하도록
**모든 응답에 불확실성 필드를 항상** 넣는다(`data_source`·`n`·`abstained`…).
대시보드에는 "AI 여부"가 아니라 **`declared`(선언) / `inferred`(추정) / `unknown`** 세 값으로 표시한다.

## 3. 프로젝트 구조 — 클린아키텍처 2단계

### 왜 2단계인가

정통 클린아키텍처는 4겹(Entities · UseCases · Adapters · Frameworks)이다.
5명이 4주 하는 프로젝트에서 4겹은 **경계를 지키는 비용이 얻는 것보다 크다.**
그래서 **경계를 하나만** 둔다. 대신 **그 하나는 절대 안 넘는다.**

```
┌─────────────────────────────────────────────────────────┐
│  app/core   【안쪽】  프레임워크를 모른다                  │
│    domain/    엔티티 · 값객체 · 상태 전이 불변식          │
│    usecases/  6기능의 실제 로직                           │
│    ports/     바깥에 요구하는 인터페이스(Protocol)         │
│    errors.py  타입 오류                                   │
└───────────────────────▲─────────────────────────────────┘
                        │ 의존 방향은 항상 안쪽으로만
┌───────────────────────┴─────────────────────────────────┐
│  app/outer  【바깥】  기술 상세                            │
│    inbound/   들어오는 쪽 — api/ · mcp/ · web/            │
│    outbound/  나가는 쪽  — db/ · rag/ · llm/ · ocr/       │
│    wiring.py  포트에 구현을 꽂는 곳(조립)                  │
└─────────────────────────────────────────────────────────┘
```

**규칙 3개**
1. `app/core`는 `fastapi` · `sqlalchemy` · `langchain` · `openai`를 **import 하지 않는다**
   (`tests/test_arch.py`가 이미 강제 중 — 새 경로도 포함시킨다).
2. `app/outer`는 `app/core`를 import 해도 되지만, **반대는 안 된다.**
3. 유스케이스는 **포트만** 받는다. 구현 클래스를 직접 알지 않는다.

### 6기능이 어디 있나

| 기능 | 유스케이스 (안쪽) | 필요한 포트 | 구현 (바깥) |
|---|---|---|---|
| 1 약관 RAG | `usecases/terms_search.py` | `TermsRetrieverPort` | `outbound/rag/` |
| 2 승인율 | `usecases/cohort.py` | `CohortStatsPort` | `outbound/db/` |
| 3 유사 케이스 | `usecases/cohort.py` | `CohortStatsPort` | `outbound/db/` |
| 4 질병명→코드 | `usecases/diagnosis.py` | `KcdLookupPort` | `outbound/db/` |
| 5 용어 챗봇 | `usecases/glossary.py` | `TermsRetrieverPort` · `ModelGateway` | `outbound/rag/` · `llm/` |
| 6 대시보드 | `usecases/admin_report.py` | `AuditLogPort` · `AgentIdentityPort` | `outbound/db/` · `inbound/web/` |
| (공통) 판정 | `usecases/precheck.py` | 위 여러 개 + `PolicyVersionResolverPort` | — |

### 담당 매핑

| 담당 | 주 작업 위치 |
|---|---|
| ① 판정 코어 | `core/domain/` · `core/usecases/precheck.py` · `core/ports/` |
| ② 약관 파이프라인 | `outer/outbound/rag/` · `ingest/` |
| ③ 집계·거버넌스 | `core/usecases/cohort.py` · `outer/outbound/db/` |
| ④ 계약·통합 | `outer/inbound/api/` · `mcp/` · `wiring.py` |
| ⑤ 화면·필수기능 | `outer/inbound/web/` |

**핵심 이점**: ①은 `core/`만 보면 되고 DB·LLM 없이 테스트한다.
②③④⑤는 각자 자기 디렉터리에서 일하고, **포트 시그니처 하나로만 만난다.**

## 4. 한계 (정직 기록)

- 기존 커머스 코드(`app/rag`, `app/services`, `app/routers` 등)는 **아직 이 구조로 옮기지 않았다.**
  P0의 "커머스 자산 정리"에서 옮기며, 그전까지는 새 구조와 공존한다.
- 2단계는 **의도적 단순화**다. 어댑터가 늘면 `outbound/` 안에서 다시 갈라질 수 있다.
- 기능 2의 데이터 확보 경로는 **여전히 미해결**이다. 구조만 준비된 상태다.
