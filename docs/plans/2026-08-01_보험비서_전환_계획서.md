## 0. 무엇을 만드는가

진료비 내역서의 **KCD 질병기호**와 **실손보험 약관**을 대조해
**보장 여부를 미리 알려주는** 서비스. 그리고 그 판정을 **API로 제공**한다.

핵심은 정확도가 아니라 **정직성**이다.
"보장됩니다"라고 잘못 말하면 사용자가 청구했다가 거절당하거나, 반대로 받을 걸 포기한다.
**근거 조항을 못 대면 "확인 불가"** 가 정답이다.

## 2. 커머스 코드를 어떻게 할 것인가 — **지우지 않고 격리한다**

코덱스와 같은 결론이다. 판단 기준은 이렇다.

| 대상 | 처리 | 이유 |
|---|---|---|
| `products` `orders` `payments` | `app/legacy/` 로 이동 + 라우터 등록 해제 | 실습 이력이지만 **보험 API 문서에 섞이면 혼란**이다 |
| `auth` `admin` `health` | **그대로 재사용** | 도메인 무관 |
| `rag` `agent` `workflow` | **개명 후 재사용** | 뼈대가 그대로 쓰인다 |
| `a2a` `mcp` `voice` `face` `bounty` `lab` `nlp` | 등록 해제(코드는 보존) | 4주 안에 못 쓴다. 코덱스도 "자를 것"으로 분류 |

**지우지 않는 이유**: 되돌릴 수 없고, 실습 산출물이라 평가 자료가 될 수 있다.
`app/legacy/` 에 모으고 `main.py` 에서 라우터만 빼면 API 표면에서는 사라진다.

## 3. 새로 만들 것 — 최소 단위

### 3-1. 도메인 모듈

```
app/insurance/
  policy_version.py     가입일 → 적용 약관 버전 확정 (세대·상품라인·판매기간)
  clause_store.py       조항 조회 (qualified_no, locator, 원문)
  kcd.py                질병명 ↔ KCD 코드 매칭 (후보 제시, 자동선택 안 함)
  coverage_rules.py     규칙 기반 판정 (보장/면책/한도/자기부담금)
  citation_guard.py     ★인용 검증 — LLM 이 댄 조항이 근거에 실재하는지 대조
```

`citation_guard` 가 이 프로젝트의 안전장치다.
**프롬프트는 지켜지길 바라는 것이고, 이건 강제된다.**

### 3-2. 라우터

| 신규 | 역할 |
|---|---|
| `precheck.py` | 보장 사전판정 (핵심) |
| `kcd.py` | 질병명 → 코드 후보 |
| `terms.py` | 약관 검색·용어 설명 |
| `cohort.py` | 청구승인율 (데이터 있을 때만) |

기존 `rag.py` `admin.py` `auth.py` `health.py` 는 유지.

## 4. 판정 파이프라인 (LangGraph)

직선이 아니라 **분기와 되돌아감**이 있어서 LangGraph가 맞다.

```
입력(질병코드·가입일·보험사)
   │
   ├─ resolve_policy_version   가입일 → 적용 약관 확정
   │      └─ 못 정하면 → abstain("적용 약관 확인 불가")
   │
   ├─ retrieve_clauses          해당 버전의 조항만 검색 (다른 버전 혼입 금지)
   │      └─ 0건이면 → abstain("근거 없음")
   │
   ├─ apply_rules               규칙 기반 1차 판정
   │
   ├─ draft_answer (LLM)        구조화 출력 강제
   │      verdict / cited_clauses[] / reason
   │
   ├─ verify_citations          ★인용한 조항이 근거에 실재하는가
   │      ├─ 통과 → 완료
   │      ├─ 조항번호가 틀림 → 허용 목록으로 **설명문만 1회 수정**
   │      ├─ 근거가 부족함  → 표적 검색 **1회**
   │      └─ 재시도 초과   → 초안 폐기, abstain
   │
   └─ 출력
```

**재시도는 `verify_citations` 바로 뒤에 두고 횟수를 못 박는다**(코덱스 권고).
자율 ReAct 루프는 쓰지 않는다 — 언제 끝날지 모르고 감사도 안 된다.

## 5. API 설계

```
POST /v1/prechecks              보장 사전판정
GET  /v1/prechecks/{id}
GET  /v1/kcd/candidates?q=우울증  질병명 → 코드 후보
POST /v1/terms/search           약관 조항 검색
POST /v1/terms/explain          용어 설명

관리자 전용
GET  /v1/admin/review-queue     검수 큐
GET  /v1/admin/metrics
GET  /v1/admin/audit-logs
```

`POST /v1/prechecks` 응답에 **반드시** 들어가야 하는 것:

```json
{
  "verdict": "covered | not_covered | unknown",
  "abstained": false,
  "reason_code": "...",
  "policy_version": { "insurer": "…", "generation": 3, "sale_start": "20190501",
                      "date_confidence": "exact" },
  "citations": [ { "clause_id": "…", "qualified_no": "보통약관/제9조",
                   "title": "…", "quote": "…", "page": 41 } ],
  "missing_documents": [],
  "rule_engine_version": "…",
  "trace_id": "…"
}
```

**`unknown` 은 HTTP 오류가 아니라 정상 결과**다(200).
입력 오류는 422, 검색·DB 장애는 503으로 구분한다.

## 6. 4주 우선순위 — 무엇을 자를 것인가

### 반드시 (P0)

1. **지원 범위 매니페스트** — 1,367건 전부가 아니라 **구조화·검수된 것만** 지원한다고 선언
2. **적용 약관 버전 결정** — 가입일 기준. **현행 약관 폴백 금지**
3. **조항 단위 검색 + 인용 검증**
4. **규칙 기반 판정 + `확인 불가`**
5. **KCD 후보 제시** — 자동 선택하지 않고 사용자가 고른다
6. **근거 사슬을 보여주는 화면 하나**
7. **골든 실패 케이스** — 근거 없음 / 조항번호 오류 / 다른 버전 혼입 / 면책 누락

### 조건부 (P1)

- 청구승인율 — 기존 DB에 **약관 버전·KCD·실제 지급결과**가 있을 때만
- 용어 챗봇 — `AnswerQuestion` 재사용이라 저비용
- 관리자 — **검수 큐와 감사로그만**

### 자른다

자율 판정 에이전트 · 별도 그래프DB · A2A · MCP · bounty · lab ·
음성 · 얼굴 · 화상 · **OCR** · 청구 제출 워크플로 · 화려한 대시보드 ·
모든 보험사 동시 지원

> OCR은 회의에서 "하드웨어 비용" 우려가 나왔는데, 그보다 **4주에 안 된다**가 더 큰 이유다.
> 사용자가 질병코드를 직접 입력하는 것으로 시작한다.

## 8. 가장 큰 위험

코덱스 지적을 그대로 옮긴다.

> 가장 큰 불확실성은 기술이 아니라 **데이터**다.
> 조항 구조화에 안정적인 조항 ID·번호·페이지·약관 버전이 아직 없다면,
> **판정 API보다 전처리가 먼저**다.

지금 전처리 v3가 돌고 있고, 목차 오인·부 경계 결함을 고쳤지만
**조 번호 충돌이 아직 남아 있다**(부까지 포함해도 37종).
`(문서, 특약ID, 조번호)` 식별키가 서야 `citations` 가 신뢰된다.

**그래서 P0의 3번(조항 단위 검색)이 실제로는 전처리 완성에 달려 있다.**
