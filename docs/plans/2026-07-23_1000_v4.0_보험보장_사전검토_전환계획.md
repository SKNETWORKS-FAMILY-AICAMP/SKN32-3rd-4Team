## 0. 한 줄 정의

> 처방전의 질병분류기호(KCD)와 **가입 시점 약관 버전**을 결합해 보장 가능성을 **사전검토**하고,
> **검증된 실제 청구 결과의 코호트 통계**를 AI 에이전트에게 제공하는 서비스.

**"지급 확정"이 아니다.** 보험금은 질병코드 하나로 결정되지 않는다(가입시기·특약·면책기간·진단방법·
치료목적·추가서류). 우리가 하는 것은 **사전검토와 통계 제공**이다.

## 1. 코어 — 무엇이 진짜 자산인가

약관 원문은 **누구나 가진 공개 자료**다. 그것만으로는 차별점이 없다.

> **가장 방어력이 높은 자산은 "같은 케이스에서 이전 고객들이 실제로 어떻게 됐는가"의 집계다.**
>
> (※ "유일하다"고 단정하지 않는다 — 입증된 주장이 아니다. 약관 해석 품질·규칙엔진 정확도·에이전트
> 사용성도 경쟁 요소가 될 수 있다. 다만 공개 자료로 복제하기 가장 어려운 것이 결과 집계다.)

그리고 이 집계는 **AI 에이전트에게 가장 값어치가 크다.** 사람은 "아마 될 것 같습니다"로 만족하지만,
에이전트는 조건부 실행을 하려면 **기계가 읽는 확정성**이 필요하다.
`status: "additional_documents_required"` + `missing_documents: [...]`는 사람에겐 안내문이지만
에이전트에겐 **다음 행동을 결정하는 분기 조건**이다 — 우리 출력의 **형태 자체가 에이전트용**이라는 것이
"왜 AI가 고객인가"에 대한 답이다.

## 2. 기존 자산 분류 (Codex 논의 + 제약 교정)

### 2-1. 그대로 재사용 — 이 프로젝트의 뼈대
| 자산 | 보험에서의 의미 |
|---|---|
| Clean Architecture · 포트/어댑터 | 도메인 교체가 인터페이스 교체로 끝난다 |
| **무폴백 오류 정책** | "판단 불가"를 억지로 답하지 않는 것이 이 도메인의 생명 |
| **근거 인용 + abstention → 지식갭 큐** | 약관 조항 인용, 처방전만으로 판단 불가 시 물러남 |
| **근거 신선도 게이트** | **약관 버전·KCD 버전 관리에 정확히 필요**. 낡은 약관으로 판정하면 치명적 |
| RBAC(role은 JWT에 없고 매 요청 DB 조회) · 감사 로그 | 의료·보험 자료 접근 통제 |
| PII 마스킹 | 민감정보 처리의 최소 전제 |
| **멱등·조건부 원자 처리 패턴** | 결과 기여·포인트 정산에 그대로 필요 |
| MCP · A2A 인터페이스 | 에이전트가 고객인 구조의 진입점 |
| 고객/운영 앱·포트 물리 분리 | 의료자료를 다루면 더 중요해짐 |

### 2-2. 축소 재사용 — 범위를 줄여서
| 자산 | 조정 |
|---|---|
| RAG 4백엔드 | **데모에서는 Hybrid(RRF) 하나만** 유지. 4개 비교는 학습 트랙이었고 지금은 산만하다 |
| `SupportCheck`(CoT 자기검증) | **"약관 근거가 설명을 지지하는가"에만** 쓴다. **지급 가능성 검증기로 오인하면 안 된다**(Codex 지적) |
| 바운티 L0 등급화 | 보험에 거의 그대로 맞는다: `verifiable`=조항으로 확인 / `outcome_linked`=**실제 지급 결과** / `opinion`=해석 여지 |
| 바운티 L1 인용 대조 | 약관 조항 대조에는 유용하나 **실제 청구결과 검증에는 부족하다**(Codex) → §4의 증빙 검수로 대체·보강 |
| 바운티 L2 포인트 원장 | 인메모리라 **영속화 필수**. 기여 보상에 쓸 것 |

### 2-4. ★Codex 의견 중 채택하지 않은 것 (제약 충돌)

Codex는 **얼굴·음성·화상도 폐기**하라고 했다. 그러나 이 프로젝트는 **과목 필수 요구사항**이 있다:

```
2. 음성 상담 챗봇 (음성 ↔ 텍스트)
3. 화상 상담 챗봇
4. 사용자 화면과 관리자 대시보드 별도 제공
5. 로그인 기능 (얼굴 로그인 2차 인증 추가)
6. 관리자 대시보드 요약 보고서 생성·저장·인쇄
→ 위 기술들이 다 사용될 수 있게 해야 함
```

따라서 **유지한다.** 오히려 보험 도메인에서 정당성이 커진다:
- **얼굴 2차 인증**: 의료·보험 자료 접근은 커머스보다 민감도가 높아 2차 인증 근거가 명확해진다
- **음성 상담**: "이 처방전으로 실비 받을 수 있어?" — 실사용 맥락에 자연스럽다
- **관리자 보고서**: 저신뢰 판정 검수 결과 보고에 그대로 쓰인다

Codex는 우리 과목 제약을 모르고 답했으므로 이 부분만 교정한다.

#### 다만 코어가 흐려지지 않게 — 필수 기능은 **코어 외곽 어댑터**로 못박는다 (Codex 권고)

이 기능들이 "프로젝트의 정체"가 되면 안 된다. 각각의 **위치**를 미리 고정한다.

| 기능 | 위치 | 성공지표 | 시간상한 | 데이터 취급 |
|---|---|---|---|---|
| 음성(STT/TTS) | **상담 API의 입출력 채널** — 판정 로직에 관여하지 않음 | 질의 인식 성공률 | 응답 지연 상한 명시 | 녹음 **보존하지 않음**(즉시 폐기), 동의 필요 |
| 화상 | 상담 UI의 표현 채널 | 세션 성립률 | 상한 명시 | 영상 **저장하지 않음**, 프레임 샘플링만 |
| 얼굴 2차 인증 | **인증 수단**(민감자료 접근 게이트) | 인증 성공/거부율 | 상한 명시 | 원본 이미지 저장 금지, **실패 시 대체 인증 경로 필수** |
| 관리자 보고서 | **검수·집계 결과의 읽기 전용 표현** | 생성 성공 | — | 집계값만, 개인 케이스 원문 미포함 |

원칙: **판정·집계 로직은 이 어댑터들을 몰라야 한다.** 음성으로 물어도 텍스트로 물어도 같은
유스케이스를 타고, 얼굴 인증은 접근 허용만 결정한다. 생체·녹음·영상은 **동의·보존·삭제·위변조 방지**
정책을 각각 문서화한다.

## 3. 최소 수직 슬라이스 (첫 구현 단위)

> **★Codex의 가장 값진 지적**: 흔한 실패는 **RAG 화면부터 바꾸고 핵심 파이프라인을 미루는 것**이다.
> 첫 구현 단위는 챗봇이 아니라 **"증빙 1건이 검수되어 통계 1개를 바꾸는 수직 슬라이스"** 여야 한다.
> **이 슬라이스에는 RAG를 넣지 않는다**(얇게 유지 — Codex).

```
증빙 1건 제출 → 문서 정합성 검사(형식·금액·중복) → status=consistent
             → 진위 확인(발행처·원본성 또는 관리자 교차검증) → status=verified
             → verified 만 코호트 집계에 반영 → 표본수 n → n+1
```

### ★검수 상태를 두 단계로 분리하는 이유 (Codex 지적, 치명적)

초안은 "형식·금액·중복 검사 통과 → Outcome **확정**"으로 썼다. **이는 잘못이다.**
그 검사가 확인하는 것은 **제출 문서의 내부 정합성**일 뿐, **실제 보험사가 그렇게 결정했는지**가 아니다.
정합성이 맞는 위조 통지서는 통과한다.

따라서 상태를 나눈다:

| 상태 | 무엇이 확인됐나 | 집계 반영 |
|---|---|---|
| `submitted` | 아무것도 | ✗ |
| `consistent` | 문서 내부 정합성(형식·금액 일치·중복 아님) | ✗ |
| `verified` | **발행처 확인·원본성 검증 또는 관리자 교차검증** | ✅ |
| `rejected` | 정합성 실패 또는 진위 확인 실패 | ✗ |

**`verified`만 통계에 들어간다.** 부트캠프 범위에서 발행처 API 확인이 불가능하면
**관리자 교차검증을 필수 경로로** 두고, 그 사실을 응답에 명시한다
(`"verification_method": "admin_review"`).

> 이것은 바운티 L1에서 이미 배운 교훈과 같은 계열이다 — **"근거성 검증은 사실성 검증이 아니다."**
> 같은 실수를 새 도메인에서 반복하지 않기 위해 상태 모델로 고정한다.

이 슬라이스가 돌면 나머지는 부가다. **화면·음성·에이전트 연동보다 먼저** 만든다.

## 4. 데모 루프 (5단계, Codex 정리 채택)

1. 처방전에서 **KCD 추출 → 사용자가 교정·승인**(OCR 신뢰도 표시)
2. 가입 상품·특약·사고일 기준으로 **적용 약관 버전 확정**
3. 관련 조항과 **면책조건을 함께** 인용해 사전검토
4. 동일 기준 **코호트의 지급액 분포·승인/부지급·표본수·수집경로** 반환
5. 청구결과와 증빙을 제출받아 **검수 후 집계가 실제로 갱신**

판정 결과는 **4단**으로만 낸다(이진 판정 금지): `보장 가능성 높음` / `낮음` / `추가서류 필요` / `전문가 검토 필요`

## 5. 데이터 전략 — 두 리스크

### 5-1. 콜드스타트 (1순위 리스크)
사례 0건이면 이 서비스의 가치는 **0**이다. 이건 추상적 걱정이 아니라 이 저장소에서 실제로 겪은 일이다
(`cs_inquiries.csv` 60행 중 고유 15개, 코퍼스 8청크로 검색 비교 불성립, 파인튜닝 중단).

Codex 권고는 "병원·손해사정사·법률상담기관과 자료 제공 계약을 먼저 확보"인데, **부트캠프 규모에서는
불가능하다.** 따라서 현실적 대응:

- **합성 사례 생성기 + 시뮬레이터**를 만든다. 흐름 시연에는 충분하다.
- ★**합성 데이터와 실제 통계를 물리적으로 분리한다**(Codex 강조). 같은 테이블·같은 API에 섞이면
  "실제 통계"라는 거짓 주장이 된다.
  **필드 하나(`data_source`)로는 부족하다** — 쿼리·집계 실수로 언제든 섞인다(Codex 지적). 따라서:
  | 분리 층위 | 조치 |
  |---|---|
  | 저장 | **별도 테이블/스키마**(또는 별도 DB) |
  | 수집 | 파이프라인 분리 — 합성 생성기는 실제 테이블에 쓸 권한이 없다 |
  | 집계 | **집계 뷰를 각각** 둔다. 하나의 뷰가 둘을 UNION 하지 않는다 |
  | API | **경로 분리**(`/v1/cohorts` vs `/v1/demo/cohorts`) + 권한 분리 |
  | 보증 | DB 제약 + **혼합 차단 테스트**(합성이 실제 집계에 유입되면 실패) |
  응답에는 `data_source`를 **항상** 표시한다.
  ※ 이 분리는 **P7이 아니라 P0~P1에서** 해야 한다(Codex) — 나중에 하면 이미 섞인 데이터를 정리해야 한다.
- 최소 공개 기준(표본수) 미만이면 **통계를 숨긴다**(k-익명성 겸용).
- 발표에서 **"이건 합성 데이터입니다"를 먼저 밝힌다.** 이 프로젝트가 계속 해온 방식이고, 오히려 신뢰를 얻는다.

### 5-2. 생존 편향 (제품을 거짓으로 만드는 리스크)
지급받은 사람은 기여 동기가 있고 **부지급자는 없다** → 승인률이 과대추정된다.
핵심 상품인 통계가 **처음부터 틀린 숫자**가 된다.

대응:
- **부지급·일부지급 사례에 더 높은 기여 보상**(역인센티브)
- **모집경로별 분모·응답률을 공개**하고, 자발 제출치는 **별도 층**으로 표시(Codex)
- 응답에 편향 경고를 **필드로** 넣는다:
  `"denial_sample_ratio": 0.17, "bias_warning": "부지급 표본이 적어 승인률이 과대추정될 수 있음"`
- 이 사고방식은 우리가 이미 한 번 적용했다 — **"만족도를 정산 기준으로 쓰지 않는다"**(그럴듯한 날조를
  장려하므로). 같은 계열이다.

| **소표본 재식별** | 최소 표본 게이트 + 희귀조합(희귀질환+지역+병원+연령) 상위 범주로 묶기 |
| **위조 증빙** | 증빙 해시·형식 검증·관리자 검수. 클라이언트 자체 확인만 신뢰하지 않는다 |
| **동일인 중복 등록** | 케이스 지문(비식별 해시)으로 중복 탐지 |
| **약관 버전 혼합** | 신선도 게이트 + 코호트 키에 `policy_version` 포함 |
| **교란변수**(치료유형·특약 차이) | 유사도 계층 분리(직접일치/준직접/참고)하여 **섞지 않는다** |
| **"지급 예측"으로 오인** | 금액은 **과거 분포만** 제시. "당신은 얼마 받습니다"는 하지 않는다 |
| **규제** | 자동화된 결정·민감정보 처리·손해사정 유사행위 해당 여부 **확인 필요**(단정 금지) |

> ※ `estimate_payment_range`처럼 **예상 지급액을 산정해 제시하는 기능**은 손해사정 유사행위로 볼 여지가
> 있는지 확인이 필요하다. 확인 전에는 **과거 분포 제시**로 한정한다.

## 7. 단계 계획

| Phase | 내용 | 완료 기준 |
|---|---|---|
| **P0** | 커머스 자산 정리(§2-3 폐기) + 도메인 스키마 정의 + ★**합성/실제 저장·집계·API 물리 분리**(§5-1) | 스키마 테스트, 폐기 후 회귀 무결, **혼합 차단 테스트** |
| **P1** | **수직 슬라이스**(§3, RAG 없이): 증빙 → `consistent` → `verified` → 집계 갱신 | 표본수 n→n+1 테스트, **`consistent`만으로는 집계에 안 들어감** 테스트 |
| **P2** | KCD 정규화 + 약관 버전 매칭 규칙엔진 | 날짜·면책기간·특약 판정 단위 테스트 |
| **P3** | 약관 RAG(Hybrid만) + 조항·면책 동시 인용 + abstention | 근거 없으면 답하지 않음 검증 |
| **P4** | 코호트 집계 API + 최소표본 게이트 + 편향 경고 필드 | 표본 미달 시 통계 미공개 테스트 |
| **P5** | MCP 도구 세트 + A2A 카드 + `llms.txt`/OpenAPI | 외부 에이전트가 화면 없이 전 루프 수행 |
| **P6** | 과목 필수 기능 재연결(음성·화상·얼굴2FA·관리자 보고서) | 각 기능 실제 화면 확인 |
| **P7** | 합성 데이터 생성기 확충(분리 구조는 P0에서 이미 완료) | 코호트별 표본 확보, `data_source` 항상 표시 |

**순서에 대한 두 가지 못박기**
1. **P1을 P3보다 먼저** — 챗봇부터 만들면 핵심 파이프라인이 미뤄진다(§3).
2. **합성/실제 분리는 P0에서** — 나중에 하면 이미 섞인 데이터를 정리해야 한다(Codex).

## 8. 하지 않을 것 (명시적 비범위)

보험금 지급 확정 · 보험사 지급 결정 자동화 · 보험상품 가입 권유·판매 · 보험료 비교 ·
완전 자동 청구 · 의료적 진단 · **실제 사용자 의료자료를 모델 학습에 사용**

## 9. 한계 (정직 기록)

- 이 계획서는 **착수 전 설계**이며 구현이 없다.
- 통계는 **합성 데이터 기반으로 시작**한다. 실제 사례가 없는 동안 어떤 수치도 "실제 승인률"이라고
  말할 수 없다.
- 규제 관련 판단(자동화된 결정 해당성, 손해사정 유사행위)은 **전문가 확인 전제**이며 본 문서는
  법률 자문이 아니다.
- 부트캠프 기간에 P0~P7 전부가 끝난다고 가정하지 않는다. **P1이 돌면 발표 가능**하고, 나머지는
  우선순위대로 진행한다.
