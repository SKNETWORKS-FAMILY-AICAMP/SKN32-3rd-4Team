## 0. 지금 평가셋에 무엇이 임의값인가

[`build_retrieval_set.py`](../../scripts/eval/build_retrieval_set.py) 안에 이렇게 박혀 있다.

| 값 | 현재 | 무엇을 좌우하나 |
|---|---|---|
| 난수 시드 | `20260802` | 어느 문서·조항이 뽑히나 |
| `CORPUS_N` | 2,000 | 검색 난이도 (크면 어려워진다) |
| `QUERY_N` | 200 | 실제로는 **145** — 제목 유일성 때문에 못 채운다 |
| `MIN_CHARS` / `MAX_CHARS` | 120 / 3,000 | 어떤 조항이 후보가 되나 |
| 단서 위치 하한 | **200자 이후** | 면책 탐침의 난이도 |
| 탐침 상한 | **60** (`break`) | 표본 크기 — 데이터 한계가 아니라 코드 상한 |
| 문서 순회 중단 | `len(pool) >= CORPUS_N*2` | ★**이것 때문에 47개 문서만 읽었다** |
| 소스 | `s5_*` 하드코딩 | 현행은 **s6** |

**이 값들이 만든 결과:**

```
출처 문서    47 / 1,367  (3.4%)
보험사 편중   삼성생명 805(40%) · 현대해상 401 · 삼성화재 304 · 흥국화재 238
             DB 127 · KB 64 · NH 61   ← 12개사 중 7개사, 5개사는 0건
```

CLAUDE.md §4 — *편향된 표본으로 비율을 말하지 않는다.* 지금은 사실상 **삼성생명 약관 벤치**다.

## 1. v1 을 왜 버리지 않고 동결하나

이미 12개 모델을 측정했고 **결과를 봤다.** [10번 계약 §3-1](../handoff/10_계약_모델_평가.md) 이 정한 원칙:

> 문항은 **결과를 보기 전에 확정하고 잠근다.** 그 방식이 반복되면 **사후 해석**이 된다.

그래서 v1 을 고치지 않는다. **셋을 바꾸는 근거가 "점수가 마음에 안 들어서"가 아니라
설계 결함(표본 대표성 · s5/s6 불일치 · 과제③ 누락)이라는 것**을 기록으로 남긴다.

★**v1 결과는 참고이며 모델 채택 근거로 쓰지 않는다.**

## P2 · 3분할 생성  ⬜

```
s6 전량
  → 문서 층화 (보험사 12 × 세대)
  → 문서당 조항 상한          ← 대형 문서 편중 방지
  → dedup (content_hash + 근사중복)
  → ★근사중복 문서군 단위로 개발 / 보정 / 테스트 3분할
  → 교차셋 근사중복 0건 검사
```

★**문서 단위가 아니라 문서군 단위**로 나눈다. 같은 상품의 개정판이 양쪽에 걸리면 누수다.
조항 중복률이 **66%** 라 이 검사가 필수다.

**목표 규모(전체 기준 — 테스트셋 수가 아니다)**

| | |
|---|---|
| 코퍼스 | 8,000 조항 |
| 제목 질의 | 600 (보험사당 ~50) |
| 면책 검색 | 270 |
| 면책 탐침 | 270 |

> 오차폭(독립표본 가정 최악): 600건 ≈ **±4%p** · 270건 ≈ **±6%p**.
> 문서 군집을 반영하면 더 넓어진다. **145건으로 0.006 차이를 순위로 읽으면 안 된다.**

생성 후 `data/eval/v2_manifest.json` 에 **실제 sha256** 기록.

## P3 · 사람 감사  ⬜  ★테스트셋 잠금 **전에** 한다

유형별 30건 또는 전체의 10% 중 **작은 쪽**. 일부는 이중검수 + 불일치 조정.

보는 것: 제목 제거가 제대로 됐나 · 면책 경계가 맞나 · 복수 정답이 정말 정답인가

★**되돌림 경로**: 감사에서 수정·탈락이 생기면 **층별 할당과 교차셋 근사중복 검사를
다시 돌린 뒤** 잠근다.

## P4 · 개발셋 1차 선별  ⬜

12개 모델 × 코퍼스 **2~4천**. **단계적 탈락** — 설정 전수 조합(Cartesian) 금지.

## P5 · 개발셋 심화  ⬜

상위 3~4개만 **8천 전체** + 설정 변형(접두어 · `max_seq`).
`dtype`(fp16/4bit)은 정확도 후보가 아니라 **배포 제약 실험**으로 분리한다.

★모델별 결과를 **즉시 저장**해 세션이 끊겨도 재개되게.
★코퍼스 임베딩을 `(모델 revision, 문서 접두어, max_seq, dtype)` 단위로 **캐시**하면
접두어 진단 비용이 크게 준다.

## GPU — Colab 이 아니라 내부 장비다

★**약관 원문을 Colab 호스팅 GPU 에 올리면서 유출을 막는 실용적 방법은 없다.**
토큰 ID 도 상당 부분 복원되고, 암호화 업로드도 계산 시점엔 복호화해야 한다.
CLAUDE.md §2 — *약관 원문은 저작물이다.*

**내부 GPU 박스가 이미 있다** — `10.20.20.1` 계정 `Yeon`.
[`docs/manuals/ssh-gpu-access.md`](../manuals/ssh-gpu-access.md) 에 절차가 있고,
**Windows 관리자 계정 함정**의 해법까지 적혀 있다:

> Windows OpenSSH 는 Administrators 그룹 계정의 `~/.ssh/authorized_keys` 를 **읽지 않는다.**
> 키를 `C:\ProgramData\ssh\administrators_authorized_keys` 에 넣어야 한다.

[완성 계획](2026-08-02_1900_프로젝트_완성_계획.md)이 *"1-3 SSH 키 인증 ❌ 막힘"* 으로 적어둔 것이
이것이고, **해법이 이미 문서에 있다.**

### 그래도 Colab 을 쓴다면

| 되는 것 | 안 되는 것 |
|---|---|
| **Colab 로컬 런타임**으로 UI만 쓰고 계산은 내부 GPU에서 | Colab 호스팅 GPU 에 약관 올리기 |
| 공개·합성 문서로 **모델 호환성만** 선별 | 최종 평가 (반드시 내부에서) |

로컬 런타임을 쓰더라도 **노트북 출력 저장을 꺼야** 한다 — 본문이 출력에 남는다.

### 규모는 GPU 제약이 아니다

기존 12건 실측이 코퍼스 **1천 건당 4.3~6.4초**(무거운 후보도 22~25초)다.
8천 건이면 모델당 **35초~3분 20초** 수준이고 질의 600 × 코퍼스 8천의 점수 계산은 작다.

★**줄여야 할 것은 표본이 아니라 설정 조합 수다.**
