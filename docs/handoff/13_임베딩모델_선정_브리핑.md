# 임베딩 모델 선정 브리핑 — 팀 공유용

작성 2026-08-03 · 코덱스 교차검증 **4라운드**
측정 환경: RTX 4070 SUPER 12GB(랩) · RTX 2000 Ada 16GB(RunPod) · sentence-transformers 5.6.1
★**주 표(§3)는 fp16 17회**, 8B 이상은 **4bit 4회**로 따로 쟀습니다(§5-9) — 두 표를 섞어 읽지 마세요.

## 0. 용어 — 표를 읽기 전에

### 0-1. 임베딩이 뭘 하나

문장을 **숫자 목록(벡터)** 으로 바꿉니다. 뜻이 비슷하면 벡터도 가까워집니다.
그래서 "도수치료 받았는데 보상되나요" 로 물어도, 그 낱말이 없는
「보상하지 않는 사항」 조항을 찾는 것을 **목표로** 합니다.
★다만 이번 평가는 **실제 사용자 구어체 질문을 재지 않았습니다**(§5-4).

낱말이 정확히 겹쳐야 찾는 방식(키워드 검색)과 다릅니다.

### 0-2. 성능 지표

모델이 조항 2,000개를 점수순으로 줄 세우면, **정답이 몇 등**인지 봅니다.

★**정답은 하나가 아닐 수 있습니다.** 코퍼스에 같은 문장을 담은 조항이 여럿이면
전부 정답으로 인정하고, 그중 **가장 높은 등수**를 씁니다(§2-2).

| 지표 | 읽는 법 | 예 |
|---|---|---|
| **R@1** | 1등이 정답인 비율 | 0.50 = 질의 100개 중 50개는 **첫 결과가 바로 정답** |
| **R@10** | 정답이 **상위 10등 안**에 하나라도 있는 비율 | 0.70 = 100개 중 70개 |
| **MRR@10** | 정답 등수의 **역수** 평균 (10등 밖은 0) | 1등 1.0 · 2등 0.5 · 4등 0.25 |

> ★**이름 주의.** 정답이 여럿일 때 "상위 k 안에 **하나라도** 있으면 성공"은
> 엄밀히는 `Recall@k` 가 아니라 **`Hit@k`(= Success@k)** 입니다.
> 표에는 관례대로 `R@k` 로 적었지만 **계산은 Hit@k** 입니다.
> "정답 5개 중 3개를 회수했다" 같은 뜻이 **아닙니다.**

- **R@1** 은 "바로 보여줄 수 있나"
- **R@10** 은 "후보 10개 안에 들어 있나" — 리랭커를 붙일 거면 이쪽이 중요합니다
- **MRR** 은 둘을 섞은 대표값. 상위권 등수 차이에 민감합니다

> 셋 다 **높을수록 좋고 0~1** 범위입니다.

### 0-3. 우리가 따로 만든 지표

| 지표 | 무엇을 재나 | 왜 필요한가 |
|---|---|---|
| **뒷부분 MRR / R@10** | 조항 **뒤쪽**에 붙은 단서 문장(「다만 …」 등)을 질의로 주고 그 조항을 찾게 한다 | ★**이게 우리 서비스의 급소에 가장 가깝다.** 입력 길이 제한에 걸리는 부분이 바로 여기다 |
| **면책 MRR** | 위 60개 중 **부정·면책 표현이 실제로 있는 16개**만 | ★처음엔 60개 전부를 「면책」이라 불렀는데, 세어 보니 실제 면책은 16개(27%)뿐이었다. **재는 것과 이름이 다르면 없는 근거를 있다고 믿게 된다.** 표본 16개는 작다 |
| ☠**벡터무변화**<br>(**무효 · §5-10**) | 조항 앞부분과 「앞부분+단서」의 코사인 거리가 **1e-6 미만**인 건수 | ★뒷부분이 최종 표현에 **영향을 주지 않았다는 강한 증상**입니다. 다만 "모델이 그 문장을 입력으로 못 받았다"는 **증거는 아닙니다.** ★이전 판에서 「면책못봄」이라 불렀는데, 재는 것과 이름이 달라 **문서·출력 표기를 바꿨습니다.** 결과 JSON 필드명은 `proviso_blind_count` **그대로**입니다 — 이미 저장된 측정 21건을 다시 돌리지 않으려고 남겼습니다 |
| **잘림** | 코퍼스 조항 중 모델 최대 입력을 넘긴 비율 | 넘으면 뒷부분이 **조용히 버려진다** |

### 0-4. 모델 사양

| 항목 | 뜻 |
|---|---|
| **차원** | 벡터 하나의 숫자 개수(768/1024/2048). 표현 용량이 커질 수 있으나 **검색 품질을 보장하지 않고 저장·검색 비용은 확실히 는다** |
| **최대 토큰** | 한 번에 읽는 길이. ★**모델의 구조적 한계**와 **배포 설정**은 다르다(§1) |
| **접두어(prefix)** | 일부 모델이 **요구하는** 머리말. 예: `query: ` / `passage: `. ★요구하는 모델에서 빠뜨리면 성능이 크게 떨어질 수 있다(§5-1) |
| **fp16** | 숫자를 16비트로 저장. 메모리·속도 이점이 있으나 **환경에 따라 다르다.** fp32·4bit 결과와 **섞어 비교하면 안 된다** |

## 1. 왜 바꿔야 하나 — 지금 **배포 설정**이 우리 과제와 안 맞는다

현재 `jhgan/ko-sroberta-multitask` 의 **배포 설정**이 **128토큰**입니다.
"512토큰 모델"로 알고 있었는데 아니었습니다.

★**모델의 한계가 아니라 설정입니다.** 백본은 512를 지원합니다 —

```
ST 배포 설정 max_seq_length     = 128
백본 max_position_embeddings    = 514
토크나이저 model_max_length     = 512
```

즉 **모델을 안 바꿔도 512로 올릴 수 있습니다.** 그 효과는 §3-2 ②에 있습니다.

```
>>> get_embeddings()._client.max_seq_length
128
```

### 눈으로 확인한 증거

```
A = "회사는 … 보상합니다."                            (128토큰 초과)
B = A + " 다만 고의로 자신을 해친 경우에는 보상하지 않습니다."

코사인 유사도 = 1.000000      ← 완전히 같은 벡터
```

면책 문장을 붙였는데 벡터가 **조금도 안 움직였습니다.**

| | 값 |
|---|---|
| 코퍼스 조항이 잘리는 비율 | **83.7%** |
| 탐침 60건 중 앞부분과 같은 벡터 | ☠**무효 — §5-10** |

> ★**「…보상합니다. 다만 … 보상하지 않습니다」에서 뒷부분이 잘립니다.**
> 우리 서비스가 절대 놓치면 안 되는 부분이 임베딩에 안 들어갑니다.
> 그래서 이건 **모델 고르기 이전의 문제**입니다.

## 2. 어떻게 쟀나

### 2-1. 남의 벤치마크를 쓰지 않았습니다

KURE 8-subset · MTEB-Korean · MLEB 어느 것도 **한국어 실손보험 약관을 재지 않습니다.**
위키·뉴스·일반 법률에서 이긴 모델이 약관에서도 이긴다는 보장이 없습니다.

### 2-2. 질의를 **지어내지 않았습니다**

LLM 으로 질문을 만들면 그 LLM 의 표현 습관에 **편향될 수 있습니다** —
평가가 모델이 아니라 **질문 생성기**를 재게 될 위험이 있습니다.
그래서 **문서에 이미 적힌 것**만 씁니다.

| 과제 | 질의 | 정답 |
|---|---|---|
| ① 제목→본문 | 조항 제목 (예: "보상하지 않는 사항") | 그 조항 본문 |
| ② **뒷부분 검색** | 조항 뒤쪽 단서 문장(다만·단·그러나·이 경우…) **원문 그대로** | 그 문장을 담은 조항 **전부**(복수 정답) |
| ②' **면책** | ②의 60개 중 부정·면책 표현이 있는 **16개** | 같음 |

- ①은 본문에서 **제목 문구를 지웠습니다.** 안 지우면 글자만 겹쳐 봐도 맞아, 임베딩이 아니라 문자열 일치를 재게 됩니다.
- ②는 단서가 **200자 이후**에 있는 것만 골랐습니다. 입력 길이에 걸리는 모델은 그 문장이 임베딩에 안 들어가 **불리합니다.**
  (앞부분 단서만으로 맞히는 경우도 있으므로 "못 찾는다"고 단정하지 않습니다.)
- ②의 표지("다만" 등)는 **떼어 냈습니다.** 남기면 그 낱말만 보고 맞힐 수 있습니다.
- ★정답은 **복수**입니다. 코퍼스 중복률이 65%라 같은 문장을 담은 조항이 여럿인데,
  하나만 정답으로 두면 **맞힌 것을 틀렸다고 세게 됩니다.**

### 2-3. 규모

```
코퍼스   조항 2,000개   (s5 · parse_status=ok 문서에서 · 중복 내용 제거)
질의     제목 145개 · 뒷부분 60개(그중 진짜 면책 16개)
탐침     60쌍
```

★**작습니다.** §5 를 보세요.

### 3-2. 이 결과가 **말하는** 것

#### ① 현재 128토큰 설정은 그대로 쓰면 안 된다

뒷부분 검색 MRR **0.133** · 조항의 **83.7%가 잘림** ·

#### ② 설정을 512로 올리면 **뒷부분 검색이 오른다** — 직접 비교로 확인

| | 128 (현재) | 512 (설정만 변경) |
|---|---:|---:|
| 뒷부분 MRR | 0.133 | **0.298** |
| 뒷부분 R@10 | 0.250 | **0.517** |
| 벡터무변화 | 34/60 | **4/60** |
| 잘림 | 83.7% | 26.6% |

★**같은 모델의 128 ↔ 512 를 직접 짝비교했다**(코덱스 지적으로 추가):


**뒷부분은 오르고, 제목은 손해가 확인되지 않습니다.**
그리고 `arctic-ko` 대비 뒷부분 −0.018 [−0.111, +0.076] —
**이 개발셋에서 arctic-ko 와의 MRR 차이를 검출하지 못했습니다.**
(★"최상위권과 동등하다"는 뜻이 아닙니다.)

#### ③ ★그러나 **제목 검색 격차는 설정으로 메워지지 않는다**

같은 512 설정이 제목 검색에서는 `arctic` 대비
**−0.130 [−0.194, −0.068]** — **구간이 0을 안 걸칩니다. 차이가 확인됩니다.**

> ★**이것이 이 조사의 결론입니다.**
> 설정 변경은 **뒷부분 검색 점수를 올리지만**(직접 비교로 확인),
> **제목 검색의 상위권 격차는 그대로다**(−0.130, 구간이 0을 안 걸침).
> 두 과제 중 하나만 봤으면 정반대 결론을 냈을 겁니다.
> ★이 결론은 **이 평가셋·이 설정**에 한정됩니다.

#### ④ 기준 모델 대비 **열세가 검출되지 않은** 후보가 여럿이다

★정확히 말하면 — **각 후보를 기준 모델 하나와만** 비교했습니다.
후보 **상호 간** 모든 쌍을 비교한 것이 아니므로
"상위권끼리 차이가 없다"고 말할 수 없습니다.

```

뒷부분 검색  arctic-ko 기준으로 16개 중 10개가 구간 0 을 걸침
```

> ★"구간이 0을 걸친다"는 **"같다"가 아니라 "차이를 검출하지 못했다"**입니다.
> 표본이 작아 못 가린 것일 수 있습니다.

> 다중비교 보정을 하지 않았으므로 **명목 95% 구간**입니다.

뒷부분 검색에서 `arctic-ko` 대비 **−0.129 [−0.210, −0.053]** —

다만 잘림 때문인지 모델 특성인지는 **이 측정으로 구분할 수 없습니다**(§5-5).

3. **실제 사용자 구어체 질의**를 넣는다. 지금은 원문 발췌뿐입니다(§5-4).
4. **문서 단위 부트스트랩** — 같은 문서에서 나온 질의들은 독립이 아닙니다.
5. **별도 holdout** 에서 최종 확인. 이 개발셋은 이미 여러 번 봤습니다.

## 5. ★믿으면 안 되는 것

### 5-1. 접두어를 안 붙이면 **모델이 억울해집니다**

1차 측정에서 `nvidia/Nemotron-3-Embed-1B` 가 MRR **0.088** 로 무너졌습니다.
모델이 나쁜 게 아니라 **접두어를 안 붙였기** 때문이었습니다.

```
접두어 없음   MRR 0.088
query:/passage: 적용   MRR 0.549      ← 6배
```

> ★모델을 탓하기 전에 **우리 설정을 의심해야** 합니다.
> "이 모델은 우리 과제에 나쁘다"고 적었으면 팀이 후보에서 지웠을 겁니다.

★**표에는 접두어 열이 없습니다.** 앞선 판에 "표에 적었다"고 쓴 것은 사실이 아니었습니다.
실제로 붙인 것은 이것이 전부입니다.

| 접두어 | 적용한 모델 |
|---|---|
| `query: ` / `passage: ` | `multilingual-e5-large` · `KoE5` · `Nemotron-3-Embed-1B` · `llama-embed-nemotron-8b` |
| `prompt_name="query"` | `Qwen3-Embedding-0.6B` · `4B` · `8B` |
| 없음 | 나머지 전부 — 모델카드가 요구하지 않았습니다 |

★"모델카드가 요구하지 않았다"는 **요구하는데 우리가 못 찾았을 가능성**을 배제하지 않습니다.
점수가 유난히 낮으면 모델이 아니라 접두어를 먼저 의심하세요 — `llama-embed-nemotron-8b`
가 그 경우였는지 **아직 못 가렸습니다**(§5-9).

### 5-2. 표본이 작습니다 — **그래서 짝비교를 붙였습니다**

질의 145개(제목) · 60개(뒷부분) · **16개(면책)**입니다.

같은 질의를 짝지어 부트스트랩 95% 구간을 재 보니
**제목 10개, 뒷부분 10개가 구간이 0을 걸칩니다**(§3-1).
→ **"1위"라고 단정하면 안 됩니다.**

★그리고 기준 대비 16개를 비교했으므로 **다중비교 보정**을 하지 않았습니다.
단일 비교처럼 읽으면 안 됩니다.

★이 평가셋을 **모델 선택에 썼으므로** 사실상 개발셋입니다.
최종 성능 주장은 **별도 holdout**에서 확인해야 합니다.

### 5-3. 코퍼스가 s5 기준입니다

전처리가 **s6**(부록 분리)로 올라갔습니다. 코퍼스를 s6 로 다시 만들면
숫자가 달라질 수 있습니다.

### 5-4. 이 평가가 재지 **않는** 것

- 실제 사용자 질문(구어체) — 우리 질의는 **전부 약관 문어체**입니다.
  ★이건 단순 제한이 아니라 **순위를 뒤집을 수 있는** 문제입니다
- 여러 조항을 조합해야 답이 나오는 경우
- 리랭커를 붙였을 때의 최종 성능
- **조항을 쪼개서 넣는 방식(chunking + parent 회수)** — 지금은 조항 하나를
  벡터 하나로 넣었습니다. 이러면 긴 문맥 모델이 구조적으로 유리합니다.
  실제 대안은 모델 교체만이 아닙니다
- 판정 정확도 — 검색이 좋아도 규칙엔진이 틀리면 소용없습니다

### 5-4-1. 그 밖의 한계 (코덱스 3라운드)

- **질의가 코퍼스 문장의 원문 발췌**다 → 의미 검색보다 문자열·표현 중첩에 유리하다
- 뒷부분 60개는 "200자 이후 + 특정 접속 표지"로 골랐다 →
  **표지 없는 면책·앞부분 면책**은 대표하지 못한다(선택 편향)
- 같은 문서·상품에서 나온 질의가 **독립이 아닐 수 있다** →
  질의 단위가 아니라 **문서 단위 cluster bootstrap** 이 더 적절할 수 있다
- 복수 정답은 **사람 판단이 아니라 문자열 포함**으로 정했다 → 라벨 누락 가능
- 면책 16개에는 **신뢰구간이 없다** — 그런데 잠정 선택 근거로 썼다
- 평균 지표는 **치명적인 개별 실패를 가린다** → 면책은 질의별 실패 목록도 봐야 한다
- holdout 은 무작위 분할이 아니라 **다른 보험사·상품·문서 버전**으로 구성해야 한다

★"코퍼스 중복 내용 제거"와 "중복률 65%"는 다른 것이다 —
전자는 **코퍼스를 만들 때 같은 `content_hash` 를 하나만 넣었다**는 뜻이고,
후자는 **원본 s5 전량의 조항 중복률**입니다.

### 5-5. 잘림 때문인지 모델 특성인지 **구분할 수 없습니다**

`multilingual-e5-large` 는 512토큰이라 27.2%가 잘리고 뒷부분 MRR 이 낮습니다.
그런데 모델과 최대 길이가 **동시에** 다르므로 원인을 가릴 수 없습니다.

가리려면 같은 모델에서 앞 512 · 뒤 512 · 슬라이딩 윈도우를 비교해야 합니다.

### 5-6. ☠4bit 통제 실험 — **결론을 철회합니다**

같은 `Qwen3-Embedding-4B` 를 다른 조건을 모두 같게 두고 정밀도만 바꿔 쟀습니다.

| `Qwen3-Embedding-4B` | fp16 | 4bit |
|---|---:|---:|
| 제목 MRR | 0.521 | 0.537 |
| 제목 R@10 | 0.676 | 0.690 |
| 뒷부분 MRR | 0.253 | 0.270 |
| ~~벡터무변화~~ | ☠**무효** | ☠**무효** |

**살아 있는 것** — 점추정은 4bit 에서 낮아지지 않았습니다.
다만 **짝비교 신뢰구간도 비열등성 검정도 없습니다.**
"4bit 가 검색 성능을 떨어뜨리지 않는다"고 결론 낼 수 없습니다 —
**점추정이 낮아지지 않았을 뿐입니다.**

☠**철회한 것** — 앞선 판에서 "벡터무변화가 fp16 0/60 → 4bit 13/60 으로
새로 나타났으므로 양자화 조건에 귀속된다"고 썼습니다. **취소합니다.**
그 지표의 계산이 틀렸고(§5-10), 하필 **4bit 쪽에서 노름이 5배 더 흐트러졌습니다.**
즉 그 13건은 양자화가 뒷부분을 못 보게 만든 증거가 아니라
**계산 결함이 4bit 에서 더 크게 나타난 것**일 수 있습니다. 구분이 안 됩니다.

> ★그래도 §5-9(4bit)와 §3(fp16)을 **한 표에서 순위 매기지 않는다**는 원칙은 그대로입니다.
> 근거가 이 지표에서 온 게 아니라 **정밀도가 다르면 비교 조건이 다르다**는 사실에서 옵니다.

> "설정 문제다"라고 단정하면 그 문장과 어긋납니다.

### 5-10. ☠**「벡터무변화」 열은 무효입니다** — 계산이 틀렸습니다

측정 21건 **전부**가 결함 있는 공식으로 계산됐습니다. **재측정 전까지 쓰지 마세요.**

무엇이 틀렸나 — 두 가지가 겹쳤습니다.

**① 벡터가 단위 노름이 아니었습니다.**
`1 − (h·w)` 로 코사인 거리를 쟀는데, 이건 두 벡터의 길이가 정확히 1일 때만 맞습니다.
실제로는 fp16 정규화 뒤 길이가 1±0.002, 4bit 는 1±0.005 였습니다.
그래서 내적이 **1을 넘고 거리가 음수**가 됩니다 — 실측 최소 **−0.00498**.
★각도가 실제로 벌어졌는데도 `< 1e-6` 문턱에 걸려 「안 움직였다」로 세어졌습니다.

**② 문턱 `1e-6` 은 잴 수 없는 값이었습니다.**
내적을 fp16 으로 더하면 1 근처의 분해능이 **2⁻¹¹ ≈ 4.9e-4** 입니다.
저장된 거리 값이 **전부 2⁻¹¹ 의 정확한 배수**였던 것이 증거입니다.

| 저장된 거리 | ÷ 2⁻¹¹ |
|---:|---:|
| 0.000488 | 1.00 |
| 0.000977 | 2.00 |
| 0.001465 | 3.00 |
| −0.000977 | −2.00 |

즉 `1e-6 미만` 이라 적었지만 실제로 센 것은 **「fp16 분해능에서 0 이하로 반올림된 것」** 입니다.
★**못 잰 것보다, 못 재는 문턱을 정의로 적어 둔 것이 더 나쁩니다.**

#### 무엇이 무효가 되나

| | 영향 |
|---|---|
| MRR · R@10 · 뒷부분 · 면책 · 잘림 | **영향 없음.** 다른 경로로 계산합니다 |
| §3-1 짝비교와 신뢰구간 | **영향 없음** |
| §3 · §5-9 의 `벡터무변화` 열 | ☠**무효** |
| §1 의 「탐침 60건 중 34건」 | ☠**무효** |
| §5-6 「4bit 에서 13/60 이 새로 나타났다 → 양자화 조건에 귀속」 | ☠**철회합니다** |

★§5-6 의 철회가 특히 중요합니다. 4bit 쪽 거리 최소값이 −0.0045~−0.0050 으로
fp16(−0.001)보다 **5배 큽니다.** 즉 4bit 는 노름이 더 많이 흐트러졌고,
그 흐트러짐이 그대로 「무변화」로 세어졌을 수 있습니다.
**「13/60 이 양자화 때문」이라는 결론은 근거가 사라졌습니다.**

#### 살아남는 것

§1 의 핵심 주장 — **128토큰 설정에서 면책 문장이 잘려 나간다** — 은 그대로입니다.
근거가 이 지표가 아니라 **직접 확인**이기 때문입니다.

```
A = "회사는 … 보상합니다."                       (128토큰 초과)
B = A + " 다만 고의로 자신을 해친 경우에는 보상하지 않습니다."
→ 코사인 유사도 1.000000
```
그리고 **잘림 83.7%** 는 토크나이저가 직접 세는 값이라 이 결함과 무관합니다.

#### 고친 것과 남은 것

```python
# 고침 — float64 로, 노름을 직접 나눈다
cos = np.sum(h * w, axis=1) / (np.linalg.norm(h,axis=1) * np.linalg.norm(w,axis=1))
deltas = 1.0 - np.clip(cos, -1.0, 1.0)
blind = int(np.sum(deltas < 1e-9))
```
결과 JSON 에 `probe_norm_min`·`probe_norm_max`·`blind_eps` 를 함께 남깁니다 —
다음 사람이 같은 함정을 확인할 수 있게.

#### 재측정 시험에서 나온 것 — **방향이 반대였습니다**

`ko-sroberta`(현재 배포 모델) 하나로 먼저 확인했습니다.

| 조건 | 벡터무변화 | 탐침 벡터 노름 |
|---|---:|---|
| 옛 공식 · GPU fp16 | 34/60 | (기록 안 함) |
| 고친 공식 · CPU float32 | 47/60 | 1.000000 |
| **고친 공식 · GPU fp16**(원래 조건) | **46/60** | 0.999617 ~ 1.000444 |

★옛 공식은 **과대 계수만 한 게 아니라 과소 계수도** 하고 있었습니다.
fp16 분해능(4.9e-4)보다 작은 차이가 전부 0으로 반올림돼,
「거리 ≤ 0」 조건에서조차 빠진 것이 있었습니다. 34 → 46 으로 **늘었습니다.**

> ★**재측정하면서 조건을 바꿀 뻔했습니다.** 처음에 `--device` 를 안 줘서
> fp32 로 쟀는데(47/60), 원래 측정은 fp16 이라 **비교할 수 없는 값**입니다.
> 그런데 결과 JSON 의 `dtype` 은 옛 값이 그대로 남아 **알아채기 어렵습니다.**
> 그래서 `probes_device`·`probes_dtype`·`probes_dtype_matches_original` 을
> 함께 저장하게 했습니다. 같은 함정을 두 번 밟을 뻔했습니다 —
> 한 번은 계산에서, 한 번은 그걸 고치면서.

#### 남은 일

**fp16 17건 재측정** — GPU 박스에서 진행 중입니다. 모델을 매번 지우며 쟀으므로
다시 받아야 합니다. `--probes-only` 를 만들어 코퍼스 2,000건 인코딩은 건너뜁니다.

**4bit 4건** — 8B 는 12GB 에 fp16 으로 안 올라가므로 RunPod 가 필요합니다.

표에서 값을 **지우지 않고 ☠로 표시**해 둔 이유는, 지워 버리면
「왜 없는지」가 사라지기 때문입니다.
