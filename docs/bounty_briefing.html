올바른 보험비서 · 설계 브리핑

지식 바운티는 “진실”을 검증하지 않습니다
무엇을 검증하는지 정확히 정리했습니다

원 기획 UC-03의 “Validator가 사실성 평가” 조항을 왜 폐기했고, 무엇으로 대체했는지 — 그리고 지금 어디까지 구현됐는지

01 문제 재정의 — “사실성 평가”는 왜 불가능한가

원 기획서 UC-03에는 이렇게 적혀 있었습니다.

Provider가 답변 + 출처 + 증거해시 제출 → Validator가 사실성·정합성·중복·재현성 평가 → 이의제기 → 포인트 정산

핵심 모순

대조할 정답(ground truth)이 없으면 참·거짓을 자동으로 판정할 수 없습니다. 우리가 가진 것은 “세계의 사실”이 아니라 Provider가 제출한 텍스트와 우리 색인뿐입니다. 그래서 “Validator가 진실을 판정한다”는 설계는 결국 특정 출처·관리자를 진실의 기준으로 삼는 권위 위임이 되고, 그 권위가 왜 옳은지는 어디에도 정의돼 있지 않습니다.

※ “검증이 가능하면 살 필요가 없다”는 식의 논리는 쓰지 않습니다 — 발견 비용과 검증 비용은 다를 수 있어 일반적으로 성립하지 않습니다. 문제의 본질은 정답의 부재입니다.

이것은 우리 팀의 실수가 아니라 이름이 붙은 난제입니다 — 정답(ground truth)이 없는 정보시장의 오라클 문제. Validator가 확인할 수 있는 건 세계의 사실이 아니라 제출물의 성질뿐입니다.

놓치기 쉬운 함정

우리가 이미 가진 SupportCheck는 “근거 → 주장”의 함의만 판정합니다. 그 근거 자체가 거짓·조작·낡은 것이면 그대로 통과합니다. 근거성 검증은 사실성 검증이 아닙니다.

02 설계 원칙 — 무엇으로 대체했는가

“진실을 검증한다”  →  “근거성·절차를 검증하고, 확인 가능한 위반에 경제적 비용을 붙인다”

이 원칙이 하지 못하는 것

“거짓을 손해로 만든다”가 아닙니다. 현재 몰수 대상은 위조 인용 · 미확인 출처 · 중복뿐이며, 근거가 잘 갖춰진 그럴듯한 허위는 이 계층을 통과합니다. 억제되는 것은 “거짓 전체”가 아니라 “객관적으로 확인 가능한 부정행위”입니다.

이 전환은 이 프로젝트가 원래 지켜온 철학과 같은 계열입니다: 근거가 없으면 답을 생성하지 않는 abstention, 오류를 그럴듯한 결과로 덮지 않는 무폴백, 한계를 문서에 남기는 정직 기록.

개발 중 실제로 고친 결함

인용 대조를 처음엔 임베딩 유사도로 구현했는데, 그러면 공격자가 실제 문서명을 쓰고 원문과 의미만 비슷한 허위 문장을 지어내면 통과했습니다. 지금은 문자 수준 원문 대조(부분 인용은 그대로 허용) + locator 일치를 요구합니다.

탐지 범위와 한계: 원문을 많이 바꿔 쓴 위조는 임계값(0.85) 아래로 떨어져 걸리지만, 원문에 가깝게 유지하면서 숫자·조건만 살짝 바꾼 위조는 통과할 수 있습니다. 반대로 정상 인용도 표기·띄어쓰기 차이가 크면 오탐될 수 있습니다. 임계값은 실 데이터로 튜닝되지 않은 시작값입니다.

04 정산 원칙 — 구매자 만족도를 쓰지 않는 이유

“구매자가 만족하면 지급한다”가 가장 자연스러워 보이지만, 이건 날조를 적극적으로 보상합니다.

결론: 만족도는 서비스 품질 신호로만 따로 수집하고, 포인트 정산식에서는 제외합니다.

05 상태 머신 — 제출부터 정산·기각·몰수까지

이의제기 절차 — 누가, 무슨 근거로, 누가 판정하나 설계 확정 · 절차 자동화 미구현

항목규칙
제기 주체바운티 요청자(requester) 또는 운영자. 제3자는 제기할 수 없다(스팸·협박 방지).
제기 기간dispute_window 진입 후 바운티 생성 시 확정한 일수(dispute_days, 최소 1일). 기간이 지나면 제기 불가.
필요 근거주장만으로는 접수하지 않는다. 확인 가능한 사유 하나 이상을 지목해야 한다 —
① 인용문이 지목 출처와 불일치 ② 출처가 허용 색인에 없음 ③ 기존 지식과 중복.
판정 주체운영자(관리자 권한). 고액·고위험 건은 2인 독립 검토 L3 미구현
판정 결과 settled 이의 근거가 확인되지 않음 → 예정대로 provider에게 지급
rejected 제출이 부적격이나 부정행위는 아님 → escrow를 요청자에게 환불, stake는 반환
slashed 객관적 위반이 확인됨 → stake 몰수
판정 불가“내용이 틀린 것 같다”는 이의는 접수하되 몰수 사유가 되지 않는다. 위 세 사유에 해당하지 않으면 settled 또는 rejected로만 갈 수 있다.

상태 전이·원장 규칙은 코드로 구현·테스트됐지만, 이의 접수 폼·검토 큐·2인 검토 워크플로는 아직 없습니다. 지금은 운영자가 상태 전이를 직접 호출하는 수준입니다.

테스트 수를 정확성 증명으로 읽지 마세요

바운티 관련 테스트는 48개가 통과합니다. 이는 정의된 계약대로 동작한다는 뜻이지, 이 설계가 옳거나 지식이 참임을 증명하지 않습니다. 실제 제출 데이터로 검증한 바 없습니다.

07 한계와 다음 작업

이 시스템이 보장하지 않는 것 반드시 인지

  • 지식의 사실성. 근거가 거짓이면 L1을 통과합니다.
  • 외부 원본의 진위. 인용 대조는 “우리 색인과의 일치”만 확인합니다. 색인 자체가 오염되면 통과합니다.
  • 독립 검증. 정합성 검사는 답변과 같은 모델의 자기 점검이라, 모델이 공유하는 오류는 잡지 못합니다.
  • 임계값의 타당성. 인용 대조 0.85 / 중복 0.95는 튜닝되지 않은 시작값입니다.
  • 정산 실행. L2는 상태·원장 규칙이며 실제 지급 인프라·영속화는 없습니다.

다음 구현 우선순위

  1. DB 영속화 — 상태머신·원장을 테이블로. 기존 OrderIdempotency 멱등 패턴 재사용.
  2. L3 표본 감사 — 고액·고위험 건 무작위 추출 + 2인 독립 검토. 목적은 전수 검증이 아니라 기대이익 역전(감사확률 × 벌칙 > 거짓 이익).
  3. Provider 인증·데이터 격리 — REQ-BNT-02(권한 밖 문서 조회 0건).
  4. L4 결과 연동 — 반품률 등 관측 신호가 있는 주장에 한정.
