## 1. 왜 tool calling인가 (기능 2·3·4의 공통 구조)

세 기능의 본체는 LLM이 아니라 **코드/DB**다:

| 기능 | 본체 (LLM 아님) | LLM의 역할 |
|---|---|---|
| 2. 청구승인율 통계 | SQL/pandas 집계 | 자연어 → get_approval_stats(코드, 연령대) 호출 변환 |
| 3. 유사 케이스 비교 | 전처리·카테고리 통합 코드 | 자연어 → search_similar_cases(...) 호출 변환 |
| 4. 질병명→질병코드 | KCD 코드 DB 조회 | 자연어 → search_disease_code(질병명) 호출 변환 |

숫자를 LLM이 세면 환각 위험이 있으므로 집계·조회는 반드시 코드가 하고,
LLM은 "올바른 툴을 올바른 인자로 부르는 번역기" 역할만 한다.
평가 대상은 답변 품질이 아니라 **tool call 정확도**다.

## 2. 평가 방법 (2단계)

- mock 툴 3종: search_disease_code / get_approval_stats / search_similar_cases
- 14케이스 5유형: 기능별 직접 호출 / 표현 정규화("혈압이 높다"→고혈압,
  "스물다섯 살"→20대) / 억제(툴 불필요 질문) / 코드 날조 함정 / 인자 부족 함정
- **1턴 채점**: 첫 호출의 툴명·인자 일치만 검사
- **멀티턴 채점**: 툴을 실제 실행해 결과를 돌려주며 최대 3턴 진행,
  "여정 중 목표 툴에 올바른 인자로 도달했는가"로 채점. 인자 부족 케이스는
  정보수집 후 정지(되묻기)는 허용, 추측 인자로 데이터 툴 호출은 실격.
  → 멀티턴이 실서비스(LangChain 에이전트 루프)의 실제 동작과 동일.

## 3. 결과 (3모델 × 14케이스, 실측)

| | **Qwen3 8B (로컬)** | GPT-4.1 | gpt-4.1-mini |
|---|---|---|---|
| 1턴 채점 | **12/14** | 11/14 | 9/14 |
| **멀티턴 채점 (최종)** | **13/14** | **13/14** | 11/14 |
| 표현 정규화 (t03/t05) | O / O | O / O | **X** / O |
| 억제 3문항 | 3/3 | 3/3 | 3/3 |
| 코드 날조 함정 (t12) | O | O | O |
| 인자 부족 함정 (t14) | O — 무호출 | O — 정보수집 후 정지 | **X — 인자 날조** |
| 응답 속도 | 2–16s (t14 704s※) | **0.6–2s** | 0.7–3s |
| 비용 / 보안 | **무료 / 로컬** | 과금 / 외부 전송 | 과금 / 외부 전송 |

※ Qwen은 애매한 상황에서 극단적으로 오래 생각하는 패턴 재현(3회째 관측:
277s, 666s, 704s) — 정답에는 도달하나 **타임아웃 필수** (6절).

### 실패 분석 (실측 확정)

- **t06은 3모델 공통 실패 → 모델이 아니라 mock 툴의 한계.**
  trace: 세 모델 모두 "2형 당뇨"로 조회 → mock DB 키("당뇨병")와 불일치로
  실패. Qwen은 "당뇨병 2형", "2형 당뇨병"으로 3턴 내내 재시도(끈질기나 실패),
  GPT는 1회 후 포기. → **질병명 툴에 유사어 매칭(임베딩 검색) 필수**라는
  기능 4 설계 요구사항의 실증. 모델 순위에는 무영향.
- **t08 등 멀티스텝은 실측으로 검증됨.** 예: GPT-4.1이 코드조회(고혈압)→
  I10 수신→search_similar_cases(I10, 50대, 삼성화재) 2턴 도달. 1턴 채점의
  X는 채점 기준 문제였음이 확정.
- **t14가 mini의 결정적 탈락 사유.** 연령대 미지정 질문에 mini는
  get_approval_stats(F32, age_group="전체")로 **존재하지 않는 인자를 날조해
  호출** — 실서비스에서 틀린 통계가 나가는 경로. GPT-4.1(정보수집 후 정지)·
  Qwen(무호출)은 안전하게 행동.
- t03 정규화 실패도 mini만 — "혈압이 높다"를 그대로 인자로 전달.

## 4. 선정 결론

**기능 2·3·4의 tool calling LLM: Qwen3 8B (로컬) 확정.**

근거 (전부 실측):
1. 멀티턴 13/14로 GPT-4.1과 동점, 유일한 실패는 툴 한계(t06)로 모델 무관.
2. 표현 정규화(연령 카테고리화, 구어→표준 질병명) 통과 — "10대/20대
   카테고리 통합" 요구사항이 sLLM으로 충족.
3. 인자 부족 시 날조하지 않음 — 통계 서비스에 적합한 안전 특성.
4. 무료·로컬 — 고객 질병·연령 정보가 외부로 전송되지 않음(이 기능군은
   사용자의 실제 민감정보를 다루는 유일한 영역이라 결정적).
5. gpt-4.1-mini는 정규화 실패 + 인자 날조로 탈락 (유료인데 무료보다 위험).
6. GPT-4.1은 품질 동점·속도 우위이나, 백그라운드 툴 변환 용도에서 초 단위
   속도가 결정 요인이 아니고 비용·보안 열세 → 대체 옵션으로 기록.

이로써 초기 티어링 설계("2·3·4번은 LLM 불필요~sLLM")가 실측 확정:
**본체는 코드, 변환기는 Qwen3 8B, 안전장치는 타임아웃+되묻기.**

## 6. 남은 일 (구현 단계 이월)

1. **타임아웃 필수** — Qwen 최악 지연 704초 실측(3회 재현: 277/666/704s).
   호출당 15–30초 제한 + 초과 시 재질문 유도 응답.
2. **질병명 툴에 유사어 매칭** — t06 실증. KCD DB 조회를 정확 일치가 아닌
   임베딩 유사도 검색으로 구현 ("2형 당뇨"≈"2형 당뇨병"). 기능 4 설계
   원안("오타·유사어는 임베딩 검색으로") 그대로.
3. **인자 부족 시 되묻기 구현** — 무호출/정지 응답이 오면 "연령대를 알려
   주세요" 류 안내 반환. Qwen의 장고(長考)도 이 UX로 흡수 가능(정지를
   빨리 유도).
4. **실제 KCD DB·통계 DB 연결** — mock 내부 교체 (인터페이스 동일).
5. tool_eval.py의 멀티턴 루프는 서비스 에이전트 실행기의 원형 — features\
   구현 시 이 패턴 재사용.
