## 2. 평가 파이프라인이 하는 일 (rag_llm_eval.py)

사용자 질문 하나가 들어오면:

1. **검색** — 질문이 "~란?", "~의 정의" 류면 용어 컬렉션(terms_e5),
   아니면 본문 컬렉션(policy_e5)에서 관련 청크 top-5를 가져온다.
   (rag_config.py의 search 함수 사용 — 접두사·필터·중복접기 자동)
2. **생성** — 청크를 [근거]로 붙여 LLM에 전달. 시스템 프롬프트 규칙:
   근거에 있는 내용만 답할 것 / 출처(보험사·세대·조항)를 표기할 것 /
   근거로 답할 수 없으면 "확인할 수 없습니다"라고 할 것 /
   보험사마다 다르면 나눠서 답할 것.
3. **자동 채점** — 출처 표기 여부, 거부 표현 여부를 검사해 O/X.
   단 자동 채점은 1차 필터일 뿐, 최종 판단은 CSV의 답변 원문을 사람이 읽는다.

이 구조는 인수인계 문서 6절의 평가 포인트 3가지
(근거 기반 답변 / citation 출처 표기 / "약관에 없음" 인정)를 그대로 검사한다.

## 3. 스모크 테스트 결과 (6문항 — 잠정치임을 유의)

| 문항 | 유형 | GPT-4.1 | Qwen3 8B | 해설 |
|---|---|---|---|---|
| S1 통원 공제금액 | 답있음 | O 5.2s | O 15.8s | 둘 다 보험사별로 나눠 답변, 출처 표기. 예외 케이스까지 짚음 |
| S2 삼성 면책사항 | 답있음 | X | X | 둘 다 "확인 불가" 거부 — 원인은 아래 4절 |
| S3 진단계약이란? | 용어 | O 1.1s | O 4.2s | 용어 컬렉션 라우팅 정상 작동 |
| S4 앱 계좌변경 | 답없음 | O | O | 약관에 없는 질문 → 둘 다 정상 거부 |
| S5 고객센터 번호 | (문항 무효) | X | X | 아래 4절 — 문항 설계 오류였음 |
| S6 면책기간이란? | 함정 | O 0.8s | O 4.7s | **하이라이트** — 아래 4절 |

**두 모델이 6문항 전부에서 동일한 O/X 패턴.** 서로 다른 모델이 같은 지점에서
같은 방식으로 실패했다는 건, 실패 원인이 모델이 아니라 공통 입력(검색 품질·
문항 설계)이라는 뜻이다. 확실한 차이는 속도뿐: Qwen3(로컬 8B)가 3~8배 느리다
(최대 33초 — RTX 3060 Ti 생성 속도 한계).

## 4. 스모크에서 배운 것 (실패 사례 해설)

### S2 — LLM이 아니라 데이터가 원인
삼성 필터 검색의 top1이 `'보상하지 않는 사항)'` 같은 **조각 청크**였다.
근거가 부실하니 LLM은 규칙대로 거부했다 — 즉 LLM은 올바르게 행동했다.
본문 데이터 중복·조각 수정본으로 재색인하면 개선될 것으로 예상.
**S2는 재색인 전후 비교의 검증 지표로 지정** (데이터 품질 → 답변 품질 인과 증명용).

### S5 — 문항 설계 오류 (환각이 아니었다)
"고객센터 전화번호"가 약관에 없을 거라 가정하고 '답없음' 문항으로 냈는데,
실제로 DB손보 약관 안에 지역 고객센터 연락처 페이지가 있었다. LLM은 그걸
찾아 근거 번호까지 달아 충실히 인용했다 — 환각이 아니라 오히려 근거 충실성의
증거. **교훈: '답없음' 문항은 만들기 전에 반드시 검색으로 실재 여부를 확인할 것.**
(정식 30문항 제작 규칙에 반영)

### S6 — 함정 통과 (가장 중요한 결과)
용어 사전에 "면책기간"이 없어서 검색은 가장 비슷한 "보험기간" 정의를
가져왔다(오답 근거). 두 모델 모두 이 오답 근거에 속지 않고 "면책기간과
보험기간은 다른 개념"임을 인지, 확인 불가로 거부했다.
**검색이 틀린 근거를 줘도 LLM이 방어한다**는 근거 충실성(faithfulness)의
실증 — 로컬 8B 모델(Qwen3)도 통과했다는 점이 특히 의미 있다.

## 5. 지금 시점의 잠정 판단 (선정 아님)

- **품질**: 6문항 기준 GPT-4.1 ≒ Qwen3 8B. 단, 복잡한 보장 판별(여러 조항
  교차 해석)은 아직 테스트 안 됨 — 8B의 한계가 나올 수 있는 영역이며
  정식 평가의 핵심 관전 포인트.
- **속도**: GPT-4.1 압도적 우위 (1~5초 vs 4~33초).
- **비용/보안**: Qwen3 우위 (무료, 데이터 외부 전송 없음).
- **예상 시나리오**: 단독 선정보다 **기능 티어링** 가능성 — 무거운 판단
  (보장 여부 판별)은 GPT-4.1, 가벼운 기능(용어 설명 등)은 Qwen3.
  S6 통과로 sLLM 티어링의 실증 근거가 하나 쌓인 상태.

## 6. 최종 선정까지 남은 일

1. **전체 데이터 재색인** — PDF 1,858건(기존 2배+) 전처리 → prep_new →
   재색인 (색인 약 100분 예상). 신규 보험사 포함이므로 임베딩 선정도
   2_model_select 재실행으로 재검증.
2. **정식 평가셋 30문항** — 답있음 20(기대 정답 요지 포함) + 답없음 5
   (사전 검색으로 실재 확인 — S5 교훈) + 용어 5(정상 용어에서 선별).
   함정 문항(S6 유형) 포함.
3. **본 평가** — 새 색인 위에서 GPT-4.1 vs Qwen3 (+필요 시 후보 추가:
   gpt-4.1-mini, Claude 등 — rag_llm_eval.py의 build_llm에 등록만 하면 됨).
4. **선정 확정** — 정확도 + 속도 + 비용 + 보안 4축으로 결정,
   임베딩과 같은 형식(README + 결과 CSV)으로 정식 인수인계.

## 7. 재현하려면 (선택)

전제: 임베딩 공유본(embed-share) + chroma_full DB 세팅 완료 상태.

```powershell
pip install langchain-openai langchain-ollama langchain-core
$env:OPENAI_API_KEY="sk-..."          # GPT 계열용
# Qwen3 로컬 실행: ollama.com 설치 후 → ollama pull qwen3:8b

python rag_llm_eval.py --models gpt-4.1          # GPT만
python rag_llm_eval.py --models gpt-4.1,qwen3    # 두 모델 비교
# 결과: out\llm_eval_results.csv (answer 원문 포함 — 사람 검토 필수)
```

문항 파일: llm_questions.json (현재 스모크 6문항. 정식 30문항으로 교체 예정)
